# 108 — 개체와 판정을 가른다 (`DiatomObject`)

P12 를 실행한다. 계획은 [P12](20260810_P12_object-and-judgement.md) 에 있고,
여기는 **무엇이 계획과 달라졌는지**와 **밟은 자리**를 적는다.

> "지금 YOLO 3차를 검토할 때 여러 프레임에 걸쳐있는 규조각을 모아서 하나의
> 개체로 간주하려고 하는 거야. 그래야 동정이든 개체수 카운팅이든 원하는대로
> 할 수 있으니까. 그런데 현재 테이블 구조가 `ObjectReview` 와 `ObjectLink`,
> `ObjectLinkMember` 로 절반만 겹치는 성격을 가진 테이블들로 갈라져 있으니
> 그걸 일원화 하려는 게 가장 큰 목적이야."

## 순서를 바꿨다

P12 는 "지금은 아니다" 로 끝났었다 — 카탈로그가 자리를 잡고, `YOLO 4차` 가
들어올 때 함께 넣자고. **그 근거의 절반이 사라졌다.**

사용자가 방침을 하나 확정했다: **한 회차의 검토 결과로 학습 자료를 만들어 다음
회차를 돌리면, 그 이전 회차의 인식 결과는 더 신경 쓸 필요가 없는 자료다.**
사람이 그린 마스크는 회차를 넘어 남지만 그것도 *다음 회차가 그 자리를 스스로
인식하기를 기대하는 것*이지 이어 붙이려는 것이 아니다.

그러면 P12 의 동기 중 **어긋남 5(묶음이 회차를 못 넘는다)** 와 미결 셋(IoU
문턱 실측 · 이전기 충돌 규칙 · 회차 간 병합)이 통째로 없어진다. 남는 것은
**한 회차 안의 일원화**이고, 그것이 원래 가장 큰 목적이었다. 4차를 기다릴
이유가 없어졌고, **종명이 0건인 지금이 이전기가 가장 싼 시점**이다.

## 계획과 달라진 것 넷

### 1. `DiatomObject` 라는 이름 (`Object` 가 아니다)

P12 는 `Object` 라고 적었는데 파이썬 내장 `object` 와 대문자 하나 차이다 —
`Object.objects.filter(...)` 가 읽기 나쁘고 검색으로 못 찾는다. 테이블은
`viewer_diatomobject` 다. `diatom` 은 생물 이름 자리라 CLAUDE.md 의 규약에 맞는다.

### 2. `ObjectReview` 는 개체를 **반드시** 갖는다

P12 원안은 조건부였다 — `removed=True` 면 개체가 없고 살아 있으면 반드시 있다.
실측하니 **`removed=1` 인데 분류가 있는 행이 30건**이었고, 그 안은 그 30건의
분류를 버린다. 그것 말고도 둘이 더 걸렸다.

무조건 갖게 하면(NOT NULL):

- **읽는 자리 79곳에 갈래가 없다.** 조건부면 전부 "개체가 없으면 빈 값" 을 타야
  하고, 안 고친 자리는 예외 없이 조용히 다르게 굴러간다(038·040 의 모양)
- **묶기·풀기가 대칭이 된다** — 묶기 = 개체 둘을 합친다, 풀기 = 개체를 가른다
- **지웠다 되살리는 사이에 묶음이 안 깨진다.** 조건부면 지우는 순간 그 판이
  묶음에서 조용히 빠지고 되살려도 안 돌아온다 — 102 가 만든 "탈락 후보를
  되살려 묶는다" 흐름과 정면으로 부딪힌다

값: 개체 행이 7,909개 서고 그중 6,120개가 "오검출" 이다. 이름과 뜻이 조금
어긋나지만 — `DiatomObject` 를 *사람이 하나로 보는 대상*으로 두고 **그것이
규조각인지 아닌지는 판정이 말한다**로 정리했다. 지운 것도 학습의 음성 표본으로
쓰이는 대상이다.

그래서 **어긋남 4(지워진 마스크가 묶음에 남는다)는 구조로 안 닫힌다** — 묶을 때
서버가 막고 `check_db` 8번이 센다. P12 의 조건부 안도 결국 거기로 갔을 것이라
실질 차이는 없다.

`NOT NULL` FK 는 `db_default` 를 못 주는데(055 의 그 위험), 확인해 보니
**파이프라인은 `ObjectReview` 에 INSERT 하지 않는다** — `rebind.py` 는
`bulk_update` 뿐이고 `import_json.py` 는 손으로만 도는 이전기 도구다.

### 3. `note` 는 판정에 남긴다

P12 의 표는 `label`·`note`·`species` 를 개체 쪽에 놓았다. 그런데 104·107 은
줄곧 코멘트를 안 번지게 해 왔고, 실측으로 코멘트가 있는 행이 **2건**인데 묶음
멤버에는 0건이다. 올리면 프레임마다 다른 말이 하나로 뭉개진다 — "이 판에서는
초점이 안 맞는다" 는 판마다 하는 말이다.

### 4. 엇갈리는데 안 고르면 **묶기를 거절한다**

107 은 "기본은 `그대로`" 였다 — 분류가 판마다 살아서 *묶되 아무것도 안 덮는*
것이 가능했다. P12 뒤로는 개체가 값을 하나만 들 수 있어 **"그대로" 가 성립하지
않는다**: 그릇의 값이 남의 동정을 덮는다.

그래서 서버가 409 로 거절한다. 지키는 것은 같다 — **사람이 적은 것을 자동으로
덮지 않는다.** 화면은 107 의 팝업이 물어보게 돼 있고, 여기 걸리는 것은 그
팝업을 안 지난 요청이다. 값이 **하나뿐일 때는 그릇이 물려받는다**(107 의 "하나뿐
이면 미리 고른다" 를 서버도 한다) — 안 그러면 대표가 비었을 때 남의 분류가
합치는 순간 사라진다.

## 읽는 자리 79곳을 어떻게 안 건드렸나

`ObjectReview` 에 **읽기 전용 통로**를 뒀다.

```python
@property
def label(self) -> str:
    return self.diatom_object.label
```

진실은 개체 하나이고 여기서는 비추기만 한다. **쓰기는 막혀 있다** —
`o.label = …` 은 `AttributeError` 다. 조용히 안 먹히는 것보다 시끄럽게 죽는
편이 낫고, setter 를 달면 묶인 판들에 번지는 일을 여기가 몰래 하게 된다.

대신 **조인이 숨는다**. 그래서 `_reviews_prefetch()` 와 `reviews_of()` 를 만들어
미리 물어 오는 자리를 전부 지나게 했다 — 안 걸면 판정 수만큼 질의가 난다.

**생 SQL 은 통로가 없다.** `_SUMMARY_SQL`·`_COVER_SQL` 이 `r.label` 로 짚고
있었고 `viewer_diatomobject` 조인을 더해 `o.label` 로 바꿨다. `export_review.py`
는 **두 판을 다 읽는다** — `diatom_object_id` 칼럼의 유무로 갈라, 옛 백업 파일도
그대로 읽는다(감사 기록의 형식 번호는 안 올렸다).

## 문 하나 — `data.judgement_for`

판정 행이 개체 없이 설 수 없으므로, **행을 만드는 자리가 셋(검토 저장 · 그리기 ·
카탈로그)인데 개체를 만드는 규칙이 셋이면 안 된다.** 하나만 빠뜨려도
`IntegrityError` 이고, 더 나쁘게는 대표(`is_rep`) 없는 개체가 서서 학습 자료를
뽑을 때 얼굴이 없는 개체가 된다. 묶기 엔드포인트와 시험 픽스처도 이 문을 지난다.

짝으로 `data.prune_objects` 가 있다 — 판정을 지우면 개체가 유령으로 남는다.
**판정을 지운 뒤에** 부른다. 순서를 바꾸면 `CASCADE` 가 살아 있는 판정을 끌고 간다.

## 밟은 자리

- **`link.delete()` 가 이제 교정을 지운다.** `ObjectReview.diatom_object` 가
  `CASCADE` 라, 예전의 "풀기 = 묶음 행을 지운다" 와 "고치기 = 멤버를 갈아끼운다"
  가 **그 판들의 교정을 통째로 지우는 줄**이 됐다. 풀기는 `_split_off` 로 개체를
  **가르고**, 고치기는 목록에 없는 멤버만 떼어 낸다
- **`atomic()` 안에서 `return` 은 롤백이 아니다.** 거절하기 전에 세운 판정 행이
  남아 **거절했는데 빈 껍데기가 생겼다**(브라우저 시험이 잡았다 — 화면에는 안
  묶였는데 DB 에 행이 둘). `_Reject` 예외로 물러난다. 103 에서 겪은 "한쪽은
  거절, 한쪽은 통과" 와 같은 모양이다
- **`is_rep` 유일 제약은 옛 대표를 먼저 내려야 한다.** 새 대표를 세우기 전에
  옛 대표가 남아 있으면 부딪힌다
- **분류 맞추기는 `keys` 가 아니라 `known` 을 훑는다.** 지정을 *물리면* 그 키는
  payload 의 `labels` 에서 사라지고 다른 표시도 없으면 `keys` 에도 안 들어온다 —
  `keys` 만 보면 **물림이 개체에 안 닿아 다른 판에 옛 분류가 남는다.** 옛
  `_spread_link_labels` 도 같은 이유로 `known` 을 봤다
- **팩토리에서 `batch=<객체>` 와 `batch_id=None` 을 함께 넘기면 뒤엣것이 이긴다** —
  묶음이 조용히 비워져 감사 기록의 묶음 이름이 사라졌다
- **`Detection` 에 `batch` 가 없다.** `run` 을 지나간다 (이전기가 거기서 한 번 섰다)
- **청소가 묶음 멤버를 지웠다.** 커밋한 뒤 사용자가 *"/review 청소가 뭐냐"* 고
  물어 그 줄을 다시 보다 찾았다. `save_review` 의 마지막 줄은 payload 가
  대표하지 않는 행을 지우는데, P12 에서 **소속이 곧 판정 행**이 되면서 그 청소가
  멤버까지 집는다 — 표시가 하나도 없는 멤버(다른 판에서 분류를 받고 이 판은
  비어 있는 흔한 모양)가 저장 한 번에 사라지고 **묶음에서 한 판이 조용히
  빠진다.** 시험 561개가 이것을 통과시켰다: 전파 시험이 *다른* 판만 확인했고
  **저장한 판 자신의 행은 아무도 안 셌다.**

  묶음을 푸는 문은 `/link` 이지 검토 화면이 아니다 — payload 에 없다는 것이
  "묶음에서 뺐다" 는 뜻일 수가 없다. 종명·`geom_edited` 를 청소에서 빼 두는 것과
  **같은 갈래**이고, 같은 자리에 얹었다. `save_catalog_entry` 의 "값을 비우면
  그 줄을 지운다" 도 같은 구멍이었다. **혼자인 개체는 안 얹는다** — 그것은
  소속이 아니라 1:1 껍데기라 예전처럼 지워야 한다.

  `CleanupKeepsMembersTest` 넷으로 못 박았고, 고치기 전에 셋이 서는 것을 봤다
- **묶기가 판정 행을 `orphan` 으로 세웠다.** 테스트 인스턴스에서 사용자가 시야
  하나를 실제로 묶어 본 것을 들여다보다 찾았다 — 후보가 멀쩡히 있는데
  (`bind_method='orphan'`·`candidate=NULL`) 두 프레임이 그렇게 앉았다.
  `save_object_link` 이 `judgement_for` 에 **후보를 안 넘겼다**: 옛 코드는
  `get_or_create(defaults={"bind_method": "exact"})` 로 박아 두고 있었다.

  거짓 고아는 조용하다. `check_db` 3번의 바인딩 집계가 흐려지고, 엔진을 갈 때
  `rebind.py` 가 다시 맺을 필요 없는 것을 맺으려 들고, 앞으로 만들 `/orphans/`
  화면에 멀쩡한 개체가 뜬다. **운영이 지금 7,726건 전부 `exact` 라 이 길은 한
  번도 시험대에 오른 적이 없다**(TODOs P02 8번) — 그래서 더 안 보인다.

  `LinkBindsToCandidateTest` 로 못 박았고, 고치기 전에 `'orphan' != 'exact'` 로
  서는 것을 봤다. **화면 시험이 아니라 사람이 눌러 본 자국을 읽어서 찾았다** —
  085 가 테스트 인스턴스를 만든 이유가 이것이다

## 이전기 — 사본에서 앞뒤로 돌려 봤다

```
개체 7,909개 (묶음에서 온 판정 12 · 1:1 로 세운 것 7,905)
판단 없이 묶기만 한 마스크에 판정 행 3건을 세웠다
분류가 있는 개체 1,770 (전 1,774 — 묶음 셋에서 같은 분류를 든 판 7개가 개체 3개가 됐다)
```

`check_db` 9절 전부 OK. 감사 기록(`review/`) diff 는 **63줄**이고 전부 설명된다:
껍데기 3건이 판정 행으로 나타나고, 묶음 안 분류가 하나로 합쳐지고, 멤버 기하가
판정의 것으로 바뀌며 키 이름만 `bbox_xywh`→`bbox` 로 달라졌다(**값은 동일**).

**`reverse` 는 완전한 역이 아니다.** 앞으로 갈 때 묶음 안의 값이 합쳐지므로
(그것이 목적이다) 되돌려도 판마다 달랐던 값은 안 돌아온다 — 되돌린 뒤 판정
7,917(원래 7,914) · 분류 1,776(원래 1,774)이고 차이는 **묶음 4개 안에서만** 난다.
`reverse` 를 두는 목적은 배포를 되돌릴 때 화면이 뜨게 하는 것이지 완전 복원이
아니다. 진짜 되돌리기는 백업 사본이다.

## 배포 — 뷰어와 파이프라인을 **함께** 올린다

파이프라인 코드는 `ObjectReview`·`ObjectLink` 를 안 쓴다. 그런데 삭제가 지나가는
길이 셋 있고, 옛 이미지의 `models.py` 가 없어진 테이블·칼럼을 짚는다:

| 자리 | 무엇이 터지나 |
|---|---|
| `group_focus_series.py:287` `slide.viewpoints.all().delete()` | 시야 CASCADE |
| `ops/prune_detections.py:134` | 후보 CASCADE → `ObjectReview.candidate` SET_NULL |
| `ops/drop_batch.py` | `ObjectReview` 를 직접 문다 |

**조인 사본에 붙여 실측했다** (055 가 시킨 그대로). 결과가 예상과 달랐다:

```
옛 이미지 v0.5.1 · 교정 9건인 시야를 지운다  →  IntegrityError: FOREIGN KEY constraint failed
새 이미지 v0.5.2 · 같은 일                  →  ObjectReview 9 · DiatomObject 6 함께 지움
```

**"없어진 테이블을 SELECT 한다" 가 아니라 FK 위반이다.** 옛 판의 `models.py` 는
`diatom_object` 를 모르므로 개체를 안 지우고, 남은 개체가 지워진 판정을 가리켜
제약이 깨진다. 그리고 **교정이 없는 시야로 시험하면 그냥 통과한다** — 처음에
그렇게 확인하고 "괜찮다" 고 읽을 뻔했다. `Collector.collect()` 만 불러 보는 것도
안 된다(지연 삭제라 통과한다). **실제로 지워 봐야 드러난다.**
