# 058 — 목록 집계가 인덱스를 발밑에서 잃었다

2026-08-06 아침. 사용자가 **"첫 페이지가 2초 정도 걸리네"** 라고 했다. 022 에서
1.32 → 0.31초로 고쳐 둔 화면이라 되돌아간 것이다.

`v0.6.1` 로 배포했고 **2.09 → 0.59초**다.

## 어디였나

먼저 재고 나서 골랐다. 컨테이너 안에서 테스트 클라이언트로 첫 페이지를 부르고
`CaptureQueriesContext` 로 질의를 전부 잡았다.

```
status 200 · 2,113 ms · 질의 82개
질의 합계 1,951 ms      ← 페이지 시간의 93%
그중 한 모양 11개가 1,927 ms   (슬라이드마다 하나 — _summary_by_sql)
  260731_rs23-gc03_369cm  746 ms
  wap13-gc47_450cm        393 ms
  260803_bp09-0901        271 ms  …
```

렌더링도 파이썬도 아니고 **SQL 하나**였다.

## 원인 — 055 가 옮긴 열쇠를 질의가 안 따라갔다

`_summary_by_sql` 은 후보마다 교정을 찾는 상관 서브질의를 서너 개 건다
(`gone`·`back`·`user_cls`, `eff_cls` 안에서 한 번 더). 후보가 97,299개다.

```
055 이전:  CONSTRAINT uniq_objreview_key UNIQUE (viewpoint_id, mask_key)
지금    :  CONSTRAINT uniq_objreview_key UNIQUE (image_id,     mask_key)
```

`Image` 를 뽑으면서 교정의 유일 제약이 이미지 쪽으로 옮겨 갔는데(055),
`data.py:730` 은 그대로 `viewpoint` 로 상관하고 있었다. **코드는 한 글자도 안
바뀌었는데 밟고 서 있던 인덱스가 없어진 것이다.**

```
지금  SEARCH U0 USING INDEX viewer_obje_viewpoi_fcb0a3_idx (viewpoint_id=?)
        (viewpoint_id, bind_method) 인덱스라 시야까지만 좁히고
        그 시야의 교정을 전부 훑으며 mask_key 를 비교한다
새로  SEARCH U0 USING INDEX sqlite_autoindex_viewer_objectreview_1
        (image_id=? AND mask_key=?)      한 번에 짚는다
```

**055 는 잘못한 것이 없다.** 그 마이그레이션은 다형 연관을 걷어내는 옳은
이사였고, 스키마 동등성도 확인했다. 놓친 것은 **그 인덱스를 짚어 쓰던 질의가
어디인지 세는 일**이었다 — 053 의 교훈("제약이 있다는 것과 조회가 그걸 쓴다는
것은 다르다")의 반대편이다. 이번엔 제약을 옮겼는데 조회가 안 따라왔다.

## 엉뚱한 길로 30분 갔다 — 시험이 자기 자신을 오염시켰다

원인을 짚기 전에 **사본에서는 같은 질의가 500 ms** 라는 결과가 나왔다. 같은
컨테이너·같은 코드·같은 크기의 파일인데 4배가 달랐다. 그래서 파일 배치를
의심했다:

- `cp` 로 뜬 **바이트 사본**도 2,093 ms — 파일시스템 탓이 아니다
- 그 사본에 **`VACUUM`** 을 걸어 108 → 58 MB 로 줄였는데도 2,065 ms
- `ANALYZE` 를 걸어도 2,091 ms

전부 헛다리였다. 진짜 이유는 **내가 앞선 측정에서 `CREATE INDEX bench_vp_mask`
를 걸어 둔 사본을 그대로 다시 복사해 쓰고 있었다는 것**이다. "빠른 사본" 은
그냥 **인덱스가 있는 사본**이었다. 인덱스 개수를 세고서야(46 vs 47) 알았다.

교훈이 둘이다.

- **성능을 잰 파일에 무엇을 만들었는지 기억할 것.** 시험이 대상을 바꾸면 그
  다음 측정은 전부 거짓말이 된다. 사본을 다시 뜨는 편이 싸다
- **엉뚱한 답도 재는 값은 진짜였다.** `VACUUM` 이 파일을 절반으로 줄이고도
  0 ms 도 못 줄인 것이 오히려 "배치 문제가 아니다" 를 확정해 줬다

## 고른 길 — 인덱스를 되살리지 않고 질의를 옮겼다

깨끗한 사본(운영의 바이트 사본)에서 갈라 쟀다.

| | 시간 | |
|---|---|---|
| ① 지금 코드 (`viewpoint` 상관) | 2,031 ms | |
| ② **`image` 상관** | **522 ms** | 3.9배 · 마이그레이션 없음 |
| ③ `(viewpoint_id, mask_key)` 인덱스를 되살린다 | 510 ms | 4.0배 · 마이그레이션 필요 |

속도는 같다. **②를 골랐다.**

- 055 가 정한 방향과 같다 — **교정은 이미지에 붙는다.** ③은 그 이사가 걷어낸
  인덱스를 성능 때문에 되살리는 꼴이라 같은 뜻이 두 곳에 남는다
- **프레임별 검토(P06 5b)가 붙으면 `viewpoint` 상관은 값도 틀린다.** 한 시야에
  이미지가 여럿이 되는 순간 다른 이미지의 교정까지 끌어온다. 지금은 시야마다
  이미지가 하나라 결과가 같을 뿐이다 — **같아 보일 때 고쳐 두는 것**이 055 §5
  에서 지우는 범위를 이미지로 옮긴 것과 같은 이유다

`web/viewer/` 안에서 `OuterRef` 를 쓰는 자리는 여기 하나뿐이라 고칠 곳도 하나였다.
