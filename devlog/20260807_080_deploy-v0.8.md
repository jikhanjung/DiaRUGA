## 배포가 드러낸 것 셋

### 1. CI 는 이미지를 굽지 못하고 있었다

태그를 밀면 GitHub Actions 가 이미지를 굽고 올리게 되어 있는데
`Username and password required` 로 죽었다. **저장소에 Docker Hub 시크릿이
없다**(`gh secret list` 가 비어 있다). v0.7.0 도 이 기계에서 밀었던 것으로 보인다.

이번에는 두 이미지 모두 로컬에서 굽고 밀었다. **CI 로 굽게 하려면
`DOCKERHUB_USERNAME`·`DOCKERHUB_TOKEN` 을 넣어야 한다** — 사람의 계정이라
여기서 정할 일이 아니라 적어만 둔다.

### 2. `/srv` 의 스크립트가 저장소와 어긋나 **없는 고장을 냈다**

배포 뒤 `check_db.py` 가 이렇게 말했다.

```
!! 시야마다 현재 검출이 하나 이하: 508건 is_current 가 둘 이상이다
```

**옛 사본이었다.** P10 이 그 검사를 "이미지마다 하나 이하" 로 고쳤는데
`/srv/DiaRUGA/scripts` 에는 옛 판이 있었다. `dbsync.sh --list` 가 여섯 개나
어긋나 있다고 알려 줬다.

배포 절차에 **`dbsync.sh --list`** 를 넣을 자리다 — 뷰어 이미지는 갈리는데
`/srv` 의 스크립트는 아무도 안 갈아 준다. 이번엔 사람이 알아봤지만, 저 문구는
"자료가 상했다" 로 읽히므로 다음엔 시간을 버린다.

### 3. 브라우저 겹의 뒷정리가 CI 를 멈췄다

`database table is locked: viewer_candidate` — **시험이 실패한 것이 아니라
뒷정리(flush)가 실패했다.** `TransactionTestCase` 가 표를 비우는 동안 살아 있는
서버 스레드가 읽기 트랜잭션을 쥐고 있었다. 로컬은 빨라서 잘 안 난다.

두 자리를 함께 고쳤다: 창을 닫기 전에 `about:blank` 로 옮겨 **진행 중인 요청을
끊고**, `_fixture_teardown` 이 잠김에 **몇 번 져 주고 다시 시도**한다.

빨간불의 뜻이 "코드가 틀렸다" 가 아닐 수 있다는 것 — 그것 자체가 비용이다.

## 가중치를 NAS 로 함께 보낸다

`sync_backup_nas.py` 에 `models_YYYYMMDD.tar` 를 더했다. 사진과 두 가지가 다르다:

- **정리하지 않는다.** 사진은 NAS 에 원본이 따로 있지만 가중치는 여기 있는 것이
  원본이다. 그리고 `Run.params.weights` 가 묶음마다 sha256 을 적어 두므로,
  파일이 사라지면 **지난 회차의 근거를 되짚을 수 없다**
- **안 바뀌었으면 안 보낸다.** 학습할 때만 바뀌므로 매일 126 MB 를 새로 나를
  이유가 없다. 가장 새 묶음과 이름·크기를 견줘 같으면 건너뛴다

같은 날 새로 학습하면 `models_YYYYMMDD_2.tar` 로 붙인다. `_2` 인 것은 정렬
때문이다 — `-2` 면 `models_260807-2.tar` 가 `models_260807.tar` 보다 **앞에**
서서(`-` < `.`) "가장 새 묶음" 을 잘못 짚는다.

**기본으로 켰다.** cron 줄을 안 고쳐도 다음 실행부터 함께 간다 — 남의 설정을
고쳤다가 되돌리기를 잊는 쪽이 위험하다.

가중치를 어디 둘지는 사람이 정했다(2026-08-07): **`/data3/DiaRUGA/models` 그대로.**
`/srv` 는 루트 디스크(87% 차 있었다)이고 SAM2 가중치도 이미 `/data3/hf` 에 있다.
