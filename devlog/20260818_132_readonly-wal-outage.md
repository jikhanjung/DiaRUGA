# 132 — `v0.14.0` 배포가 읽기 전용 DB 로 엎어졌다 (운영 3분)

2026-08-18 · `main` · [130](20260818_130_atlas-schema-and-import.md) 배포 중에 났다

`v0.14.0` 을 내보내다 마이그레이션 `0038` 이 **`attempt to write a readonly
database`** 로 죽고, 컨테이너가 재시작을 반복하며 **17:52~17:55 운영이
내려갔다.** 마이그레이션 잘못이 아니었다.

## 1. 무엇이 막고 있었나

```
drwxrwsr-x paleoadmin paleoadmin  /srv/DiaRUGA/db/
-rw-r--r-- paleoadmin paleoadmin  DiaRUGA.db       ← 소유자라 쓸 수 있다
-rw-r--r-- sclee      paleoadmin  DiaRUGA.db-wal   ← 그룹 쓰기가 없다 · 12:10 생김
-rw-r--r-- sclee      paleoadmin  DiaRUGA.db-shm   ← 같음
```

컨테이너는 `user: "1000:1000"`(=`paleoadmin`)으로 돈다. 본 DB 는 소유자라 쓸 수
있는데 **형제 파일 둘을 못 써서** SQLite 가 DB 전체를 읽기 전용으로 봤다.
**WAL 을 못 쓰면 읽기 전용이다** — 본 파일의 권한은 그것을 못 이긴다.

## 2. 그 파일이 왜 그 소유자였나

**오전 11시대 작업(125) 중에 상태를 보려고 운영 DB 를 직접 열었다** — 다른
세션이 `sqlite3` 로 `mode=ro` 로 붙어 `page_count`·freelist 를 쟀다. 열기
직전의 `ls` 에는 `DiaRUGA.db` 하나뿐이었으니 **`-wal`·`-shm` 은 그 순간 생겼다.**

**전제가 틀렸고, 틀린 방향이 나빴다.** 그 자리의 메모는 *"운영 DB 는 WAL 이라
`mode=ro` 로도 못 연다 — `-shm` 을 못 써서 첫 읽기가 실패한다"* 였다. 그런데
`db/` 가 `drwxrwsr-x` 라 **그룹이 파일을 만들 수 있다.** 그래서 읽기는 실패하지
않고 **성공했고**, 대신 남이 못 쓰는 형제 파일 둘을 남겼다.

> **"안전하게 실패한다" 는 전제가 실제로는 "조용히 성공하고 남을 막는다" 였다.**

이 저장소가 반복해서 당한 그 모양이다 — 실패하리라 믿고 한 일이 성공해 버리는
것. 063 의 `update_or_create` 도, 051 의 "읽기 전용인데 우클릭이 살아 있는
화면" 도 같은 줄이다.

## 3. 5시간 46분 동안 아무도 몰랐다

```
12:10  -wal·-shm 이 sclee 소유로 생긴다  ← 이때부터 컨테이너는 못 쓴다
17:51  배포가 0038 을 적용하려다 죽는다   ← 처음으로 드러난다
17:55  chmod g+w 뒤 곧바로 붙는다
```

**`/healthz` 가 그 사이 내내 `ok` 였다.** 읽기만 하기 때문이다. `smoke.sh` 도
통과한다 — 여는 화면이 전부 읽기다. **쓸 수 있는가를 아무도 안 물었다.**

**DB 에 남은 것은 성하다** — 12:03 의 교정 **10,341** 에서 안 움직였고, 그 사이
시간별 사본 여섯이 전부 같은 수다(사본을 열어 세었다).

**그런데 사람은 부딪혔다** — 그 무렵 검토를 돌리던 사용자가 **저장 하나가
안 됐다**고 했다. 화면은 실패를 띠로 말했을 것이다(116 에서 세운 자리다).
**그 한 건은 사람이 다시 해야 한다.**

### 요청 쪽 기록은 남아 있지 않다 — "없다" 가 아니라 "못 본다"

처음에는 *"12:10~17:51 에 POST 가 0건이니 아무도 저장을 시도하지 않았다"* 로
읽었다. **그 근거를 물린다.**

- `docker logs --since 8h` 를 줬지만 **배포가 컨테이너를 새로 띄운 뒤였다**
  (생성 17:51). 컨테이너가 10분밖에 안 살았으니 **8시간치가 아니라 10분치**를
  본 것이고, 그 줄들도 대부분 축소본 굽기 요청이었다
- 옛 컨테이너의 로그는 그것과 함께 사라졌다
- 호스트 nginx 로그(`/var/log/nginx/access.log`)에는 남아 있는데 **`adm` 그룹이라
  이 계정이 못 읽는다** — 빈 결과가 나왔지만 그것도 "없다" 가 아니다

**빈 결과를 "없었다" 로 읽으면 안 되는 자리였다.** 사람의 제보와 어긋났을 때
제보를 의심하지 않고 근거를 다시 본 것이 맞았다.

말할 수 있는 것만 남기면 이렇다.

| 말할 수 있다 | 근거 |
|---|---|
| DB 의 교정 행은 12:03 이후 안 움직였다 | 시간별 **사본** 여섯을 세었다 |
| readonly 오류 24건은 **전부 마이그레이션**에서 났다 | 트레이스백이 `schema.py create_model` 이고 `views.py`·`save_review` 프레임이 없다 |
| 저장 하나가 실패했다 | **사람이 겪었다** |
| 그 시도가 언제였나 | **모른다** — 요청 기록이 없다 |

## 4. 코드는 이 함정을 이미 알고 있었다 — 한쪽만

`deploy/host/testdeploy.sh` 5단계가 사본을 갈아 끼운 뒤 `chmod g+w` 를 하고
주석까지 달아 두었다:

> 사본은 백업(644)에서 오고 만든 사람이 소유자가 된다 — 컨테이너는 1000:1000
> 으로 도므로, 배포한 계정이 uid 1000 이 아니면 소유자가 아니라 그룹으로
> 붙는다. 644 면 거기서 읽기 전용이 되어 검토가 통째로 막힌다.

**같은 문장이 운영 쪽에는 없었다.** 테스트는 사본을 *만들어 넣으니* 그 자리를
지날 수밖에 없었고, 운영은 파일이 이미 있는 것을 전제해서 **"누가 형제 파일을
새로 만들 수 있다" 를 안 봤다.**

## 5. 그래서 정한 것

**운영 DB 는 어떤 방법으로도 직접 열지 않는다. `mode=ro` 도 아니다.**
`db/` 가 그룹 쓰기라 열기가 성공해 버리고, 그 순간 형제 파일이 연 사람 소유로
생겨 **컨테이너가 그때부터 못 쓴다.** 상태는 이렇게 본다.

| 보려는 것 | 어디서 |
|---|---|
| 행 수·무결성·앞뒤 | `deploy/host/dbrun.sh check_db.py` (컨테이너 문) |
| 파일 크기·freelist 같은 물리 상태 | `/data3/DiaRUGA/backup/` 의 **사본** |
| 도는 판·안전망 | `/healthz` · `smoke.sh` |

CLAUDE.md 의 "배포·컨테이너" 함정에 한 줄로 넣었다. 이 규약이 원래 막으려던
사고 둘(낡은 `models.py`·root 로 돈 컨테이너)과 **같은 뿌리인데 방향만
반대다** — 그때는 호스트가 *썼고*, 이번엔 호스트가 *읽기만 했는데도* 막았다.

## 6. 안 한 것 — 다음에 볼 자리

**`/healthz` 가 "쓸 수 있는가" 를 안 본다.** 읽기만 하는 검사는 이 고장을
5시간 46분 동안 통과시킨다. `integrity_flags` 옆에 한 칸을 더하거나
(`writable`), `smoke.sh` 가 임시 테이블 하나를 만들었다 지우는 방법이 있다.
**이번 판에 안 넣었다** — 배포를 붙잡을 값이 아니고, `/healthz` 는
`deploy.sh` 의 기동 게이트가 딛고 있어(034) 손댈 때 그쪽을 함께 봐야 한다.
