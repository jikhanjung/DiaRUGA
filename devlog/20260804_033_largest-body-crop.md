# 같은 실수를 옆 함수에서 또 했다 — `largest_body` 도 전체를 훑고 있었다

**날짜** 2026-08-04
**앞선 문서** `20260803_030_shape-metrics-crop.md` (같은 종류의 고침)

030 에서 `shape_metrics()` 를 26배 빠르게 고쳤는데, **전체 시간은 개체당
73 ms → 66 ms 밖에 안 줄었다.** 그 함수는 애초에 7 ms 였고, 진짜 병목은 바로
옆에 있었다.

---

## 1. "YOLO 가 왜 느리냐" 는 물음에서 시작했다

합성본 실행이 생각보다 오래 걸려 단계별로 쟀다.

```
1) YOLO 추론만              79 ms    ← 3%
2) 마스크를 dict 로 바꾸기   689 ms    ← 15 ms/개체
3) 지표 계산              1,702 ms    ← 37 ms/개체
4) 판정 + 중첩정리           0.5 ms
```

**추론은 3% 다.** 나머지는 전부 우리 후처리다.

지표 계산 안을 다시 쪼개니 답이 하나로 모였다.

```
largest_body     1,616 ms   35.1 ms/개체   96%
shape_metrics       16 ms    0.3 ms/개체    1%   ← 030 에서 고친 것
texture_score       59 ms    1.3 ms/개체    4%
```

## 2. 030 과 글자 그대로 같은 실수

```python
n, labels, stats, _ = cv2.connectedComponentsWithStats(
    seg.astype(np.uint8), connectivity=8)   # 2752×2208 = 6백만 화소
…
return labels == idx, …                     # 또 6백만
```

마스크는 이미지 전체 크기로 오는데 개체는 그 안의 0.3% 다. **연결 성분은
국소적이라 bbox 밖의 배경은 답에 영향을 주지 않는다** — 자르면 된다.

030 에서 정확히 같은 것을 고쳐 놓고 **옆 함수를 안 봤다.** 그때 "개체마다 전체를
훑는 자리가 더 있는지" 를 훑었어야 했다.

## 3. 그리고 자를 자리를 찾느라 또 훑었다

처음 고침은 이랬다.

```python
ys, xs = np.nonzero(seg)      # ← 6백만 화소 스캔
x0, x1 = xs.min(), xs.max()
```

**아끼려던 비용을 그대로 썼다.** 재 보니 35.1 → 35.1 ms, 하나도 안 줄었다.

030 에서 이미 배운 것이었다 — *"`bbox` 를 주면 그것으로 자른다. 안 주면 마스크를
훑는데, 그 훑기가 아끼려던 비용만큼 든다 — 부르는 쪽은 이미 bbox 를 갖고 있다."*
같은 문장을 써 놓고 같은 실수를 했다.

`bbox` 를 인자로 받게 하니 35.1 → 11.0 ms 가 됐다.

## 6. 어댑터도 함께 고쳤다

`YoloGenerator` 가 마스크를 GPU 에서 통째로 numpy 로 옮긴 뒤 `> 0.5`·`nonzero`
를 했다. 개체마다 6백만 화소를 세 번 훑는 셈이다. **YOLO 가 예측한 상자만큼만**
잘라 오게 했다.

마스크가 상자를 조금 넘칠 수 있으므로(상자와 마스크가 따로 예측된다) 둘레에
24 화소 여유를 두고, **잘린 창의 테두리에 마스크가 닿으면 전체로 물러난다.**
답이 달라지는 것보다 느린 편이 낫다.

## 남는 것

- **`largest_body` 의 남은 11 ms 는 전체 크기 배열을 만들어 돌려주는 몫**이다.
  부르는 쪽(`shape_metrics`·`texture_score`)이 어차피 bbox 로 자르므로, 잘린
  마스크와 오프셋을 그대로 넘기면 이것도 사라진다. 다만 호출부 여러 곳을
  손대야 해서 이번에는 하지 않았다
- **"개체마다 전체를 훑는 자리" 를 한 번에 훑어야 한다.** 두 번 다 하나씩
  찾았고 두 번 다 옆에 또 있었다
