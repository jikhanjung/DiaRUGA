# [계획] 검토 도구를 데스크탑 앱으로 낸다

**작성일** 2026-08-05
**상태** 미착수
**앞선 문서** `docs/20260805_desktop-app-review.md` (검토와 근거 — 이 계획의 전제는
전부 거기서 나왔다) · `20260805_049_cpu-inference-benchmark.md` (CPU 실측) ·
`20260803_P04_yolo-training.md` (검출 엔진)
**규약** `.guides/desktop/` — 형제 프로젝트들이 같은 사고를 겪고 도달한 표준.
**처음부터 지킨다.** 나중에 읽으면 이미 늦은 항목이 들어 있다.

---

## 왜 지금인가

지금 시스템은 **운영할 사람이 있어서** 성립한다 — nginx · Docker · cron 폴러 ·
백업 로테이션 · 무결성 깃발 · 배포 게이트. 밖의 연구자에게 이것을 요구할 수 없다.
GPU 서버가 없고, 서버를 운영할 줄 모르고, 클라우드는 비싸다.

**측정이 데스크탑 안의 성립을 증명했다** (049):

| | 값 |
|---|---|
| YOLO11m-seg, CPU | **1.7초/시야 · 75초/슬라이드** (GPU 와 결과 동일) |
| 코어 수 의존 | **거의 없다** (12스레드 1.665초 = 4스레드 1.657초) |
| 저장 | 슬라이드당 400 MB → **50 슬라이드도 20 GB** |

**GPU 가 없어도 되고, 저장도 PC 에 들어간다.** 그리고 혼자 쓰면 이 시스템에서
가장 위험한 문제(교정 동기화·충돌)가 **아예 없어진다** — DB 도 쓰는 쪽도 하나뿐이다.

## 이미 정해진 것 — 다시 논의하지 않는다

| | 결정 | 근거 |
|---|---|---|
| 라이선스 | **AGPL-3.0** | 검토 4절. `LICENSE` 배치 완료 |

| 웹 뷰어 | **버리지 않는다** | 연구소 안에서는 서버 구조가 잘 돈다. 데스크탑은 대체가 아니라 배포판 |

## 이 계획에서 새로 정하는 것 둘

### 1. 같은 저장소 안에 둔다 (`desktop/`)

별도 저장소로 가르면 **`judge.py` 가 두 벌이 된다.** 판정 규칙이 유일한 정의라는
지금 구조가 이 프로젝트의 뼈대이고(`judge.py` 머리말), 그것을 잃으면 "웹과 앱의
계측이 다르다" 는 사고가 시간 문제로 온다.

```
DiaRUGA/
  judge.py · segment_diatoms.py · focus_stack.py …   ← 지금 그대로, 둘 다 쓴다
  web/        Django 뷰어 (연구소 서버)
  desktop/    PySide6 앱          ← 새로 만든다
```

라이선스도 한 벌로 유지된다. 배포 산출물만 갈라진다.

### 2. Django ORM 을 그대로 쓴다 — 서버 없이

`models.py` 는 15개 모델에 **한 번씩 당하고 얻은 제약**이 박혀 있다 —
`(slide, name)` 유일 제약, `db_default`, `mask_key` 로 붙는 교정. 마이그레이션도
17개 쌓여 있다. **다른 ORM 으로 옮기면 그 판단들을 다시 겪는다.**

Django 는 서버 없이 라이브러리로 쓸 수 있고, **이미 그렇게 쓰고 있다** —
`check_db.py` · `backup_db.py` 계열이 `django.setup()` 만 하고 ORM 을 쓴다.
데스크탑 앱도 같은 방식이면 `models.py` · `data.py` · `judge.py` 가 **그대로 간다.**

대가는 둘이다. **PyInstaller 로 Django 를 얼리는 것이 까다롭고**(앱 탐색·
템플릿 수집), 설치 부피가 는다. 1단계에서 **먼저 확인할 항목**으로 잡는다 —
여기서 막히면 계획이 흔들리므로 가장 먼저 부딪혀 본다.

## 범위

**포함** — 그룹핑 · 합성(all-in-focus) · 검출(YOLO) · 문턱 적용 · 검토·교정 ·
계측 내보내기. 즉 **혼자 쓰는 데 필요한 전부.**

**당분간 제외** — 다중 사용자 · 서버 동기화 · 학습(GPU 서버의 몫) · 종 동정 ·
SAM2 백엔드(CPU 3.4분/시야라 기본으로 못 쓴다. GPU 가 있으면 선택지로 남길 수는 있다).

## 단계

**한 번에 만들지 않는다.** 위험이 큰 것을 뒤로 미루는 순서다.

### 1단계 — 읽기 전용 검토 뷰어

기존 `DiaRUGA.db` 와 사진 폴더를 열어 **보기만** 한다. 쓰지 않는다.

- 시야 목록 · 시야 화면 · 마스크 겹쳐 그리기 · 레이어 토글
- **원본 해상도 확대·이동** (웹이 못 하는 것)
- **초점 시리즈를 휠로 훑기** (웹이 못 하는 것)

> **완료 기준.** 운영 DB 의 **사본**을 열어 임의의 시야 10개를 웹 뷰어와 나란히
> 놓고 **같은 개체·같은 계측값**이 보인다. 그리고 **PyInstaller 로 얼린 산출물이
> 실제로 뜬다** (위의 Django 확인이 여기서 끝난다).

**위험 낮음 — 쓰지 않으므로 재생성 불가한 자료를 건드리지 않는다.**

### 2단계 — 교정까지

삭제 · 되살림 · 분류 지정 · 메모 · 검토 완료 표시. 단축키까지.

여기서 **이미 혼자 쓰는 도구로 완성**이다. 사진과 DB 를 손으로 옮겨 주면 쓴다.

> **완료 기준.** 사본 DB 에서 시야 하나를 교정하고, 웹 뷰어로 같은 DB 를 열어
> **교정이 그대로 읽힌다.** 반대 방향도 같다. `check_db.py` 가 통과한다.

**주의.** 저장 계약이 "그 시야의 교정 전체를 갈아치운다" 는 것이다. 앱도 **늘
전체를 쓴다.** 이 전제가 깨지면 나머지를 지운다 — 이 프로젝트가 **두 번 당했다.**

### 3단계 — 검출을 앱 안으로

YOLO 를 앱이 직접 돌린다. **CPU 가 기본, GPU 가 있으면 자동으로 쓴다.**

- 가중치를 어떻게 실을 것인가 (아래 "배포" 참고)
- 진행 표시와 취소 — 슬라이드 하나에 CPU 75초다. 멈출 수 있어야 한다
- `judge.py` 로 판정, 문턱은 지금 화면(`/thresholds/`)과 같은 것을 제공

> **완료 기준.** 같은 합성본에 대해 앱의 검출 결과가 **서버 파이프라인과 일치**한다
> (개체 수·`mask_key`·계측값). 049 의 벤치마크로 확인한다.

### 4단계 — 합성·그룹핑까지

초점 시리즈 묶기와 all-in-focus 합성. 여기까지 오면 **서버가 아예 필요 없다.**

- **사진 반입 경로를 새로 설계해야 한다.** 지금은 NAS 의
  `DiatomPhotos/<촬영일>/<슬라이드>/` 구조를 전제로 폴더명에서 슬라이드를 읽는다.
  밖의 연구자는 그 규칙을 모른다 — **폴더를 고르면 앱이 묻는 반입 화면**이 필요하다
- 합성은 슬라이드당 약 3분(`Run` 기록 평균 187초)이라 CPU 로 감당된다

> **완료 기준.** 사진 폴더 하나만 주면 검토 화면까지 **사람 손 없이** 도달한다.

### 5단계 — 배포

**여기에 비용이 몰린다.** `.guides/desktop/` 전부가 해당된다 — OS 매트릭스 ·
CI 빌드 · 코드 서명 · 설치/설정/데이터 위치 · 판 번호 단일 출처 · 업데이트 경로.

## 데이터가 어디에 놓이는가

`.guides/desktop/file-locations.md` 의 원칙 — **설치 위치 · 설정 위치 · 사용자
데이터 위치는 서로 다른 세 답이다.** 이 앱에 맞추면:

| | 무엇 | 성격 |
|---|---|---|
| 설치 위치 | 실행 파일 · 모델 가중치 | 읽기 전용. 업데이트가 갈아 끼운다 |
| 설정 위치 | 창 크기 · 단축키 · 마지막 폴더 | 작다. 지워져도 된다 |
| **사용자 데이터** | **`DiaRUGA.db` · 사진 · 합성본 · 썸네일 캐시** | **재생성 불가가 섞여 있다** |

**사용자 데이터 자리를 사람이 고르게 한다.** 사진이 슬라이드당 400 MB 라
시스템 기본 위치에 조용히 쌓으면 안 된다. 그리고 **백업 대상이 어디인지를 앱이
분명히 말해야 한다** — 서버에는 시간별 백업과 무결성 깃발이 있지만, PC 에는 없다.

> **이 프로젝트의 규약을 앱에도 가져간다.** `cp DiaRUGA.db` 금지(WAL) ·
> 큰 작업 전 스냅샷 · 검증 통과 뒤에 제 이름. `backup_db.py` 가 이미 그렇게
> 되어 있으므로 **앱이 그것을 부르면 된다.**

## 위험과 완충

| 위험 | 완충 |
|---|---|
| **5,500줄을 다시 쓴다** | `_detection.html` 의 주석이 사실상 설계 문서다. **읽고 시작할 것.** 캐시된 dict 를 고치지 않는 것, 지운 개체를 골랐을 때 "선택 없음" 이라 하지 않는 것 같은 판단이 거기 있다 |
| PyInstaller + Django 가 까다롭다 | **1단계 완료 기준에 넣었다.** 여기서 막히면 계획이 흔들리므로 가장 먼저 부딪힌다 |
| torch 부피 (CPU 휠도 수백 MB) | 설치 파일이 커진다. GPU 판까지 지원하면 갈라진다 — **5단계에서 정한다** |
| 모델 가중치 배포 (YOLO 45 MB) | 설치 파일에 넣는다. **첫 실행 때 받는 방식은 피한다** — 이 조직은 사내망 TLS 가로채기를 겪었고, 밖의 연구자 환경은 더 모른다. **오프라인 설치가 기본이어야 한다** |
| 사진 반입 규칙이 밖에서 안 통한다 | 4단계의 설계 항목으로 명시했다 |
| 교정을 잃는다 | 1단계는 읽기 전용. 2단계는 사본 DB 로만 시험 (**"화면을 눌러 보는 시험은 사본 DB 에 붙인다"**) |

## 하지 않기로 한 것과 그 이유

- **오프라인 동기화·병합** — 지금 저장 계약(전체 갈아치우기) 위에 얹으면 재생성
  불가한 자료를 가장 잃기 쉬운 방식으로 다루게 된다. 필요해지면 **저장 계약을
  증분으로 바꾸는 서버 재설계가 먼저**다
- **Electron · Tauri** — 앞은 원본 확대·초점 훑기의 이득을 못 얻고 파이썬
  파이프라인과 두 벌이 된다. 뒤는 Rust 자산이 사내에 없다
- **SAM2 를 기본 엔진으로** — CPU 3.4분/시야. 대화형으로 못 쓴다
- **웹 뷰어 폐기** — 연구소 안에서는 지금 구조가 잘 돈다. 자료가 쌓이는 곳도 여기다

---

## 아직 답이 없는 것

- **첫 배포 OS 의 우선순위.** 규조 연구자들이 실제로 무엇을 쓰는가. Windows 가
  1순위일 가능성이 높지만 **추측하지 말고 확인할 것**
- **앱 이름.** 웹 뷰어와 같은 `DiaRUGA` 로 갈지, 갈래를 나눌지
- **계측 결과 내보내기 형식.** CSV 는 `TODOs.md` 에 이미 있다. 밖의 연구자에게는
  이것이 오히려 주력 기능일 수 있다
- **업데이트 경로.** 자동 갱신을 넣을지, 받아서 다시 설치하게 할지

---

## 완료의 모양

> 규조 연구자가 **설치 파일 하나를 받아 설치하고**, 자기 현미경 사진 폴더를
> 고르고, **GPU 없는 노트북에서** 검출 결과를 검토해 계측을 내보낸다.
> 서버도, 명령줄도, 우리 도움도 필요하지 않다.

여기까지 가는 길에 **2단계에서 멈춰도 손해가 없다** — 그 자리도 쓸 만한 도구다.
