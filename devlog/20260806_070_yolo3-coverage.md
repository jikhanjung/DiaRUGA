## 2. `recipe` 가 `Run.params` 에 없었다 — 메모가 구했다

같은 묶음에 이어 붙이려면 **같은 조건**이어야 한다. 그런데 기록된 것은 이만큼이다.

```json
{"backend": "yolo", "max_um": 150.0, "min_um": 10.0,
 "points_per_side": 32, "rebind_iou": 0.5, "scale": 1.0}
```

**`conf` 와 가중치 경로가 없다.** 둘 다 검출 결과를 바꾸는 값이다.

살린 것은 `RunBatch.note` 에 사람이 적어 둔 한 줄이었다.

> `YOLO11m-seg v1 로 전체를 한 번 훑은 묶음. 판정 켬(기본 문턱)·conf 0.01·scale 1.0`

읽어 보니 셋 다 코드 기본값과 같아 그대로 갔다. **메모가 없었으면 짐작해야 했고,
짐작이 틀리면 한 묶음 안에 조건이 다른 검출이 섞인다** — 묶음을 둔 목적(028,
"무엇을 무엇과 비교하는지가 화면에 잡히도록")이 그 자리에서 무너진다.

**P10 5단계(`RunBatch.recipe`)가 필요한 이유가 실측으로 확인된 셈이다.** 사람의
메모에 기대는 것은 이번에 운이 좋았던 것이다.

## 4. OOM 은 조각화가 아니라 **개체 수의 함수**였다

실행이 `partial` 로 남고 스스로 말해 줬다.

```
Run 236: partial  OOM 으로 7장을 건너뛰었다 — 그만큼 검출이 없다.
                  GPU 를 다른 작업과 나눠 쓰고 있지 않은지 볼 것
```

**이 한 줄이 없었으면 11장이 조용히 비었다.** "돌았다" 와 "다 돌았다" 가
구분되는 것이 그 값이다.

처음엔 긴 실행의 VRAM 조각화로 짐작했다. 사용자가 **"재시도해도 또 OOM 날
가능성이 높아 보여"** 라고 했고, 새 프로세스로 다시 돌려 보니 그 말이 맞았다.

### 요구한 덩어리가 원인을 말한다

마스크 한 장이 원본 해상도로 `2752 × 2208 × 4바이트 = 24.3 MB` 다. 실패한
할당을 그것으로 나누면 이렇다.

| 요구한 크기 | ÷ 24.3 MB | |
|---|---|---|
| 3,208,642,560 | **132.0** | 한 번 실패 후 통과 |
| 3,720,347,648 | **153.1** | 네 번 실패 |
| 3,793,747,968 | **156.1** | 네 번 실패 |
| 3,816,816,640 | **157.0** | 네 번 실패 |
| 4,741,660,672 | **195.1** | 네 번 실패 |

**정수에 붙는다.** 개체마다 마스크 한 장을 원본 해상도로 늘리는 자리이고,
**8 GB 카드는 130개 언저리에서 넘친다.** 무작위가 아니라 그 이미지의 성질이라
같은 파일이 매번 걸린다.

그리고 여유 메모리가 `190 MB → 1.75 GB → 270 MB → 1.70 GB` 로 오르내린다 —
파이토치가 캐시를 비우고 재시도하지만 **필요한 4.7 GB 에는 애초에 못 미친다.**
재시도가 의미 없는 이유다.

### 걸린 것이 한 시야에 몰려 있었다

남은 5장이 전부 `369cm` 의 `g073` 이었다. 그 슬라이드는 프레임당 평균 35개인데
(14,220 ÷ 405) 이 시야는 150~200개다.

**가장 빽빽한 시야가 곧 못 도는 시야다.** 그리고 그것이 검토가 가장 필요한
자리다 — `max_det` 로 자르면 **진짜 개체를 버린다.**

## 5. CPU 가 답이었다 (사용자 제안)

> "YOLO 를 CPU 로 돌리면 메모리는 넉넉할 것 같은데"

맞았다. GPU 로 네 번 시도해 다 실패한 5장이 **CPU 에서 한 번에 통과**했다.

```
[1] device=cpu  검출 1개 · 개체 163개
[2] device=cpu  검출 1개 · 개체 127개
[3] device=cpu  검출 1개 · 개체 128개
[4] device=cpu  검출 1개 · 개체 138개
[5] device=cpu  검출 1개 · 개체 165개
```

개체 수가 127~165 로, §4 가 계산한 경계(130개 언저리)와 같은 자릿수다.

- **장치를 고르는 플래그가 없다.** `device = "cuda" if torch.cuda.is_available()`
  라 자동이다 — `CUDA_VISIBLE_DEVICES=` 로 가렸다
- **RAM 은 56 GB 여유**라 4.7 GB 는 문제가 아니다
- 속도는 049 실측으로 시야당 1.7초. 5장이면 10초다
- **`gpu_lock()` 은 `cuda` 일 때만 걸린다** — CPU 갈래는 폴러와 안 부딪힌다

마지막 줄이 중요하다. **자동 대체 경로로 쓰기에 안전하다**는 뜻이다:
GPU 가 OOM 이면 그 한 장만 CPU 로 물러나도 다른 작업을 안 막는다.

> 마스크를 나눠 늘리는 수정(개체 32개씩 → 최대 요구 4.7 GB → 0.8 GB)은 여전히
> 맞는 방향이지만, **CPU 대체가 있으면 급하지 않다.** 검출 경로를 건드리는 일이라
> 파이프라인 이미지를 다시 굽는데, P09·P10 배포 때 어차피 굽는다.

## 6. `--keep-current` 는 건너뛰기를 안 한다 — 중복 671장

```python
if args.keep_current:
    print("--keep-current: 새 검출을 is_current 로 올리지 않는다 …")
elif not args.no_db and not args.force:
    # 이미 검출한 시야를 건너뛴다 …
```

관문이 `elif` 아래에 있고, 그 이유가 주석에 적혀 있다 — 관문은 재검출이
`is_current` 를 옮기기 때문에 있는 것이고 `--keep-current` 는 그걸 안 하므로
"여기서 걸러 버리면 견주고 싶은 자리가 하나도 안 남는다".

맞는 설계다. 대신 **빠진 것만 다시 돌려도 이미 끝난 것까지 다시 쌓인다.**

`prune_detections.py` 가 정확히 그 찌꺼기를 치우는 도구다(머리말이 이 경로를
첫 줄에 적어 두었다).

```
지울 검출 1084건 · 딸린 후보 38993건 → 지웠다
남은 중복 0 · 교정 7,472 그대로
```

**묶음을 넘어서는 안 지운다** — SAM2 508개는 손도 안 댔다.

## 7. 밟은 것 하나 — `docker compose run` 이 stdin 을 먹는다

11장을 다시 돌리려고 이렇게 썼다.

```bash
while IFS= read -r f; do
  docker compose run --rm pipeline python segment_diatoms.py "$f" …
done < 목록.txt
```

**한 장만 돌고 끝났다.** `docker compose run` 이 stdin 을 물려받아 목록의 나머지를
통째로 삼킨다. 로그에 `[1]` 하나만 남고 "끝" 이 찍혀서, 처음엔 나머지가 다
성공한 줄 알았다.

```bash
while IFS= read -r f <&3; do
  docker compose run --rm -T … </dev/null
done 3< 목록.txt
```

`-T` 로 TTY 를 끄고, 파일은 fd 3 으로 읽고, 컨테이너의 stdin 은 `/dev/null` 로
막는다. **셋 다 필요하다.**
