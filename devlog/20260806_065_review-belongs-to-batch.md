# 065 — 교정이 어느 검출을 보고 한 판단인지 들고 있게 한다 (P09 0단계)

2026-08-06. 계획은 [P09](20260806_P09_mask-editing.md) 에 있다. 여기는 실제로 한
일과 그 길에 배운 것이다.

`ObjectReview` 의 열쇠가 `(image, mask_key)` 에서 **`(image, batch, mask_key)`**
가 됐다. 마이그레이션 0025 · 시험 9개 · 코드 다섯 자리.

**마스크 편집을 검토하다 나온 것이다.** 사람이 마스크를 그리고 고치는 이야기를
하려면 "그 교정이 어느 검출에 대한 것인가" 를 먼저 정해야 했고, 그쪽이 더
근본이었다.

---

## 1. 왜 지금인가 — 숫자가 밀어붙였다

`yolo-3차` 를 current 로 올리면 무슨 일이 나는지 운영 DB 사본으로 `rebind` 의
알고리즘을 그대로 흉내 내 세었다. 같은 이미지 위에 YOLO 검출이 있는 449 시야,
교정 6,668건 기준.

| | 건 | |
|---|---|---|
| `exact` | **0** | **0.0%** |
| `iou` | 2,625 | 39.4% |
| `orphan` | 4,043 | 60.6% |

**`exact` 가 0 이다.** HANDOFF 4.1 이 "엔진을 갈면 거의 0 이 된다" 고 적어 둔
것이 측정값이 됐다 — `mask_key` 는 bbox 문자열이라 엔진이 다르면 **하나도** 안
맞는다.

고아 4,043 의 97%(3,922)는 **지운 것**이다. 그것이 고아가 되는 것은 손실이 아니라
**좋은 소식이다** — YOLO 가 그 오검출을 재현하지 않았다는 뜻이다. 진짜로 잃는
판단은 121건이다.

문제는 반대쪽에 있었다.

| iou 로 붙는 2,625 | |
|---|---|
| 지운 것 1,512 | **그중 1,076건이 YOLO 의 *통과* 후보에 붙는다** |
| 살아 있는 개체 1,113 | 분류 1,072 · 되살림 567 |

**SAM2 에 대고 "오검출" 이라 한 판단이 YOLO 가 낸 통과 후보에 옮겨 붙는다.**
마스크가 나빠서 지웠던 자리를 YOLO 가 제대로 그린 경우가 거기 섞여 있고, 사람은
**자기가 지우지 않은 것이 지워져 있는 것**을 본다. 그리고 그것은 되돌릴 수 없다 —
`rebind` 가 옛 상태를 지우면서 옮기기 때문이다.

**그래서 갈아타기 전에 끝나 있어야 하는 일이다.**

---

## 2. 좁히는 축이 이미지가 아니었다

처음에는 `rebind`·`save_review` 의 범위를 `(image, batch)` 로 **통째로 잠그려고**
했다. 사용자가 "물려주기는 IoU 로 하는 거지?" 라고 물어서 다시 재 봤고, 그
방향이 틀렸다는 것이 드러났다.

| 교정이 앉은 이미지 | 전체 | 지운 것 | **분류** |
|---|---|---|---|
| `stack` (합성본) | 5,875 | 4,666 | **1,186** |
| `frame` (싱글턴 153 시야) | 1,597 | 1,405 | 185 |

**분류의 88%가 합성본 위에 있다.** 살아 있는 개체에 붙은 분류 1,355건을 YOLO
프레임 검출에 대고 맞춰 보면 IoU 0.5 에서 **1,176건(87%)이 닿고, 그중 1,039건이
합성본 출신**이다. 통째로 잠그면 그만큼을 사람이 다시 지정해야 한다.

**옮기면 안 되는 것 1,076 · 옮기면 이득인 것 1,072. 거의 같은 크기다.**
한 규칙으로 처리하면 절반이 틀린다.

| 교정 | 무엇에 대한 판단인가 | 속하는 곳 |
|---|---|---|
| `removed`·`accepted` | 그 batch 가 낸 그 마스크가 틀렸다 | **batch** |
| `label`·`note` | 이 규조각이 Eucampia 다 | 개체 — batch 도 이미지도 넘는다 |
| 사람이 그린 마스크 | 여기 규조각이 있다 | 이미지 — **어느 batch 에도 없다** |

문턱은 재 보니 **신경 쓸 자리가 아니었다** — IoU 0.3~0.7 에서 87~89%로 10%
차이뿐이다. 합성본과 프레임이 같은 좌표계라 맞을 것은 확실히 맞는다. `rebind`
기본값 0.5 를 그대로 쓴다.

## 3. 그 길에 찾은 구멍 — `rebind` 가 이미지를 안 가렸다

```python
reviews = list(ObjectReview.objects.filter(viewpoint=viewpoint))
```

`save_review` 는 P06 5a 에서 이미지로 좁혔는데 **`rebind` 는 같이 안 좁혔다.**
지금은 시야마다 이미지가 하나라 안 드러난다.

프레임별 검토로 가는 순간 그 길로 **합성본 위의 교정 5,875건이 프레임 검출에
IoU 로 옮겨 붙는다** — 같은 시야라 좌표계가 같아서 IoU 가 실제로 맞는다.
"합성본은 참고용" 이라고 정해 놓고 그 교정이 프레임으로 새어 들어가는 모양이다.

**한 곳을 좁혔으면 같은 것을 하는 다른 곳도 세어 봐야 한다.** 055 에서 `Image` 를
뽑을 때 "다형 연관을 실제로 만지는 자리 — 아홉" 을 세었는데, `rebind` 가 그
목록에 없었다.

## 4. 원칙을 뒤집는가 — 아니다

`CLAUDE.md` 는 **"교정은 `Candidate` 가 아니라 `mask_key` 에 붙는다"** 를 굵게
적어 두었다. batch FK 를 다는 것이 그것을 어기는가.

그 원칙이 막으려는 것은 **재검출하면 사라지는 것에 매다는 것**이다. `Candidate` 는
회차마다 새로 생기고 옛 것은 뒤로 밀린다. **`RunBatch` 는 그렇지 않다** — 검출을
덮어쓰지 않고 쌓으므로 batch 행은 **지나가면 안 바뀌는 사건의 이름**이다.

여전히 `mask_key` 로 붙고, batch 는 **그 키가 어느 세계의 키인지**를 말한다.
한 겹 더 정확해지는 것이지 뒤집는 것이 아니다.

**덤이 두 개인데 둘 다 크다.**

- **읽기 전용을 풀 수 있다.** 051 에서 `?batch=` 화면을 읽기 전용으로 막은 이유는
  위험해서가 아니라 **저장할 자리가 없어서**였다. batch 마다 자리가 생기면 막을
  이유가 없다
- **017·027·053 이 구조적으로 불가능해진다.** 셋 다 "다른 검출을 보고 보낸
  payload 가 남의 교정을 지운" 사고다. 삭제 범위가 `(image, batch)` 가 되면
  다른 묶음의 교정에 **닿을 수가 없다**

---

## 5. 제약이 둘인 이유 — SQLite 는 NULL 끼리 안 부딪힌다

사람이 그린 개체는 `batch` 가 NULL 이다. 그러면 `(image, batch, mask_key)` 유일
제약이 **안 잡는다** — SQLite 는 NULL 을 서로 다른 값으로 보므로 같은 키가 여럿
설 수 있다.

```python
UniqueConstraint(fields=["image", "batch", "mask_key"],
                 condition=Q(batch__isnull=False), name="uniq_objreview_key"),
UniqueConstraint(fields=["image", "mask_key"],
                 condition=Q(batch__isnull=True), name="uniq_objreview_manual"),
```

조건을 뒤집은 부분 제약을 따로 둔다. Django 5.0 의 `nulls_distinct` 는
PostgreSQL 15+ 전용이라 여기서는 못 쓴다.

**시험으로 확인했다** — 같은 `(image, mask_key)` 로 manual 행을 둘 만들면
`IntegrityError` 가 난다. 안 그랬으면 이 갈래는 **예외 없이 조용히** 통과했을
것이다.

## 6. 픽스처가 현실에 없는 자료를 만들고 있었다

`save_review` 에 "묶음 없는 검출에는 저장을 거절한다" 는 가드를 넣자 **시험 5개가
섰다.** 픽스처의 기본 검출이 `run=None` 이라 묶음이 없었다.

운영의 현재 검출 508개는 **전부 `sam2-전수` 에 들어 있다.** 픽스처가 그 사실을
안 지키면 시험이 **현실에 없는 상태를 만들어 놓고 통과한다.**

**가드가 아니라 픽스처를 고쳤다.** 064 가 "픽스처가 운영 자료 자리에 사진을
썼다" 를 적어 둔 것과 같은 종류다 — 시험이 만드는 자료도 규칙을 지켜야 한다.

## 7. 되살려서 잡히는 것을 봤다

시험 9개를 붙이고 **옛 범위로 되돌려 봤다.** 4개가 섰다.

```

FAIL 사람이_그린_개체는_다시_맺지_않는다
FAIL 빈_목록이_다른_묶음의_교정을_안_지운다  False is not true : 027 이 다시 났다
FAIL 빈_목록이_사람이_그린_개체를_안_지운다  False is not true : 재생성 불가한 자료다
```

**실패할 수 없는 시험은 없는 것보다 나쁘다**(P08 §1). 통과하는 것을 보고 "있다"
고 말하지 않는다.

## 9. 남은 것

- **운영 반영은 안 했다.** 마이그레이션만 먼저 걸면 옛 뷰어 이미지가 `batch` 를
  안 채워 교정이 `batch=NULL` 로 앉는다 — **사람이 그린 개체의 자리다.**
  HANDOFF 6절대로 **뷰어·파이프라인 이미지를 함께 올린 뒤** 걸어야 한다
- `label`·`note` 를 묶음 사이로 물려주는 것은 **5단계**다. 이 판은 잠그기만 한다
- `check_db.py` 가 14개가 됐다 — HANDOFF 3.2 의 "13개" 는 운영에 반영한 뒤에
  고친다 (지금은 운영이 아직 13개인 것이 맞다)
