# 개체 하나 재려고 이미지 전체를 훑고 있었다

**날짜** 2026-08-03
**앞선 문서** `20260803_025_yolo-first-training.md` (YOLO 도입)

`shape_metrics()` 가 개체마다 **이미지 전체 크기 배열을 네댓 번 훑고** 있었다.
개체당 10.5 ms → 0.41 ms, **26배**. 값은 한 자리도 안 바뀌게 했다.

---

## 1. YOLO 로 갈아타면서 비로소 보였다

SAM2 시절에는 안 보였다. 추론이 시야당 20초인데 지표 계산 10 ms 는 0.05% 다.
YOLO 추론이 74 ms 가 되자 **후처리가 전부**가 됐다.

실행 이력을 회귀하면 이렇게 나온다.

```
초/장 = 0.199 + 0.073 × (개체 수)
        고정 199 ms (JPEG 디코드 + 추론 74ms + DB) · 개체당 73 ms
```

프레임 수가 아니라 **개체 수**가 시간을 정한다. 그래서 같은 892 프레임인데
슬라이드마다 0.39초에서 2.7초까지 갈렸다.

> **73 ms 중 `shape_metrics` 는 10.5 ms 다.** 회귀값에는 텍스처 계산·DB 쓰기가
> 함께 들어 있다. 처음에 73 ms 를 통째로 이 함수 탓으로 적었는데 틀렸다 —
> 직접 재고 나서 알았다. 나머지 60 ms 는 아직 안 봤다.

## 2. 무엇이 비쌌나

```python
m = np.ascontiguousarray(seg.astype(np.uint8))     # 2752×2208 = 6백만 화소
cnts, _ = cv2.findContours(m, ...)                 # 전체 훑기
canvas = np.zeros(m.shape, dtype=np.uint8)         # 6 MB 할당
cv2.ellipse(canvas, ...)                           # 전체 캔버스에 그리기
inter = np.logical_and(m, canvas).sum()            # 6백만
union = np.logical_or(m, canvas).sum()             # 6백만
```

개체 중앙값이 169 px 다. **실제로 쓰는 곳은 그 안의 0.3%** 다.
`texture_score()` 는 이미 `gray[y:y+h, x:x+w]` 로 잘라 쓰고 있었다 —
이 함수만 안 잘랐다.

## 3. 값을 지키느라 두 번 틀렸다

`judge` 가 이 값들로 판정한다. 달라지면 지금까지의 검출·문턱 이력과 어긋난다.
**"빨라졌다" 보다 "안 바뀌었다" 가 어려웠다.**

### 첫 번째 — 폴리곤 좌표가 잘린 창 기준이 됐다

잘라서 계산했더니 반환되는 `polygon` 이 크롭 좌표가 됐다. 그것은 **저장돼서
뷰어가 사진 위에 그리는 값**이다. 마스크가 전부 엉뚱한 자리에 그려졌을 것이다.

### 두 번째 — `fitEllipse` 가 좌표에 민감했다

좌표만 되돌렸더니 이번엔 `ellipse_iou` 가 **3,000개 중 1,011개**나 달라졌다
(상대차 중앙 1.6%, 최대 58%).

원인: `cv2.fitEllipse` 는 float32 로 푼다. 같은 모양이라도 좌표가 옮겨지면
결과가 1e-7 쯤 달라지고, 그 뒤의

```python
cv2.ellipse(canvas, (int(round(cx)), int(round(cy))), ...)
```

가 그 차이를 **1 픽셀 이동으로 증폭**한다. 1 픽셀이면 IoU 가 1~2% 움직인다.
`_major_px` 의 상대차가 8.6e-08 인데 `ellipse_iou` 는 1.6e-02 였다 — 이 대비가
곧 증폭의 증거다.

### 세 번째 — 윤곽만 잘라 찾고, 곧바로 되돌린다

```python
m = seg[cy0:cy1+1, cx0:cx1+1]        # 여기만 잘라서 훑는다
c = max(cv2.findContours(m, ...)[0], key=cv2.contourArea)
c = c + [[[cx0, cy0]]]               # 곧바로 원래 좌표로
# 이 아래는 옛 코드와 글자 그대로 같다
```

**계산은 전부 옛 좌표에서 한다.** `findContours` 만 잘라서 돌리고, 나온 윤곽은
점 몇백 개라 되돌리는 비용이 없다.

타원 IoU 캔버스는 **마스크와 타원을 모두 덮는 만큼만** 잡되 이미지 밖으로는
안 나간다. 그 바깥은 마스크도 타원도 0 이라 교집합·합집합에 아무것도 더하지
않는다 — 이미지 전체에 그리던 옛 결과와 정확히 같다. 휜 봉상에 맞춘 타원은
마스크를 크게 벗어나므로 그 몫을 축정렬 외접 상자로 정확히 구한다.

`bbox` 는 부르는 쪽에서 받는다. 안 받고 `np.nonzero(seg)` 로 찾으면 **그 훑기가
아끼려던 비용만큼 든다** — 처음에 그렇게 만들었다가 오히려 느려졌다(11.6 ms).

## 4. 확인

```
무작위 3,000개    2,997 완전 동일 · 1 다름(ellipse_iou 0.0015)
신장비≥3 800개    차이 0 · judge 판정 뒤집힘 0
속도              10.5 ms → 0.41 ms (26배)
```

드물게 남는 차이는 **타원이 마스크를 크게 벗어나는 병적인 봉상**(축 40×1900
같은 것)에서만 났다. 89,541개 중 문턱 ±0.02 안에 있으면서 신장비 3 이상인 것이
1,840개(2.06%)이므로 이론적 상한은 그만큼이지만, 실측 표본에서는 0건이었다.

## 5. 재는 데 25분을 버렸다

검증을 **후보 74,000개 전수**로 잡았다. 옛 코드가 개체당 10.5 ms 인 데다 비교용
마스크를 매번 6백만 화소 배열에 칠해야 해서 25분짜리 일이 됐다. 게다가 멈췄다고
생각한 컨테이너가 안 죽어서 둘이 CPU 를 두고 경쟁했다.

**표본이면 될 일이었다.** 마지막 확인(신장비≥3 800개)은 1분이 안 걸렸다.
`pkill` 은 호스트에서 도는 것이라 **컨테이너 안의 프로세스를 못 죽인다** —
`docker stop` 을 써야 하고, 멈춘 뒤에는 파이썬이 버퍼에 남긴 출력이 날아간다
(`python -u` 를 쓸 것).

## 남는 것

  텍스처는 이미 잘라 쓰지만 대역 통과 필터가 무거울 수 있다 — 재 보지 않았다
