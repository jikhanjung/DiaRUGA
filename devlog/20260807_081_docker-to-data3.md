# 081 — Docker 저장소를 `/data3` 로 옮긴다

2026-08-07 · 루트 디스크가 87% 였다

## 왜

루트(`/dev/nvme0n1p2`, 228 G)가 **87%** 였다. 파이프라인 이미지 하나가 7.58 GB 고
회차를 돌리면 계속 는다. `/data3` 는 7.3 T 에 6.3 T 가 비어 있다.

## 먼저 알아야 했던 것 둘

**이 도커는 DiaRUGA 만의 것이 아니다.** 컨테이너 넷이 산다 —
`diaruga-web-1` · `phyloserver-web-1` · `scoda-server` · `refserver`.
데몬을 세우면 넷이 다 내려간다.

그런데 넷 다 `restart: unless-stopped` 였다. 그래서:

- `systemctl stop docker` → 넷 다 SIGTERM 받고 내려간다 (호스트 재부팅과 같은 길)
- `systemctl start docker` → **넷 다 스스로 돌아온다**
- 반대로 `docker compose stop` 으로 멈춘 것은 "사람이 멈춘 것" 이라 **안 돌아온다**

그래서 **DiaRUGA 만 곱게 내리고**(SQLite WAL — 쓰는 쪽이 빠져야 본체로 정리된다)
나머지 셋은 데몬에 맡겼다. 실제로 셋은 저 혼자 돌아왔고 DiaRUGA 만 손으로 올렸다.

## 이 작업이 **이미 있던 위험**도 고쳤다

`docker.service` 에 마운트 의존이 없었다(`RequiresMountsFor=` 가 비어 있었다).
그런데 컨테이너들이 이미 `/data3` 를 물고 있다:

```
diaruga-web-1      /data3/DiaRUGA
phyloserver-web-1  /data3/backups/status · /data3/sp_photos
```

부팅 때 `/data3` 가 늦게 붙거나 실패하면 **도커가 그 경로를 빈 디렉토리로 만들어
붙인다.** phyloserver 가 빈 사진 폴더를 보게 되는 식이다 — 500 도 404 도 아니고
"자료가 없는 것처럼 도는" 상태다. `RequiresMountsFor=/data3` 는 새 위험을 막는
것이자 **이미 있던 이 위험을 없앤 것**이다.

## 순서

```
① 도커를 켜 둔 채 미리 복사        서비스 영향 없음. 여기서 대부분이 넘어간다
② 폴러 정지 + DiaRUGA 만 곱게 내림
③ systemctl stop docker docker.socket    socket 을 빼면 CLI 한 번에 되살아난다
④ 차이만 다시 (--delete)          이때 사본이 정지 상태의 원본과 일치한다
⑤ daemon.json 에 data-root        **nvidia 런타임 블록을 함께 둔다**
⑥ RequiresMountsFor=/data3
⑦ systemctl start docker
```

`rsync` 는 `-aHAX --numeric-ids` 다. **`-H` 가 필수다** — overlay2 는 레이어를
하드링크로 공유하므로 빼면 용량이 몇 배로 분다.

**두 번 도는 것이 요점이다.** 1차는 서비스를 켜 둔 채라 일관되지 않지만, 그
동안 정지 시간이 0 이다. 2차는 멈춘 뒤 **바뀐 것만** 넘기므로 짧다.

## 재어 보니

| | |
|---|---|
| `docker system df` 가 말한 것 | 37.6 GB |
| **실제로 넘어간 것** | **~72 GB** |
| 1차 복사 | 약 20분 (파일 531,226개) |
| 2차 복사 | 2분 미만 — **실제로 넘어간 파일 14개** |
| 2차가 지운 것 | 17 GB |

**`docker system df` 를 믿고 예상을 냈다가 두 배로 틀렸다.** 그 명령은 공유
레이어를 한 번만 세는데 `/var/lib/docker` 에는 컨테이너 쓰기 층·containerd
콘텐츠 저장소·로그가 함께 있다. 다음에 옮길 일이 있으면 `du -sh` 로 잰다.

2차가 17 GB 를 지운 것은 **1차가 도커를 켜 둔 채 뜬 사본이라서**다 — 그때 있던
임시 레이어가 딸려 왔고, 정지 뒤에는 없는 것들이었다. `--delete` 가 그것을
걷어냈다. 예상대로 도는 모습이다.

### 진행 표시가 되돌아가는 것

1차에서 `99% → 92%` 로 내려갔다. `rsync -a` 는 **증분 재귀**라 목록을 미리 다
세지 않고 훑으면서 발견한다 — 퍼센트의 분모가 자란다. 줄 끝의
`ir-chk=1064/531226` 이 그것을 그대로 보여 준다(`ir` = incremental recursion).

2차에서는 반대로 **화면이 멈춘 듯 보였다.** `--info=progress2` 의 숫자는 넘길
때만 움직이는데 그 패스가 한 일은 대부분 **훑기와 지우기**였다. 프로세스가
`D`(디스크 대기)에 있고 `/data3` 사용량이 줄어드는 것으로 살아 있음을 확인했다.

## 확인한 것

```
DockerRootDir  /data3/docker · overlay2
이미지         14개 — 이름까지 그대로 (집합으로 대조)
컨테이너       4개 · 셋은 스스로 돌아옴 · DiaRUGA 만 손으로
GPU            CUDA 보임 True · RTX 3060 Ti · 8.2 GB   ← nvidia 런타임 살아 있다
smoke          통과 (판 v0.8.1)
check_db       DB 가 앞뒤가 맞는다
폴러           16:17 스캔 재개
루트 디스크    87% → 81%
```

**GPU 확인을 눈으로 안 하고 넘어가면 안 된다.** `daemon.json` 을 통째로 덮는
순간 nvidia 런타임이 사라지고, 그것은 **다음 검출이 돌 때**에야 드러난다.

한 번 헛짚었다: 뷰어를 올리자마자 smoke 를 쳐서 `/healthz 000` 이 나왔다.
gunicorn 이 아직 뜨는 중이었다 — `deploy.sh` 에 기동 게이트가 있는 이유가 이것이다.

## 남은 것

- **옛 자리를 아직 안 지웠다.** `/var/lib/docker` 는 그대로 있다. 며칠 돌려 보고
  `mv /var/lib/docker /var/lib/docker.old` → 확인 → 삭제. 되돌릴 길이
  `daemon.json` 한 줄로 끝나야 한다
- `/data3` 는 이제 **사진·백업·도커**를 함께 인다. 6.3 T 여유라 지금은 넉넉하지만
  세 가지가 같이 크는 곳이라는 것은 기억해 둘 것
- `containerd` 의 자리(`/var/lib/containerd`)는 안 옮겼다 — overlay2 이미지는
  도커 쪽에 있고 그쪽은 작다
