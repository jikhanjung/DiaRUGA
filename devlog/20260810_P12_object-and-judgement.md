# P12 — 개체와 판정을 가른다 (`Object` / `MaskJudgement`)

**이것은 계획이다. 아직 아무것도 안 바꿨다.**

## 어디서 시작됐나

104(묶인 개체는 분류를 함께 받는다)를 넣은 직후 사용자가 물었다.

> "엄밀히 말하면 `ObjectLink` 에 라벨을 넣고, 그것이 `ObjectReview` 의 라벨에
> 대해 우선권을 가지게 하면 되는 것 같은데."

그때는 **읽는 자리 79곳**을 근거로 비정규화를 택했다(104 의 "라벨의 집" 절).
그런데 같은 날 105(개체 카탈로그)가 `ObjectReview` 에 **종명(`species`)** 을
넣으면서 질문이 다시 왔다.

> "지금 `ObjectReview` 에 종명을 넣는다고 하니 `ObjectLink`/`LinkMember` 와
> 어떻게 연결을 시켜야 하나 고민이 되는 거야."

종명은 라벨보다 **더 순수하게 개체의 성질**이다. 그래서 같은 질문이 더 날카롭게
돌아왔고, 파고들다 보니 **경계가 묶음에 있지 않다**는 결론에 닿았다.

## 지금 모습 — 세 테이블의 해부

### 무엇을 짚는가

| 테이블 | 묻는 것 | 열쇠 | 칸 |
|---|---|---|---|
| `ObjectReview` | **이 마스크가 어떤가** | `(image, batch, mask_key)` | `removed`·`accepted`·`label`·`species`·`note`·`geom`·`geom_edited`·`bind_*` |
| `ObjectLink` | **이것들이 하나인가** | `viewpoint` + `batch` | `note` (내용은 멤버가 갖는다) |
| `ObjectLinkMember` | **그 이미지에서는 어느 마스크인가** | `(image, batch, mask_key)` | `is_rep`·`geom` |

**`ObjectReview` 와 `ObjectLinkMember` 는 사실상 같은 성격이다.** 열쇠가 같고,
`geom` 스냅샷을 각자 들고, `Candidate` 에 FK 로 안 매달리는 규약도 같다. 다른
것은 무엇을 말하느냐뿐이다 — 하나는 판정, 하나는 소속.

### 왜 값으로 매는가

둘 다 **사람이 만든 재생성 불가 자료**다. `Candidate` 에 FK 로 매달면 재검출
한 번에 조인이 깨지며 판단이 사라진다 — *재생성 불가한 것이 재생성 가능한 것의
자식이 되면 안 된다*(CLAUDE.md). 그래서 마스크를 `(image, batch, mask_key)` 로
짚고 기하를 스스로 든다. 검출기가 바뀌어도 읽힌다.

같은 이유로 **`ObjectLinkMember` 와 `ObjectReview` 사이에도 FK 가 없다.** 둘은
같은 열쇠를 가리킬 뿐이라 각자 혼자 존재할 수 있다.

### 실측 (운영 DB, 2026-08-10)

```
Candidate            122,333
ObjectReview           7,906   ← 개체의 6.3% 에만 붙어 있다
  그중 batch=NULL        170   ← 사람이 그린 마스크 (대응 Candidate 가 없다)
  고아(짝 없음)            0
ObjectLink                 3
ObjectLinkMember           9
  교정 행이 없는 멤버       3   ← 판단 없이 묶기만 한 마스크
  지워진 채 남은 멤버       0   ← 지금 0 이지만 막는 것이 없다
분류가 어긋난 묶음         2 / 3
```

마지막 줄이 이 문서를 쓰게 만든 숫자다.

## 어긋나 있는 다섯

**1. `ObjectReview` 가 두 가지를 겸한다.** 모델 주석이 이미 선을 그어 놨다:

| 칸 | 무엇에 대한 판단인가 | 속하는 곳 |
|---|---|---|
| `removed`·`accepted` | 그 batch 가 낸 그 마스크가 틀렸다/맞다 | **batch** |
| `label`·`note`·`species` | 이 규조각이 Eucampia 다 | **개체** — batch 를 갈아도 참이다 |

**뜻은 갈라 놓고 자리는 한 행이다.** 그래서 batch 를 갈면 동정까지 함께 별개가
된다 — 105 가 "엔진마다 카탈로그가 완전히 별개" 를 방침으로 적어 둔 것이 이
구조의 그림자다.

**2. 라벨은 번지고 종명은 안 번진다.** 104 가 `label` 만 묶음을 따라 번지게
했다. 종명은 그대로다 — 지금은 카탈로그가 시야마다 이미지 하나만 내서 표가 안
날 뿐이다.

**3. 전파는 소급되지 않는다.** 104 는 **저장할 때** 번지게 한다. 그전에 붙은
판단은 그대로라서, 지금 운영의 묶음 셋 중 둘이 어긋나 있다. 규칙으로 만든
정합성은 **규칙이 생기기 전의 자료를 못 고친다.**

**4. 지워진 마스크가 묶음에 남을 수 있다.** `ObjectLinkMember` 는 `removed` 를
전혀 안 본다. 오검출이라고 판정한 마스크가 "그 개체의 그 판" 으로 남아 있어도
막는 것이 없다. 운영에는 아직 0건이다.

**5. 묶음이 회차를 못 넘는다** (105 덧 · TODOs). 멤버가 `batch` 를 열쇠에 들고
묶음 자체도 `batch` 에 매여 있다. 같은 규조각이 `sam2-전수` 와 `yolo-3차` 에
각각 잡혀 있어도 **하나라는 것을 담을 자리가 없다.**

## 버린 안 둘

### A. 그대로 두고 전파한다 (지금 하고 있는 것)

라벨을 `ObjectReview` 에 두고 저장할 때 묶음 멤버에 번지게 한다(104).

- **값**: 읽는 자리 79곳을 안 건드린다. 내보내기는 어차피 판마다 라벨이 필요하니
  이 비정규화가 그쪽이 원하는 모양이기도 하다
- **비용**: 진실이 N벌 · 소급 불가 · 쓰기 경로가 늘 때마다 전파를 기억해야 함 ·
  값을 검사(불변식)로 치러야 함

### B. `ObjectLink.label`/`species` + 우선권

라벨·종명을 묶음으로 올리고, 묶였으면 그쪽이 이긴다.

- **값**: 구조적으로 어긋날 수 없다. 종명에는 특히 맞다 — 읽는 자리가 **넷뿐**
  (`catalog_rows`·`save_catalog_entry`·`species_seen`·`save_review` 의 보존 규칙,
  + 템플릿 둘). 라벨의 79곳과 계산이 다르다
- **버린 이유**: **집이 둘이 된다.** 묶인 것은 `ObjectLink`, 아닌 것은
  `ObjectReview` — 그런데 개체 122,333개 중 묶인 것은 9개다. 읽는 쪽은 늘 두
  갈래를 타야 하고, **안 고친 자리는 예외 없이 옛 값을 보여준다**(038·040 의
  모양). 그리고 무시되는 진실 하나가 DB 에 계속 앉아 있게 된다

## 제안 — 경계는 묶음이 아니라 **개체와 판정** 사이다

B 를 버린 이유는 전부 "묶였나?" 를 조건으로 삼은 데서 나왔다. 그 조건을 없애면
된다 — **판단받은 모든 마스크가 개체를 갖게** 한다.

```
Object          개체 하나 — label · species · note            ← batch 무관
   ▲ N:1
MaskJudgement   (image, batch, mask_key) 의 판정              ← removed · accepted
   ╎                                                            geom · geom_edited
   ╎ 값 조인 (0..1 : 0..1)                                       is_rep · bind_*
Candidate       검출이 낸 개체                                 ← 재생성 가능
```

| 지금 | 새것 |
|---|---|
| `ObjectLink` | **`Object`** |
| `ObjectLinkMember` + `ObjectReview` | **`MaskJudgement`** |

`ObjectLink` 가 지금은 **묶인 것에만** 있어서 우선권이 필요했다. 모두가 가지면
규칙이 사라진다. 동작도 자연스러운 말이 된다:

- **묶기** = 개체 둘을 하나로 합친다 (판정이 옮겨 붙는다)
- **풀기** = 개체를 가른다
- **동정·분류** = `Object` 의 칸 하나를 쓴다 — **번지게 할 것이 없다**

### 카디널리티와 제약

```
Object 1 ──── N MaskJudgement        최소 1 (멤버 없는 Object 는 유령)
                 그중 is_rep 정확히 하나
MaskJudgement 0..1 ── 0..1 Candidate  값 조인, 양쪽 다 없을 수 있다
```

- **판정 없는 개체가 대다수다** — 6.3% 에만 판단이 있다. 안 건드린 통과분에는
  행이 안 생기고 그게 맞다
- **개체 없는 판정도 있다** — 사람이 그린 마스크 170건, 재검출로 짝을 잃은 고아

`object_id` 는 **nullable 이되 조건부 필수**다.

| MaskJudgement | Object |
|---|---|
| `removed=True` (오검출) | **없다** — 규조각이 아니라고 판정한 것이니 개체일 수 없다 |
| 그 밖(살아 있는 마스크) | **반드시 있다** |

```python
CheckConstraint(check=~Q(removed=False, object__isnull=True),
                name="live_judgement_has_object")
```

**이것이 어긋남 4를 구조로 닫는다** — 지우면 `object_id` 를 떼고, 되살리면 다시
붙는다. 규칙을 기억할 필요가 없다.

유일 제약은 지금 것을 그대로 물려받는다: `(object, image)` · `(image, batch,
mask_key)` · `batch IS NULL` 용 짝 제약 · `is_rep` 은 개체당 하나.

### 무엇이 풀리나

- **전파가 필요 없다** — 104 의 `_spread_link_labels` 도, 그것을 지키는 불변식
  검사도 사라진다. 진실이 하나면 어긋날 수가 없다
- **회차를 갈아도 동정이 산다** — `batch` 는 판정에만 남는다. 엔진을 바꾸면
  마스크 판정만 다시 하고 사람이 적은 종명은 그대로다. 105 덧이 요구한
  **"개체 동일성을 담는 층"** 이 바로 이것이고, 그것이 "물려준다" 를 조인으로
  바꿔 준다
- **지워진 것이 개체에 남지 않는다** (위 CheckConstraint)
- **집계가 겹치지 않는다** — 같은 규조각이 판 넷에 잡혀도 `Object` 가 하나다

### 무엇이 안 풀리나 — 여기를 착각하면 안 된다

**`Object` 를 세는 것은 "이 시야에 규조각 몇" 이 아니다.** `Object` 는 *사람이
무언가 말한* 마스크에만 생긴다 — 지금도 멤버 9건 중 3건은 교정 행 없이 묶기만
한 마스크다. 집계는 여전히 `Candidate` 에서 나오고, `Object` 는 그 위에서
**겹치는 것을 하나로 세게** 해 줄 뿐이다.

## 밟으면 안 되는 곳

**1. 이름을 바꾸는 것이 위험의 대부분이다.** `Core`→`Locality` 때 Django 가
**옛 테이블을 지우고 새로 빈 것을 만드는** 순서를 냈다(063). `ObjectReview`
라는 이름은 두고 **`object_id` FK 만 더하는 쪽**이 훨씬 싸고 안전하다. 이름이
뜻보다 좁아진 것이지 구조가 틀린 게 아니다 — 주석에도 그렇게 적혀 있다.

**2. 이전기가 재생성 불가 7,906행을 만진다.** 이 저장소에서 가장 위험한 종류다.
순서는 **새 테이블 → `RunPython` 으로 자료 이동 → 옛 칸 걷기**이고 `reverse` 도
함께 적는다. 사본으로 먼저 돌리고 `verify` 로 앞뒤를 센다. 큰 작업 전 백업은
말할 것도 없다.

**3. 합칠 때 충돌 규칙이 필요하다.** 지금도 묶음 셋 중 둘이 어긋나 있다.
이전기가 그걸 만나면 무엇을 남길지 정해야 하고, **사람이 적은 것을 자동으로
덮으면 안 된다.** 종명은 현미경 보며 적는 것이다.

**4. 카탈로그 번호는 이미 밖으로 나간다.** `catalog.py` 가 *번호는 안 바뀐다* 를
못 박아 뒀다(논문·표에 적히므로). `Object` 를 단위로 삼으면 번호를 개체 기준으로
바꾸고 싶어지는데, **그때도 번호 규칙은 지금 그대로여야 한다.**

**5. 뷰어와 파이프라인 판을 함께 올린다.** 스키마를 조이는 마이그레이션은 옛
파이프라인 이미지가 걷힌 칼럼에 INSERT 하면 폴러가 선다(055). 조인 사본에
파이프라인 컨테이너를 붙여 먼저 돌려 볼 것.

## 언제

**지금은 아니다.** 105(카탈로그)가 `ObjectReview` 를 매일 만지는 중이고, 여기서
스키마를 흔들면 정면으로 부딪힌다. 순서는:

1. **카탈로그가 자리를 잡는다** — 동정이 실제로 쌓이고 쓰임이 드러난다
2. **그동안은 규칙으로 버틴다** (아래)
3. **`YOLO 4차` 가 들어오고 집계를 묶음 단위로 갈 때 `Object` 를 함께 도입한다**
   — 읽는 자리를 한 번에 훑는 유일한 기회다. 105 덧이 "스키마는 4차가 실제로
   들어온 뒤에 박는다" 고 한 것과 같은 시점이다

## 그때까지의 규칙 셋

스키마 없이 되고, 카탈로그 작업과 안 부딪힌다.

- **종명도 묶음을 따라 번지게** — `save_catalog_entry` 에 104 와 같은 규칙
- **묶을 때 종명·분류가 서로 다르면 사람에게 묻는다** — 지금 팝업은 아무것도 안
  묻는다. 조용히 대표 것으로 덮으면 남의 동정을 잃는다. **이것이 가장 급하다**
- **`check_db.py` 불변식** — "묶음 안의 분류·종명이 어긋난 것 N건". 비정규화를
  택했으면 그 값은 검사로 치러야 하고, 안 치르면 그냥 비정규화다

## 미결

- 이전기의 충돌 규칙 — 대표 우선 / 다수결 / 사람에게 물음
- `Object` 가 시야를 넘을 수 있는가 — 지금 `ObjectLink` 는 못 넘는다(스테이지가
  움직인 뒤라 "같은 자리" 라는 근거가 없다). 회차를 넘는 것과 시야를 넘는 것은
  **다른 문제**다
- 회차끼리 무엇을 근거로 맺는가 (IoU 문턱은 실측), 그리고 사람이 고칠 수 있게
  할 것인가 — 고치게 하면 그것도 재생성 불가 자료가 된다 (105 덧)
