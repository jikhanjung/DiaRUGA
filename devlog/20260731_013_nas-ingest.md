# NAS 에서 슬라이드를 가져와 끝까지 돌린다

**작성일** 2026-07-31

## 정찰과 반입을 나눈다

형제 프로젝트의 EPMA 반입과 같은 갈래다. NAS 디렉토리는 사람이 만든 것이라 예외가
많아서, 먼저 **읽기 전용으로 훑어** 무엇이 있고 무엇이 안 맞는지 보고 나서 가져온다.

```
scan_nas.py    읽기 전용. DB 도 파일도 안 건드린다
ingest_nas.py  새것만 가져와 Slide 행을 만든다
```

첫 실행:

```
새 슬라이드 — 1개
  260731/RS23-GC03 369cm    사진  412   1365.9 MB  조용 77.7분
이미 있음 — 3개
  260729/RS23-GC03 71cm · WAP13-GC47 116cm · WAP13-GC47 450cm
```

### 고장이 정상처럼 보이면 안 된다

NFS 가 빠지면 `/nfs/temp-share` 는 그냥 빈 로컬 디렉토리가 된다. 그것을 훑으면
"새 슬라이드가 하나도 없다" 가 되어 **아무 일도 안 하는 것이 정상 동작처럼 보인다.**
`/proc/mounts` 로 실제 nfs 마운트인지 확인하고, 아니면 멈춘다.

### 촬영 중인 폴더를 건드리지 않는다

절반만 가져가면 그룹핑이 시야를 잘못 묶고, 그 위에 검출과 교정이 쌓인 뒤에
되돌리는 것은 훨씬 비싸다. inotify 는 NFS 에서 못 믿으므로(P01 §1) **파일 개수와
가장 최근 mtime 이 일정 시간 그대로면** 끝난 것으로 본다(`--quiet-min`, 기본 20분).

완벽하지 않다 — 촬영자가 오래 쉬었다 다시 찍으면 중간에 끝난 것으로 볼 수 있다.
그래서 `Slide.state` 로 사람이 되돌릴 수 있게 해 뒀다.

### 받다 만 것이 정상처럼 보이면 안 된다

`<대상>.part/` 로 받아 **개수와 바이트를 대조한 뒤에** 제 이름을 준다. 이름이
붙어 있으면 온전히 받은 것이다. 중간에 죽으면 `.part` 가 남고 다음 실행이 지우고
다시 받는다. (백업 lane 의 `.part` 와 같은 규칙이다 — devlog 009.)

## 전 과정이 JSON 없이 돈다

`focus_stack.py --slide` 와 `segment_diatoms.py --slide` 를 붙여 대상을 DB 에서
고르게 했다. `groups_*.json` 이 파이프라인에서 완전히 빠졌다.

```
scan_nas → ingest_nas → group_focus_series → focus_stack --slide → segment_diatoms --slide
```

`segment_diatoms --slide` 는 합성본이 있으면 그것을, 싱글턴 시야는 그 한 장을
고른다 — 예전에 `run_batch.sh` 가 JSON 을 읽어 하던 일이다.

## 검토 게이트가 실제로 걸렸다

```
그룹핑 직후   processing · 시야 74 · 차단 배너 표시 · 저장 409
검출 완료 후  done       · 배너 자동 해제 · 검토 열림
```

라이브 뷰어에서 확인했다. 검출 74개가 끝나자 `mark_done_if_complete()` 가 상태를
열었고 배너가 사라졌다.

검토 화면은 따로 만들지 않았다. 캐러셀(`_shots.html`)은 `stack`·`frames` 로
그리므로 검출과 무관해서, **개체가 0개인 검출**(`data.preview_detection`)을 넘겨
주면 같은 화면이 그대로 돈다. 감출 것은 화면이 아니라 도구다.

## 그리고 배율 문제가 드러났다

새 슬라이드가 **0.045 µm/px** 다. 기존 세 슬라이드는 0.1126 이다.

```
260729  Plan-Apochromat 40x/0.95 Korr      NominalMagnification 40   0.1126
260731  Plan-Apochromat 100x/1.40 Oil DIC  NominalMagnification 100  0.0450
```

배율 비 100/40 = 2.5, µm/px 비 0.1126/0.045 = 2.5. XML 안에서는 앞뒤가 맞는다.

**크기 문턱은 문제없다.** µm 단위라 두 슬라이드에 같은 뜻으로 걸린다
(`major_um` 중앙값 18.7 → 15.1). 비율 지표(solidity 0.89→0.87, ellipse_iou
0.79→0.78, elongation 1.82→2.17)도 무차원이라 그대로다.

**텍스처만 무너졌다.**

| | 260729 | 260731 |
|---|---|---|
| texture 중앙 | **1,903** | **109** |
| texture p90 | 9,490 | 525 |
| 통과율 | 18.6% | **1.6%** |

`texture_score()` 는 주파수 대역 안의 max/median 이다. 대역은 µm 로 정의돼 있어
같은 물리 구조를 보지만, 해상도가 촘촘해지면 대역이 스펙트럼 중심 쪽으로 넓게
밀려와 중앙값이 올라가고 비가 줄어든다.

### 아직 결론이 안 났다

사용자가 화면을 보고 **"오른쪽(100x)에 조흔이 안 보이고 개체가 작고 많아 보인다"**
고 했다. 그런데 픽셀 측정은 반대를 가리킨다:

- 개체 bbox 긴 변 중앙값 173 → **307 px** (1.8배 크게 찍힘)
- 조흔 지배 주기 18.2 → **35.5 px** (1.95배 넓게 찍힘)

둘 다 "더 확대됨" 이지만 비율이 1.8~1.95 로 XML 의 2.5 에는 못 미친다.

**둘 다 참일 수 있다** — 100x oil 을 침지유 없이 쓰면 픽셀 간격은 광학 배율대로
촘촘한데 실제 분해능이 크게 떨어진다. 조흔이 35 px 간격에 있어도 대비가 없어 안
보이는 상태가 되고, 지금 수치와 정확히 들어맞는다.

**문턱만 낮춰서 넘기지 않기로 했다.** 68개만 통과한 것이 문턱 탓이 아니라 상이
흐려서라면, 낮춘 문턱은 쓰레기를 통과시킬 뿐이다. 촬영한 사람에게 확인한 뒤에
정한다.

### 비교 이미지를 두 번 만들었다

처음 것은 **내가 잘못 만들었다.** 각 슬라이드에서 100 µm 를 잘라 같은 크기로
맞췄는데, 신규 쪽은 2220 px(원본 높이 2208 px 을 넘는다 — 사실상 전체 화면)를
760 px 로 2.9배 줄였고 기존 쪽은 888 px 를 1.17배만 줄였다. 축소율이 2.5배 달라
오른쪽 세부가 뭉개졌다. "작고 많아 보인다" 는 인상은 맞았고 원인이 내 이미지였다.

다시 만든 것은 양쪽 다 **원본 800×800 픽셀 그대로**다(리샘플 없음). 비교용
이미지를 만들 때 한쪽만 크게 줄이면 그 자체가 결론을 바꾼다.
