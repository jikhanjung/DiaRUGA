# 044 — 잘못 묶인 시야를 화면에서 가른다

2026-08-04. 사람이 `/engine/164/260731_am22-gc10b_25cm/6/` 을 보다가 말했다:
"22131 은 singleton 이고 22132, 22133 이 같은 시야인 것 같다."

맞았다. 그리고 **그 슬라이드에 같은 오류가 넷이었다.**

## 1. 확인

DB 는 `22131 · 22132 · 22133` 을 한 시야로 묶고 있었다. 상관계수를 다시 재고,
**위상상관으로 스테이지가 실제로 움직였는지**를 함께 봤다.

| 쌍 | 상관 | XY 이동 | 위상상관 응답 |
|---|---|---|---|
| 22130-22131 | 0.324 | — | — (경계, 맞다) |
| **22131-22132** | **0.629** | **461 px** | **0.01** |
| 22132-22133 | 0.998 | 0 px | 1.03 (같은 시야, 맞다) |

같은 슬라이드에서 `22155-22156`(0.723) · `22159-22160`(0.623) ·
`22170-22171`(0.594) 도 같은 모양이었다. **시야 26개가 아니라 30개여야 한다.**

## 2. 왜 안 걸렸나 — 분리도 지표가 순환논법이다

`group_focus_series.separability()` 는 **임계값이 만들어 낸 그룹**을 가지고
"그룹 안" 과 "경계" 를 나눈다. 0.594 짜리 쌍은 임계값 0.55 가 그룹 **안**에
넣었으므로 "그룹 안 최솟값" 이 되고, 그래서

```
within_min 0.594 > between_max 0.494  →  겹침 0  →  정상
```

이 나온다. **임계값이 너무 낮아서 생긴 오류를, 그 임계값으로 라벨링한 분포로는
원리상 절대 못 잡는다.** 자기 자신과의 일관성만 재는 것이지 옳은지를 재는 게
아니다.

018 이 이 슬라이드를 두고 적은 숫자가 바로 그 넷이다.

```
AM22 25cm 그룹 안 34쌍: 0.594 0.623 0.629 0.723 | 0.986 … 0.998
           경계 25쌍:  … 0.475 0.494
```

그때는 "양 끝만 빼서 여유가 좁다고 한 것" 으로 읽었다. **저 넷은 꼬리가 아니라
별개의 무리다** — `0.723 → 0.986` 의 틈(0.263)이 `0.494 → 0.594` 의 틈(0.100)보다
넓다. 018 의 결론을 뒤집는다. 지표를 고친 것 자체는 옳았지만(꼬리 통계는 표본
수에 딸려 간다), **고친 지표가 이 오류를 통과시켰다.**

전 슬라이드 1,318 프레임을 훑으니 진짜 같은 시야인 쌍은 어디서나 **0.95 이상**
(10장의 최솟값이 0.9520~0.9957)이고 경계는 **0.5377 이하**다. 사람이 눈으로
확인한 결과 `BP09 22489-22490`(0.813)은 같은 시야였다 — **임계값 창은
`0.723 ~ 0.813` 이다.** 0.55 는 경계 무리의 바로 윗턱에 앉아 있었다.

> 창이 이렇게 좁다는 것 자체가 상관계수 하나로는 부족하다는 뜻이다. 위상상관
> 응답을 둘째 신호로 넣는 쪽이 근본이다 — 그건 따로 잡는다.

## 3. 고치는 길이 자료를 지우는 길이었다

`--force` 안내문은 이렇게 적혀 있었다.

> 정말 다시 묶으려면 --force (교정은 mask_key 로 남지만 고아가 된다).

**거짓이었다.** `ObjectReview.viewpoint` 가 `CASCADE` 다 — 시야를 지우면 교정
행이 함께 사라진다. `mask_key` 는 칼럼 값일 뿐이고, 행이 없으면 아무것도 아니다.
`ViewpointReview`·`Detection`·`Stack` 도 같다.

게다가 `save_grouping()` 은 `slide.viewpoints.all().delete()` 로 **슬라이드
전체**를 지운다. 이 슬라이드는 4개가 틀렸는데 **26개가 다 날아가고 교정 100건이
사라진다.** 4개를 고치려고 22개를 버리는 꼴이다.

처음에는 지우기 전에 교정을 파일로 뽑는 장치를 만들려 했다. **버렸다** — 사람이
말했다: "교정을 그냥 날리고 해당 시야들만 다시 보면 된다. 그룹핑이 잘못됐을 때
쉽게 재그룹핑이 가능하게 만드는 게 낫다." 그 말이 맞다. 비용 계산이 다르다.
**시야 네 개를 다시 검토하는 것은 싸고, 그룹핑을 못 고치는 것은 비싸다.**

## 4. 만든 것 — 부분 재분할

`viewer/regroup.py` 가 구현이고, **화면과 CLI 가 같은 것을 부른다.**

```
/d/<slug>/g/<n>/          검토 화면 아래 "시야 가르기" (접힘)
/d/<slug>/g/<n>/split     POST. confirm=1 인 두 번째 POST 만 실제로 고친다
resplit.py --slide … --after 22131 [--apply]
```

**가르는 시야만 지운다.** 나머지는 애초에 건드리지 않으므로 그 아래 검출·교정은
지킬 필요조차 없다 — 그대로 남는다. 사본 DB 시험에서 교정 100건 중 **77건이
손대지 않은 채 남고 23건만** 사라졌다(가른 4개 시야의 것).

밟은 곳 넷:

- **`tag` 는 합성본 파일 이름을 낳는다**(`<tag>_focused.jpg`). 살아남는 시야의
  `tag` 는 안 건드린다. 딸려 오는 것: `tag` 의 `g###` 접두가 `idx` 와 어긋날 수
  있다 — 접두는 **만들어질 때의 번호**이고 신원은 `tag` 문자열 자체다
- **`idx` 는 다시 매긴다.** `(slide, idx)` 가 유일 제약이라 중간에 끼울 수 없고,
  조각을 목록 끝으로 보내면 촬영 순서가 깨진다. 전부 큰 값으로 치운 뒤 0부터
- **하류는 손댈 것이 없었다.** `focus_stack` 은 `Stack` 이 없는 시야만,
  `segment_diatoms` 는 `is_current` 검출이 없는 시야만 처리한다. 새로 생긴 시야가
  정확히 그것이다. 슬라이드를 `processing` 으로 돌려놓으면 **폴러가 1분 안에
  이어서 하고** `mark_done_if_complete()` 가 `done` 으로 연다. 폴러는 `pending`
  일 때만 다시 묶으므로 방금 한 분할을 되돌리지 않는다
- **화면 조각을 `_detection.html` 에 두지 않았다.** 그건 `/engine/`(읽기 전용)과
  공유한다 — **027 이 정확히 그 자리에서 났다.** `group.html` 에만 두고 서버가
  다시 막는다(`review_blocked` 면 409). 화면에서 감추는 것은 막는 것이 아니다

**JS 를 한 줄도 쓰지 않았다.** 브라우저가 없어 이벤트 배선을 시험할 방법이 없고
(HANDOFF 3.3), 그 종류의 고장은 사람이 눌러 보기 전까지 안 드러난다. 체크박스와
POST 로 되는 일에 배선을 만들 이유가 없다.

**두 걸음이다.** 첫 POST 는 무엇이 사라지는지 숫자로 보이기만 한다 — 검출 몇 건,
교정 몇 건, 검토가 끝난 시야였는지까지. `confirm=1` 이 실린 두 번째 POST 만
고친다.

## 6. 임계값은 건드리지 않기로 했다

분석은 `0.55 → 0.77` 을 가리켰지만(창이 `0.723~0.813`) **그렇게 하지 않는다.**
사람의 판단이다: **손으로 가를 수 있으면 그것으로 충분하다.**

근거가 선다. 전 슬라이드 1,318 프레임에서 애매한 구간(0.55~0.95)에 든 쌍은
스물두 개뿐이고, 그중 **실제로 틀린 것은 AM22 25cm 의 넷**이었다. 나머지는
사람이 눈으로 확인해 전부 정상이었다. 열 장에 네 번이면 **임계값을 옮겨 얻는
것보다 옮기다 잘못 갈라 놓을 위험이 크다** — 창이 0.09 밖에 안 되고, 그 창은
슬라이드 열 장에서 얻은 것이다. 표본이 늘면 창이 닫힐 수도 있다.

무엇보다 **고치는 비용이 싸졌다.** 이 devlog 가 만든 것이 그것이다 — 화면에서
누르면 그 시야만 다시 간다. 자동으로 옳게 맞히는 것보다, 틀렸을 때 **한 번에
고칠 수 있는 것**이 지금 단계에서 값이 크다.

> 딸려 오는 것: **앞으로 들어오는 슬라이드에서도 같은 오류가 난다.** 그리고
> 지금은 **아무도 알려 주지 않는다** — 사람이 캐러셀을 넘겨 보다 알아채야 한다.
> 부담이 커지면 그때 "이 시야는 확인해 보세요" 를 띄우는 쪽을 먼저 본다.
> 임계값을 옮기는 것은 그다음이다.
