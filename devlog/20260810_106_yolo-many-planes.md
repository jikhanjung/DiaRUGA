# 106 — YOLO 는 시야에 판이 여럿이다

105 에서 개체 카탈로그를 만들고 나서, 사용자가 YOLO 로 써 보며 잇달아 세 가지를
보고했다. 파헤쳐 보니 **셋이 다 한 뿌리**였다 — 카탈로그를 "개체 하나 = 마스크
하나" 로 만들었는데 YOLO 에서는 그 전제가 깨진다.

```
SAM     시야 570개 전부 판이 하나 (합성본 417 · 단독 프레임 153)   → 전제가 맞는다
YOLO    합성본 1장 + 프레임 2~10장                                → 전제가 깨진다
```

SAM 에서는 잘 돌았다(사용자 확인). 그래서 105 의 시험 137개가 전부 통과한 채로
이 구멍이 남아 있었다.

## 고친 것 — `v0.10.1`

### 카탈로그에서 유형을 바꿔도 묶음에 안 번졌다

> "지금 내가 묶음의 유형을 결정하여도, 묶음의 다른 프레임에서는 변경이 되지 않고
> 있어."

104 가 "묶인 개체는 분류를 함께 받는다" 를 만들었는데 그 코드가 **`save_review`
안에만 있었다.** 카탈로그의 저장은 개체 하나만 고치는 좁은 문이라 그 자리를 안
지났다 — 카드에서 유형을 바꾸면 그 판에만 앉고 묶음의 다른 프레임은 그대로였다.

**저장은 성공으로 보이고 묶음 안이 어긋난다.** 학습 자료로 내보내면 같은 개체가
봉상이면서 원형인 표본이 된다.

`save_catalog_entry` 가 `_spread_link_labels` 를 부르게 했고, **화면이 "저장됨 ·
묶음 3장에 함께" 라고 적는다.** 다른 판은 이 화면에 없어서 적지 않으면 번졌는지
알 방법이 없다 — 그래서 사람이 판을 넘겨 다시 지정하고 있었다.

**유형만 번진다.** 종명·코멘트는 `_spread_link_labels` 가 그은 선을 그대로 따랐다
(번지게 할지는 사람이 정할 일이라 앞서가지 않는다).

### 기하 스냅샷의 키가 두 벌이었다

같은 이름의 칸이 표마다 모양이 다르다.

| | |
|---|---|
| `ObjectReview.geom` | `{"bbox": …, "polygon": …}` |
| `ObjectLinkMember.geom` | `{"bbox_xywh": …, "polygon": …}` |

그런데 **묶음 멤버가 사람이 그린 개체면 `ObjectReview.geom` 을 그대로 실어서**,
한 칸에 두 모양이 섞인다. 카탈로그가 `bbox` 만 읽어서 묶은 카드의 크롭 상자가
비었고, **예외 없이 조용히 원래 상자로 되돌아갔다** — 다른 판의 그림을 이 개체의
옛 자리로 잘라 냈다. `data.geom_box()` 로 읽는 자리를 모았다.

**시험이 통과하고 있던 이유도 같이 나왔다** — 픽스처가 `bbox` 를 쓰고 있어 현실과
달랐다. 실제 저장이 쓰는 모양으로 바꾸고 두 모양을 다 밟게 했다. 픽스처가 현실에
없는 모양을 세우면 **시험이 옛 규칙을 증언한다.**

## 못 고친 것 — 카탈로그가 YOLO 개체의 절반을 못 본다

> "YOLO에서 합성본에서의 검출이 없으면 해당 데이터는 어떻게 저장되지?"

카드는 `candidate_rows` 의 규칙을 물려받아 **합성본 검출을 기준으로** 낸다. 그
규칙은 SAM 용이었다. 실측:

```
합성본+프레임 둘 다 있는 시야 417개
  프레임 개체 16,782 중 합성본에도 있는 것 11,659
  프레임에만 있는 것              5,123   ← 카탈로그에 아예 안 나온다
  (합성본 통과 개체는             4,444)
```

**저장할 자리는 있다.** `ObjectReview` 열쇠가 `(이미지, 묶음, mask_key)` 라 프레임
이미지에 동정을 앉힐 수 있고, 카탈로그 번호도 `-f<순번>-` 을 이미 낸다. **화면이
안 보여줄 뿐이고, 그래서 저장될 일도 없다.**

갈래 하나 더: 시야에 합성본 검출이 아예 없으면 프레임마다 카드가 생겨 같은 규조각이
2~10번 나온다. 지금 `yolo-3차` 에서 그런 시야는 **0개**다(합성본 검출 0인 153개는
전부 합성본 이미지 자체가 없는 단독 프레임 시야다) — 오늘은 안 밟히지만 밟히면
번호가 판마다 달라 서로 다른 개체가 된다.

### 왜 "프레임도 다 내자" 로 안 끝나나

같은 규조각이 초점면마다 잡혀 **카드가 2~10장씩 중복된다.** 접으려면 "이 마스크들이
한 개체다" 를 아는 것이 있어야 하는데, 그것이 묶음이고 **사람이 손으로 만든다.**

그리고 **번호가 걸린다.** 지금 번호는 `-f<프레임>-` 로 판을 구분하므로, 프레임
개체를 카드로 내면 같은 규조각에 번호가 여러 개 생긴다. **이름이 여러 개면 이름이
아니다.**

### C 안을 만들었다가 접었다

"프레임에만 있는 개체 n개가 더 있습니다" 를 화면이 적게 하는 안이다. 다 써서
시험까지 통과했는데(`data.frame_only_count`, 시험 6개) **사용자 판단으로 접었다.**

> "생각해보니 그게 같은 개체인지 네가 판단하는 능력이 아직 없을 거야."
> "애초에 묶여있는 개체도 지금 네 개 밖에 안되는데, 네가 데이터를 어떻게 만들어…"

맞는 지적이다. 센 방식이 **"중심이 합성본 개체의 상자 안에 드는가"** 였는데 그건
결국 같은 개체인지를 기계가 판정한 것이고, 그 판정을 견줄 근거가 **묶음 4개**뿐이다.
IoU 로 재도 문턱을 정해야 하고 그 문턱이 곧 판정이 된다 — 그것은 P11 에서 **사람이
묶어서 하기로 한 일**이다. 숫자를 화면에 적으면 추측을 숫자로 포장하는 셈이다.

**교훈**: 화면에 숫자를 내려면 그 숫자를 견줄 근거가 있어야 한다. "버리고 있다는
것을 보이게 한다" 는 목적은 맞지만, 그 수단이 스스로 판정을 하나 만들어 버렸다.

## 새로 시작한 것 — 그린 마스크를 판마다 번지게 하기 (1단계까지)

> "현재는 모든 프레임에서 일일이 마스크를 그려서 규조 개체를 입력해야 하고, 그
> 다음에야 규조 객체를 묶을 수가 있는데, YOLO에서 마스크를 그리면, 같은 시야의
> 모든 프레임에 동일한 마스크를 추가하고, 묶어줬으면 좋겠어. 그리고 기준은
> 마스크를 그린 프레임으로 해줘."

**되는 근거는 하나다 — 같은 시야는 스테이지가 안 움직인다.** 초점만 다르므로
좌표가 그대로 맞는다. 이건 기계가 판정하는 것이 아니라 촬영 방식이 보장한다
(위의 C 안과 갈리는 지점이 정확히 여기다).

### 정한 것 셋 (사용자 방침)

| | 정한 것 | 왜 |
|---|---|---|
| 1 | **합성본에도 넣는다** | 개체 카탈로그가 합성본 기준이라, 안 넣으면 그린 개체가 카드로 안 나오고 동정도 못 적는다 |
| 2 | 한 판에서 지우면 **멤버만 벗긴다** | 다른 판의 복제는 남는다 — 어떤 초점면에서는 안 보이는 것을 반영할 수 있어야 한다 |
| 3 | 나중에 경계를 고치면 **그 판만** | 초점면마다 생긴 모습이 조금씩 다르고, 그것이 학습 자료로 새 맞다 |

대표는 **그린 판**이다.

### 서버에서 한다

104 와 같은 이유다 — 화면은 지금 보는 판만 들고 있고 `/review` 는 판 하나에 대한
저장이라, 클라이언트가 다른 판의 행을 만들어도 **그 판을 열기 전엔 DB 에 안 간다.**

**키를 그대로 쓴다.** 그린 개체의 키는 불투명 난수(`m<8자리>`)이고 유일 제약이
`(이미지, 키)` 라, 같은 키를 다른 판에 앉히는 것이 곧 "이것들은 한 개체다" 다.

**"YOLO 에서만" 을 엔진 이름으로 판정하지 않는다.** 복제 대상을 *이 회차에 현재
검출이 있는 판*으로 잡았더니 SAM(시야당 판 하나)과 단독 프레임 시야는 복제할 곳이
없어 자동으로 지나간다. 검출이 없는 판에 넣으면 그 판 화면이 마스크를 안 그리고
저장도 못 받아(`save_review` 가 거절한다) **손댈 수 없는 유령**이 된다.

만든 것: `data._spread_drawn()` · `data._unlink_drawn()` · `_save_drawn` 이 그
둘을 부르고 응답에 `drawn_spread` 를 싣는다. 시험 18개
(`tests/test_drawn_spread.py`). 다섯 가지를 되살려 잡히는 것을 봤다 — 복제를 안
한다 / 대표를 안 정한다 / 저장마다 다시 번진다 / 지울 때 묶음째 지운다 / 응답에
안 싣는다.

### 왜 반쪽으로 배포하면 안 되는가

복제한 마스크는 **다른 판의 화면이 모른다.** 그 판은 페이지를 열 때 받은 상태를
들고 있고, `/review` 는 "뷰어는 늘 전체를 보낸다" 를 전제로 payload 에 없는 그린
개체를 지운다. 그래서 프레임 3에 그리고 프레임 5로 넘어가 저장하면 **복제가 그
자리에서 사라진다.**

104 가 분류 번지기에서 정확히 이 함정을 지났고, 그래서 서버가 번진 것을 응답에
실어 화면이 자기 상태에 얹는다(`spreadLabels`). 이 기능도 **서버 + 화면 두
조각**이고 하나만 넣으면 자료를 잃는다.

**그래서 1단계를 커밋도 배포도 하지 않고 접었다.** 남은 것:

- **2단계** — 응답의 `drawn_spread` 를 다른 판의 `shotDets`·`shotState` 에 얹는다
  (`spreadLabels` 옆, 같은 모양)
- **3단계** — 브라우저 시험. 핵은 하나다: **그린 뒤 다른 판으로 넘어가 저장해도
  복제가 살아 있는가**

## 접어 둔 것 — 보관함에 둘

```bash
git stash list
#  C 안 (프레임에만 있는 개체 수를 화면에 적는다)
#  그린 마스크 번지기 1단계 (서버)
```

**번호가 밀린다** — 새로 접을 때마다 `stash@{0}` 이 바뀌므로 **메시지로 짚는다.**
되살릴 때는 `git stash list` 로 번호를 확인하고 `git stash pop stash@{n}`.

되살린 뒤 확인할 것: `python web/manage.py test viewer --exclude-tag browser`.
두 갈래가 서로 다른 파일을 만지므로 따로 꺼내도 된다 —
C 안은 `frame_only_count` + 화면 안내줄, 번지기는 `_save_drawn` 근처다.

## 다음에 볼 것

**"개체" 를 일급으로 만드는 일**이 이 devlog 의 세 갈래 전부의 뒤에 있다.

지금 DB 에서 일급인 것은 **마스크**(어느 판의 어느 자리)이고, 개체는 사람이 묶을
때만 생기며 그 묶음도 **시야를 못 넘고 회차를 못 넘는다**(`ObjectLink.batch` 가
하나, 멤버가 `(image, batch, mask_key)` 로 짚는다). 카탈로그 번호를 진짜로 개체에
붙이려면 그 층이 있어야 한다.

`TODOs.md` 의 "회차를 넘어 같은 개체를 묶는다" 와 같은 문제다 — **프레임을 넘는
것과 회차를 넘는 것이 결국 한 층이다.** 사용자 판단으로 **YOLO 4차가 들어온 뒤**에
스키마를 박는다.

그때까지 SAM 쪽은 이 문제가 없다 — 시야마다 판이 하나라 규칙과 자료가 맞는다.
한국(BP) 을 SAM 으로 동정하려면 관리 화면에서 검토 대상을 갈면 검토·크롭·카탈로그가
함께 옮겨 간다.
