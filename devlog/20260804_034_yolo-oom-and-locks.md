# 8 GB 카드에서 YOLO 가 OOM 난다 — 한 장이 카드의 91% 를 쓴다

**날짜** 2026-08-04
**앞선 문서** `20260803_033_largest-body-crop.md`

2차(판정 없는 YOLO) 를 돌리다 프레임 몇 장이 조용히 빠졌다. 파고들다 세 가지를
찾았고, 둘은 고쳤고 하나는 **장비의 한계**라 기록만 남긴다.

---

## 1. 왜 2차만 OOM 나나

같은 가중치·같은 conf 인데 1차는 1,318장이 다 됐고 2차만 빠졌다. 원인은
`--no-shape-filter` 가 아니라 **어느 프레임이냐**다.

```
Snap-21379 (rs23)   검출 110개 (conf 0.01)
  마스크 한 벌 = 110 × 2208×2752 × 4바이트 = 2.49 GiB
  혼자 돌려도 최대 예약 6.96 GiB / 카드 7.65 GiB   ← 91%
```

`retina_masks=True` 는 ultralytics 가 **검출 전부를 원본 해상도로 펼쳐 주는**
옵션이다. 편해서 켜 두었는데, 검출이 100개를 넘는 프레임에서는 그것만으로
카드를 채운다. 파이프라인에서는 모델이 이미 올라와 있어 넘친다.

1차가 무사했던 것은 운이었다 — 같은 프레임에서 판정을 켜든 끄든 추론은 같고,
그때는 앞 프레임이 남긴 것이 조금 적었을 뿐이다.

## 2. 고친 것 — 재시도가 무력했던 이유

OOM 을 잡아 `empty_cache()` 하고 다시 해 보게 해 뒀는데 **하나도 안 살아났다.**
다시 시도할 때 남은 자리가 0.9 GB 였다. 혼자 돌리면 6.96 GiB 로 들어가는
프레임인데 그랬다.

원인은 파이썬이다.

```python
except torch.cuda.OutOfMemoryError:
    torch.cuda.empty_cache()      # ← 아무것도 못 비운다
    payload = process(...)        # 재시도
```

**`except` 블록 안에서는 역추적이 살아 있고, 역추적은 실패한 호출의 지역변수를
붙들고 있다** — 즉 방금 자리를 못 찾은 그 큰 GPU 텐서들을. 참조가 남아 있으면
`empty_cache()` 는 할 일이 없다.

재시도를 `except` **밖으로** 뺐다. `rs23` 이 146 → 150/151 이 됐다.

```python
payload = oom_first = None
try:
    payload = process(...)
except torch.cuda.OutOfMemoryError:
    oom_first = True
if oom_first:                     # ← 여기서는 역추적이 없다
    gc.collect(); torch.cuda.empty_cache()
    ...
```

## 3. 고친 것 — 실행이 성공으로 남았다

OOM 으로 건너뛴 프레임이 있어도 실행은 `done` 이었다. 프레임 수를 세어 보고서야
알았다. `Run.STATUS` 에 **`partial`** 을 더하고, 한 장이라도 건너뛰면 그것으로
끝나게 했다. `counts` 에 `oom`·`oom_retry_ok` 도 남긴다.

## 4. 안 고친 것 — 그리고 왜

### `retina_masks=False` 는 값을 바꾼다

메모리는 1/4 이지만(6.05 → 1.67 GiB) **모든 개체의 경계가 달라진다.**

```
Snap-22057   개체 94 · 다른 것 94 · 화소차 164,376
합성본        개체 46 · 다른 것 46 · 화소차  64,825
```

`retina_masks=False` 로 받은 `masks.data` 는 **이미 0/1 로 잘린** 마스크라,
그것을 확대하면 계단이 생긴다. `True` 는 ultralytics 가 **프로토타입(연속값)을
먼저 확대한 뒤 자른다** — 순서가 달라 경계가 어긋난다.

충실히 재현하려면 프로토타입 단계까지 내려가야 하는데, 그건 ultralytics 내부
구현에 기대는 일이라 판이 바뀌면 조용히 깨진다. **0.08% 를 위해 치를 대가가 아니다.**

### `expandable_segments` 는 도움이 안 됐다

PyTorch 가 오류 메시지에서 직접 권하는 설정인데, 켜니 오히려 재시도 성공이
3 → 0 이 됐다. 조각남이 문제가 아니라 **총량이 모자란 것**이기 때문이다.

### conf 를 올리면 취지가 흐려진다

```
conf 0.01 → 110개 · 2.49 GiB     conf 0.05 → 61개     conf 0.10 → 47개
```

2차의 목적은 **판정 없이 다 보는 것**이다. 낮은 conf 를 버리면 정확히 보고 싶은
경계선 위의 것들이 사라진다.

## 5. 남긴 것

**1,318장 중 1장**(`Snap-21379`, 0.08%)이 어떤 방법으로도 안 들어간다.
`partial` 로 표시돼 있어 "다 됐다" 고 착각할 일은 없다.

**이것은 코드 문제가 아니라 장비 문제다.** 학습을 돌린 RTX 8000(48 GB)에서는
6.96 GiB 가 아무것도 아니다. 나중에 그쪽에서 돌리거나, 이 장비에 계속 둘 거라면
그때 프로토타입 단계로 내려가는 값을 치르면 된다.

## 곁다리 — DB 잠금으로 229장을 잃었다

같은 실행 중에 **`database is locked` 로 `bp09-0901` 프레임 229장이 통째로
날아갔다.** 뷰어와 파이프라인이 같은 SQLite 를 쓰는데, WAL 이라 읽기는 여럿이
동시에 되지만 **쓰기는 한 번에 하나**다. 파이프라인이 개체 수천 개를 한
트랜잭션으로 넣는 동안 사람이 검토를 저장(31건)하자 20초를 기다리다 죽었다.

트랜잭션을 둘로 나눴다 — 개체를 넣는 것과 `is_current` 를 옮기는 것은 원자성
요구가 다르다. 후자만 한 덩어리여야 한다(갈라지면 교정이 안 붙은 검출이 화면에
보인다). 전자는 `is_current=False` 라 뷰어에 아예 안 보인다. 자세한 것은
커밋 `8c7ef8b`.

**지금까지 안 터진 이유는 파이프라인이 돌 때 사람이 검토하지 않았기 때문**이다.
그것이 일상이 되면 SQLite 를 다시 볼 문제가 된다.
