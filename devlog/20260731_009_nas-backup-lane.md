# 검증된 스냅샷을 NAS 로 밀어 둔다

**작성일** 2026-07-31
**근거** `.guides/web/data-safety.md` (형제 프로젝트들이 실제 사고를 겪고 도달한 규약)

---

## 왜 지금

컨테이너로 옮기고 나서 `.guides/web/data-safety.md` 를 제 구성과 대조했다.
**MUST 위반이 하나 나왔고**(§8, 앞 커밋에서 고쳤다), 그것과 별개로 이 장비의
구조적 약점이 드러났다.

**이 머신은 개발서버이자 운영서버이자 백업서버다.** 그래서 가이드의 두 MUST 는
구조상 성립하지 않는다:

- "빌드는 prod 밖에서, prod 는 pull·swap 만" — 호스트가 하나뿐이다
- "오프사이트 호스트가 prod 에서 pull" — 백업서버가 곧 prod 다

두 번째가 실질적인 문제였다. `backup_db.py` 의 사본이 전부 `/data3` 안이라
**디스크 한 장이 죽으면 사람의 교정 2,408건이 같이 간다.** `export_review.py`
(P02 5단계)가 아직 없어 교정이 DB 에만 있으므로 이것이 유일한 안전망이다.

NAS(`172.16.112.125`)는 물리적으로 별개 장비다. 가이드가 말하는 **pull 방향은
못 만들지만**(백업 쪽에서 prod 로 들어올 경로가 없다) 기계 분리라는 핵심 이득은
챙길 수 있다. 그 절충을 명시적으로 하고 `sync_backup_nas.py` 를 만들었다.

## 라이브 DB 를 복사하지 않는다 (§4)

오프사이트 track 은 **`backup_db.py` 가 검증을 통과시킨 단일 파일 스냅샷만**
소비한다. 도는 WAL DB 를 본체·`-wal`·`-shm` 따로 복사하면 체크포인트와 경합해
찢어진 사본이 나온다. 그리고 이 track 이 **가장 오래 남는 사본**을 들고 있으므로,
"가장 값진 백업이 가장 덜 검증된 것" 이 되는 형태를 피해야 한다.

대가는 최대 한 주기만큼의 신선도 손실인데, 그 값이면 싸다.

## 수신 후 다시 검증한다 (§2)

NAS 에 놓은 파일을 열어 `integrity_check` 와 행 수(`viewer_objectreview`)를 다시
본다. 임시 이름(`.part`)으로 받아 검증을 통과해야 제 이름을 준다 — **이름이
붙어 있으면 검증을 통과한 것**이고, 받다 만 파일이 정상 사본처럼 보이지 않는다.

## 게이트를 실제로 터뜨려 봤다

가이드의 메타 규칙 중 하나가 이것이다 — *"A fixture that doesn't reproduce the
failure condition produces false knowledge. Mutation-test each gate."* 백업
회귀 테스트가 빈 픽스처로 초록이던 사례가 있었다고 한다. 그래서 둘 다 터뜨렸다.

**게이트 1 — NAS 가 안 붙었을 때.** NFS 가 빠지면 `/nfs/temp-share` 는 그냥 빈
로컬 디렉토리가 되고, 거기 쓰면 *"오프사이트에 뒀다"고 믿으면서 실은 원본과 같은
디스크에 쌓인다.* `/proc/mounts` 로 실제 nfs 마운트인지 본다. NFS 아닌 경로를
주니 거부하고 **디렉토리조차 만들지 않았다.**

**게이트 2 — 깨진 스냅샷.** 난수 12.7 MB 를 스냅샷인 척 섞고 `--keep 1` 로
정리까지 걸었다.

```
diatom_20260102_000000_broken.db  검증 실패 — file is not a database
  증거를 남겼다: diatom_20260102_000000_broken.db.corrupt
1개가 검증에 실패했다. 정리를 건너뛴다.
diatom_20260101_000000_good.db  integrity=ok  viewer_objectreview=2408
종료코드: 1
```

**정리를 건너뛴 덕에 정상 사본이 살아남았다.** 이 건너뛰기가 없었으면
`--keep 1` 이 좋은 사본을 쫓아냈을 것이다 — 가이드가 든 실제 사고가 정확히
그것이다(깨진 원본이 채택되고 로테이션이 좋은 사본을 전부 밀어내 *N 시간 뒤
복구 가능한 스냅샷이 0개*). 증거 사본은 `.corrupt` 라 정리 glob 에 안 걸린다.

## 복구 리허설도 했다 (§11)

`integrity_check` 는 **스키마 부트스트랩 실패를 못 잡는다.** 가이드에 있는
사례가 그것이다 — 백업이 무결성 검사는 통과하는데 거기서 새 DB 를 세우면 첫
사용에서 죽었고, 우연히 발견됐다.

그래서 NAS 사본으로 실제 경로를 밟아 봤다.

| 단계 | 결과 |
|---|---|
| NAS 사본 → `check_db.py` | 전 항목 통과 |
| `manage.py migrate` | `No migrations to apply` |
| 뷰어 렌더링 (테스트 클라이언트) | `/` 200 · `/d/rs23/` 200 · `/d/rs23/g/0/` 200 |

## 유지 개수는 조율한 숫자가 아니라 관계다 (§6)

`로컬 유지 개수 × 주기 ≥ 오프사이트 간격`. 오프사이트가 하루 간격이면 30 이
한 달치다. 값을 늘리는 것은 무손실이다(늘려도 지워지는 것이 없다). 디스크 상한
용도로 이 값을 겸하게 두지 않는다 — 그건 별개 문제다.

## 유의

**cron 에서는 `timeout` 으로 감싼다.** NAS 가 `hard` 마운트라 내려가면 접근하는
프로세스가 무한 대기한다. 스크립트 머리말에 cron 한 줄을 적어 두었다.

아직 cron 에 걸지 않았다 — 지금은 큰 작업 전에 손으로 돌린다. 자동 수집(P03
4·5단계)을 붙일 때 같이 건다.

## 남은 격차

- **표준 deploy 동사 5개**(preflight/deploy/seed/smoke/rollback) 가 없다
- 무결성 실패를 health 엔드포인트로 잇는 sentinel 이 없다 (§2). `/healthz` 는
  있지만 백업 상태를 보지 않는다
- `export_review.py`(P02 5단계)가 여전히 없다. 교정이 DB 에만 있는 한 이 lane 이
  유일한 안전망이다
