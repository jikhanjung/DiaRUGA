## 1. instance mask — bbox 만 저장하고 있었다

검출된 개체에 마스크를 씌워 달라는 요청을 받고서야 **마스크를 저장하지 않고 있었다는
것을 알았다.** `masks_to_records` 가 `"rle": None` 으로 자리만 잡아 두고, 형태 지표를
계산한 뒤 `_seg` 를 버렸다. 001 때부터 그대로였다.

### 무엇을 저장할 것인가

| 방식 | 크기 | 판단 |
|---|---|---|
| 마스크 전체 (RLE) | JSON 이 수십 배 | 과하다 |
| **단순화한 외곽선** | **2배** | 채택 |

뷰어는 윤곽만 있으면 SVG `<polygon>` 으로 그릴 수 있다. `approxPolyDP` 로
둘레에 비례해(`epsilon = 0.004 * peri`) 단순화하면 크기와 무관하게 같은 정도로
줄어든다.

실측: 윤곽점 **중앙값 16개**(9~23), JSON **56 → 112 KB**.

좌표는 `[x0,y0,x1,y1,...]` 평탄 배열로 넣었다 — 좌표쌍 리스트보다 JSON 이 작다.

### 렌더링

SVG 의 `viewBox` 를 이미지 픽셀 좌표계로 잡고 `preserveAspectRatio="none"` 을
주면, 폴리곤 좌표를 변환 없이 그대로 쓰면서 확대·축소에 자동으로 따라간다.
`pointer-events: none` 이라 마우스 판정은 종전대로 bbox 가 한다 — 히트 판정은
사각형이 쉽고, 드래그 범위 선택 로직도 bbox 기반이다.

### 대가 — 전체 재검출

기존 JSON 에는 윤곽이 없으므로 124개 시야를 다시 돌려야 했다. 마침 WAP13 배치가
절반쯤(90장 중 42장) 진행 중이었는데, **그대로 두면 남은 48장도 윤곽 없이 나오므로
즉시 중단하는 편이 쌌다.** 중단 시점에 재시작하면 42 + 82 = 124장, 끝까지 두면
90 + 124 = 214장이었다.

합성본 49개는 보존해 재사용했고, 교정 기록(`review/`)은 bbox 기반 키라 그대로
유효했다 — SAM2 AMG 는 격자 포인트가 고정이라 추론이 결정적이다.

## 2. 교정 UI — 되돌릴 수 있게

002 시점에는 오검출을 지우면 되돌릴 방법이 **"교정 전체 초기화" 하나뿐**이었다.
개별 복구 경로를 세 가지 만들었다.

| 경로 | 동작 |
|---|---|
| 유령 박스 클릭 | 지운 것이 점선으로 남아 있어 클릭 한 번에 복구 |
| Ctrl+Z | 삭제·복구·수동채택이 이력에 쌓여 역순 취소 |
| 컨텍스트 메뉴 | 여러 개를 범위 선택해 한꺼번에 복구 |

### 서버가 삭제분을 버리고 있었다

유령 박스를 만들려다 발견했다. `detection_for` 가 교정 기록의 `removed` 에 든
개체를 **아예 목록에서 빼버려서**, 새로고침하면 되살릴 대상이 사라졌다.
`removed_candidates` 로 따로 넘기도록 고쳤다.

### 우클릭 = 컨텍스트 메뉴

우클릭 즉시 삭제는 위험해서 메뉴로 바꿨다. 다만 **우클릭 드래그가 이미 화면
이동에 배정돼 있어** 충돌한다. 움직임이 4 px 미만일 때만 메뉴를 띄우는 것으로
갈랐다 — 좌클릭의 "클릭 vs 범위선택" 판정과 같은 방식이다.

메뉴는 상황에 따라 항목이 달라진다: 살아 있는 대상이 있으면 "오검출로 삭제",
지워진 것이 있으면 "되살리기", 빈 곳이면 "이 자리의 탈락 후보 보기"(없으면 비활성).

### 표시 방식

지운 것을 붉게 채웠더니 **아래 이미지가 가려져 지운 게 맞는지 확인할 수 없었다.**
채우기를 없애고 붉은 점선 테두리만 남겼다. 마스크도 그리지 않는다.

## 3. 뷰어 잔버그 두 건

### Django `{# #}` 는 한 줄 전용

주석이 페이지에 그대로 렌더링됐다. `{# ... #}` 는 여러 줄을 지원하지 않아서,
줄바꿈이 끼면 주석 태그로 인식되지 않고 리터럴 텍스트가 된다.
`{% comment %}...{% endcomment %}` 로 바꿨다. 템플릿 전체를 검사해 같은 실수가
더 없는지 확인했다(이 한 건뿐).

### 그룹 페이지가 검출 목록으로 스크롤됨

갤러리 초기화에서 첫 항목에 `scrollIntoView` 를 호출한 것이 원인이었다. 스트립을
가로로 맞추려던 건데 페이지 세로 위치까지 끌고 내려갔다.

최초 표시에는 스크롤하지 않고, 이후 프레임을 넘길 때만 **스트립의 `scrollLeft` 만**
조정하도록 바꿨다. 페이지는 건드리지 않는다.

## 5. 전 시료 검출 완료

124개 시야, 장당 평균 **20.9초**, 합성 포함 약 50분.

| 시료 | 시야 | 그룹당 | 합계 | 봉상 | 원형 |
|---|---|---|---|---|---|
| RS23-GC03 71cm | 34 | 24.6 | 836 | 689 | 146 (17%) |
| WAP13-GC47 116cm | 47 | 14.7 | 691 | 468 | 223 (32%) |
| WAP13-GC47 450cm | 43 | 26.7 | 1,149 | 850 | 299 (26%) |
| **합계** | **124** | | **2,676** | **2,007** | **668 (25%)** |

### 5.1 합성본이 낫다 — 124개 시야로 확인

002 §2 에서 시야 하나로 관찰한 것이 전체에서 재현됐다.

| | 시야 | 원시 | 크기통과 | 최종 | 통과율 | 장축 중앙 |
|---|---|---|---|---|---|---|
| 합성본 | 81 | 250 | 153 | **22.8** | **14.9%** | **18.3 µm** |
| 싱글턴 | 43 | 258 | 152 | 19.3 | 12.7% | 16.9 µm |

원시·크기통과 개수는 사실상 같은데 **최종 판정 통과율이 다르다.** 장축 중앙값도
합성본이 크다 — 초점 흐림 잔해가 작은 쪽에 몰린다는 002 §2.1 의 관찰과 일치한다.

다만 인과의 증거는 아니다. 싱글턴은 촬영자가 한 장만 찍기로 한 시야라 애초에
다른 모집단일 수 있다.

### 5.2 116cm 가 희박한 것은 싱글턴 탓이 아니다

002 §9 에서 미뤄 둔 질문에 답이 나왔다. 시료별로 나눠 보면:

| 시료 | 합성본 | 싱글턴 |
|---|---|---|
| RS23 71cm | 26.4 | 16.0 |
| **116cm** | **12.3** | **16.7** |
| 450cm | 26.5 | 27.4 |

**116cm 만 합성본이 싱글턴보다 적다.** 다른 두 시료는 정반대다. 즉 116cm 의 낮은
밀도는 합성 유무와 무관한 **시료 자체의 성질**이다 — 규조각이 실제로 적다.

덧붙여 116cm 의 합성본 그룹은 평균 2.0장짜리라 합성 효과 자체가 미미하다.
RS23(4.4장)·450cm(2.3장)과 비교하면 이 시료는 초점 시리즈를 제대로 찍지 않았다.

### 5.3 원형 668개

002 §11 에서 "원형 기준은 실물로 검증된 적이 없다"고 적었는데, 검증 대상이
생겼다. 116cm(32%)·450cm(26%)는 RS23(17%)보다 원형 비율이 확연히 높다.
**여전히 미검증이며 다음 작업의 1순위다.**

## 6. README 갱신 중 발견 — scale 0.5 에서 텍스처가 조용히 열화된다

README 에 "`--scale 0.5` 면 코드가 텍스처 점수를 0으로 반환한다"고 쓰려다
확인해 보니 **사실이 아니었다.**

| scale | µm/px | 조흔 주기 | 상태 |
|---|---|---|---|
| 1.0 | 0.1126 | 3.6 ~ 14.2 px | 정상 |
| **0.5** | 0.2252 | **1.8 ~ 7.1 px** | **일부 Nyquist(2px) 미만 — 가드 안 걸림** |
| 0.4 | 0.2815 | 1.4 ~ 5.7 px | 같음 |
| 0.15 | 0.7507 | 0.5 ~ 2.1 px | 가드 발동 |

`texture_score()` 의 가드는 `max_period_px < 2.5` 라 **대역의 긴 쪽**만 본다.
그런데 앨리어싱은 **짧은 쪽**에서 먼저 생긴다. scale 0.5 면 주기 1.8 px 구간이
Nyquist 아래인데도 가드가 걸리지 않아, 앨리어싱이 섞인 점수가 그대로 나온다.
문턱 1000 을 그대로 쓰면 안 되는 상황이다.

**현재 장비(RTX 8000)에서는 원본 해상도를 쓰므로 실害는 없다.** 다만 저사양에서
돌릴 일이 생기면 가드를 `min_period_px < 2.0` 기준으로 바꿔야 한다.
**아직 고치지 않았다** — README 에 함정으로 명시만 해 뒀다.

이런 종류의 오류가 나온 경위를 적어 두면: 텍스처 대역을 µm 로 정의한 것은
`--scale` 에 무관하게 같은 물리 구조를 보게 하려는 의도였다(002 §5.2). 그 의도는
맞지만, **스케일이 바뀌면 대역이 픽셀 격자에 대해 이동한다**는 점은 따로 처리해야
했다. 가드를 넣긴 했으나 방향을 잘못 잡았다.
