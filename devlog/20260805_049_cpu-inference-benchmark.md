# 049 — CPU 로 검출이 되는가를 쟀다. 되는데, 라이선스가 걸린다

2026-08-05. 데스크탑 앱 검토(`docs/20260805_desktop-app-review.md`) 중에 나온
질문이다 — **GPU 없는 PC 에서 SAM2.1 이 도는가, 돈다면 얼마나 걸리는가.**
추정으로 답할 이유가 없어서 쟀다.

## 1. 방법

`tools/bench_sam2.py` · `tools/bench_yolo.py`. **DB 를 건드리지 않는다** —
모델을 직접 올려 한 장에 대해 시간만 잰다.

```bash
cd /srv/DiaRUGA
IMG=/data3/DiaRUGA/stacked/g073_Snap-22061-22065_focused.jpg   # 후보 383개 시야
docker compose run --rm pipeline python /app/tools/bench_sam2.py cuda 48 "$IMG"
docker compose run --rm pipeline python /app/tools/bench_sam2.py cpu  48 "$IMG" 12
docker compose run --rm pipeline python /app/tools/bench_yolo.py cpu <가중치> "$IMG" 5 12
```

운영과 같은 설정이다 — `sam2.1-hiera-base-plus` · `points_per_side=48` ·
`pred_iou 0.5` · `stability 0.75`, YOLO 는 `imgsz=1280`.
장비: RTX 3060 Ti(8 GB) · Ryzen 5 5600G(6코어 12스레드).

> **첫 판은 `_depth.jpg` 로 쟀다가 버렸다.** 그것은 깊이맵이지 all-in-focus
> 합성본이 아니다 — 검출 0개가 나와서 알아챘다. **파일 이름의 꼬리를 보고
> 고를 것.** `_focused.jpg` 가 검출을 돌리는 대상이다.

## 2. 결과

| 엔진 | GPU/시야 | CPU/시야 | GPU/슬라이드 | CPU/슬라이드 | 배수 |
|---|---|---|---|---|---|
| SAM2.1 `pps=48` | 13.0초 | **3.4분** | 9.8분 | **2.5시간** | 16배 |
| YOLO11m-seg 1280 | 0.09초 | **1.7초** | 4.2초 | **75초** | 18배 |

슬라이드 한 장 = 시야 45개(452/10) 기준.

**결과는 같다.** SAM2 는 CPU·GPU 둘 다 마스크 422개, YOLO 는 둘 다 검출 146개다.
**정확도를 잃는 것이 아니라 느리기만 하다.**

## 3. SAM2 의 병목은 인코더가 아니라 디코더다

| | GPU | CPU | 배수 |
|---|---|---|---|
| 이미지 인코더 (이미지당 1회) | 0.30초 | 2.37초 | 7.9배 |
| 디코딩 (점 2,304개) | 12.74초 | 200.2초 | 15.7배 |
| **점당** | 5.5 ms | **86.9 ms** | 15.8배 |

**인코더는 CPU 에서도 2.4초로 견딜 만하다.** 문제는 점 2,304개를 도는 디코더다.
그러므로 `--points-per-side` 가 곧 CPU 소요다 — 거의 선형이다. 48 → 24 로
낮추면 점이 1/4 이라 **약 50초/시야**가 된다. 대신 작은 개체를 놓친다.
**CPU 로 SAM2 를 쓴다면 여기가 조절 손잡이다.**

## 4. YOLO 는 코어 수에 거의 안 딸려 간다

| 스레드 | 중앙값 |
|---|---|
| 12 | 1.665초 |
| 4 | 1.657초 |

**차이가 없다.** 코어를 늘려도 안 빨라진다는 것은, 뒤집으면 **사무용 노트북에서도
같은 속도가 나온다**는 뜻이다. 배포를 생각하면 이쪽이 더 중요한 성질이다.

## 5. 곁다리 — 8 GB VRAM 에서 SAM2 가 빠듯하다

GPU 실행에서 `CUDACachingAllocator ... OOM ... 1.5 GB 할당 시도` 경고가 떴다.
할당기가 물러서서 끝까지 돌긴 했지만, **`points_per_batch=32` 로 8 GB 가 빠듯하다**는
뜻이다. 4 GB 노트북 GPU 라면 배치를 더 줄여야 하고 그만큼 느려진다.
`poll_nas.sh` 가 `PPB` 를 환경변수로 빼 둔 이유가 이것이다.

## 6. 그리고 라이선스 — 성능과 정확히 반대로 걸려 있다

컨테이너 안에서 확인한 값이다.

| | 판 | 라이선스 |
|---|---|---|
| **ultralytics** (YOLO11) | 8.4.7 | **AGPL-3.0** |
| **SAM-2** | 1.0 | **Apache 2.0** |
| torchvision | 0.28.0 | BSD |
| PyQt5 (Modan2 스택) | — | GPL v3 |

**CPU 에서 쓸 만한 쪽이 AGPL 이고, 라이선스가 자유로운 쪽이 CPU 에서 3.4분이다.**

사내에서 우리끼리 쓰는 지금은 아무 문제가 없다 — AGPL 의 의무는 **배포하거나
네트워크로 서비스할 때** 걸린다. 그런데 밖으로 배포하는 데스크탑 앱을 만들면
그 순간 걸린다. 선택지는 셋이고, 셋 다 대가가 있다:

1. **앱 전체를 AGPL-3.0 으로 공개한다** — 학술 도구라면 오히려 자연스럽다.
   이 길로 가면 PyQt5(GPL v3)도 그대로 쓸 수 있다(AGPLv3 와 호환)
2. **Ultralytics 상용 라이선스를 산다** — 돈이 든다
3. **ultralytics 를 안 싣는다** — Apache 2.0 계열(YOLOX·MMDetection/RTMDet-Ins·
   detectron2 등)로 다시 학습하거나, SAM2 만 쓴다.
   **주의: 가중치까지 AGPL 이 따라가는지는 다툼의 여지가 있다.** ultralytics 로
   학습한 `best.pt` 를 ONNX 로 내보내 중립 런타임에서 돌리는 것이 코드 의존은
   끊지만, 배포 전에 확인이 필요하다 — 여기서 단정하지 않는다

## 7. 이 측정이 바꾼 것

앞서 쓴 데스크탑 검토 문서는 **"연구소 서버가 계속 있다"** 를 전제로
"검토자 한 명의 속도" 만 봤고, 그래서 만들지 말자고 결론냈다. 실제 동기는
**배포 가능성**이었다 — GPU 서버가 없고 서버 운영을 못 하는 연구자에게
이 도구를 주는 것. 전제가 다르면 결론도 다르다.

측정은 그 방향을 지지한다. **저장은 문제가 아니고**(슬라이드당 원본 380 MB ·
합성본 26 MB → 50 슬라이드도 20 GB), **GPU 도 필수가 아니다**(YOLO 1.7초).
비싼 것은 저장이 아니라 24시간 떠 있는 GPU 인스턴스인데, 데스크탑은 그 항목을
없앤다. 문서를 그 전제로 다시 썼다.
