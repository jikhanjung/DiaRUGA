# 114 — 판 둘을 내보내고, 병합을 PR 로 지나가게 한다 (`v0.11.2` · `v0.12.0`)

08-11~08-12 에 쌓인 것이 배포를 기다리고 있었다. 등급·자세(`0034`)는 태그·이미지가
서 있었고, 번지기와 등급·코멘트 이전(`0035`·`0036`)은 `work/20260812-sclee` 에
있었다. 이 문서는 **그 둘을 내보낸 기록**이고, 그 김에 **이 저장소가 처음으로 PR 을
쓴 기록**이다.

## 1. 왜 두 번에 나눠 내보냈나

`0034` → `0035` 는 **등급을 판정에 넣었다가 하루 만에 개체로 옮기는** 것이다.
한 판에 겹쳐 내보내면 중간 상태가 아무 데도 안 남는다. 사용자 결정은
*"판 하나에 두 이야기를 겹치지 않는다"* 였다.

기술적으로는 겹쳐도 됐다 — `0034`→`0035`→`0036` 이 기동 때 순서대로 다 돌고,
운영에 등급이 **0건**이라 옮길 값이 없었다. **그래서 더 갈라 놓기 좋았다**:
되돌릴 일이 생겨도 어느 판으로 돌아갈지가 분명하다.

## 2. 파이프라인이 새 스키마에서 도는가 — 실측

`0035`·`0036` 이 **칼럼을 걷는다**(`ObjectReview.grade`·`note`). 이 저장소에서
칼럼을 걷은 것은 `0032` 이후 처음이고, 그때는 **옛 파이프라인 이미지가 교정 있는
시야를 지울 때 `FOREIGN KEY constraint failed` 로 죽었다**(108). 규약대로 사본에
붙여 봤다.

백업 사본을 스크래치로 떠서 `0036` 까지 올린 뒤 `honestjung/diaruga-pipeline:v0.5.2`
를 붙였다. **운영 `db/` 는 마운트하지 않았다** — `docker compose run` 이 아니라
`docker run` 으로 스크래치만 물렸다.

| 갈래 | 결과 |
|---|---|
| `ObjectReview` 한 행 읽기 (전체 칼럼 SELECT) | ❌ `no such column: viewer_objectreview.note` |
| `ObjectReview` 세기 (`COUNT`) | ✅ |
| **교정 22건이 달린 시야 지우기** (108 이 잡은 갈래) | ✅ 통과 |
| `batch_plan.py` (폴러가 실제로 부른다 · `viewer.data` 를 쓴다) | ✅ |

**갈래가 갈린 이유가 요점이다.** `ObjectReview` 를 가리키는 FK 도 시그널도 없어서
Django 가 **fast-delete** 로 간다 — 지울 행을 안 불러오고 `DELETE … WHERE` 만 낸다.
그래서 없는 칼럼을 짚을 일이 없다. `0032` 때 죽은 것은 그 조건이 달랐기 때문이다.

**그리고 `note` 만 문제였다.** `grade` 는 `0034` 로 어제 생긴 칸이라 `v0.5.2` 이미지의
모델이 아예 모른다 — 모르는 칼럼은 SELECT 하지 않는다. **옛 판이 위험한 것은 걷힌
칼럼을 *아는* 경우뿐이다.**

> **"파이프라인은 `ObjectReview` 를 안 만드는데 왜 확인하나"** — 만드는 것이 문제가
> 아니다. **Django 는 행을 불러올 때 모델이 아는 칼럼을 전부 SELECT 하고, cascade
> 삭제는 지울 대상을 먼저 불러온다.** `pipeline/group_focus_series.py` 의
> `slide.viewpoints.all().delete()` 가 그 자리이고 `ObjectReview.viewpoint` 는
> `CASCADE` 다. **쓰기가 아니라 읽기가 위험하다.**

**결론: 뷰어만 올린다.** 다만 이것은 **지금 코드 기준**이다 — `pipeline/` 에
`ObjectReview` 를 읽는 줄이 하나라도 들어오면 그날로 물린다. HANDOFF 5절에 그렇게
적었다: **다음에 파이프라인 이미지를 구울 때 함께 올린다.**

## 3. `note` 를 꼭 걷어야 했나 — 다시 물었다

배포 직전에 나온 질문이다. *"칼럼을 남기면 옛 파이프라인이 안전한데?"*
맞는 말이고, 그것이 **expand–contract(parallel change)** 라는 표준 패턴이다 —
넓히고, 다음 판에 걷는다.

그런데 이 저장소에서는 남기는 쪽이 더 비쌌다.

- `0036` 의 `to_object()` 는 코멘트를 **복사할 뿐 원본을 안 지운다**(칼럼째 걷을
  거라 지울 이유가 없었다). 칼럼을 남기면 **같은 말이 두 자리에 앉는다**
- 그러면 `/review` 의 **빈 껍데기 청소**가 헷갈린다 — `obj.note` 가 살아 있어
  "내용이 있는 행" 으로 판정된다. `data.py` 가 그 줄을 `obj.note` → `dobj.note`
  로 바꾼 것이 정확히 이 자리다
- `ops/export_review.py` 가 **같은 말을 두 번 싣는다**
- 그래서 남기려면 `0036` 이 원본을 비우는 일까지 해야 하고, 그러면 *"일부러 비워
  둔 칼럼"* 과 **그것을 지키는 불변식 하나**가 는다

**미루고 얻는 안전이 이미 2절에서 확보돼 있었다** — 파이프라인이 그 칼럼에 안
닿는다. 그래서 걷는 쪽으로 갔다. **판단이 갈릴 수 있는 자리라 여기 적어 둔다.**

## 4. 판별 코멘트가 사라지는 것에 대해

`0036` 은 검토 화면에서 **개체 코멘트를 적는 자리를 걷는다**(읽기는 남는다).
*"검토 화면에서 frame 별로 코멘트 남기는 기능이 있잖아"* 라는 물음이 나왔고,
숫자를 보고 넘어갔다.

| | |
|---|---|
| 판정 코멘트 (`ObjectReview.note`) | **2건** — 둘 다 대표 판 · 내용이 시험용으로 보인다 |
| 한 개체에 코멘트가 여럿 | **0** — 이어붙이기 규칙이 발동할 자료가 없다 |

**지금 자료에서는 "판별 코멘트" 와 "개체 코멘트" 가 사실상 같은 말이다.** 접힐 것이
있는 개체가 다섯뿐이고 그마저 겹치는 코멘트가 없다.

> **그 비율은 앞으로 바뀐다.** 번지기와 프레임 검출이 들어오면 개체 하나에 판이
> 여럿 달린다 — 프레임에만 있는 개체가 이미 5,123 이다(106). `112` 가 *"같은 말을
> 판 넷에 적게 된다"* 고 한 것이 그 이야기이고, **반대로 그때가 "이 판에서만" 이라고
> 적고 싶어질 시점이기도 하다.** 이 결정의 유효기간은 거기까지다.

`0035` 와 합쳐 보면 **판(초점면)에 대해 사람이 적을 자리는 대표(`is_rep`) 하나로
모였다.** 판정에 남는 것은 `removed`·`accepted`·`geom`·`auto_confirmed` 다.

## 5. 병합을 PR 로 지나가게 했다 — 이 저장소의 첫 PR

브랜치는 이미 `main` 위에 얹혀 있었다(08-12 17:11 · 커밋일이 그 시각으로 몰려 있는
것이 흔적이다). **그대로 `--ff-only` 로 붙여도 됐다.** 그런데 CI 트리거가 이렇다.

```yaml
on:
  push:
    branches: [main]        # ← work/* 는 아니다
    tags: ['v*']
  pull_request:
    branches: [main]        # ← PR 을 열면 돈다
```

**즉 `work/*` 를 push 한 것만으로는 CI 가 한 번도 안 돌았다.** 브랜치 문서가 적어
둔 절차(`main` 에 병합 → push 가 CI 를 돌린다)는 틀리지 않다 — 태그 전이라 배포에
안 닿는다. 다만 **깨진 코드가 이미 `main` 에 앉은 뒤에 알게 된다.** PR 은 그 순서를
뒤집는다. **PR 이 여기서 사는 값은 그 한 가지다.**

`sclee` 가 시험을 안 돌린 것이 아니다 — `112` 에 *"브라우저 시험이 하나 잡았다"*
가 적혀 있고 `111` 은 *"화면 조각만 끄면 셋이 실패한다"* 까지 확인해 뒀다.
**"돌렸다" 와 "이 커밋에서 깨끗한 환경으로 돌았다" 가 다를 뿐이다.**

### 병합은 로컬 `--ff-only` 로 했다

PR 은 열되 **GitHub 의 병합 버튼을 안 눌렀다.**

**GitHub 의 "Rebase and merge" 는 ff 가 가능한 상황에서도 커밋을 다시 쓴다.**
author 는 유지되지만 committer 와 날짜가 바뀌어 SHA 가 달라지고, 그러면

- `sclee` 의 로컬 브랜치가 `main` 과 **갈라진다** — 내용은 같은데 git 은 다른
  것으로 본다. **계정마다 작업 트리가 따로인 이 저장소에서는 실제로 물리는 자리다**
- **태그가 브랜치에 없는 커밋을 가리킨다**

그래서 로컬에서 `git merge --ff-only` 로 붙이고 push 했다. **push 하면 GitHub 이
그 커밋들이 `main` 에 들어온 것을 알아보고 PR 을 자동으로 `MERGED` 로 닫는다** —
실제로 그렇게 닫혔다. CI·리뷰 자리는 얻고 SHA 는 지킨다.

### 그래서 다음부터 이렇게 한다

```bash
# 작업 중
git switch -c work/<YYYYMMDD>-<계정>
python web/manage.py test viewer

# 마무리 — main 을 들여온다. **`git pull --rebase` 로는 안 된다**
git fetch origin
git rebase origin/main                  # upstream 이 자기 브랜치라 대상을 명시한다
python web/manage.py test viewer        # **얹은 뒤 다시 돌린다**
git push --force-with-lease origin work/<…>

# PR
gh pr create --base main --head work/<…>

# 통과·리뷰 뒤 — 로컬에서 붙인다
git switch main && git pull --ff-only
git merge --ff-only work/<…> && git push origin main
```

**함정 셋을 적어 둔다.**

- **인자 없는 `git pull --rebase` 는 `main` 을 안 들여온다.** 그것은
  `git rebase @{upstream}` 이고, work 브랜치의 upstream 은 `origin/work/…`
  — **자기 자신**이다. `pull --rebase` 는 *같은 브랜치를 둘이 만질 때* 쓰는 도구다
- **얹은 뒤 시험을 다시 돌린다.** rebase 는 충돌 나는 자리만 보여 주는데, 이
  저장소에서 위험한 것은 **안 나는 쪽**이다 — 106 의 stash 가 그렇게 버려졌다
  (`data.py` +128줄이 충돌 없이 붙는데 전제가 이미 바뀌어 있었다)
- **force-push 는 `--force-with-lease`.** 다만 그 임대는 **`git fetch` 가 갱신한다**
  — 남의 커밋을 본 적도 없는데 검사가 통과할 수 있다. `--force-if-includes` 를
  함께 주면 *"봤다"* 가 아니라 *"얹었다"* 를 요구한다 (git 2.30+, 이 머신은 2.43)

## 6. 배포

```

08:06  v0.11.2   0034      · smoke 통과 · check_db 전부 OK
```

둘 다 **뷰어만** 올렸다(`PIPELINE_TAG=v0.5.2` 그대로).

**smoke 가 여는 화면이 시야 목록 하나뿐이라**(9.7절 · 086 이 그 구멍으로 나왔다)
매번 `/crops/`·`/detections/`·`/catalog/`·`/g/1/`·`/thresholds/`·`/system-settings/`
를 손으로 열어 확인했다. **일곱 다 200 이었다.**

자료도 봤다 — 코멘트 2건이 개체로 옮겨졌고(`개체 1297`·`1301`), 시야 코멘트 6건은
그대로이고, `ObjectReview` 에서 `note`·`grade` 두 칼럼이 사라졌다.

### `check_db` 10번이 비어 보이는 것은 고장이 아니다

배포 뒤 `check_db` 를 돌리면 `=== 10. 등급·자세 ===` 아래에 **한 줄도 안 찍힌다.**
매긴 개체가 0건이면 절 전체를 건너뛰기 때문이고, `-v` 를 주면 이유를 적는다.

```
=== 10. 등급·자세 ===
   (아직 등급·자세를 매긴 개체가 없다)
```

**늘 0 인 검사를 두면 덮은 줄 알게 된다** — 코드가 그렇게 적어 두었다. 처음 봤을
때 고장으로 의심했는데 의도된 것이었다. **여기 적어 두는 이유는 다음 사람이 같은
의심을 하기 때문이다.**

## 7. 열려 있던 것 하나가 닫혔다 — CI 가 이미지를 올린다

HANDOFF 9.9 가 *"CI 가 이미지를 Docker Hub 로 올리는지 아직 확인 안 했다"* 를
08-10 부터 들고 있었다. 시크릿은 들어와 있는데 그 뒤로 밀린 태그가 없어서였다
(`v0.8.0`~`v0.11.2` 는 **전부 이 머신에서 손으로 올렸다** — *"시험을 통과한 것만
이미지가 된다"* 는 관문이 실제로는 사람 손에 걸려 있었다).

`v0.12.0` 에서 갈렸다.

| | `Docker Hub 로그인` |
|---|---|
| PR (`pull_request`) | **건너뜀** — 굽기만 하고 안 올린다 |
| 태그 (`push: tags`) | **돌았다** → `honestjung/diaruga:v0.12.0` 이 레지스트리에 섰다 |

**굽기는 늘 검증하되 올리는 것은 태그일 때만이다.** 배포 절차에서 "손으로 push" 를
뺄 수 있다.
