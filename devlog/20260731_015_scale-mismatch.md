# XML 의 배율이 실제 광학계와 달랐다

**작성일** 2026-07-31
**관련** `20260731_013_nas-ingest.md` (이 문제가 처음 드러난 곳)

---

## 증상

NAS 에서 자동으로 들어온 첫 슬라이드(`260731/RS23-GC03 369cm`)의 검출 통과율이
**1.6%** 였다. 기존 슬라이드는 18.6% 다.

지표를 갈라 보니 하나만 무너져 있었다.

| 지표 | 260729 | 260731 |
|---|---|---|
| `major_um` 중앙 | 18.7 | 15.1 |
| `solidity` 중앙 | 0.89 | 0.87 |
| `ellipse_iou` 중앙 | 0.79 | 0.78 |
| `elongation` 중앙 | 1.82 | 2.17 |
| **`texture` 중앙** | **1,903** | **109** |

XML 에는 이렇게 적혀 있었다.

```
260729  Plan-Apochromat  40x/0.95 Korr M27   NominalMagnification 40   0.1126 µm/px
260731  Plan-Apochromat 100x/1.40 Oil DIC    NominalMagnification 100  0.0450 µm/px
```

## 광학 경로를 검산했더니 XML 안에서는 앞뒤가 맞았다

ZEN 은 `Scaling/AutoScaling` 에 배율을 만드는 요소를 다 적어 둔다.

```
카메라 화소 ÷ (대물렌즈 × 옵토바 × 카메라어댑터) = µm/픽셀
```

네 슬라이드 모두 **오차 0.0000%** 로 `Scaling/Items/Distance` 와 일치했다.

| 슬라이드 | 광학 경로 | 계산 | 기록 |
|---|---|---|---|
| 260729 ×3 | 40 × 1.6 × 0.63 = 40.32 | 4.54 / 40.32 = 0.112599206 | 0.112599206 |
| 260731 | 100 × 1.6 × 0.63 = 100.8 | 4.54 / 100.8 = 0.045039683 | 0.045039683 |

**여기서 "메타데이터는 맞다" 고 결론지었는데, 그게 틀렸다.** 산술은 맞지만
*입력*이 틀렸다. ZEN 은 소프트웨어에서 **선택된** 대물렌즈로 계산한다. 렌즈
교환대가 수동이면 실제 광학계와 어긋날 수 있다.

## 사람의 관찰이 먼저 맞았다

*"왼쪽에서는 봉상의 내부 가로선들이 잘 보이는데 오른쪽에는 그런 게 안 보이고
뭐가 되었든 왼쪽보다 훨씬 작게 많이 보이는 느낌이야."*

그리고 결정타 — **"규조류 사진은 40x 로 찍는다. 100x 로 찍지 않았다."**

내 계측은 세 번 다 "더 확대됐다" 를 가리켰다(개체 bbox 173→307 px, 조흔 주기
18.2→35.5 px). 그런데 **화면을 본 사람의 말이 맞았다.**

## 확인 — 픽셀은 그대로 두고 배율 가정만 바꿔 봤다

리샘플하지 않는다. 같은 픽셀에 "픽셀당 몇 µm 인가" 만 달리 넣어 텍스처를 다시 쟀다.

| 260731 개체 60개 | p25 | 중앙 | p75 |
|---|---|---|---|
| 0.045 µm/px (XML 주장) | 55 | **83** | 150 |
| **0.1126 µm/px (실제 40x)** | 1,741 | **2,659** | 4,374 |
| 대조: 260729 (40x 확실) | 1,014 | **1,872** | 3,474 |

배율을 0.1126 으로 놓으면 텍스처가 기존 슬라이드보다 **오히려 높다.** 정상이다.

**XML 의 배율이 틀렸다.** 조흔은 실제로 3.6~14 px 간격에 있는데 8.9~35.5 px
대역을 뒤졌으니 못 찾은 것이다.

## 왜 텍스처만 무너졌나

`um_per_px` 가 들어가는 곳은 `texture_score()` 의 두 줄뿐이다.

```python
min_px, max_px = lo_um / um_per_px, hi_um / um_per_px   # (0.4, 1.6) µm
band = (r >= 1.0 / max_px) & (r <= 1.0 / min_px)
```

조흔 주기를 µm 로 정의해 두고 픽셀로 환산해 **스펙트럼의 어느 고리를 볼지** 정한다.
`--scale` 을 바꿔도 같은 구조를 보게 하려는 좋은 설계다 — `um_per_px` 가 맞을 때는.

2.5배 틀리면 두 고리가 **20% 밖에 안 겹친다.**

| 가정 | 조흔 주기 | 보는 고리 |
|---|---|---|
| 0.1126 (실제) | 3.6~14.2 px | r ∈ [0.070, 0.282] |
| 0.045 (XML) | 8.9~35.5 px | r ∈ [0.028, 0.113] |

**지표마다 고장 나는 방식이 다르다.**

| 지표 | 배율이 2.5배 틀리면 |
|---|---|
| `solidity`·`elongation`·`ellipse_iou` | 영향 없음 (무차원) |
| `major_um`·`area_um2` | 비례해서 틀림 — 나중에 곱해 고칠 수 있다 |
| **`texture`** | **무너진다** — 값이 뜻을 잃어 다시 계산하는 수밖에 없다 |

앞의 둘은 회복 가능하고 눈에도 띈다(37.8 µm 짜리가 15.1 µm 로 나오면 이상하다).
그런데 텍스처는 **"규조각이 아니다" 라는 그럴듯한 답**으로 나온다. 예외도 안 나고
값도 정상 범위다. `check_db.py` 머리말이 말하는 *예외가 나지 않고 그냥 틀린 상태*
그대로다.

`max_px < 2.5` 일 때 0 을 내는 Nyquist 안전장치는 있는데, **반대 방향(대역이 너무
넓어지는 쪽)에는 아무것도 없었다.**

## 고친 것 — 따로 정해 주지 않으면 40x 로 계산한다

`zen_meta` 가 XML 의 대물렌즈 배율을 그대로 믿지 않는다. **카메라 화소·옵토바·
어댑터는 XML 실측값을 쓰고 대물렌즈만 40x 로 고정해 다시 계산한다.** 장비 구성이
바뀌면 나머지는 따라간다.

```
40x 슬라이드     → 0.112599206  (그대로, 경고 없음)
100x 로 적힌 것  → 0.112599206  + 경고
```

다른 배율로 찍었다면 알려 줘야 한다. **자동으로 알아내려 하지 않는다** —
이번에 그러려다 두 번 틀렸다.

- `--um-per-pixel` (CLI)
- `Slide.um_per_pixel_override` (슬라이드 속성 편집 화면). 자동 파이프라인에는
  CLI 인자를 줄 자리가 없어서 만들었다. 채우면 XML 을 이긴다

## 내가 틀린 것 세 가지

기록해 둔다. 같은 함정에 다시 빠지지 않으려고.

**1. 비교 이미지를 잘못 만들었다.** 각 슬라이드에서 100 µm 를 잘라 같은 크기로
맞췄는데, 신규 쪽은 2220 px(원본 높이 2208 px 을 넘는다 — 사실상 전체 화면)를
760 px 로 2.9배 줄였고 기존 쪽은 888 px 를 1.17배만 줄였다. **축소율이 2.5배 달라
오른쪽 세부가 뭉개졌다.** 비교용 이미지를 만들 때 한쪽만 크게 줄이면 그 자체가
결론을 바꾼다.

**2. "텍스처 지표가 해상도에 딸려 간다" 고 진단했다.** 아니었다. 리샘플 시험에서
그렇게 보인 건 **이미 올바른 배율의 영상을 0.4배로 줄여 조흔을 스스로 뭉갰기**
때문이다. 잘못된 전제(XML 이 맞다)로 설계한 시험은 그 전제를 확인해 줄 뿐이다.

**3. "산술이 맞으니 메타데이터도 맞다" 고 했다.** 네 번 다 소수점까지 맞아떨어지는
것을 보고 확신했는데, 검산은 **XML 안의 일관성**만 확인한다. 입력이 실제와 다르면
아무리 정확히 계산해도 틀린 답이 나온다.

공통점: **계측이 사람의 눈과 어긋났을 때 계측을 먼저 믿었다.** 이 경우 사람이
맞았다.

## 남은 것

- 260731 슬라이드를 합성부터 다시 돌린다. 합성본 사이드카(`*_scale.json`)에
  옛 값이 굳어 있어서 검출만 다시 해서는 안 된다. **교정이 아직 없어 지금이 가장
  싼 시점이다** — 재바인딩할 것이 없다
- 배율이 기존과 다른 슬라이드가 들어오면 `state="failed"` 로 세워 사람에게 묻는
  장치는 아직 없다. 지금은 경고만 찍고 40x 로 계산하고 넘어간다
- 촬영 쪽 확인: ZEN 의 대물렌즈 설정이 실제 교환대와 어긋나 있다. 다음 촬영 전에
  맞춰 두면 이런 일이 다시 안 생긴다
