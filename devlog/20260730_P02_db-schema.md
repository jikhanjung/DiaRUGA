# [계획] SQLite 스키마 — 데이터와 설정을 DB 로 모은다

**작성일** 2026-07-30
**상태** 1~4단계 완료 (모델·이전·대조·뷰어). 5~8 남음 — §5 참조

## 정한 것

| | |
|---|---|
| 원본(source of truth) | **DB** — 스크립트 4개가 DB 에 직접 쓴다 |
| `out/*.json` 등 | **내보내기 형식**으로만 남는다 |
| 교정 기록 | DB 가 원본, `export_review.py` 로 `review/*.json` 을 git 에 남긴다 |
| 접근 | **Django ORM** (`web/viewer/models.py` + migrations) |
| DB 파일 | `<DATA_ROOT>/diatom.db` — **gitignore** |

지금은 `DATABASES = {}` 이고 `models.py` 도 없다(파일에서 직접 읽는 구조였다).
그 결정을 뒤집는 것이므로 `data.py` 첫머리의 주석도 함께 고쳐야 한다.

## 1. 무엇이 JSON 이었나 (옮길 대상)

| 지금 | 개수·크기 | 만드는 것 | 옮길 곳 |
|---|---|---|---|
| `groups_*.json` | 3개 · 40 KB | `group_focus_series.py` | `Site` + `Core` + `Slide` + `Viewpoint` + `Frame` |
| `out/*_candidates.json` | 124개 · **25.3 MB** | `segment_diatoms.py`, `refilter.py` | `Detection` + `Candidate` |
| `review/*_review.json` | 124개 · 100 KB | 뷰어 | `ViewpointReview` + `ObjectReview` |
| `stacked/*_scale.json` | 81개 | `focus_stack.py` | `Stack` |
| `stacked/stack_report.json` | 1개 (32항목만 남음) | `focus_stack.py` | `Stack` + `Run` |

JSON 이 아니지만 함께 옮길 것: 사진 옆 **XML**(345개)에서 읽는 µm/px·촬영시각,
`run_batch.sh` 의 실행 설정, `segment_diatoms.py` argparse 문턱 기본값,
`data.py` 의 `CLASS_LABELS`.

**아무 데도 없어서 새로 생기는 것**: 실행 이력(`Run`), 슬라이드 처리 상태(NAS).

`settings.py` 의 경로(`DATA_ROOT`, `IMAGE_DIRS`, …)는 **DB 로 옮기지 않는다** —
배포 환경마다 다른 값이라 환경변수가 맞다.

### 2.0 `Site` · `Core` — 시료의 출처

폴더명 `RS23-GC03 71cm` 은 세 토막이다: **지역 RS23 · 시추코어 GC03 · 깊이 71cm**
(기준점, 아마도 해저면에서부터). 남극에서 채취한 시추코어의 규조류다.

```
Site (RS23, WAP13)           code · name · region · lat/lon
  └─< Core (GC03, GC47)      code · kind · lat/lon · water_depth_m · collected_at
        └─< Slide (깊이별)    depth_cm
```

**통짜 문자열로 두면 안 되는 이유**: 이 시료의 분석 목적이 *같은 코어에서 깊이에
따른 군집 변화*와 *지역별 차이*다. 이름을 갈라 담아야 깊이순 정렬과 지역별 묶음이
질의로 나온다. `Slide.Meta.ordering = ["core", "depth_cm", "name"]` 로 코어 안에서는
깊이순이 기본이다.

```
RS23-GC03     71 cm   개체 811
WAP13-GC47   116 cm   개체 632
WAP13-GC47   450 cm   개체 1079     <- 같은 코어의 두 깊이가 묶인다
```

지역 코드의 **정식 명칭은 비워 두고 사람이 채운다.** 코드만으로 단정할 수 없다 —
`WAP` 는 통상 West Antarctic Peninsula 를 뜻하지만 이 시료에서는 다르게 쓰였을 수
있어서, 코드는 저장하고 `name`·`region` 은 편집 가능하게 남긴다.

**재실행마다 새 행을 쌓는다**(덮어쓰지 않는다). 전량 한 바퀴가 개체 18,936행 ≈ 25 MB

(P01 §3 이 요구하는 것이고 지금은 덮어써서 불가능하다). 필요하면 `--prune` 으로
`is_current=false` 인 것을 지운다.

"탈락분도 지표째 남긴다" 는 원칙(README)이 스키마로 표현된다.

**`rle` 은 버린다** — 지금도 항상 `null` 이다.

### 2.7 교정 — `ViewpointReview` · `ObjectReview`

```
ViewpointReview
  viewpoint_id (unique)
  done          bool        검토 완료
  note          text        시야 전체 코멘트
  updated_at

ObjectReview
  id, viewpoint_id, mask_key            ← **candidate_id 가 아니라 mask_key 로 붙인다**
  candidate_id  → Candidate (nullable)  바인딩된 결과 (조인용, 재검출 때 다시 맺는다)
  bind_method   exact|iou|manual|orphan  어떻게 맺혔나
  bind_score    1.0 | 0.93 | null        iou 로 맺었으면 그 값
  geom          JSON                     bbox + polygon 스냅샷 (**모든 행에 저장**)
  removed       bool        오검출로 지움
  accepted      bool        탈락분에서 되살림
  label         cls 덮어쓰기 (nullable)
  note          text
  updated_at
  unique(viewpoint_id, mask_key)
  index(viewpoint_id, bind_method)       고아를 한 번에 뽑아 보고할 수 있게
```

**왜 `candidate_id` 를 키로 삼지 않나** — 검출을 다시 돌리면 `Candidate` 행이 새로
생긴다. 지금 bbox 키를 쓰는 이유가 바로 그것이고(README), DB 로 옮겨도 사정은 같다.
`mask_key` 를 진짜 키로 두고 `candidate_id` 는 **바인딩 결과**로 채운다(ingest·재검출
때 다시 맺는다). 맺히지 않은 교정은 고아로 남지만 **사라지지는 않는다** — 지금
`tighten_bbox.py` 가 키를 옮겨 주는 것과 같은 자리다.

`removed` 와 `accepted` 를 한 칼럼(상태)으로 합치지 않는다. 되살렸다가 다시 지운
개체가 있고, "사람이 지웠다가 이긴다" 는 규칙이 두 값의 조합으로 표현된다(devlog 005 §4.1).

#### 재검출에서 교정이 살아남는가 — 실측

`ObjectReview` 가 `Detection` 을 참조하지 않으므로, 재검출은 `candidate_id` 만 다시
맺으면 된다. 문제는 `mask_key` 가 그대로인지다. **같은 설정으로 한 장을 다시 돌려
재 봤다.**

```
원시 마스크: 저장 시점 133개 · 방금 133개
크기 통과 키 77개 -> 일치 77개 (100%) · 어긋남 0개
```

**같은 설정이면 키가 하나도 어긋나지 않는다**(Turing 에서 fp16 autocast 를 켜고 돌리는데도
결정적이었다). 문턱만 바꾸는 `refilter` 는 마스크를 건드리지 않으므로 더 안전하다.

반대로 **설정을 바꾸면 대량으로 어긋난다.** 실험 중 `--iou-thresh` 를 0.5 → 0.6 으로
잘못 넣었을 때 원시 마스크가 133 → 117 로 줄었다. `--scale`·`--points-per-side` 변경,
그리고 **엔진 교체(P01 §3)가 그 경우다.**

#### 자동 재바인딩은 보수적으로만

어긋난 것을 IoU 로 다시 맺어 봤더니 **짝의 IoU 중앙값이 0.085** 였다. SAM 이 같은
자리에 여러 스케일의 마스크를 내므로, "조금 어긋난 같은 개체" 가 아니라 **다른 스케일의
다른 마스크**와 짝지어진다. 그래서

```
1) exact   mask_key 가 같다            -> bind_method=exact, score=1.0
2) iou     IoU >= 0.9 인 짝이 유일하다  -> bind_method=iou,   score=IoU
3) orphan  그 밖에는 맺지 않는다        -> bind_method=orphan, 사람에게 보고
```

**고아를 지우지 않는다.** 재생성 불가한 자료이므로 맺히지 않은 채로 남겨 두고, 이전
스크립트가 "N개가 붙지 않았다" 를 출력한다.

#### `geom` 스냅샷 — 모든 교정 행이 기하를 들고 있는다

폴리곤은 `Candidate` 에만 있다. 재검출이 그 마스크를 내지 않으면 `ObjectReview` 행은
남아도 **그릴 것이 없다.** 그래서 **되살린 것만이 아니라 지운 것까지, 모든 교정 행에**
bbox·폴리곤을 스냅샷한다. 이유가 셋이다.

1. **교정이 검출기와 독립이 된다.** 엔진을 갈아도(P01 §3) 사람의 판단은 그대로 읽힌다
2. **지운 것(`removed` 2,027개)이 학습의 어려운 음성 표본이다** — "SAM 이 후보로 냈는데
   사람이 규조각이 아니라고 한 것" 은 그냥 버릴 자료가 아니다. 기하가 없으면 못 쓴다
3. **고아를 언제나 그려 볼 수 있다**(§3)

비용은 작다 — 교정 2,283행 × 폴리곤 ≈ 1 MB.

이것이 P01 §6 의 **수동 박스 그리기**로 그대로 이어진다 — SAM 이 후보로도 잡지 못한
개체는 애초에 `Candidate` 가 없으므로, 사람이 그린 것을 담을 곳이 `ObjectReview.geom`
이다. 두 문제가 같은 자리에서 풀린다.

**지금 아무 데도 없는 것이다.** `refilter` 를 돌리면 앞의 판정이 덮어써지고 무엇으로

"원형 669 → 514 는 언제 무슨 문턱으로 바뀐 것인가" 에 답할 수 있다.

### 2.9 설정 — `ThresholdSet` · `ClassDef` · `Setting`

```
ThresholdSet
  id, name           "기본 v2 (areolae 1500)"
  min_um, max_um, texture_min,
  round_max_elong, round_min_iou, round_min_solidity, round_texture_min,
  rod_min_elong, rod_max_elong, rod_min_iou, rod_min_solidity
  is_default, created_at, note

ClassDef                      지금 data.py 의 CLASS_LABELS
  key        "eucampia"
  label      "Eucampia"
  badge      "euc"
  color      "255,110,190"    지금은 CSS 에 흩어져 있다
  is_taxon   true             형태 칸과 분류학 칸을 가르는 값
  sort_order, active

Setting                       그 밖의 것 (key/value)
  key, value(JSON), updated_at
```

`ThresholdSet` 을 표로 두면 **문턱을 이름으로 붙여 비교**할 수 있다("1500 vs 2000 을
같은 시야에 걸어 보고 개수를 나란히"). `ClassDef` 를 표로 두면 **분류를 더할 때 배포가
필요 없다** — Eucampia 를 넣은 것이 코드 수정이었는데, 앞으로 속이 늘어날 것이다.

## 3. 재바인딩과 고아 화면 — 새 run 과 기존 교정을 잇는다

**중기적으로 이것이 이 스키마의 핵심 기능이 된다.** 지금은 같은 설정이면 100% 붙으니
문제가 없어 보이지만, 그 상태는 오래가지 않는다.

### 언제 어려워지는가

| 무엇을 바꾸나 | `exact` 로 붙는 비율 |
|---|---|
| 문턱만 (`refilter`) | 100% — 마스크를 건드리지 않는다 |
| 같은 설정으로 재검출 | 100% (실측, §2.7) |
| `--scale`·`--points-per-side` 변경 | 크게 떨어진다 (원시 마스크가 133 → 117 로 줄었다) |
| **엔진 교체 (P01 §3, YOLO 커스텀)** | **거의 0** — 다른 모델은 다른 마스크를 낸다 |

그리고 하필 그때가 **교정 기록이 학습 정답으로 쓰이는 시점**이다. 검출기가 바뀌어도
사람의 판단은 남아야 한다 — 그래서 `geom` 을 모든 행에 저장한다(§2.7).

### 고아 화면 (`/d/<slug>/orphans/`)

맺히지 않은 교정만 모아 보여준다. **그 목록이 곧 "무엇이 달라졌나" 다.**

```
┌ 고아 교정 47개 ─ [삭제 31] [되살림 9] [분류 5] [코멘트 2] ─ 크기순 ┐
│ ┌──────────┐  사람: 오검출로 삭제        이 자리의 새 후보 2개      │
│ │ geom 크롭 │  22.4 µm · 봉상            ┌────┐ ┌────┐             │
│ │  (세움)   │  "조각난 것"               │ A  │ │ B  │  [연결]      │
│ └──────────┘                            └────┘ └────┘             │
```

- 크롭은 `geom` 의 bbox 로 자른다 — **`/crop` 엔드포인트를 그대로 쓴다**(방향 세움과
  스케일바까지 공짜로 따라온다)
- 오른쪽에 그 자리의 새 후보를 함께 놓는다. 지금 "빈 곳 클릭 → 탈락 후보 펼쳐 보기"
  와 같은 방식이라 조작이 낯설지 않다
- 동작 세 가지: **이 후보에 연결**(`bind_method=manual`) · **그대로 두기** ·
  **교정 폐기**(사람이 명시적으로 버릴 때만)
- 엔진 교체 직후에는 고아가 2,000개 규모다 → 페이지네이션과 필터가 필수

### 이 화면이 곧 엔진 비교 화면이다

`reconcile` 결과를 이렇게 읽는다.

| 숫자 | 뜻 |
|---|---|
| `exact` 비율 | 두 검출이 얼마나 같은 마스크를 내는가 |
| **`orphan` 중 `accepted`·`label` 이 붙은 것** | **새 엔진이 놓친 것** (사람이 규조각이라 한 것) |
| `orphan` 중 `removed` | 새 엔진이 애초에 내지 않은 오검출 — 좋은 신호다 |
| 새 후보 중 아무 교정도 안 붙은 것 | 새로 생긴 것 → 사람이 봐야 할 대상 |

**P01 §3 이 요구하는 "교체 전후를 같은 시야로 비교" 가 이 화면에서 바로 읽힌다.**
그래서 `Detection` 이력을 지우지 않는다(§2.5).

## 4. 크기와 성능

| | 지금 | DB |
|---|---|---|
| 첫 화면 | JSON **251개** 읽기 · 371 ms | 질의 몇 개 · 수 ms |
| 개체 18,936개 | 25.3 MB JSON | 폴리곤이 대부분 — 비슷하거나 조금 작다 |
| 크기 분포·분류 집계 | 124개 파일 전부 열기 | `GROUP BY` 한 줄 |

SQLite 설정(GPU 배치가 쓰는 동안 뷰어가 읽어야 한다):

```python
DATABASES = {"default": {
    "ENGINE": "django.db.backends.sqlite3",
    "NAME": PROJECT_ROOT / "diatom.db",
    "OPTIONS": {"timeout": 20,
                "init_command": "PRAGMA journal_mode=WAL; PRAGMA synchronous=NORMAL;"},
}}
```

**WAL 이 필요하다** — 기본 journal 모드면 검출 배치가 쓰는 동안 뷰어 읽기가 막힌다.

## 5. 이전 순서 (되돌릴 수 있게)

각 단계는 앞 단계를 지우지 않는다. **JSON 은 마지막까지 남겨 두고 대조한다.**

1. `models.py` + 첫 마이그레이션. `DATABASES` 채우기
2. **`import_json.py`** — 지금의 JSON 전부를 DB 로 넣는다(멱등, 다시 돌려도 같은 결과).
   `groups → Slide/Viewpoint/Frame`, XML → Frame 배율·시각, `stacked/* → Stack`,
   `out/* → Detection/Candidate`, `review/* → *Review`
3. **대조 스크립트** — DB 와 JSON 이 같은 답을 내는지 확인한다. 개체 수, 분류별 개수,
   교정 수, 시야별 통과 수를 양쪽에서 세어 **완전히 일치**해야 다음으로 간다.
   교정은 `bind_method` 별로도 센다 — 이전 직후에는 **전부 `exact`** 여야 한다
   (같은 검출 결과를 그대로 넣는 것이므로 어긋날 이유가 없다)
4. 뷰어를 DB 로 돌린다(`data.py` → ORM). 이때도 JSON 은 그대로 있다 →
   같은 화면이 나오는지 눈으로 대조
5. `export_review.py` — DB → `review/*.json` (git 에 남길 감사 기록)
6. 스크립트 4개를 DB 에 쓰게 고친다. `out/*.json` 은 `--export-json` 으로만.
   `segment_diatoms.py` 는 새 `Detection` 을 쌓고 `is_current` 를 옮기며,
   **교정을 다시 맺고 그 결과(exact/iou/orphan 개수)를 출력한다**
7. JSON 을 원본에서 내린다. `README`·`data.py` 주석 갱신
8. **재바인딩 + 고아 화면**(§3). 6번까지는 `exact` 만으로 충분하지만, 학습·엔진
   교체에 들어가기 전에는 반드시 있어야 한다 — 없으면 교정이 조용히 버려진다

**3번에서 한 칸이라도 어긋나면 멈춘다.** 교정 기록 2,027 + 133 + 123 이 재생성 불가한
자료이고, 이것이 어긋난 채로 4번을 하면 무엇이 맞는지 알 수 없게 된다.

## 7. 미리 짚어 둘 것

- **`.db` 는 gitignore.** 교정은 `export_review.py` 가 JSON 으로 내보내 git 에 남는다.
  DB 를 잃어도 JSON + 산출물로 되살릴 수 있다는 성질을 유지한다
- **컨테이너화(P01 §5)와 상충한다.** 처리 스크립트가 Django 를 필요로 하게 되므로
  "뷰어만 작은 이미지" 가 안 된다. 처리 이미지에 Django 를 넣거나, 나중에 얇은
  DB 모듈로 갈라야 한다 — 지금 결정은 ORM 이므로 그 값을 치른다
- **`refilter.py` 가 UPDATE 로 바뀌면 이력을 남길 수 있다.** 지금은 덮어써서 사라진다
- **`tighten_bbox.py` 는 DB 이전 뒤에 하는 편이 낫다.** `mask_key` 를 바꾸는 작업이라
  `ObjectReview` 재바인딩과 같은 문제를 푼다 — 한 번만 풀면 된다. 그때는 옛 키와 새
  키가 1:1 로 대응하므로 `bind_method=exact` 를 유지할 수 있다(dry-run 에서 미매칭 0)
- **`is_current` 를 옮기는 것과 교정을 다시 맺는 것은 한 트랜잭션이어야 한다.** 중간에
  끊기면 뷰어가 "교정이 붙지 않은 새 검출" 을 보여준다
- 이미지·npz 는 DB 에 넣지 않는다. 경로만 둔다
