## 6단계를 하려니 8단계가 딸려 왔다

`segment_diatoms.py` 를 DB 로 옮긴다는 것은 **검출을 덮어쓰지 않고 쌓는다**는 뜻이다
(`Detection.is_current` 가 뷰어가 볼 것을 가리킨다). 그런데 새 검출은 `Candidate`
행을 통째로 새로 만들므로, 교정의 `candidate` 링크가 전부 끊긴다.

교정 자체는 사라지지 않는다 — 진짜 키가 `(viewpoint, mask_key)` 이고 `geom` 에
기하를 스스로 들고 있기 때문이다. 하지만 **다시 맺어 주지 않으면 뷰어가 그 개체를
못 그린다.** 그게 P02 8단계("재바인딩 + 고아 화면")인데, 찾아보니 **exact/orphan
말고는 아무것도 없었다.** `import_json.py` 도 `data.py` 도 `mask_key` 가 정확히
맞을 때만 맺는다.

그래서 재바인딩 장치를 먼저 만들었다. 8단계의 *고아 화면*은 여전히 남는다.

## rebind.py — 규칙을 한 곳에만 둔다

`judge.py` 와 같은 이유다. `segment_diatoms.py`, `group_focus_series.py`(6단계
마지막), 고아 화면(8단계)이 전부 같은 규칙을 써야 한다.

| 방법 | 언제 | bind_score |
|---|---|---|
| `exact` | 새 검출에 같은 `mask_key` 가 있다 | 1.0 |
| `iou` | 없지만 bbox 가 충분히 겹치는 개체가 있다 | 그 IoU |
| `orphan` | 아무것도 없다 | null |

**같은 개체를 둘이 가져가지 않는다.** exact 를 먼저 전부 맺고, 남은 교정만 아직
임자 없는 개체와 IoU 로 맺되 점수 높은 짝부터 가져간다. `manual`(사람이 직접 맺은
것)은 건드리지 않는다 — 기계가 사람의 판단을 풀면 안 된다.

`geom` 이 비어 있는 옛 행을 위해 `mask_key` 에서 bbox 를 되살릴 수 있게 해 뒀다.
키가 `x_y_w_h` 를 이어 붙인 것이라 그대로 돌아온다.

### 얼마나 어긋나는지 재 봤다

bbox 를 인위적으로 밀어 놓고 롤백하며 확인했다.

| 어긋난 정도 | 결과 |
|---|---|
| 3 px | iou 67 (전부 다시 맺힘) |
| 12 px | iou 60 · 고아 7 |
| 60 px | iou 3 · 고아 64 |

작은 개체가 먼저 떨어져 나간다. 60 px 쯤 되면 고아가 맞다 — 다른 개체다.

## 실제 재검출에서 드러난 것

교정이 가장 많은 시야(rs23 g2, 67건)로 돌려 봤다.

```
재바인딩: exact 26 · iou 40 · 고아 1
```

**같은 이미지·같은 문턱인데 `mask_key` 가 26개만 맞았다.** SAM2 가 미세하게 다른
마스크를 낸다(배치 크기가 달랐다). IoU 재바인딩이 없었으면 **67건 중 41건이 교정에서
떨어져 나갔을 것이다.** 만들기를 잘했다.

옛 검출 #50 은 `is_current=False`·`superseded_by=125` 로 남고, 교정 67건은 전부 새
검출의 개체를 가리킨다(옛 개체를 가리키는 것 0건, 기하 잃은 것 0건).

**이 시험 검출은 되돌렸다.** 0729 는 그대로 두기로 해서, `is_current` 를 #50 으로
돌리고 다시 맺으니 `exact 67` 로 복귀했다 — 되돌리기까지 같은 장치로 된다.

## check_db 가 잘못 세고 있었다

재검출 뒤 `check_db.py` 가 고아를 **41건**이라고 했다. 실제 고아는 1건이다.

검사가 "`mask_key` 가 현재 검출에 있는가" 로 보고 있었다. 그 기준이면 IoU 로
정상적으로 맺힌 40건이 전부 고아로 잡힌다. **진짜 고아는 가리키는 개체가 아예
없는 것**이므로 `candidate_id is None` 으로 고쳤다. 링크 검사도 "옛 검출의 개체를
가리키는가" 로 뜻을 바꿨다 — 재바인딩이 중간에 끊기면 그렇게 된다.

재바인딩을 만들면서 그것을 검사하는 쪽도 같이 손봐야 했다.

## 한 트랜잭션

`is_current` 이동과 재바인딩이 갈라지면, 그 사이에 뷰어를 연 사람은 "교정이 하나도
안 붙은 새 검출"을 본다. 통째로 한 트랜잭션이다.

`focus_stack.py` 는 반대로 그룹마다 짧게 커밋한다(합성이 12초라 통으로 묶으면 뷰어
쓰기가 오래 막힌다). 성격이 다른 작업이라 다르게 간다.

## 떨어진 조각을 버린다 (2026-07-31 부터)

005 §5 가 짚어 둔 것을 이제 적용한다. 후처리를 껐으므로 SAM 마스크에 떨어져 나온
작은 조각이 남는데, **bbox·면적은 마스크 전체에서 오고 폴리곤·형태 지표는
`shape_metrics()` 가 가장 큰 윤곽 하나에서 낸다.** 두 갈래가 다른 것을 본다.

이번에 잰 값은 005 보다 심했다 — **마스크 279개 중 106개(38%)** 가 연결 성분이
여럿이었다(005 는 한 사진에서 24/117 = 21%).

본체만 남기니 통과분이 62 → 55 로 줄었다. bbox 가 조여지면서 중복 정리가 제대로
걸린 것이다(005 가 예측한 방향: 2,522 → 2,193). 원형이 1 → 2 로 는 것은 형태 지표를
본체 기준으로 다시 계산한 결과다.

### 크기 관문도 같이 고쳐야 했다

005 가 미리 적어 둔 함정이다. `filter_records()` 는 **bbox 긴 변**으로 크기를
걸렀는데 README 와 `judge.classify()` 는 **타원 장축**이다. 지금까지는 bbox 가
떠돌이 조각 때문에 부풀어 있어서 이 관문이 거의 안 걸렸다. 본체만 남겨 bbox 가
조여지자 **타원 장축은 범위 안인데 bbox 로는 밖인 개체**가 생긴다(005 실측 33개,
장축 중앙값 11.2 µm — 관문 한가운데다). 타원 장축으로 맞췄다.

### 0729 는 다시 돌리지 않는다

`bbox_xywh` 가 교정 기록의 키다. 전수 검토를 마친 자료의 키를 흔들면 2,400여 건을
다시 맺어야 한다 — 005 가 `tighten_bbox.py` 를 만들어 dry-run 까지 하고도 적용하지
않은 이유가 그것이다.

그래서 **교정이 있는 시야는 `--force` 없이 재검출하지 않는다.** GPU 를 올리기
전에 걸러 낸다.

```
건너뜀 g002_…: 사람의 교정 67건이 있다 (다시 검출하려면 --force)
```

옛 방식으로 돌려야 할 때를 위해 `--all-bodies` 를 남겨 뒀다.

## 이 장비는 RTX 8000 이 아니다

스크립트의 기본값은 RTX 8000(48 GB) 기준이었다. 이 장비는 **3060 Ti 8 GB** 라
`--points-per-batch 64` 로는 OOM 이 난다. 16 으로 내렸다 — 배치로 나눠 넣을 뿐이라
검출 결과는 같다. `run_batch.sh` 에서 `PPB` 로 바꿀 수 있다.

OOM 을 조용히 넘기면 `검출 0개 · done` 으로 끝나 성공처럼 보인다. 전부 OOM 이면
`Run` 을 `failed` 로 남긴다.
