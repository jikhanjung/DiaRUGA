# 077 — 판정 캐시가 어긋난 이유: 판정한 뒤에 버렸다

2026-08-07 · v0.8.0 배포 직후

배포 뒤 `check_db.py` 가 `yolo-3차` 에서 **판정 캐시 9건**을 잡았다. P10 1·2단계
때도 같은 9건을 봤고 그때는 "`refilter.py` 로 풀렸다" 로 넘겼다 — 원인을 못
좁혔다. 이번에 끝까지 짚었다.

## 판정 캐시란

`Candidate.passed`·`cls`·`reject` 는 **저장된 사실이 아니라 순수 함수의 캐시**다.

```
지표(불변) + 문턱(파라미터)  →  judge.py  →  passed / cls / reject
```

지표는 이미지가 안 바뀌면 안 바뀌고, 문턱은 `ThresholdSet` 이 들고 있다. 그러니
**다시 계산하면 저장된 값과 같아야 한다.** `check_db.py` 가 매번 그것을 대조한다
— 어긋나면 refilter 가 중간에 끊겼거나, 문턱만 바꾸고 후보를 안 고쳤거나,
`judge.py` 를 고치고 재판정을 잊은 것이다.

## 그런데 넷째 길이 있었다

```
1. YOLO 가 bbox 가 똑같은 마스크 둘을 낸다
2. judge.apply 가 **둘 다 보고** 판정한다 — dedupe 가 하나로 다른 하나를 누른다
3. save_detection 이 넣을 때 같은 mask_key 는 **첫 것만 두고 버린다**
4. check_db 는 **남은 것만으로** 다시 계산한다 → 누르던 상대가 없으니 다른 답
```

`save_detection` 에 이렇게 적혀 있었다.

```python
# 같은 bbox 가 두 번 나오면 unique 에 걸린다 — 첫 것만 둔다
if key in seen:
    continue
```

유일 제약을 지키려는 옳은 방어인데, **자리가 틀렸다.** 판정 뒤에 버리면 판정이
본 집합(34개)과 저장된 집합(33개)이 달라진다. **저장된 답도 맞고 다시 계산한
답도 맞다** — 본 것이 다를 뿐이다. 아무리 다시 계산해도 안 맞는 종류다.

### 왜 하필 가장자리의 봉상인가

어긋난 9건의 `mask_key` 가 전부 x ≈ 2700 이다. 이미지 폭이 2752 다.

가장자리에서 잘린 규조각은 **연결 성분이 여럿**이 되고, `keep_largest_body` 가
본체만 남기면 **서로 다른 마스크가 같은 bbox 로 수렴한다.** 그래서 같은 열쇠가
둘 생긴다.

### 숫자

| | 넣을 때 잃은 검출 | 판정이 어긋난 검출 |
|---|---|---|
| `yolo-3차` | 1,799 중 **18** (1%) | 8 — **전부 그 18 안에** |
| `sam2-전수` | 508 중 83 (16%) | 0 |

여덟은 하나같이 **정확히 1개씩** 잃었다(`n_sized` − 저장 = 1).

**SAM 쪽이 16%인데 0인 이유**는 그 사이에 `refilter.py` 를 돌렸기 때문이다.
refilter 는 저장된 지표로 판정을 다시 쓰므로 **정의상 자기 자신과 일치하게**
만든다. YOLO 는 한 번도 안 돌렸다. 즉 지금까지 이 고장은 **refilter 가 덮어
왔다** — 회차를 돌리기 시작하면 새 묶음마다 다시 나타난다.

## 고친 것

**`judge.collapse_boxes()` 를 두고 판정 앞에서 접는다.** `judge.py` 는 import 가
하나도 없는 파일이라(P02 6단계) 파이프라인·refilter·시험이 같은 것을 쓴다.

- 열쇠는 `mask_key` 와 **같은 규칙**으로 만든다(`int()` 로 깎은 bbox 네 값).
  다르면 접은 줄 알고도 DB 에서 또 부딪힌다
- **면적이 큰 쪽을 남긴다.** 같은 자리를 가리키는 둘 중에서는 마스크가 더 많이
  잡힌 쪽이 근거가 많다. 같으면 먼저 온 것 — 어느 쪽이든 **결정적**이어야 한다
- 원래 자리에 남긴다. 뒤에서 `id` 를 다시 매기므로 순서가 흔들리면 안 된다

`save_detection` 의 `seen` 은 **그대로 둔다.** 이제 안 걸리는 것이 정상이고,
걸리면 그것이 새 고장의 신호다.
