# [004] 스케일을 XML 에서 읽고, 뷰어를 탭 + 캐러셀로 고친다

**작성일** 2026-07-29

두 가지를 했다. 하나는 계측의 기준값을 상수에서 메타데이터로 옮긴 것이고,
하나는 그룹 화면을 "합성본만 보는 화면" 에서 "원본까지 오가며 검증하는 화면" 으로
바꾼 것이다. 둘은 관계없어 보이지만 스케일바에서 만난다 — µm/px 를 제대로
알아야 사진 위에 눈금을 그릴 수 있다.

---

## 1. 스케일 하드코딩 제거 (`zen_meta.py`)

### 무엇이 문제였나

`segment_diatoms.py` 에 이렇게 박혀 있었다.

```python
UM_PER_PIXEL = 0.11259920634920635
```

여기에 걸려 있는 것이 계측값(면적 µm², 장·단축 µm)만이 아니다.

- **크기 관문** 10~150 µm
- **텍스처 대역** `TEXTURE_PERIOD_UM = (0.4, 1.6)` — µm 로 정의한 대역을 픽셀
  주기로 환산하는 기준이 이 값이다

345장이 모두 한 세션·같은 광학계라 지금까지는 맞았다. 문제는 **조건이 달라졌을 때
아무 신호도 없다는 것**이다. 예외도 경고도 없이 결과 전체가 배율만큼 어긋난다.
NAS 로 슬라이드가 자동으로 들어오기 시작하면 촬영 조건을 사람이 매번 확인하지
않게 되므로, 그때가 가장 위험하다(P01 §1).

### 어떻게 고쳤나

`zen_meta.py` 를 새로 만들고 결정 순서를 이렇게 뒀다.

```
XML (Scaling/Items/Distance)  >  사이드카 <파일명>_scale.json  >  기본값
```

- **XML 이 있으면 언제나 XML.** 사이드카가 같이 있어도 XML 이 이긴다.
- **합성본에는 ZEN XML 이 따라오지 않는다.** `focus_stack.py` 가 원본에서 읽은
  값을 `<tag>_focused.jpg_scale.json` 으로 물려준다. focus_stack 자신의
  `--scale` 리사이즈도 반영한다(`native / scale`).
- 기본값으로 물러날 때, 값이 광학현미경 범위(0.001~100 µm/px) 밖일 때,
  X·Y 픽셀 크기가 다를 때, **한 번의 실행에서 배율이 섞일 때** 각각 경고한다.
  경고는 원인별로 한 번만 낸다 — 배치에서 수백 줄이 쏟아지면 아무도 안 읽는다.
- `segment_diatoms.py --um-per-pixel <값>` 으로 직접 지정하면 XML 을 읽지 않는다.
  메타데이터가 틀렸다고 판단한 사람의 지시가 우선이라고 봤다.
- 결과 JSON 에 `um_per_pixel_native` 와 `um_per_pixel_source`
  (xml/sidecar/default/cli) 를 남긴다. 나중에 계측값을 의심할 때 **어디서 온
  배율인지** 부터 확인할 수 있어야 한다.

XML 을 찾는 규칙(`<파일명>.jpg_metadata.xml`)이 세 곳에 흩어지지 않도록
`group_focus_series.py` 의 `read_timestamp` 도 `zen_meta` 로 옮겼다.

### 광학계 비교는 하지 않았다

P01 에는 "광학계 구성이 이전과 다르면 경고" 도 적혀 있었지만 넣지 않았다.
**µm/px 가 같으면 계측값은 어긋나지 않는다.** 감시할 값 하나를 정확히 고르는
편이, 검증하지 못한 태그 이름을 여럿 추측해 넣는 것보다 낫다고 봤다.

### 검증의 한계 — 실제 XML 로는 확인하지 못했다

**이 작업을 한 머신에는 촬영 데이터가 없다**(`260729/` 없음, GPU 없음).
그래서 `test_zen_meta.py` 를 만들어 **합성 XML** 로만 확인했다. 17개 항목:
정상 파싱, 다른 배율, 네임스페이스, 잘린 XML(정규식 폴백), XML 없음,
사이드카, XML 우선순위, 말도 안 되는 값 거부, Scaling 블록 없음, X≠Y, 배율 혼재.

구조는 README 에 적힌 `Scaling/Items/Distance` 를 따랐고 `Distance` 아래
`Value` 를 읽지만, **실제 ZEN 파일에서 한 번도 돌려 보지 않았다.**
데이터가 있는 장비에서 `python segment_diatoms.py <원본> -o out` 을 한 장만
돌려 `um_per_pixel_source` 가 `xml` 로 찍히는지 확인해야 한다.
`default` 로 찍히면 파서가 실제 구조를 못 맞춘 것이다.

테스트는 표준 라이브러리만 쓰므로 `python3 test_zen_meta.py` 로 어디서든 돈다.

## 2. 뷰어 — 탭 + 캐러셀 + 레이어 토글 + 스케일바

### 왜 바꿨나

그룹 화면이 세 덩어리(합성 사진 / 개체 표 / 갤러리)로 세로로 늘어서 있었다.
정작 하고 싶은 일 — **합성본에서 잡은 검출이 원본 사진에서도 맞는지 보는 것** —
은 갤러리에서 원본을 열면 검출 레이어가 사라져서 할 수 없었다.

### 무엇을 했나

- **탭**: `검출 화면` / `개체 목록`. 표가 화면을 밀어내지 않는다.
- **캐러셀이 갤러리를 흡수했다.** 사진 아래 가로 스트립에 합성본 · 깊이 맵 ·
  원본 프레임이 전부 걸린다. **hover 는 미리보기, 클릭은 교체.**
  미리보기는 이미지를 먼저 받아 두고 바꾼다(토큰으로 경쟁 상태를 막았다).
- **바뀌는 것은 `<img>` 의 src 뿐이다.** 검출 레이어·확대·이동·선택·교정 상태는
  DOM 에 그대로 남는다. 그래서 원본 프레임 위에 같은 마스크가 얹힌 채로 넘어간다.
- **우상단 bbox / mask 체크박스.** 끄더라도 `.box` 요소는 지우지 않는다 —
  **클릭 판정을 bbox 가 하므로 지우면 선택이 죽는다.** 테두리만 투명하게 하고
  선택·hover 표시는 남겼다. 안 보이는 것을 조작하고 있으면 헷갈린다.
  상태는 localStorage 에 남아 그룹을 옮겨도 유지된다.
- **우하단 스케일바.** `canvas` 가 아니라 `detview` 의 자식이라 확대/이동 변환을
  받지 않는다. 그래서 어디로 끌고 가든 늘 같은 자리에 있고, 길이만 다시 잰다.
  눈금은 1·2·5 계열로 떨어뜨린다(100% 에서 50 µm, 618% 에서 10 µm).
- 옛 갤러리(`stage` + `strip`)는 **삭제했다.**

### 알아 둘 것 — 원본 프레임의 마스크는 조금 어긋난다

합성 과정에서 ECC 로 프레임들을 서로 맞춘 뒤 합쳤으므로, **정렬 보정 전 원본**에
합성본 기준 좌표를 얹으면 그만큼 밀린다. 캐러셀에서 원본 프레임을 고르면
캡션에 그 사실을 적어 둔다. 검출이 맞는지 보는 데는 지장이 없지만,
픽셀 단위로 판단할 일이 생기면 기억해야 한다.

### 검증

브라우저가 없는 머신이라 **합성 데이터 + jsdom** 으로 확인했다.
2752x2208 짜리 가짜 시야 5장 + 합성본 + 깊이 맵 + 후보 10개/탈락 4개를 만들고,
Django 개발 서버에 실제로 붙여 페이지를 받아 눌러 봤다. **38개 항목 통과** —
캐러셀 hover/클릭, 사진을 바꿔도 레이어·배율·박스가 유지되는지, 탭 전환,
레이어 토글과 localStorage, 스케일바가 배율에 따라 바뀌는지, 기존 선택 기능이
살아 있는지. 싱글턴 그룹(합성본 없이 원본 한 장에 검출이 붙는 경우)도 따로 확인했다.

**Django 템플릿은 DEBUG 와 무관하게 캐시된다.** `Engine.__init__` 이 `loaders` 를
명시하지 않으면 항상 `cached.Loader` 로 감싼다. `runserver --noreload` 로 띄우면
템플릿만 고쳐도 반영되지 않는다 — 재시작해야 한다. 이것 때문에 한참 헤맸다.

## 3. 남은 것

003 §8 에서 달라진 것만 적는다.

1. **실제 ZEN XML 로 파서 확인** (위 §1). 데이터가 있는 장비에서 한 장이면 된다.
2. **원형(중심목) 기준 검증** — 여전히 1순위, 변함없음.
3. **재현율 실측** — 변함없음. 이번 캐러셀이 여기에 직접 쓰인다.
   원본 프레임을 오가며 봐야 "SAM 이 놓친 것" 을 셀 수 있다.
4. **텍스처 가드 방향 수정** — 손대지 않았다. 현재 장비에서는 실害 없음.
5. **116cm 그룹핑 임계값** — 변함없음.
