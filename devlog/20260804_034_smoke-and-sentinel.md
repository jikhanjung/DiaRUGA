# 안전망이 스스로를 알리게 한다 — 무결성 깃발과 `smoke`

**작성일** 2026-08-04
**근거** `.guides/web/data-safety.md` §2 · `operations.md` §4·§5 · `README.md`(표준 동사)

## 016·009 가 남겨 둔 두 줄

devlog 016 과 009 는 같은 문장으로 끝난다.

> - 표준 deploy 동사 5개(preflight/deploy/seed/smoke/rollback) 가 없다
> - 무결성 실패를 health 엔드포인트로 잇는 sentinel 이 없다. `/healthz` 는
>   백업 상태를 보지 않는다

이번에 그중 둘을 했다. 순서를 이렇게 잡은 이유가 있다. **다른 셋은 편의지만 이
둘은 안전망 자체다.** 009 에서 백업 게이트를 만들 때 이미 깨진 사본을 잡아내고
정리를 건너뛰게 해 두었는데, 그 사실이 **로그에만 남았다.** 그 로그를 읽는 사람이
없는 동안 게이트는 통과 여부와 무관하게 **아무에게도 말하지 않았다.**

가이드가 그것을 한 줄로 정리한다 (operations §5):

> A cron job that only logs its failure is "the illusion of a check."

## 깃발은 파일이다

`db_sentinel.py`. DB 옆에 `INTEGRITY_FAIL` 한 장을 놓고 `/healthz` 가 그것을 읽는다.

**DB 에 적지 않은 것이 요점이다.** 이 깃발이 서는 상황이 곧 DB 를 믿을 수 없는
상황이다. 깨진 DB 에 "DB 가 깨졌다" 고 적을 수는 없다.

자리는 `/srv/diatom/db/` 다. 그 디렉토리를 **통째로** 마운트해 둔 덕(016 에서
`/srv` 통마운트를 잘라 내며 정한 것)에, 호스트의 `backup_db.py` 가 세운 깃발을
컨테이너 안의 뷰어가 그냥 읽는다. 마운트를 디렉토리로 둔 값을 여기서 한 번 더 봤다.

### track 마다 한 줄이다

백업 track 이 둘이다 — 시간별 `backup_db.py`, 오프사이트 `sync_backup_nas.py`.
처음에는 깃발 하나를 공유하게 썼다가 되돌렸다. **나중에 성공한 track 이 남의
실패를 지운다.** NAS 사본이 깨졌다는 깃발을 다음 시간별 백업이 조용히 내리는 식이다.

그래서 줄마다 주인을 적고 자기 줄만 지운다.

```
2026-08-04T10:57:47	backup_db	사본을 뜨지 못했다 — database disk image is malformed
```

### NAS 가 안 붙은 것은 깃발이 아니다

`sync_backup_nas.py` 는 **검증 실패에만** 깃발을 세운다. NAS 가 안 붙은 것은 자료가
상한 것이 아니라 lane 이 잠깐 없는 것이다. 그것까지 세우면 NAS 점검 한 번에 뷰어가
degraded 가 되고 배포 smoke 가 막힌다. **가장 센 신호가 잡음에 묻히면 안 된다.**

오프사이트 가용성은 별도 신호가 맡을 몫으로 남겼다.

## `/healthz` — 세 상태, degraded 는 **200**

```json
{"status":"ok","version":"v0.1.19",
 "db":{"slide":10,"viewpoint":448,"detection":3823,"objectreview":5590},
 "integrity_flags":[],"backup":{"age_h":0.1,"max_age_h":null},"notes":[]}
```

| 상태 | 코드 | 뜻 |
|---|---|---|
| `ok` | 200 | 정상 |
| `degraded` | **200** | 서비스는 되는데 손상이 감지됐다 |
| `unhealthy` | 503 | DB 를 못 열거나 자료가 통째로 없다 |

**degraded 를 503 으로 두면 안 된다**는 것이 가이드에서 가장 반직관적인 대목이었다.
이유가 둘인데 두 번째가 실질적이다.

1. 503 은 "여기로 보내지 말라" 는 교통 신호다. 재시작으로 안 고쳐질 상태에 대고
   앞단이 호스트를 빼거나 계속 돌리게 만든다
2. **`deploy.sh` 의 기동 게이트가 200 을 기다린다.** degraded 에 503 을 내면
   "백업이 깨졌다" 는 신호가 **배포 자체를 못 끝내게** 만든다

배포를 세우는 판단은 `smoke.sh` 가 `status != ok` 로 한다. 신호와 조치를 갈랐다.

### 가볍게 유지한다

인증이 없는 엔드포인트다. 여기서 `integrity_check` 를 돌리면 누구나 부를 수 있는
DoS 표면이 된다. **비싼 검사는 백업이 한 번 하고**, 여기서는 그것이 남긴 파일을
읽기만 한다. 나머지는 `count(*)` 넷과 `stat` 하나다.

### 빈 DB 는 unhealthy 다

`slide` 가 0 이면 503 이다. 마운트가 어긋나 컨테이너가 빈 DB 를 새로 만들어도
"파일이 있는가" 검사는 통과한다 — 016 에서 마운트를 옮길 때 `rows > 0` 로 확인했던
그 함정이다(data-safety §8). 그때는 손으로 셌고, 이제 게이트가 센다.

### 신선도 게이트는 꺼 둔 채로 넣었다 (그리고 같은 날 켰다)

`DIATOM_BACKUP_MAX_AGE_H` 를 주면 백업이 낡았을 때 degraded 를 낸다. 처음에는
**꺼 둔 채로** 넣었다 — `backup_db.py` 가 cron 에 없어서(009) 켜면 늘 울리고,
**늘 울리는 경보는 안 보게 된다.**

그 자리에서 cron 까지 걸어 켰다. 아래 §"백업 lane 을 cron 에 걸었다" 참고.

## `smoke.sh` — 200 은 "떴다" 일 뿐이다

```
=== smoke 2026-08-04 11:05:54 ===
  ✓ /healthz 200
  ✓ status=ok
  ✓ 판 v0.2.0
  ✓ 자료 있음 (슬라이드 10 · 교정 5590)
  ✓ nginx 경유 http://127.0.0.1/diatom/ 200
```

기동 게이트가 이미 보는 1·2번 말고, **3·4번이 이 스크립트의 값어치다.**

- **판이 안 갈렸는데 갈린 줄 아는 것** — 026 에서 실제로 당했다. 폴러가 없는
  파이프라인 태그를 가리켜 4시간 반을 멈췄는데 로그는 "NAS 가 내려갔는가" 라고 적었다
- **빈 DB 를 물고도 멀쩡해 보이는 것** — 위의 §8 함정

불변식으로 `objectreview` 를 고른 이유는, 그것이 이 프로젝트에서 **다시 만들 수
없는 유일한 자료**이기 때문이다. 사진도 산출물도 다시 돌리면 나온다.

`deploy.sh` 가 마지막에 이것을 부른다. **점검 깃발을 먼저 내리고** 부른다 — 깃발이
서 있으면 nginx 를 거치는 길이 503 이라 정작 확인할 것을 못 본다.

**smoke 가 실패해도 되돌리지 않는다.** 새 판은 떠 있고, 무엇이 걸렸는지는 사람이
본다 (deployment §9 — 손상에 반사적으로 롤백하지 말 것).

## 게이트를 전부 터뜨려 봤다

009 에서와 같은 규칙을 지켰다 — *"Mutation-test each gate: remove it and confirm a
test fails."* 빈 픽스처로 초록이던 백업 회귀 테스트 이야기가 가이드에 있다.

| 터뜨린 것 | 나온 것 |
|---|---|
| 깃발을 손으로 세움 | `/healthz` degraded · **200** · smoke 실패(1건) |
| 깃발 내림 | ok |
| 빈 DB 를 물림 | unhealthy · 503 · "슬라이드가 0 이다" |
| 난수를 DB 인 척 | unhealthy · 503 · "file is not a database" |
| 판을 틀리게 기대 | "판이 다르다 — 기대 v0.9.9 · 실제 v0.2.0" |
| 신선도 문턱을 켬 | degraded |
| 깨진 원본 + `--keep 1` | 정상 사본 3개가 **살아남음** · `.corrupt` 증거 · 깃발 · 종료 1 |

## 그 김에 걸린 두 가지

**둘 다 게이트를 터뜨려 보지 않았으면 못 봤을 것들이다.**

### 1. 뜨다 만 사본이 정상 사본의 이름을 달고 있었다

깨진 원본으로 `backup_db.py` 를 돌리니 `diatom_20260804_105628.db` 가 남았다.
반쯤 쓴 파일인데 **이름이 정상 사본과 같다.** 그러면 두 가지가 어긋난다.

- 정리 glob(`diatom_*.db`)에 걸린다. **가장 새 파일이라 살아남고 멀쩡한 사본을
  하나 밀어낸다** — 백업이 백업을 지우는 형태다
- 오프사이트 track 이 그것을 스냅샷으로 알고 집어 간다

`sync_backup_nas.py` 는 NAS 쪽에서 이것을 이미 `.part` 로 풀어 두었다 — *"이름이
붙어 있으면 검증을 통과한 것"*. 같은 규칙을 로컬 track 에도 넣었다. 이제 제 이름은
검증을 통과한 뒤에 준다.

같은 절(§2)이 말하는 `.corrupt` 증거 남기기도 이때 함께 넣었다. 그 전까지는 검증에
실패한 사본이 그냥 `.db` 로 남아 있었다.

### 2. 부산물을 이름 바꾼 **뒤에** 쓸었다

`.part-wal`·`.part-shm` 이 남았다. 이름을 `.corrupt` 로 바꾼 다음 새 이름 기준으로
쓸어서, 옛 이름의 형제를 아무도 안 치우게 된 것이다. **연결을 먼저 닫고, 쓸고,
그 다음에 이름을 바꾼다** — 마지막 연결이 빠져야 `-wal`·`-shm` 이 정리된다.

## 사람이 읽는 문구도 게이트다

첫 `smoke.sh` 를 지금 뜬 컨테이너(옛 판, 평문 `ok` 를 낸다)에 대고 돌렸더니
**한 가지 원인이 세 줄의 다른 진단으로 번졌다.**

```
✗ status=읽지 못했다
✗ 판이 다르다 — 기대 v0.1.19 · 실제 없음
✗ 자료가 비었다 (슬라이드 -1 · 교정 -1) — DB 마운트를 볼 것
```

원인은 "응답이 JSON 이 아니다" 인데 **DB 마운트를 파라고 세 번 말한다.** 응답을
못 읽으면 거기서 멈추고 한 줄만 내게 고쳤다.

가이드에 같은 이야기가 있다 (deployment §9) — 낡은 FATAL 문구가 실행 코드를 고친
뒤에도 사람에게 계속 잘못된 조치를 시켰다. *"Audit the human-read strings too."*

## 백업 lane 을 cron 에 걸었다

009 이후로 계속 "아직 cron 에 걸지 않았다" 로 남아 있던 것이다. 깃발이 생기고 나서야
걸 값어치가 생겼다 — **그전에는 실패해도 아무도 몰랐다.**

```cron
20 * * * *  backup_db.py --keep 48            → /data3/diatom/logs/backup.log
40 4 * * *  timeout 600 sync_backup_nas.py --keep 720  → …/logs/nas-sync.log
```

세 track 이 이제 다 있다 (data-safety §1) — 배포 전 스냅샷(`deploy.sh`, 20개) ·
시간별 · 일별 오프사이트.

### 유지 개수는 관계에서 나왔다 — 그리고 옮길 때 뜻이 바뀐다

§6 이 말하는 관계는 `유지 개수 × 주기 ≥ 오프사이트 간격` 이다. 시간별 + 일별이면
24 가 나온다. **48 로 뒀다** — 손으로 뜬 "before-대공사" 스냅샷이 오프사이트로
건너가기 전에 로테이션에 밀려나지 않도록 2배 여유를 준 것이다(48 h ≥ 24 h).

**여기서 하나 걸렸다.** `sync_backup_nas.py` 의 `--keep 30` 은 009 에서 "한 달치" 로
정한 값이다. 그때는 스냅샷이 손으로 뜨는 것이라 하루 한두 개였다. **시간별이 되면
같은 30 이 30일이 아니라 30시간이 된다** — cron 을 거는 것만으로 오프사이트 보존이
30일에서 1.25일로 조용히 줄어드는 것이다.

720(= 30 × 24)으로 바꿨다. 값이 아니라 **관계를 주석에 적어 두는 이유**가 이것이다.
숫자만 있으면 주기가 바뀔 때 아무도 그것이 낡았다는 것을 모른다.

NAS 는 18 T 가 남아 있어 용량은 문제가 아니다(지금 44개 1.4 GB). §6 이 짚은 대로
**유지 개수를 디스크 상한 용도로 겸하게 두지 않는다** — 그건 별개 문제다.

### 신선도 문턱은 3 이다

009 의 `--stale-hours` 는 26 이었다. 그건 일별을 전제한 값이다. 시간별로 뜨는
지금은 **3** 이 맞다 — 두 번 연달아 걸러야 울린다.

이 신호가 잡는 것이 둘이다. 시간별 백업이 **멈췄거나**, 무결성 게이트가 채택을
**막고 있거나**. 뒤엣것은 깃발이 이미 즉시 알리므로 겹치지만, 이쪽은 **배포와
무관하게** 돈다 — §4 가 말하는 "배포가 뜸하면 탐지도 뜸해지는" 구멍을 메운다.

### 게이트를 또 한 번 잘못 터뜨렸다

켠 뒤에 확인한다고 가장 새 사본 **하나**의 시각을 4시간 전으로 미뤘는데 `ok` 가
나왔다. `/healthz` 는 mtime 의 **최대값**을 보므로 그 다음 파일이 새것이 됐을 뿐이다.
게이트가 아니라 시험이 틀렸다.

사본 44개의 mtime 을 전부 미뤄서 볼 수도 있었지만 **그 시각 자체가 신호**라 되돌릴
수 없다. 임시 디렉토리에 사본 하나를 두고 확인했다 — `4.0 > 3.0` → degraded.

*안전망을 시험하다 안전망을 상하게 하지 않는다.*

## 아직 안 한 것

- 표준 동사 셋이 남았다 — `preflight` · `rollback` · `seed`("(none)" 선언)
- 오프사이트 lane 가용성(NAS 가 안 붙음)을 나르는 신호가 없다. 깃발은 **자료가
  상했을 때만** 세운다 — 섞으면 NAS 점검 한 번에 배포가 막힌다
- `integrity_check` 는 **스키마 부트스트랩 실패를 못 잡는다**(§11). 009 에서 손으로
  리허설했지만 게이트는 없다
- 손으로 뜬 스냅샷과 시간별 스냅샷이 **같은 이름 규칙으로 같은 통에** 있다.
  로테이션이 사람이 고른 복구 지점을 밀어낼 수 있어 48 로 여유를 뒀지만, 갈라 두는
  편이 옳다
