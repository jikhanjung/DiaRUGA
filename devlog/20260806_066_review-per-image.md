프레임마다 하나 — YOLO 는 합성본이 아니라 원본 프레임을 보므로 `yolo-3차` 를

## 1. 지금 코드가 전부 "시야마다 하나" 를 전제하고 있었다

그리고 **운영에 그 상태가 아직 없어서 전부 통과한다.** 그것이 이 단계의 성격이다 —
고장을 고치는 것이 아니라 **아직 안 난 고장의 자리를 세는 것**이다.

세 자리였다.

```python
det = next((d for d in vp.detections.all() if d.is_current), None)   # 아무거나
reviews = {o.mask_key: o for o in vp.object_reviews.all()}            # 안 거른다
by_key = {c.mask_key: c for c in Candidate.objects.filter(
    detection__viewpoint=vp, detection__is_current=True)}             # 시야 전체
```

- **첫 줄** — 화면이 그릴 검출과 저장이 앉힐 이미지를 **아무거나** 집는다
- **둘째 줄** — 합성본에서 한 판단이 프레임 화면에 얹혀 보인다. 같은 시야라
  좌표계가 같아서 `mask_key` 가 실제로 맞는다(프레임끼리 45% 겹친다는 실측이
  P06 에 있다)
- **셋째 줄** — **프레임 A 의 키가 프레임 B 의 화면에서 통과한다.** 삭제 범위는
  이미지로 좁혀져 있으므로 엉뚱한 이미지의 키로 만든 행이 남는다

셋 다 예외가 안 나고 **그럴듯한 화면**이 나온다.

## 2. 이름이 아니라 id 로 짚는다

화면이 "어느 이미지를 보고 있다" 를 서버에 말해야 한다. 무엇으로 짚는가.

**프레임 이름은 슬라이드끼리 겹친다** — 카메라 일련번호라 같은 날 이어 찍으면
번호대가 이어지고, 260803 두 슬라이드에서 143종이 겹쳤다. 053 이 정확히 그
자리에서 났다: 싱글턴 시야 12개가 남의 슬라이드를 열고 있었고 "검토 완료" 만 누른
빈 payload 하나가 남의 교정 7건을 지웠다.

**이름은 겹쳐도 주소는 안 겹친다.** `image` 는 pk 로 보내고, 서버가 **그 id 가 이
시야의 것인지** 다시 확인한다.

**못 찾으면 조용히 대표에 앉히지 않고 거절한다.** 시험이 그것을 잡는다 — 옛
코드는 남의 이미지를 짚어도 **200 을 내고 저장한다.**

```
FAIL 남의_이미지를_짚으면_거절한다
     AssertionError: 200 != 409 : {"ok": true, … "labels": 1}
```

"저장이 성공으로 보이는데 엉뚱한 자리에 앉는" 갈래다.

## 3. 집계 — 부풀면 보고서에 실린다

검토는 모든 이미지에서 하되 **집계는 시야마다 대표 이미지 하나**에서 낸다
(P09 5.3). 다 세면 같은 규조각이 **합성본 1 + 프레임 3.6 장에서 4.6번** 세어진다.
**학습 자료로는 맞고 계측 통계로는 틀리다.**

`_SUMMARY_SQL`·`_COVER_SQL` 에 `rep` CTE 를 두었다.

```sql
WITH rep AS (
    SELECT d.id AS det_id, d.viewpoint_id, d.image_id, run.batch_id,
           ROW_NUMBER() OVER (
               PARTITION BY d.viewpoint_id
               ORDER BY CASE i.kind WHEN 'stack' THEN 0 ELSE 1 END, d.id) AS rn
      FROM viewer_detection d ... WHERE d.is_current)
```

고르는 규칙은 `representative_detection` 과 **같아야 한다** — 규칙이 둘이 되면
목록과 상세 화면의 숫자가 어긋나고, 그 어긋남은 아무 예외도 안 낸다.

**교정을 묶음으로도 맞춘다.** `(image, mask_key)` 만으로 맺으면 묶음을 갈아탄 뒤
같은 이미지에 남은 **옛 회차의 교정이 새 후보에 붙는다.** 키가 겹칠 확률은
낮지만(엔진이 다르면 `exact` 가 0%다) 겹치면 `LEFT JOIN` 이 행을 불려 개수가
조용히 는다. `IS` 로 비교하는 것은 사람이 그린 개체가 `batch IS NULL` 이라서다.

`detected_groups` 는 **검출 수가 아니라 시야 수**다. 분자는 대표 하나만 세는데
분모가 4.6배가 되면 시야당 평균이 그만큼 작아진다.

### 값이 안 바뀐 것을 확인하는 편이 더 어렵다

운영 사본에서 옛 SQL 과 새 SQL 을 나란히 돌렸다.

```
옛 SQL  196.4 ms · 행 62
새 SQL  190.6 ms · 행 62
값이 같은가: 같다        남는 개체 합계: 옛 2151 · 새 2151
```

62행이 전부 같고 시간도 같다 — `rep` 가 후보를 오히려 줄인다.

## 4. 시험이 운영에 없는 상태를 먼저 만든다

`add_frame_detections(vp)` 를 픽스처에 더했다. 프레임마다 현재 검출을 하나씩 더
만들어 **시야 하나에 현재 검출 넷**인 상태를 세운다.

**없으면 갈아타는 날 한꺼번에 드러난다.** 그 날 잃는 것은 재생성 불가한 교정이다.

되살려서 잡히는 것을 봤다 — 옛 모습으로 되돌리니 **9개가 섰다.**

```
데이터 층 (5)   합성본 교정이 프레임 화면에 얹혔다 : 1 != 0
               프레임 화면의 저장이 합성본 교정을 지웠다
               남의 이미지를 짚으면 거절한다 : 200 != 409
집계 (4)        프레임 검출이 붙자 개체 수가 늘었다 : 9 != 3
               표지의 개체 수가 프레임만큼 부풀었다 : 9 != 3
               평균의 분모는 시야 수다 : 4 != 1
               옛 묶음의 분류가 이번 회차 집계에 섞였다 : 3 != 0
```

### 픽스처의 헬퍼도 같은 전제를 갖고 있었다

`World.detection()` 과 `add_review()` 가 `vp.detections.get(is_current=True)`
였다. 프레임 검출을 올리자 `MultipleObjectsReturned` 로 섰는데, 그것은 **시험이
못 쓰게 된 것이지 코드가 틀렸다는 말이 아니라** 무엇이 문제인지를 가린다.

셋이 `data.representative_detection` 하나를 보게 했다. **규칙이 갈라지면 시험이
화면과 다른 것을 증언한다.**

## 5. 화면 — 배관은 거의 다 있었다

사용자가 "화면은 이미 거의 되어 있는 거 아냐?" 라고 물었고, 보니 맞았다.
`/engine/` 이 **같은 이유로 이미 캐러셀로 판을 갈아 끼우고 있었다.**

```
_shots.html      판마다 data-detkey 를 이미 붙인다
_detection.html  swapDet(s) 이 그 열쇠로 개체를 갈아 끼운다
engine_viewpoint shot_dets 를 만들어 넘긴다
```

검토 화면이 그것을 안 쓰고 있었을 뿐이다. **프레임마다 판을 따로 그리면 세로로
늘어서서 같은 자리에서 비교할 수가 없다** — "이 규조각이 어느 초점면에서
잡혔나" 는 자리가 안 움직여야 보인다.

### 진짜 일은 저장이었다

`/engine/` 은 읽기 전용이라 **그릴 것만** 넘기면 됐다. 검토 화면은 판마다 교정이
따로다.

- `shot_dets` 에 교정 상태(`gone`·`accepted`·`labels`·`notes`)와 **`image`** 가
  함께 실린다. `image` 가 빠지면 **화면은 프레임을 보여 주면서 저장은 대표
  이미지로 간다** — 예외도 경고도 없다
- 판마다 상태를 기억한다(`shotState`). 안 보낸 교정을 들고 판을 옮길 수 있다
- **처음 열린 판도 등록해 둔다.** 안 하면 옮겼다 돌아왔을 때 서버 값으로
  되돌아가 방금 한 일이 사라진다
- 판을 떠나기 전에 `flushSave()` · 고른 개체는 판을 안 넘어간다(번호로 짚는다)

### 미리보기가 저장 대상을 움직이고 있었다

`preview(i)`(hover)가 `swapDet` 을 부른다. 예전에는 검토 화면에서 첫 줄에
빠져나가 **무해했다.** 이제는 커서가 지나가는 것만으로 교정 상태와 저장 대상이
따라 움직인다 — **판을 고르지도 않았는데 그 판으로 저장이 나가는 길**이다.

미리보기는 **그리기만** 바꾸게 갈랐다(`swapDet(s, false)`). 고르는 것은
`commit` 뿐이고, `unpreview` 는 고른 판의 그림으로 되돌린다.

### 처음 열리는 판은 집계의 대표와 다른 일이다

집계는 밀도를 위해 **늘 합성본**을 골라야 한다. 화면은 사람에게 무엇을 먼저
보일지를 정한다 — 합성본에 개체가 없으면 **개체가 가장 많은 판**으로 물러난다.
`engine_viewpoint` 가 실측으로 정한 규칙 그대로다(그 화면에서 여러장 시야 317개
중 247개가 합성본이 아닌 판에서 열렸다). YOLO 는 합성본 검출이 314개로 시야
355개보다 적어 **그 상태가 41개 난다.**

### 브라우저로만 잡히는 것들

시험 6개를 붙였다. **3겹으로는 절대 안 걸린다** — 서버가 내는 HTML 은 판
하나뿐이고 갈리는 것은 브라우저 안에서다. 배선을 끊어 보니 잡힌다:
`curImage` 를 끊으면 2개, 첫 판 등록을 끊으면 1개.

그 길에 둘을 배웠다.

- **`{# #}` 를 여러 줄로 썼다.** CLAUDE.md 에 적혀 있는 그대로 화면에 샜고,
  템플릿 시험이 잡았다(`test_템플릿_문법이_화면에_새지_않는다`)
- **판 단추를 누르면 페이지가 스크롤된다.** playwright 가 단추까지 스크롤하면서
  사진이 뷰포트 위로 밀려나고(svg y: 105 → −268), 그 뒤의 클릭이 화면 밖을
  찍는다. "프레임 판에서는 우클릭 메뉴가 안 뜬다" 는 **없는 고장을 쫓을
  뻔했다** — 시험이 만드는 함정이다

## 6. 내보내기 형식 3

형식 2 는 시야 하나에 `(이미지, 묶음)` **하나**를 전제했고, 깨진 DB 를 만나면
**쓰지 않고 멈췄다.** 갈아타는 순간 감사 기록이 멈춘다는 뜻이다.

```json
"n_images": 2, "n_objects": 7,
"images": [ {"image": …, "kind": "stack", "batch": "sam2-전수",
             "n_objects": 5, "objects": [ … ]}, … ]
```

- **이미지도 묶음도 id 가 아니라 이름·경로로 적는다.** 감사 기록은 두 DB 를
  견주는 물건이라 저장소마다 달라지는 id 를 적으면 diff 가 거짓말을 한다
- **묶음 이름은 그룹 머리에 한 번.** 개체마다 실으면 diff 만 시끄러워진다
- **차례를 못 박는다** — 합성본 먼저, 프레임은 경로순. dict 의 순서에 기대면
  DB 행 순서가 바뀔 때마다 파일 전체가 다시 써져 diff 가 자료 변화를 못 보인다
- `done`·`note` 는 여전히 시야당 하나다 (P06 §8)

**아무것도 안 잃었다.** 운영 사본에서 형식 2 와 3 을 나란히 내보내 대조했다 —
개체 7,472건의 열쇠 집합이 같고 내용이 다른 것 0, 파일 508개의 `done`·`note` 도
같다. `--check` 도 통과한다.

시험 7개. 묶는 열쇠에서 `batch` 를 빼면 1개, 정렬을 빼면 1개가 선다.

> **시험이 사본을 떠서 넘기려다 섰다** (2분 넘게 안 끝났다). 시험 하나가 열어 둔
> 트랜잭션 위에서 sqlite 의 backup API 가 잠금을 기다린다. 살아 있는 연결을
> 그대로 넘기고 `row_factory` 만 되돌린다 — 켜 둔 채로 두면 **이 시험이 아니라
> 다음 시험이 깨진다.**

## 7. 남은 것

- **사람이 그린 개체는 아직 집계에 안 잡힌다.** `Candidate` 가 없어서 후보 기반
  SQL 이 못 본다. 3단계에서 함께 본다
- **운영 반영은 아직이다.** 0단계와 함께 뷰어·파이프라인 이미지를 올린 뒤에
  마이그레이션을 건다 (065 §9)
- 그다음이 2단계(그리는 근거를 `Candidate ∪ ObjectReview` 로)다
