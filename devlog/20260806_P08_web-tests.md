## 3. 픽스처 — 이 계획의 진짜 비용

모델이 16개고 그래프가 깊다.

```
Site → Locality → Sample → Slide → Viewpoint → Frame → Image → Detection → Candidate
                                        ↓                          ↓
                                 ViewpointReview            ObjectReview (mask_key 로)
```

**`web/viewer/tests/factories.py` 하나를 먼저 만들고 나머지가 전부 그것을 쓴다.**
매 시험이 자기 자료를 손으로 세우면 픽스처가 시험보다 길어지고, 스키마가 바뀔 때
전부를 고쳐야 한다.

정하는 것 셋.

**3.1 최소 그래프를 만드는 함수 하나 + 덮어쓰기.** `make_slide(slug="rs23")` 가
`Site` 부터 `Candidate` 까지 한 벌을 세우고, 시험이 필요한 것만 인자로 흔든다.
053 을 재현하려면 `make_slide(slug="a")` · `make_slide(slug="b")` 를 **같은 프레임
이름으로** 부를 수 있어야 한다.

**3.2 이미지 파일은 임시 디렉토리에.** 뷰가 디스크에서 사진을 읽는다
(`DATA_ROOT` · `IMAGE_DIRS`). `override_settings` 로 `tmp_path` 를 물리고 1×1
PNG 를 심는다. **`/data3` 에도 `/nfs` 에도 절대 붙지 않는다.**

**3.3 `OUTCROP_DIR` 은 없는 경로로 둔다.** "NAS 가 안 붙은 날에 지점 페이지가
500 이 되면 안 된다"(settings.py) — 그 갈래가 기본으로 시험된다.

## 4. 도구 — pytest 를 쓰지 않는다

**Django 기본 러너(`manage.py test`)로 간다.**

`requirements-web.txt` 가 "뷰어는 Django 와 PIL 만 쓴다" 는 경계를 지키고 있고
그것이 뷰어 이미지를 200 MB 대로 유지한다(P03). pytest-django 를 끌어들여
얻는 것(픽스처 문법·파라미터화)보다 그 경계가 흐려지는 값이 비싸다. 지금
필요한 시험은 전부 `TestCase` 로 쓸 수 있다.

개발 의존은 **`requirements-dev.txt`** 로 따로 뺀다 — 4겹의 `playwright` 하나뿐이고,
**어느 컨테이너 이미지에도 넣지 않는다**(`python-docx` 를 그렇게 두었다).

### 4.1 운영 DB 를 만지지 않는다는 것을 시험이 스스로 확인한다

Django 가 sqlite 에는 알아서 인메모리 테스트 DB 를 준다. **그래도 assert 를
넣는다.** 이 프로젝트는 그 가정이 한 번 깨지면 다시 만들 수 없는 자료를 잃는다
(교정 6,700여 건). 공용 베이스 `TestCase` 의 `setUpClass` 에서:

```python
name = str(connection.settings_dict["NAME"])
assert name == ":memory:" or "test" in Path(name).name, name
```

HANDOFF 3.3 이 "시험 코드에 `assert` 로 사본인지 확인하는 줄을 넣는다" 고 적어
둔 것과 같은 것을, 사람이 기억하는 대신 **베이스 클래스가 하게** 한다.

### 4.2 마이그레이션은 실제로 돌린다

`--keepdb` 나 마이그레이션 건너뛰기를 기본으로 쓰지 않는다. **"`NOT NULL` 칸을
더할 때 `db_default` 를 함께 준다"**(CLAUDE.md)는 규칙이 지켜졌는지는 마이그레이션이
실제로 돌아야 보인다.

### 4.3 어디서 도는가

**저장소에서 호스트 venv 로 돈다.** DB 규약(`dbrun.sh`)이 막으려는 것은 "같은
파일을 두 벌의 환경이 만진다" 인데, 시험은 **자기 DB 를 새로 만들고 끝나면
버린다** — `backup_db.py`·`export_review.py` 와 같은 자리다. 컨테이너를 요구하면
아무도 안 돌린다.

## 5. CI — 뷰어만 GitHub 으로 간다

저장소가 public 이라 GitHub Actions 가 무료다. `.github/` 자체가 아직 없다.

**어디서 무엇을 하는지를 먼저 못 박는다** (사용자 판단 2026-08-06).

```
GitHub:  push → 시험 → (통과하면) 뷰어 이미지 build/push       234 MB
여기:    파이프라인 이미지 build/push                          7.2 GB
서버:    deploy.sh <태그>  ← 사람이 부른다                     (지금 그대로)
```

### 5.1 뷰어 이미지는 GitHub 에서 굽는다

234 MB 고 의존성이 Django·pillow·gunicorn 셋뿐이라 1~2분이다. 그리고 진짜
이득은 크기가 아니라 순서다 — **바로 앞 job 이 그 코드로 시험을 다 돌린 뒤에
굽는다.** 지금은 "시험 없이 굽고 배포하고 smoke 로 확인" 인데, 그것이 "시험을
통과한 것만 이미지가 된다" 로 바뀐다.

### 5.2 파이프라인 이미지는 GitHub 에서 굽지 않는다

**구워도 확인할 수가 없다는 것이 결정적이다.** GitHub 러너에는 GPU 가 없어
`segment_diatoms.py` 를 한 번도 못 돌린다. "빌드는 됐는데 도는지는 모르는
7.2 GB 이미지" 를 Docker Hub 에 올리는 것이 되고, 그것은 지금보다 나쁘다 —
여기서는 최소한 `docker compose run --rm pipeline` 을 한 번 돌려 볼 수 있다.

나머지 셋은 그 다음이다.

- **캐시가 안 맞는다.** GHA 캐시는 저장소당 10 GB 인데 torch 층 하나가 6 GB 라
  두 벌이 안 들어간다 — 사실상 매번 콜드 빌드다. 여기서는 `Dockerfile.pipeline`
  이 의존성을 코드보다 먼저 깔아서(그러려고 `diaruga-base` 를 FROM 안 했다)
  코드만 고치면 마지막 층만 다시 만든다. 초 단위 대 8분
- **업로드가 붙는다.** 콜드 빌드 + 7.2 GB push 면 커밋마다 20~30분이다
- **러너 디스크가 빠듯하다.** `ubuntu-latest` 의 `/` 여유가 14 GB 대다

GitHub 쪽으로 끌리는 이유가 하나 있다 — **사내망 TLS 가로채기가 없다**
(`download.pytorch.org`). 그런데 그건 이미 `deploy/ca/` + `PIP_CERT` 로
Dockerfile 안에 해결돼 있어 위 넷을 감수할 값이 아니다.

### 5.3 대신 의존성이 썩는 것만 주기적으로 본다

파이프라인 의존성이 조용히 상하는 것(휠이 yank 되거나 인덱스에서 사라지는 것)은
5.2 로는 안 잡힌다 — 지금은 **다음에 구울 때** 알게 된다. 굽지 않고 그것만 본다.

**두 조각으로 나눈다. 한 덩어리로 하면 안 싸다.**

```bash
# 1) 휠 — 인덱스 둘 다 PEP 658 을 내주므로 메타데이터만 읽는다. 30초 안쪽
pip install --dry-run --ignore-installed \
    --extra-index-url https://download.pytorch.org/whl/cu126 \
    -r <(grep -v '^SAM-2' requirements-pipeline.txt)

# 2) git 핀 — 그 SHA 가 아직 있는가. 요청 하나
curl -sfo /dev/null https://api.github.com/repos/facebookresearch/sam2/commits/<sha>
```

**SAM-2 를 빼는 것이 요점이다.** 그 줄은 git 의존성이라 pip 이 메타데이터를
만들려고 격리 빌드 환경을 세우는데, `sam2/pyproject.toml` 의
`[build-system] requires` 에 `torch>=2.5.1` 이 있어 **`--dry-run` 인데도 몇 GB 를
받는다.** 그런데 핀한 SHA 는 내용이 안 바뀌므로 거기서 실제로 깨지는 것은
"저장소가 없어졌다 · 커밋이 GC 됐다" 뿐이고, 그것은 요청 하나로 확인된다.

확인해 둔 것 (2026-08-06): PyPI 와 `download.pytorch.org` 둘 다
`data-core-metadata` 를 내준다 — 1번이 싼 근거가 그것이다. 그리고 지금 핀은
멀쩡하다(`torch-2.13.0+cu126-cp312-cp312-manylinux_2_28_x86_64.whl` 이 있고
cu126 의 최신 계열이 2.13.0 이다).

**이것이 못 잡는 것을 적어 둔다** — `apt-get` 층, CA 인증서 단계, 실제 설치가
되는지, 그리고 **GPU 에서 도는지.** 굽기 전에 알 수 있는 것을 미리 아는 것이지
빌드의 대체가 아니다.

### 5.4 CI 는 배포하지 않는다

`deploy.sh` 는 사람이 부른다. 거기에 스냅샷·기동 게이트·smoke 가 붙어 있고
(`.guides/web/`), 그 판단을 자동화하면 규약이 지키려던 것이 사라진다.

### 5.5 셀프호스티드 러너는 쓰지 않는다

떠오를 만한 선택지라 적어 둔다. 이 서버에 러너를 붙이면 GPU 도 쓰고 캐시도
따뜻하지만, **저장소가 public 이라 안 된다** — 누구든 fork 에서 PR 을 열면 그
워크플로가 이 서버에서 임의 코드로 돈다. 그 서버에 `DiaRUGA.db` 가 있다.

### 5.6 job 구성

- `ubuntu-latest` · python 3.12 · `requirements-web.txt` + `requirements-dev.txt`
- 1~3겹은 push 마다. **4겹(브라우저)은 따로 job** 으로 두고 실패해도 다른 것을
  막지 않게 한다 — 처음에는 헤드리스 환경 차이로 흔들릴 것이다
- **자료도 DB 도 저장소에 없다.** 시험이 전부 픽스처를 세우므로 문제가 안 된다.
  이것이 픽스처를 제대로 만드는 또 하나의 이유다

`smoke.sh` 는 그대로 둔다. **역할이 다르다** — CI 는 코드가 맞는지를 묻고,
smoke 는 뜬 것이 사는지를 묻는다. 061 에서 확인했듯 자료가 바뀌는 자리의 검사도
smoke 몫이다.

## 7. 정하지 않고 남기는 것

- **파이프라인 스크립트(`segment_diatoms.py` 등)는 이번 범위 밖이다.** GPU·SAM2
  가 필요하고 CI 에서 못 돈다. `judge.py` 는 순수 함수라 1겹에 들어온다
- **눈에 보이는 것 둘은 여전히 자동으로 못 본다** (HANDOFF 3.3) — 색 대비,
  좁은 칸에서 글자가 넘치는가. 판을 낼 때 **"무엇이 안 덮였는지" 를 함께 적는
  것**이 지금도 최선이다
- **커버리지 측정은 안 붙인다.** 숫자가 목표가 되면 §1 이 무너진다
