## 왜 지금인가

두 가지가 같은 날 겹쳐서 드러났다.

**하나. 환경이 장비 한 대에 묶여 있다.** 오늘 서버를 바꿨더니 뷰어가 안 떴다.
`ALLOWED_HOSTS` 에 옛 장비의 주소(`172.16.112.150`)와 이름(`jikhanserver`)이
박혀 있었기 때문이다. 이건 증상이고, 같은 뿌리에서 나온 것이 더 있다:

- venv 는 `~/venv/diatom` 인데 `run_batch.sh` 는 `.venv/bin/python` 을 부른다
- `requirements.txt` 에 Django 가 빠져 있다 (뷰어가 Django 5.2 로 도는데도)
- 새 환경을 만들려면 이 함정들을 하나씩 다시 밟아야 한다

**둘. 촬영이 계속된다.** NAS `/nfs/temp-share/DiatomPhotos/` 에 지금은 `260729/`
하나뿐이지만 슬라이드 폴더가 계속 올라온다. 그때마다 사람이 붙어서 그룹핑·합성·
검출을 돌릴 수는 없다.

P01 §1 이 이미 이 흐름을 그려 뒀고, `Slide.state` 상태기계
(`pending`/`copying`/`processing`/`done`/`failed`)와 `discovered_at`·`copied_at`·
`processed_at` 이 **스키마에 이미 들어와 있다**(`models.py:99-116`).
그때 "NAS 로 폴더가 계속 들어오면 상태 관리가 필요해진다" 고 적어 둔 것을 이제 쓴다.
마이그레이션 없이 쓸 수 있다.

## 먼저 못 박을 것 — 자동화의 전제

**지금 상태로 주기 실행을 붙이면 사람의 교정 2,400여 건이 날아간다.**

파이프라인 4개 중 `refilter.py` 만 DB 를 쓰고 나머지 셋은 아직 JSON 을 쓴다
(P02 6단계 진행 중). 그래서 검출 뒤에 `import_json.py` 를 한 번 돌려야 뷰어에
반영되는데, 이 스크립트는 **`Candidate` 를 지우고 다시 만든다.** 주기 실행
루프에 넣는 순간, DB 에서만 한 교정이 옛 JSON 값으로 조용히 되돌아간다.

그래서 **P02 6단계 완료가 자동화의 전제**다. 순서를 뒤집지 않는다.

## 구조

```
NAS (ro)                        /data3/diatom (rw)              컨테이너
/nfs/temp-share/DiatomPhotos/ ─▶ photos/<슬라이드>/  ─┐
                                 stacked/            ├─▶ web       (Django, 9090, 상주)
                                 out/                │   pipeline  (CUDA+SAM2, 일회성)
                                                     │
저장소  diatom.db ────────────────────────────────────┘
```

`/data3` 를 고른 이유: 7.3 T 에 6.3 T 여유이고 ext4 이며, 이미 `/data3/epma` 가
같은 용도로 쓰이고 있다(phyloserver 선례). `/` 는 74% 차 있어 슬라이드당 1 GB 가
쌓이면 곧 문제가 된다.

### 반드시 지킬 것 둘

**1. `diatom.db` 는 파일이 아니라 디렉토리째로 bind mount 한다.**
WAL 은 `-wal`·`-shm` 형제 파일을 만든다. 파일 하나만 물리면 그 형제들이 컨테이너
내부 fs 에 생겨 **호스트 파이프라인과 컨테이너 뷰어가 WAL 을 공유하지 못한다.**
같은 DB 를 보는 줄 알았는데 아닌 상태가 된다 — 조용해서 더 위험하다.

**2. DB 는 로컬 ext4 에만 둔다.** NFS 위의 SQLite 는 잠금이 깨진다.

### 컨테이너는 `1000:1000` 으로 실행한다

root 로 돌면 `diatom.db` 의 소유자가 바뀌어 호스트의 `backup_db.py`·`check_db.py`
가 못 쓰게 된다. 백업이 유일한 안전망인 상황에서 그건 받아들일 수 없다.

## 버린 선택지

**상주 GPU 워커.** SAM2 를 한 번 올려두고 재사용하면 모델 로딩 시간을 아낀다.
버렸다 — PyTorch 의 캐싱 할당자는 해제한 VRAM 을 드라이버에 돌려주지 않아서
**한 번 찍은 최대치를 프로세스가 죽을 때까지 물고 있다.** 3060 Ti 는 8 GB 뿐이고
`ollama` 가 같은 카드를 쓴다. `restart: unless-stopped` 까지 붙으면 리부팅해도
계속 잡혀 있다.

대신 **일회성 실행**(`docker compose run --rm`)으로 간다. 오늘 확인한 것:
`--gpus all` 로 컨테이너를 띄워도 안에서 CUDA 컨텍스트를 만들지 않으면
**VRAM 은 0 이다**(띄우기 전 77 MiB → 띄운 후 77 MiB). 장치 노드만 보일 뿐
메모리를 예약하지 않는다. 지금 호스트 venv 로 하던 것과 점유 거동이 같다.

**컨테이너 안에 cron 을 넣는 것.** phyloserver 를 참고하려 했으나, 열어 보니
**컨테이너 안에 cron 이 아예 없었다.** `crontab` 바이너리도 없고 `/nfs` 도
마운트되어 있지 않다 — EPMA 스캔은 사람이 호스트에서 직접 돌리는 관리 커맨드다.
이 장비에서 실제로 도는 NAS cron 은 `onychomonitor/make_video.sh` 하나뿐이다.

**컨테이너에 `docker.sock` 을 물려 스스로 GPU 컨테이너를 띄우게 하는 것(DooD).**
버렸다 — 소켓을 주는 것은 사실상 root 를 주는 것이다. 트리거만 호스트 cron 이
맡고 **실제 작업은 전부 컨테이너 안에서** 돌게 한다. 목적은 그것으로 달성된다.

**이미지 하나로 합치기.** 뷰어까지 CUDA 이미지(~6 GB)에 넣으면 단순하지만,
뷰어 한 줄 고칠 때마다 6 GB 를 다시 굽는다. `diatom-base`(코드+Django, ~200 MB)
→ `diatom-pipeline`(base 를 FROM, torch cu126 + SAM2)로 층을 나눈다.

**NAS 를 직접 읽고 처리하기(복사 없이).** 버렸다 — 994 MB 짜리 슬라이드를 합성
단계에서 반복해 읽으면 NFS 왕복이 비싸고, `hard` 마운트라 NAS 가 흔들리면 처리
중인 작업이 통째로 멈춘다. EPMA 선례대로 로컬로 복사한 뒤 처리한다.

**inotify 로 새 폴더 감지.** P01 §1 이 이미 못 박았다 — NFS 에서 inotify 는
믿을 수 없다. 폴링으로 간다.

**`diatom.db` 를 `/data3` 로 옮기기.** 이번엔 보류했다. 교정이 재생성 불가라
이동 단계를 최소화한다. `DIATOM_DB` 환경변수가 이미 있으니 나중에 언제든 옮길 수 있다.

## 단계

### 0. 안전망
`backup_db.py --note before-dockerize`, `requirements.txt` 에 Django 추가,
`/data3/diatom` 생성(루트 소유라 sudo 한 번 필요).

### 1. 데이터를 `/data3` 로, `DATA_ROOT` 를 환경변수로
뷰어는 모든 경로를 단일 `DATA_ROOT` 기준 상대경로로 다루고 `IMAGE_DIRS` 를
화이트리스트로 쓴다(`data.py:661-673`). **이 구조를 그대로 두고 뿌리만 옮긴다** —
경로 해석 코드는 건드리지 않는다.

`260729/` 는 `photos/` 로 이름을 바꾼다. 날짜가 아니라 용도가 이름이어야
슬라이드가 계속 들어와도 맞다. `Slide.image_dir` 이 `260729/RS23-GC03 71cm` 꼴이라
데이터 마이그레이션이 한 번 필요하다.

### 2. 컨테이너화 (동작은 그대로)
`deploy/` 아래에 `Dockerfile.base`, `Dockerfile.pipeline`, `entrypoint-web.sh`,
`docker-compose.yml`. `requirements.txt` 를 web/pipeline 둘로 가른다.
`pipeline` 은 `profiles:` 로 묶어 `compose up` 에 딸려 뜨지 않게 한다.

이 단계에서는 **기능을 하나도 바꾸지 않는다.** 뷰어가 컨테이너에서 같은 화면을
내는지만 본다.

### 3. P02 6단계 완료 — 가장 크고 가장 위험하다
HANDOFF §4 가 정한 순서를 그대로 따른다: `focus_stack.py` → `segment_diatoms.py`
→ `group_focus_series.py`. 순서를 바꾸지 않는다 — 재그룹핑이 `Viewpoint` 를
재편하면 그 아래 검출·교정이 통째로 어긋나므로 그룹핑이 마지막이다.

`segment_diatoms.py` 에서 **`is_current` 이동과 교정 재바인딩은 반드시 한
트랜잭션**이어야 한다. 중간에 끊기면 뷰어가 "교정이 붙지 않은 새 검출"을 보여준다.

### 4. NAS 스캔·인제스트
phyloserver 의 EPMA 커맨드에서 가져올 것은 알고리즘이 아니라 **정찰과 반입을
나눈 것**이다:

- `scan_nas` — 읽기 전용, DB 를 건드리지 않고 리포트만. 기존 `Slide.image_dir`
  집합과 대조해 새 폴더만 가려낸다
- `ingest_nas` — `--dry-run` 먼저. 복사하고 `Slide` 행을 만들며 상태를 옮긴다

**업로드 완료 판정**(P01 §1): 촬영 중인 폴더를 건드리면 안 된다. 파일 개수와
최대 mtime 이 일정 시간 그대로면 완료로 본다.

**이미지와 `*_metadata.xml` 을 같이 가져온다.** `zen_meta.py` 가 µm/px 를 여기서
읽는다. XML 이 없으면 스케일이 기본값으로 조용히 떨어진다 — 004 에서 한 번 당했다.

**그룹핑 경고.** P01 §1 이 지적한 대로, 상관계수 분포가 양분되지 않는 슬라이드는
지금 조용히 잘못 묶인다. 116cm 가 47그룹 중 26개 단독인 것이 촬영을 덜 한 탓인지
임계값이 안 맞는 탓인지 아직 모른다. 슬라이드마다 *그룹 내 최소 상관*과 *그룹 간
최대 상관*의 간격을 기록하고, 좁으면 `state="failed"` + `state_note` 로 사람을
부른다. **자동으로 넘기지 않는다** — 잘못 묶인 시야 위에 쌓은 검출과 교정은
나중에 되돌리기가 훨씬 비싸다.

### 5. 주기 실행
호스트 cron → `deploy/poll_nas.sh`. `flock` 으로 중복 실행을 막고, `timeout` 을
건다(NAS 가 `hard` 마운트라 내려가면 무한 대기한다). 새 폴더가 없으면
**GPU 를 건드리지 않고 끝난다.**

## 유의

- **`/nfs/temp-share` 는 `hard` 마운트다**(`fstab` 에 `defaults`). NAS 가 내려가면
  접근하는 프로세스가 멈춘다. 컨테이너에는 `ro` 로 물리고 cron 에 `timeout` 을 건다.
  `fstab` 을 `soft,timeo=` 로 바꾸는 것은 쓰기 중 조용한 손상 위험이 있어 별개
  판단으로 남긴다
- **디스크**(P01 §1): 슬라이드당 ~1 GB. `/data3` 는 당분간 넉넉하지만 원본 보존
  정책은 정해야 한다. 저장소의 `backup/`(3.3 GB)도 `/data3` 로 옮길 만하다
- **`export_review.py`(P02 5단계)가 아직 없어 교정이 DB 에만 있다.** 이 작업
  내내 `backup_db.py` 가 유일한 안전망이다. 단계마다 뜬다
- 1·2단계까지 하고 뷰어가 컨테이너에서 정상인지 확인한 뒤 3단계로 넘어간다 —
  3단계부터 교정을 만진다
