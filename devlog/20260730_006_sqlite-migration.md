## 1. 왜 뒤집었나

### 파일을 너무 많이 연다

슬라이드가 3장인데 첫 화면 한 번에 **JSON 251개를 읽었다**(캐시 없을 때 371 ms).

| 화면 | 캐시 없음 | 읽은 JSON |
|---|---|---|
| 데이터셋 목록 | 371 ms | 251개 |
| 그룹 목록 | 115 ms | 69개 |
| 검출 결과 갤러리 | 189 ms | 69개 |

NAS 로 사진이 계속 들어오면(P01 §1) 이 숫자가 선형으로 늘어난다. 크로스 시야
질의(크기 분포, 분류별 집계)도 124개 파일을 다 열어야 한다.

### 그보다 큰 이유 — 둘 곳이 없던 것들

성능보다 이쪽이 결정적이었다.

- **실행 이력이 없다.** `stack_report.json` 이 합성본 81개인데 **32항목만** 남아
  있다 — 실행마다 덮어써서 앞의 기록이 사라졌다. `refilter` 도 판정을 덮어쓰므로
  "원형 669 → 514 가 언제 무슨 문턱으로 바뀌었나" 에 답할 수 없다
- **문턱 11개가 결과 124개에 복사돼** 있다. 이름을 붙여 비교할 수가 없다
- **처리 상태를 둘 곳이 없다.** `run_batch.sh` 는 산출물 파일이 있는지만 본다.
  NAS 를 붙이면 대기/복사중/처리중/완료/실패가 필요해진다
- **시료의 출처가 문자열 하나에 뭉쳐 있다** — 아래 4절

### 정한 것

| | |

## 2. 스키마에서 판단이 필요했던 곳

### 2.1 교정은 `Candidate` 가 아니라 `mask_key` 에 붙는다

검출을 다시 돌리면 후보 행이 새로 생긴다. FK 로 매면 사람의 판단이 **조인 실패로
사라진다.** 그래서 `(Viewpoint, mask_key)` 를 진짜 키로 두고 `candidate` 는
바인딩 결과(nullable)로 채운다.

전제가 맞는지 재 봤다 — 사진 한 장을 같은 설정으로 다시 돌려 키를 맞췄다.

```
원시 마스크: 저장 시점 133개 · 방금 133개
크기 통과 키 77개 -> 일치 77개 (100%) · 어긋남 0개
```

**같은 설정이면 하나도 어긋나지 않는다**(Turing 에서 fp16 autocast 를 켜고 돌리는데도
결정적이었다). 반대로 실험 중 `--iou-thresh` 를 0.5 → 0.6 으로 잘못 넣었을 때
원시 마스크가 133 → 117 로 줄었다. **엔진 교체(P01 §3)는 그 극단이다.**

어긋난 것을 IoU 로 다시 맺어 봤더니 **짝의 IoU 중앙값이 0.085** 였다. SAM 이 같은
자리에 여러 스케일의 마스크를 내므로 "조금 어긋난 같은 개체" 가 아니라 **다른
스케일의 다른 마스크**와 짝지어진다. 그래서 자동 재바인딩은 `IoU ≥ 0.9` 로 아주
보수적으로만 걸고 나머지는 고아로 남겨 사람에게 보고한다(8단계).

### 2.2 모든 교정 행이 기하를 들고 있는다

처음에는 "되살린 것만" 이라고 적었는데, 학습 관점에서 보니 부족했다.

```
ObjectReview.geom = {"bbox": [...], "polygon": [...]}   # 모든 행
```

1. **교정이 검출기와 독립이 된다** — 엔진을 갈아도 사람의 판단이 그대로 읽힌다
2. **지운 것 2,044개가 학습의 어려운 음성 표본이다** — "SAM 이 후보로 냈는데
   사람이 규조각이 아니라고 한 것" 은 버릴 자료가 아니다. 기하가 없으면 못 쓴다
3. 고아를 언제나 그려 볼 수 있다

비용은 2,306행 × 폴리곤 ≈ 1 MB 다. 그리고 이것이 P01 §6 의 **수동 박스 그리기**의
저장소도 된다 — SAM 이 후보로도 못 잡은 개체는 애초에 `Candidate` 가 없으니까.

### 2.3 검출은 덮어쓰지 않고 쌓는다

`Detection.is_current` 가 뷰어가 볼 것을 가리키고, `superseded_by` 가 이력을 잇는다.
전량 한 바퀴가 개체 18,936행 ≈ 25 MB 라 SQLite 에는 부담이 아니다. **교체 전후를
같은 시야로 비교**해야 하고(P01 §3), 지금은 덮어써서 불가능하다.

### 2.4 통과분·탈락분 두 배열을 한 표로

문턱을 바꾸면 개체가 무리를 옮겨 다닌다. 지금은 두 배열 사이로 옮기느라 파일을
다시 쓰지만, `passed` 칼럼 하나면 `refilter` 가 **UPDATE 한 번**이다. "탈락분도
지표째 남긴다" 는 원칙이 스키마로 표현된다.

### 2.5 설정을 표로

- `ThresholdSet` — 결과 124개에 복사돼 있던 문턱 11개가 **1행**으로 모였다.
  이름을 붙여 비교할 수 있다("1500 vs 2000 을 같은 시야에 걸고 개수를 나란히")
- `ClassDef` — 분류 정의와 색. **Eucampia 를 넣은 것이 코드 수정이었는데** 속은
  계속 늘어난다. 표로 두면 배포가 필요 없다

## 3. 이전과 대조 — 3단계가 관문이다

교정 2,306행은 **재생성 불가한 자료**다. 어긋난 채로 뷰어를 옮기면 무엇이 맞는지
알 수 없게 되므로, 대조가 통과할 때까지 다음으로 가지 않기로 했다.

### `import_json.py` — 8초, 멱등

```
분류 정의 5개 · 설정 2개
슬라이드 3 · 시야 124 · 프레임 345 (XML 읽음 345)
  RS23 · 코어 GC03 · 깊이 71cm
  WAP13 · 코어 GC47 · 깊이 116cm, 450cm
합성본 81개 (stack_report 항목 32개 — 덮어써져 일부만 남아 있다)
검출 124개 · 개체 18936개 · 문턱 조합 1개
시야 교정 124개 · 개체 교정 2306개 (exact 2306 · orphan 0)
```

XML 345개를 다 읽어 프레임마다 µm/px·촬영시각이 들어갔다. 두 번 돌려도 같은
결과다.

### `verify_db.py` — 검사 37개 전부 일치

**개수만 맞고 값이 틀리는 경우**를 잡으려고 지표 합까지 셌다.

| | JSON | DB |
|---|---|---|
| 통과분 / 탈락분 | 2,522 / 16,414 | 2,522 / 16,414 |
| `area_px` 합 | 411,262,211 | 411,262,211 |
| `texture` 합 | 54,051,089.1 | 54,051,089.1 |
| 폴리곤 좌표 수 | 882,880 | 882,880 |
| 교정 행 | 2,306 | 2,306 |
| 바인딩 | — | **exact 2,306 · orphan 0 · geom 없는 행 0** |
| 교정 반영 통과분 / 유령 / 후보 풀 | 627 / 2,044 / 16,265 | 같음 |

**이전 직후에는 바인딩이 전부 `exact` 여야 한다** — 같은 검출 결과를 그대로 넣는
것이므로 어긋날 이유가 없다. 하나라도 `orphan` 이면 이전 로직이 틀린 것이다.

### 뷰어 대조 — 개체 dict 하나하나까지

옛 `data.py` 를 `data_json` 이라는 이름으로 함께 올려 두고, 뷰가 쓰는 세 함수
(`datasets`, `dataset_detail`, `group_detail`)의 결과를 **재귀적으로** 비교했다.
124개 시야 전부.

이 대조가 세 가지를 잡았다. 눈으로는 못 볼 것들이다.

1. **유령은 파일에 적혀 있던 `id` 를 유지해야 한다.** 통과분은 화면에서 면적순으로
   다시 매기지만 지운 것은 그 값을 그대로 쓴다 → `Candidate.raw_id` 를 만들었다
   (내보내기로 JSON 을 재현할 때도 필요하다)
2. **탈락분에도 `cls` 가 있을 수 있다** — 중첩정리로 떨어진 126개는 판정을 통과한
   뒤 정리됐기 때문이다
3. **`n_labeled` 는 통과분만 세야 한다** — 탭 머리의 "사람지정" 과 정의가 같아야
   화면끼리 어긋나지 않는다. 지웠는데 분류가 남은 개체가 2개 있었다

처음 돌렸을 때 34,552군데가 어긋났다고 나왔다. 실제 원인은 위 두 가지뿐인데
개체마다 곱해져 그렇게 보였다 — **차이를 한 곳으로 좁히는 것이 대조의 요령**이다.

### 함수 이름과 반환 형태를 그대로 유지했다

`data.py` 를 DB 기반으로 다시 쓰면서 함수 이름·반환 dict 를 **JSON 시절과 같게**
두었다. 그래야 템플릿과 뷰를 건드리지 않고 갈아 끼울 수 있고, 위처럼 값을 직접
비교할 수 있다. 모델 인스턴스를 템플릿에 넘기고 싶은 유혹이 있었지만, 그러면
이 대조가 불가능해진다.

## 4. 시료의 출처를 갈라 담았다

작업 중에 사용자가 알려 준 것 — 폴더명 `RS23-GC03 71cm` 은 세 토막이다.

```
RS23      지역
GC03      시추코어 ID
71cm      기준점(아마도 해저면)에서부터의 깊이
```

남극에서 채취한 시추코어의 규조류다. **이것을 통짜 문자열로 두면 안 되는 이유**가
분명하다 — 이 시료의 분석 목적이 *같은 코어에서 깊이에 따른 군집 변화*와
*지역별 차이*다.

```
Site (RS23, WAP13)  ──< Core (GC03, GC47) ──< Slide (depth_cm)
```

`Slide.Meta.ordering = ["core", "depth_cm", "name"]` 이라 코어 안에서는 깊이순이
기본이다. 이제 이런 것이 질의로 나온다.

```
RS23-GC03     71 cm   개체 811
WAP13-GC47   116 cm   개체 632
WAP13-GC47   450 cm   개체 1079     <- 같은 코어의 두 깊이가 묶인다
```

**지역 코드의 정식 명칭은 비워 두었다.** `WAP` 는 통상 West Antarctic Peninsula 를
뜻하는데 사용자는 웨델해라고 했다. 어느 쪽으로든 내가 단정해 적으면 나중에 논문
표에 그대로 실릴 수 있어서, 코드만 저장하고 `Site.name`·`region` 은 사람이 채우도록
남겼다.

## 5. 백업 — DB 가 유일한 사본이 되는 구간

`export_review.py`(5단계)를 미루기로 했으므로, 당분간 교정이 **DB 에만** 있다.
`diatom.db` 는 gitignore 이고 커밋된 `review/*.json` 은 이전 시점 스냅샷이다.

`backup_db.py` 를 만들었다. 두 가지를 지킨다.

- **`cp diatom.db` 로는 안 된다.** WAL 모드라 최근 쓰기가 `-wal` 에 있고 그냥
  복사하면 불완전한 사본이 나온다. SQLite 의 backup API 는 잠금을 잡고 일관된
  사본을 만든다(쓰는 중에도 안전하다)
- **사본은 파일 하나로 딱 떨어져야 한다.** backup 은 journal 모드까지 복사하므로
  그대로 두면 WAL 로 남아 읽을 때마다 `-shm` 이 생기고 옮길 때 딸려 다녀야 하는
  파일이 늘어난다 → `PRAGMA journal_mode=DELETE`

뜬 뒤에 `integrity_check` 와 행 수를 출력한다 — 뜨기만 하고 깨진 것을 모르면 뜻이
없다. `backup/` 은 로컬 안전망이라 gitignore 다.

### 치른 값

- **컨테이너화(P01 §5)와 상충한다.** 처리 스크립트가 Django 를 필요로 하게 되므로
  "뷰어만 작은 이미지 / 처리는 큰 이미지" 로 갈라 두려던 것이 깨진다 — 처리
  이미지에 Django(작다)를 넣게 된다. ORM 을 고른 값이다
- **JSON 이 반쯤 살아 있는 구간이 생겼다.** 스크립트는 JSON 을 쓰고, DB 에 넣으려면
  `import_json.py` 를 한 번 돌려야 한다. 6단계까지의 임시 상태다

## 7. 남은 것

| 단계 | |
|---|---|
| 5. `export_review.py` | 미뤘다 — 당분간 DB 위주로 작업하기로 했고 `backup_db.py` 가 안전망 |
| **6. 스크립트 4개를 DB 에** | **다음 작업.** `refilter.py`(119줄)부터 — 가장 작고, 문턱 이력이 바로 생기고, `segment_diatoms.py`(489줄)에 필요한 조각을 먼저 검증할 수 있다 |
| 7. JSON 을 원본에서 내리기 | |
| 8. 재바인딩 + 고아 화면 | **학습·엔진 교체 전에 반드시** — 없으면 교정이 조용히 버려진다 |

6단계에서 조심할 것: **`is_current` 이동과 교정 재바인딩은 한 트랜잭션이어야 한다.**
중간에 끊기면 뷰어가 "교정이 붙지 않은 새 검출" 을 보여준다.

그리고 `tighten_bbox.py`(bbox 본체 정렬, 005 §5)는 **DB 이전이 끝난 뒤 8단계와 함께**
하는 것이 낫다. `mask_key` 를 바꾸는 작업이라 재바인딩과 같은 문제를 푼다 — 한 번만
풀면 된다. 그때는 옛 키와 새 키가 1:1 로 대응하므로 `exact` 를 유지할 수 있다.
