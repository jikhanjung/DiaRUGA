# 087 — 테스트 배포를 운영과 같은 갈래로 관리한다

2026-08-08 · [085](20260807_085_test-instance.md) 의 남은 자리

## 문제

085 는 테스트 자리를 **손으로 만들었다.** compose 와 `.env` 가 `/srv/DiaRUGA/test/`
에만 있었고, nginx 설치 스크립트도 거기 있었다. 저장소에는 nginx 조각 하나뿐이다.

그 상태의 값이 이것이다:

- **되살릴 수 없다.** 이 머신이 죽으면 테스트 자리는 사람의 기억에서만 나온다
- **어긋나도 모른다.** 운영은 `sync_to_srv.sh` 가 "저장소의 것과 글자 그대로
  같다" 를 지키고 `smoke.sh` 가 표류를 알린다. 테스트에는 그 짝이 없었다
- **판을 거는 절차가 머릿속에 있다.** `.env` 의 태그를 고치고, 사본을 새로 뜨고,
  올리고, 확인한다 — **네 단계를 사람이 순서대로 기억한다.** 잊는 것은 대개
  사본이고, 그러면 옛 자료로 새 판을 보게 된다

운영이 이것을 이미 풀어 놓았다. 그 갈래를 그대로 가져온다.

## 한 일

```
deploy/test/docker-compose.yml       ← /srv/DiaRUGA/test/docker-compose.yml 의 원본
deploy/test/env.template             ← .env 견본
deploy/host/sync_test_to_srv.sh      저장소 → /srv/DiaRUGA/test
deploy/host/testdeploy.sh            판을 건다
deploy/host/install-nginx-test.sh    nginx (root, --uninstall 있다)
deploy/nginx/DiaRUGATest-subpath.conf   (085 에서 이미 저장소에 있었다)
```

운영과 짝이 맞는다 — `deploy/srv/` ↔ `deploy/test/`, 스크립트는 둘 다
`deploy/host/`. **저장소가 만들고 `/srv` 가 돈다** 는 규칙이 양쪽에 같이 선다.

## `testdeploy.sh` — 순서가 곧 안전장치다

운영 `deploy.sh` 와 같은 뜻의 순서다.

```
1. 안전 검사        테스트가 운영 자료를 만지는 길 넷을 센다
2. 이미지           받다 실패하면 지금 도는 것을 안 건드리고 끝난다
3. .env 의 IMAGE_TAG 만   제자리에서. 파일을 다시 만들지 않는다
4. 내린다           쓰는 쪽이 빠져야 WAL 이 본체로 정리된다
5. DB 사본          갈아 끼운다  ← 운영에는 없는 단계
6. 기동 게이트      200 이 안 나오면 로그를 보여주고 실패로 끝낸다
7. smoke            **운영과 같은 스크립트**를 환경만 갈아 끼워
```

### 5번이 운영과 다른 자리다

운영은 있는 DB 를 그대로 둔다. 테스트는 반대로 **사본이 낡는 것이 기본 고장**이다.
옛 자료로 새 판을 보면 "고쳤는데 안 바뀐다" 가 나오고, **그 시간은 판을 의심하는
데 쓰인다** — 실제로는 자료가 옛것일 뿐인데.

그래서 기본이 "갈아 끼운다" 이고, 안 갈려면 `--keep-db` 를 **명시해야** 한다.
기본과 예외의 방향이 반대면 사람이 잊는 쪽으로 굴러간다.

**가져오는 것은 시간별 스냅샷이다.** `backup_db.py` 가 `--keep 24` 로 떠 두는
그것 — **검증을 통과한 뒤 제 이름을 받은** 파일이라 `cp` 해도 안전하다(도는 DB 를
`cp` 하면 WAL 이라 불완전한 사본이 나온다).

`--fresh-db` 로 지금 시점을 뜰 수도 있지만 **기본으로 두지 않았다.** 손으로 뜬
것은 `manual/` 에 쌓이고 **로테이션이 안 건드린다** — 미리보기를 돌릴 때마다
108 MB 가 영구히 는다. 하루 몇 번 돌리는 자리에서 그건 금방 문제가 된다.

### 1번이 이 스크립트가 있는 이유의 절반이다

테스트가 운영 자료를 만지는 길이 넷 있고, **넷 다 조용하다.**

| 검사 | 어기면 |
|---|---|
| `DIARUGA_DB` 가 운영 DB 인가 | 테스트에서 한 교정이 운영으로 들어간다 |
| `DIARUGA_OUTCROP_DIR` 이 NAS 원본인가 | 화면에서 지운 사진이 **진짜로** 지워진다 |
| `DIARUGA_SCRIPT_NAME` 이 `/DiaRUGA` 인가 | 링크가 전부 운영으로 샌다 |
| compose 가 운영 `db/` 를 마운트하는가 | `.env` 가 성해도 파일로 닿는다 |

`tests/base.py` 가 시험에 대해 하는 일과 같다 — **사람이 기억하는 대신 기계가
센다.** 검사는 돌기 전에 하고, 걸리면 아무것도 안 건드린 채 선다.

**넷 다 실제로 서는 것을 확인했다.** 긁어 낸 사본 디렉토리에 어긴 설정을 하나씩
넣어 돌렸다:

```
1) 운영 DB 를 가리키면      → ✗ 테스트가 **운영 DB** 를 가리킨다
2) NAS 원본을 가리키면      → ✗ 테스트가 **NAS 원본** 노두 사진을 가리킨다
3) 서브경로가 /DiaRUGA 면   → ✗ 링크가 전부 운영으로 샌다
4) compose 가 운영 db/ 면   → ✗ 테스트 compose 가 **운영 db/ 를 마운트**한다
5) 성한 설정               → 안전 검사 통과
```

### 7번 — smoke 를 새로 만들지 않았다

`smoke.sh` 는 이미 `DIARUGA_SRV`·`DIARUGA_HEALTH`·`DIARUGA_SITE` 로 매개변수화돼
있었다. 환경만 갈아 끼우면 테스트 자리를 본다 — 판 비교는 테스트 `.env` 의
`IMAGE_TAG` 를 읽고, 목록에서 링크를 뽑아 따라가는 검사도 `/DiaRUGATest/…` 로
간다.

**검사가 둘이면 한쪽만 늙는다.** 075 에서 화면이 둘이라 같은 고장을 두 번 고친
것과 같은 이야기다.

## 치운 것

`/srv/DiaRUGA/test/install-nginx.sh` 를 지웠다. 저장소의
`deploy/host/install-nginx-test.sh` 가 대신하고, 같은 일을 하는 파일이 두 자리에
있으면 **어긋나고 어느 쪽이 맞는지를 사람이 기억해야 한다.** 저장소 것에는
`--uninstall` 이 붙어 있어 되돌리는 길도 같은 파일 안에 있다.

## 남은 것

- **`.env` 는 여전히 `/srv` 에만 있다** — 비밀키가 들었으니 그게 맞다. 견본에
  새 항목이 생기면 `sync_test_to_srv.sh` 가 **알리기만** 한다(운영과 같다)
- **테스트에도 `rollback` 이 없다.** 운영과 같은 구멍이다(016). 다만 테스트는
  `testdeploy.sh <옛 판>` 이 사실상 그 일을 한다 — 자료가 사본이라 되돌릴 것이 없다
- **두 화면을 가르는 표시가 아직 없다.** 이 갈래를 상설로 쓰기로 하면 그것과
  `localStorage` 공유가 다음 순서다
