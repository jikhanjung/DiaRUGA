# 053 — 검토 저장이 남의 시야를 지우고 있었다. 이름으로 찾은 탓이다

2026-08-05. 051 에서 "합성본 검출은 `frame` 이 NULL 이다" 를 확인하다가, 사용자가
**"지금 실제 `frame` 에는 어떤 값이 들어가지?"** 라고 물었다. 그 칸을 따라가다
`stem` 으로 시야를 찾는 자리에 닿았고, 거기서 **터져 있는 것**을 찾았다.

**교정은 재생성 불가다.** 017(14건)·027(37건)에 이어 같은 계열의 세 번째다.

## 1. 무엇이 터져 있었나

`save_review` 는 **`stem` 하나로 시야를 찾았다.**

```python
def _viewpoint_of(stem):
    if stem.endswith("_focused"):
        return qs.filter(tag=stem[:-len("_focused")]).first()
    fr = Frame.objects.filter(name=stem).values_list("viewpoint_id", flat=True).first()
    return qs.filter(id=fr).first() if fr else None
```

**`.first()` 다.** 그런데 **프레임 이름은 슬라이드끼리 겹친다** — 카메라
일련번호라 같은 날 이어 찍으면 번호대가 이어진다. 실측 143종이다. 이건 이미
알고 있던 함정이고 HANDOFF 에 *"이름만으로 찾지 말 것"* 이라고 적혀 있으며
`Frame` 에 `(slide, name)` 유일 제약까지 있다. **제약은 있는데 조회가 그걸 안
썼다.**

합성본 시야는 stem 이 `<tag>_focused` 라 안전하다. 문제는 **싱글턴 시야**다 —
합성본이 없어 stem 이 곧 프레임 이름이다.

```
싱글턴 시야 135개 중 자기 stem 으로 자기를 못 찾는 것: 12개
  260803_gc03-c1_72cm g1  (Snap-22241) → 실제로 열리는 시야: bp09-0901 g2  (교정 7행)
  260803_gc03-c1_72cm g8  (Snap-22263) → bp09-0901 g10 (교정 12행)
  ...                                    노출된 교정 합계 138행
```

## 2. 왜 조용히 지워지는가 — 두 겹의 방어가 둘 다 안 걸린다

`save_review` 는 마지막에 이렇게 한다.

```python
ObjectReview.objects.filter(viewpoint=vp).exclude(mask_key__in=keys).delete()
```

앞에 "현재 검출에 없는 키가 섞이면 409" 라는 방어가 있다(027 이후에 넣었다).
그런데 **키가 하나도 없으면 그 검사가 통과한다** — `keys` 가 빈 집합이면
`unknown` 도 빈 집합이다. 그리고 빈 `keys` 로 `exclude` 하면 **그 시야의 교정
전부**가 지워진다. 이건 "교정 전체 초기화" 의 정상 경로라서 그 자체로는 옳다.

즉 **개체는 하나도 안 건드리고 "검토 완료" 만 누르면** 방어가 전부 비껴간다.
사본에서 재현했다:

```
검토하는 화면 : gc03-c1_72cm g1 (싱글턴, stem=Snap-22241) · 교정 0행
사람이 한 일  : '검토 완료' 만 눌렀다

save_review 반환: {'removed': 0, 'accepted': 0, ...}   ← 예외도 409 도 아니다
bp09-0901 g2 의 교정: 7 → 0
```

**200 이 돌아오고, 화면에는 "저장됨" 이라고 뜬다.** 백업 숫자를 세지 않으면
모른다 — 027 과 똑같다.

## 3. 고친 것

### 3.1 이름으로 찾을 때 모호하면 거절한다

`_viewpoints_by_stem()` 이 **여럿이면 여럿을 그대로** 돌려주고, 고르는 일은
부르는 쪽이 한다. `_viewpoint_of()` 는 **하나일 때만** 돌려준다.

아무거나 집는 길을 없앴다. 옛 화면(배포 중에 열려 있던 탭)이 `stem` 만 보내면
이제 409 다 — 그 시야는 저장이 안 되지만, **남의 교정을 지우는 것보다 낫다.**
해당하는 것은 이름이 겹치는 싱글턴 시야 20개다.

### 3.2 저장 요청이 `(slug, gid)` 로 시야를 짚는다

이름은 겹치지만 **주소는 겹치지 않는다.** 화면은 이미 슬러그와 시야 번호를
알고 있으므로 보내지 못할 이유가 없었다.

```
POST /review  {"stem": …, "slug": "260803_gc03-c1_72cm", "gid": 1, …}
```

`stem` 은 버리지 않고 **검증용**으로 남겼다 — 그 시야의 현재 검출 이미지와
다르면 받지 않는다. 실측으로 payload 의 stem 은 452 시야 전부에서 현재 검출
`image_path` 의 stem 과 같았으므로, 어긋나면 그것은 **화면과 저장 대상이 다른
상태**다. 화면과 저장이 어긋난 채 통과하는 길을 하나도 남기지 않는다.

`(slug, gid)` 가 없으면 3.1 의 길로 떨어진다 — 배포 중에 열려 있던 탭을 위한
것이고, 모호하면 거절한다.

## 4. 확인

사본 DB 에 붙여 네 경우를 다 눌러 봤다.

| 보낸 것 | 결과 |
|---|---|
| `stem` 만 (이름 겹침) | **409** "이 이름의 시야가 2개다 … 저장하지 않았다" · 교정 7행 그대로 |
| `stem + (slug, gid)` | **200** · 자기 시야만 검토 완료 · 남의 교정 7행 그대로 |
| stem 이 어긋남 | **409** "화면과 저장 대상이 어긋난다 — … 현재 검출은 Snap-22241 인데 Snap-99999 을 보냈다" |
| 모르는 slug | **409** "모르는 시야다" |

그리고 **검출이 있는 시야 452개 전부**에 대해 `(slug, gid, stem)` 이 자기 시야로
풀리는 것을 확인했다. 브라우저로도 눌렀다(사본 `:8091`) — 삭제·탈락 되살리기·
Ctrl+Z 가 200 으로 저장되고, 읽기 전용 화면은 여전히 `/review` 를 하나도 안
보낸다.

## 5. 남은 것

- **`review_blocked(stem)` 도 같은 길을 썼다.** 이제 뷰가 시야를 먼저 짚고
  `review_blocked(vp.slide)` 로 부른다. stem 을 받는 갈래는 남겨 두었지만
  이제 모호하면 None 이라 조용히 남의 슬라이드 상태를 보는 일은 없다
- **`verify_db.py` 의 `detection_for(stem)`** 도 같은 함수를 쓴다. 모호하면
  None 이 되어 그 시야를 건너뛴다 — 대조 스크립트라 지우는 쪽 위험은 없다
- **빈 payload 가 전부를 지우는 설계 자체는 그대로다.** 그것이 "교정 전체
  초기화" 이기 때문이다. 이번에 막은 것은 **엉뚱한 시야에 그것이 가는 길**이다

## 6. 교훈

**제약이 있다는 것과 조회가 그걸 쓴다는 것은 다르다.** `Frame` 에 `(slide, name)`
유일 제약이 있었고 HANDOFF 에 경고까지 적혀 있었는데, 정작 그 이름으로 찾는
코드가 `.first()` 였다. 제약을 넣을 때 **그 이름으로 찾는 자리를 전부 세어
봤어야 한다.**

그리고 **방어는 "무엇을 보내는가" 가 아니라 "어디에 쓰는가" 에도 걸어야 한다.**
027 이후 넣은 방어는 키를 검사했지 **대상**은 검사하지 않았다. 키가 없으면
검사할 것도 없어서 통째로 비껴갔다.
