# 배포를 스크립트로 만든다 — 손으로 `cp` 하던 것을 걷어낸다

**작성일** 2026-08-03
**근거** `.guides/web/deployment.md` §2 · §5 · §6 · §10

---

## 시작은 내가 남긴 찜찜함이었다

이미지를 Docker Hub 에 올린 뒤 배포 구성을 고치면서 이렇게 적었다.

> 앞으로 판을 올리실 때 **저장소 쪽을 고치고 복사**하시면 어긋나지 않습니다 —
> 배포 쪽만 고치면 다음 복사 때 되돌아갑니다.

사람이 기억해야 하는 규칙을 남긴 것이다. 물어보니 형제 프로젝트에 그런 스크립트가
있다고 해서 `.guides/web/deployment.md` 를 폈다. **§2 가 정확히 그 얘기였다.**

## 세 스크립트, 소유자가 다르다 (§2)

| 스크립트 | 도는 곳 | 하는 일 |
|---|---|---|
| `build.sh` | 빌드 호스트 | 시험 → 판 올림 → build → push |
| **`sync_to_srv.sh`** | prod | 저장소의 배포 파일을 `/srv/` 로 |
| `deploy.sh` | prod | pull → 스냅샷 → 교체 → health 게이트 |

가이드가 든 함정이 인상적이다 — *어떤 `build.sh` 가 빌드 호스트에서 `/srv/…` 로
복사하려 했는데 그 경로가 없어 **조용히 건너뛰었고** prod 는 변경을 못 받았다.*
prod 전용 일은 prod 전용 스크립트에 둔다.

이 머신은 개발·운영·빌드를 겸하지만(devlog 016) **파일은 갈라 두는 편이 낫다.**
언젠가 나뉠 수도 있고, 나뉘지 않더라도 "이건 어디서 도는 것인가" 가 이름에 적혀
있는 편이 읽기 쉽다.

## 판을 compose 에서 `.env` 로 옮겼다 (§5)

내가 처음 한 것은 배포 compose 에 판을 박는 것이었다.

```yaml
image: honestjung/diatom:v0.1.0     # ← 저장소와 /srv 의 파일 내용이 달라진다
```

§5 는 **`.env` 의 `IMAGE_TAG` 를 제자리에서 고치라**고 한다. 그러면 두 compose 가
**글자 그대로 같아져서** 복사가 안전해진다 — 다르면 복사할 때마다 어긋나고, 어느
쪽이 맞는지를 사람이 기억해야 한다. 그게 애초에 내가 남긴 찜찜함이었다.

```yaml
image: honestjung/diatom:${IMAGE_TAG:?IMAGE_TAG 를 .env 에 넣을 것}
```

`:?` 를 붙인 이유: 값이 없을 때 조용히 `latest` 로 흐르면 무엇이 도는지 알 수 없다.

**`.env` 는 통째로 다시 만들지 않는다.** 비밀키와 지금 도는 판이 거기 있다.
가이드에 있는 사례가 무섭다 — 어떤 배포가 `> .env` 로 파일을 새로 써서 크롤러
자격증명이 날아갔고 **3.5개월을 몰랐다.** `sync_to_srv.sh` 도 `.env` 는 없을 때만
만들고, 견본에 새 항목이 생기면 **알려만 준다.**

## `deploy.sh` — 순서가 곧 안전장치다 (§5)

```
1. 이미지를 받는다        받다 실패하면 도는 것을 안 건드리고 끝
2. .env 의 IMAGE_TAG 만   통째로 다시 만들지 않는다
3. 유지보수 깃발          내리는 동안 502 를 안 보인다
4. 내린다                 쓰는 쪽이 빠져야 WAL 이 정리된다
5. 배포 전 스냅샷         새 판이 DB 를 건드렸을 때 돌아올 지점
6. 올리고 health 게이트   200 이 안 나오면 실패로 끝낸다
7. 깃발 해제              trap 이라 중간에 죽어도 풀린다
```

실패하면 되돌릴 명령을 그 자리에 찍는다. 지금 도는 판을 처음에 읽어 두는 이유가
그것이다.

### 밟은 것 — 스냅샷이 조용히 건너뛰어졌다

첫 배포에서 이 줄이 찍혔다.

```
경고: backup_db.py 를 못 찾았다 — 스냅샷 없이 진행한다
```

`[ -x "$REPO/backup_db.py" ]` 로 봤는데 그 파일은 실행 권한이 없다(`-rw-rw-r--`).
어차피 `python backup_db.py` 로 부르므로 권한은 상관없는데, `-x` 로 물어서 없는
것으로 판정한 것이다.

**스냅샷은 되돌아올 지점이다.** 경고만 찍고 진행할 일이 아니다. `-f` 로 고치고,
못 뜨면 **멈추게** 했다(`DIATOM_SKIP_SNAPSHOT=1` 로만 강행).

두 번째 배포는 제대로 떴다 — `24.9 MB · integrity=ok · 4초`.

## 점검 안내 (§6)

컨테이너를 갈아 끼우는 5~30초 동안 nginx 는 맨 502 를 낸다. 사람이 보기에 고장과
구별되지 않는다. `deploy.sh` 가 세우는 깃발을 nginx 가 보고 안내를 낸다.

**두 화면을 가른다.**

| 상황 | 화면 |
|---|---|
| 깃발 있음 (배포 중) | 503 · "시스템 점검 중입니다" · 5초마다 자동 재시도 |
| 깃발 없는데 502/504 | "뷰어에 연결할 수 없습니다" · 10초마다 · 확인 명령 안내 |

깃발 없이 죽은 것을 "점검 중" 이라고 하면 **거짓말**이다. 그때는 정말로 멈춘
것이고, 사람이 그걸 알아야 조치한다.

가이드가 짚은 함정도 피했다 — `error_page 503 = /…` 처럼 `=` 를 쓰면 **상태가
200 으로 바뀐다.** 크롤러도 스크립트도 정상으로 읽는다. URI 만 주고 `internal` 로
직접 접근을 막았다.

확인:

```
깃발 있음  → 503 · "시스템 점검 중입니다"
깃발 없음  → 200
/diatom-maintenance.html 직접 → 404
```

## 이 머신에서 성립하지 않는 것

§0 은 *"빌드는 prod 밖에서, prod 는 pull·swap 만"* 이라고 한다. 이 머신은 한 대가
개발·운영·백업을 겸해서 구조상 못 지킨다(devlog 016 에 적어 둔 그대로다).
§3(인스턴스별 변수)·§4(SSH 원격 배포)도 인스턴스가 하나뿐이라 해당이 없다.

**못 지키는 것을 못 지킨다고 적어 두는 편이** 반쯤 지키고 다 지킨 척하는 것보다
낫다.

## 남은 것

- `build.sh` 가 없다. 지금은 `DIATOM_TAG=… docker compose build && … push` 를
  손으로 친다. **시험을 통과해야 push 하는 관문**(§2)이 없는 것이 그 값어치다
- `DEPLOY.md`(배포별 변경 기록, §10)가 없다
- 판을 한 곳에서 올리는 장치(§10)가 없다 — 지금은 `IMAGE_TAG` 와 git 태그가 따로다
