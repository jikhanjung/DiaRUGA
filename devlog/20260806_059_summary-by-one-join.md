# 059 — 집계를 왼쪽 조인 한 번으로 (v0.6.2)

2026-08-06. 058 로 첫 페이지가 2.09 → 0.59초가 된 뒤, 사용자가 **"속도를 더
빠르게 할 방법은 없을지 살펴봐줘"** 라고 했다. 남은 0.59초를 다시 갈랐다.

`v0.6.2` 로 배포했고 **0.59 → 0.12초**다. 처음(2.09초)과 비교하면 17배다.

## 고친 방법 — 조인은 한 번이면 된다

교정은 `(image, mask_key)` 가 **유일**하다(055). 그러면 왼쪽 조인이 후보 하나에
교정 **0 또는 1** 행만 붙이므로 행이 안 불어나고, 서브질의 넷이 조인 하나가 된다.

```sql
FROM viewer_candidate c
JOIN viewer_detection d ON d.id = c.detection_id AND d.is_current
JOIN viewer_viewpoint v ON v.id = d.viewpoint_id
LEFT JOIN viewer_objectreview r ON r.image_id = d.image_id AND r.mask_key = c.mask_key
GROUP BY v.slide_id, eff_cls
```

    집계 11개   500 → 77 ms
    첫 페이지   547 → 122 ms   (SQL 59 · 파이썬 63)
    코어 페이지 188 → 46 ms

## 왜 원시 SQL 인가

**Django ORM 이 이 조인을 낼 수 없다.** 관계가 FK 가 아니라 `(image_id, mask_key)`
짝이기 때문이다. `ObjectReview.candidate` FK 가 있긴 하지만 **그것을 조인 열쇠로
쓰면 안 된다** — 재검출에서 끊기라고 만든 칸이다(P02). 교정이 `mask_key` 에 붙는
것은 소유 방향의 선택이고, 그 선택의 대가가 "ORM 으로는 조인을 못 쓴다" 이다.

대신 규칙이 SQL 문자열로 들어갔으므로 **머리말에 그 사실을 적었다** — 판정 규칙은
`_apply_review`·`_guess_cls` 와 같아야 하고 경계값(1.4 · 2.0 · 20.0)까지 같아야
목록과 상세의 숫자가 어긋나지 않는다.

**분류 목록은 SQL 에 안 박았다.** `eff_cls` 로 묶어 와서 파이썬에서 접는다 —
`ClassDef` 에 행을 더하면 저절로 따라오고, 모르는 분류로 나온 개체도
`n_detected` 에는 들어간다(화면의 분류 열에만 안 보인다). 038~040 이 세운 방향이다.

## 재 보고 버린 것 둘

- **한 질의로 묶기**(`GROUP BY slide` 하나로 11개를 대신) — **567 ms 로 오히려
  느리다.** 실행 계획을 보니 이미 `viewpoint(slide_id)` → `detection(viewpoint_id)`
  → `candidate(detection_id)` 로 타고 들어가 **필요한 것만 읽고 있었다.** 묶으면
  전체를 훑고 나서 나눈다. **"질의를 줄인다" 가 곧 "일을 줄인다" 는 아니다**
- **SQLite 프라그마** — `cache_size = -262144` 로 500 → 468 ms(6%),
  `mmap_size` 는 차이 없음. 자료가 108 MB 라 이미 페이지 캐시에 들어 있다
