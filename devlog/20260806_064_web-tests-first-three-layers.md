## 1. 시험이 `/data3/DiaRUGA` 에 사진을 썼다

**첫 실행에서 났다.** 픽스처가 만든 사진 9장과 디렉토리 4개가 운영 자료 자리에
실제로 만들어졌다.

```
/data3/DiaRUGA/photos/260801/rs23/Snap-21000.jpg      … 6장
/data3/DiaRUGA/photos/260801/bp09-0901/Snap-21000.jpg … 3장
/data3/DiaRUGA/stacked/rs23/g000_Snap-21000_focused.jpg
/data3/DiaRUGA/stacked/bp09-0901/g000_Snap-21000_focused.jpg
```

### 무엇이 안 망가졌나 — 그리고 그것이 운이었다는 것

덮어쓴 것은 없었다. 이유가 둘인데 **둘 다 우연이다.**

- 진짜 `stacked/` 는 **평면**이다(파일 1,437개가 바로 아래에 있다). 픽스처는
  `stacked/<슬러그>/` 라는 **없던 모양**을 만들어서 안 겹쳤다
- `260801` 은 **없던 촬영일**이다(진짜는 260729·260731·260803·260805)

픽스처가 `stacked/g000_Snap-21264-21267_focused.jpg` 라는 이름을 골랐거나 촬영일을
260803 으로 잡았으면 **진짜 합성본을 673바이트짜리 회색 사각형으로 덮었다.**

DB 는 안 닿았다(테스트 DB 는 인메모리였다). 폴러도 안 물었다 — `scan_nas.py` 는
`/nfs/temp-share/DiatomPhotos` 를 보고, 3단계는 DB 의 `pending|processing` 행을
본다. 둘 다 이 파일들과 무관하다. `check_db.py` 도 통과했다.

넷을 지우고 원래대로 돌려놨다.

### 원인은 순서였다

```python
class _SafeRootsMixin:
    @classmethod
    def setUpClass(cls):
        super().setUpClass()          # ← 이 안에서 setUpTestData() 가 돈다
        settings.DATA_ROOT = cls._tmp / "data"    # ← 너무 늦다
```

`TestCase.setUpClass()` 가 `setUpTestData()` 를 부르고, **픽스처가 파일을 쓰는
자리가 거기다.** 뿌리를 그 다음에 갈았으니 픽스처가 도는 동안에는 아직 진짜
`/data3` 였다. 시험 본체는 임시 뿌리를 봤고 — 그래서 `/img` 가 404 로 실패했다.

**그 404 가 아니었으면 몰랐을 것이다.** 시험은 통과하고 파일만 조용히 쌓였을
것이고, 다음에 같은 이름을 고르는 날 진짜 자료를 덮었을 것이다.

### 진짜 원인은 문을 하나만 잠근 것이다

베이스 클래스에 안전 장치를 넣긴 했었다.

```python
name = str(connection.settings_dict["NAME"])
assert name == ":memory:" or "test" in Path(name).name
```

**DB 문만 봤다.** 이 저장소가 잃으면 안 되는 것은 교정(재생성 불가)이고 그것은
DB 에 있으니 맞는 방향이었는데, `DATA_ROOT` 는 사진·산출물 쪽이라 안 봤다.
그런데 파일은 **Django 가 대신 격리해 주지 않는다** — DB 는 러너가 알아서
테스트 DB 를 주지만 파일 뿌리는 아무도 안 갈아 준다. 자동으로 안전한 쪽만
확인하고 손으로 해야 하는 쪽을 안 확인했다.

**그리고 잠갔다는 착각을 줬다.** "베이스 클래스가 확인한다" 고 머리말에 적어
놓고 그 밑에서 픽스처가 운영 자료에 쓰고 있었다 — 051 이 저장만 잠그고 우클릭
메뉴를 열어 둔 것과 같은 모양이다. **막는 것으로 끝나지 않는다는 규칙이 시험
장치에도 든다.**

### 고친 것 둘

1. **순서** — 뿌리를 먼저 갈고 `super().setUpClass()` 를 부른다
2. **쓰는 자리에서 다시 본다** — 파일을 쓰는 문을 `base.write_image` 하나로
   모으고, 거기서 `DATA_ROOT` 가 임시 디렉토리인지 확인한다. 아니면 예외다

2번이 더 중요하다. **순서에 기대는 안전은 다음에 순서가 바뀌면 조용히 풀린다** —
실제로 4겹(`LiveServerTestCase`)은 `setUpClass` 에 서버 띄우기가 한 겹 더 있어
순서가 또 다르다. 쓰는 자리에서 보면 순서가 어떻든 걸린다.

## 4. 4겹이 "사본 DB 에 붙인다" 를 대체한다

HANDOFF 3.3 의 규칙은 **브라우저는 반드시 사본 DB 에 붙인다** 였다(운영에 붙이면
클릭 한 번이 교정을 지운다 — 027). 자동 시험에서는 그 규칙이 필요 없어졌다:
`StaticLiveServerTestCase` 가 **테스트 DB 위에 서버를 띄우므로** 운영에 붙을
경로 자체가 없다. 손으로 `:8099` 를 띄우고 사본을 물리는 것보다 안전하다.

**손으로 눌러 볼 때는 기존 규칙이 그대로 남는다** — 그쪽은 사람이 주소를 고른다.

붙이면서 걸린 것 둘.

- **`LiveServerTestCase` 는 `TransactionTestCase` 다.** `setUpTestData` 로 만든
  자료가 두 번째 시험에서 사라진다(표를 시험마다 비운다). 픽스처를 `setUp` 으로
  옮겼다
- **playwright 동기 API 는 이벤트 루프 위에서 돈다.** Django 의 `async_unsafe`
  가 ORM 을 막아 `SynchronousOnlyOperation` 이 났는데, **시험 본체가 아니라
  뒤처리(flush)에서 터져서** 원인이 잘 안 보였다. `DJANGO_ALLOW_ASYNC_UNSAFE=1`
  을 브라우저 모듈에서만 켠다

## 5. CI — 뷰어만 GitHub 으로 (사용자 판단)

```
GitHub:  push → 시험 → (통과하면) 뷰어 이미지 build       234 MB
여기:    파이프라인 이미지 build/push                     7.2 GB
서버:    deploy.sh <태그>  ← 사람이 부른다                (그대로)
```

**파이프라인을 GitHub 에서 안 굽는 이유는 크기가 아니라 확인이다.** 러너에
GPU 가 없어 `segment_diatoms.py` 를 한 번도 못 돌린다 — "빌드는 됐는데 도는지는
모르는" 7.2 GB 를 Docker Hub 에 올리는 것이 되고, 그건 지금보다 나쁘다. (캐시가
10 GB 라 torch 6 GB 층이 매번 콜드가 되는 것, 업로드가 붙는 것은 그 다음이다.)

대신 의존성이 썩는 것만 주간으로 본다(`deps.yml`). **두 조각으로 나눈 것이
요점이다** — 한 덩어리로 `--dry-run` 하면 안 싸다.

- **휠**은 인덱스 둘 다 PEP 658 을 내줘서(2026-08-06 확인: PyPI 와
  `download.pytorch.org` 둘 다 `data-core-metadata`) 메타데이터만 읽는다
- **SAM-2 는 뺀다.** git 의존성이라 pip 이 메타데이터를 만들려고 격리 빌드
  환경을 세우는데 `[build-system] requires` 에 `torch>=2.5.1` 이 있어
  **`--dry-run` 인데도 몇 GB 를 받는다.** 핀한 SHA 는 내용이 안 바뀌므로 거기서
  깨지는 것은 "저장소가 없어졌다·커밋이 GC 됐다" 뿐이고 요청 하나로 확인된다

**뷰어 이미지는 태그를 밀 때만 push 한다.** 그 밖에는 굽기만 한다 — Dockerfile
이 깨진 것은 잡되 판 번호는 사람이 정한다.

**CI 는 배포하지 않는다.** `deploy.sh` 에 스냅샷·기동 게이트·smoke 가 붙어 있고,
그 판단을 자동화하면 규약이 지키려던 것이 사라진다.

### 흔들리는 것 — CI 가 잡아 줬다

31개를 함께 돌린 어느 한 번이 `errors=2` 로 끝났는데 **출력을 안 남기고 넘어갔고**
그 뒤 17회 연속 통과라 무엇이었는지 몰랐다. 짐작을 원인이라고 적지 않고
(026 의 교훈) 열린 항목으로 뒀다.

**CI 에서 같은 것이 났고, 거기서는 메시지가 남았다.**

```
django.db.utils.IntegrityError: UNIQUE constraint failed: viewer_slide.slug
Ran 6 tests in 2.563s
FAILED (errors=2)
```

같은 `errors=2` 다. 원인은 이렇다 — 표를 비우는 것은 `TransactionTestCase` 의
뒤처리(flush)인데 그것이 **살아 있는 서버 스레드와 경합한다.** 앞 시험의
페이지가 아직 이미지를 받는 중이면 그 연결이 트랜잭션을 물고 있어 flush 가
늦고, 다음 시험의 `Slide.objects.create(slug="rs23")` 가 부딪힌다. **로컬은
빨라서 잘 안 나고 러너는 느려서 난다.**

고칠 자리는 앱이 아니라 픽스처였다 — **픽스처가 제 유효성을 남의 뒤처리에
기대면 안 된다.** 청소를 기다리는 대신 시험마다 다른 슬러그를 쓴다. 그 부딪힘
자체가 없어진다.

> **시험 이름을 슬러그로 못 쓴다.** 이 저장소의 시험 이름은 한글이고
> `<slug:slug>` 는 그것을 안 받는다 — 정수 카운터를 쓴다.

CI 두 번 연속 통과를 확인했다. **경합 자체가 사라졌다고는 못 한다** — 다만
이 시험들에서 그것이 드러날 길이 없어졌다.

**교훈은 CI 쪽이다.** 로컬 17회로는 못 잡은 것을 러너가 첫 판에 잡았다. 느린
환경이 경합을 드러낸다.
