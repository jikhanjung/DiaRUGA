# 060 — 시야 목록이 개체를 만들지 않는다 (v0.6.3)

2026-08-06. 059 에서 첫 페이지를 0.12초로 만들고 나니 다음이 보였다.

```
/d/…369cm/   825 ms · SQL 1 ms · 파이썬 824 ms
```

**질의는 이미 빨랐다.** 파이썬이 개체를 물질화하는 값이었다. `v0.6.3` 으로
배포했고 **825 → 81 ms** 다.

## 겹쳐 있던 것 둘

### 1. 쓰지도 않는 묶음의 후보까지 당겼다

`_viewpoints_of` 의 `prefetch_related("detections__candidates")` 는 **그 시야에
달린 모든 검출**의 후보를 당긴다. 그런데 이 저장소는 **엔진을 두 벌 쌓아 둔다**
(`sam2-전수` · `yolo-3차`, 051).

```
RS23-GC03 369cm 의 후보 28,697개
  sam2-전수 11,048   ← 화면이 쓰는 것
  yolo-3차  17,649   ← 한 개도 안 쓴다
```

`Candidate.polygon` 이 JSONField 라 **올리는 값이 곧 파싱 비용**이다. 프로파일의
`json.raw_decode` 31,563회가 이것이었다.

`Prefetch` 로 현재 검출만 당기게 하고(`only_current=True`), **`engine_viewpoint`
는 그대로 뒀다** — 거기는 `?batch=` 로 고른 묶음의 검출을 봐야 해서 현재 것만
당기면 화면이 통째로 빈다. 그래서 기본값을 바꾸지 않고 **부르는 쪽이 고르게** 했다.

이것만으로 825 → 429 ms.

### 2. 11,048개를 만들어 370개를 그렸다

그러고도 시야마다 `detection_for_viewpoint` 로 후보를 전부 dict 로 만들고 있었다.
**이 화면이 개체에서 쓰는 것은 표지에 얹을 마스크와 그 수뿐이다** — 통과 2,462 ·
탈락 8,586 중 실제로 그리는 것은 시야당 다섯 남짓, 슬라이드 전체로 923개다.

남는 개체만 뽑는 질의 하나(`_kept_masks`)로 바꿨다. 남는 조건은 059 의 집계와
같은 규칙이고, **표시 분류도 `mask_class` 와 같은 규칙을 SQL 에 옮겨 적었다** —
사람이 지정한 것이 먼저, 되살린 것은 `manual`, 나머지는 자동 판정. 그리는 순서도
넓은 것부터로 같다(작은 개체가 안 묻히게).

`_slide_summary` 의 **details 갈래도 걷었다.** "이미 만든 dict 를 넘기면 두 번
세지 않는다" 는 것이었는데, 그 갈래가 있으려면 화면이 개체를 전부 물질화해야
한다. 059 로 SQL 이 7 ms 가 됐으므로 그 절약이 뒤집혔다. 두 길의 값이 슬라이드
11개에서 같은 것을 확인하고 SQL 쪽만 남겼다.

    825 → 429 → 81 ms       (질의 하나 · 마스크 하나 · 집계 하나)

## "썸네일에 마스크를 구워 넣으면 안 되나"

사용자가 물었다. **되지만, 이 문제의 답은 아니었다.**

비용은 **그리는 데** 있지 않았다 — 마스크 923개를 SVG 로 내보내는 것은 공짜에
가깝고, 값은 그것을 고르려고 개체 11,048개를 만드는 데 있었다. 그 자리를 고치면
구울 이유가 없어진다.

구웠을 때 잃는 것도 적지 않다:

- **사람의 교정이 그림에 박힌다.** 지우거나 분류를 바꿀 때마다 표지를 다시
  구워야 하고, 안 구우면 화면이 조용히 낡는다 — 교정은 하루에도 수백 건 바뀐다
- **켜고 끌 수 없고 테마를 못 따라간다.** SVG 는 색을 CSS 가 정해서 어두운
  화면·밝은 화면에서 각각 읽히고, 확대하면 원본 화소로 간다
- **P02 7단계에서 걷어낸 overlay JPG 가 정확히 그것이었다** — 1,496장 752 MB 를
  구워 두고 아무도 안 읽었다

그래도 **길은 열려 있다.** 표지가 지금보다 훨씬 커지거나 마스크가 시야당 수백
개가 되면 굽는 편이 싸진다. 그때는 `.thumbcache` 와 이미 있는 `v=` 갈이 규칙
(교정 시각)을 그대로 쓰면 된다.
