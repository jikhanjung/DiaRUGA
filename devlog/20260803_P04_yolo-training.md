# [계획] 사람의 검토로 검출기를 학습시킨다 (YOLO)

**작성일** 2026-08-03
**상태** 미착수
**앞선 문서** `20260729_P01_roadmap.md` (학습 계획의 원형) · `20260730_P02_db-schema.md`
(교정을 학습 자료로 쓰려고 만든 스키마)

---

## 왜 지금인가

검토가 231 시야에서 끝났고, 그것이 만든 것은 이렇다.

| | 수 |
|---|---|
| 통과 개체 (양성) | **1,473** |
| **사람이 지운 것 (음성)** | **4,056** |
| 검출기가 놓쳐 사람이 되살린 것 | **387** |
| 사람이 분류를 지정한 것 | 852 |

**음성 4,056개가 이 자료의 핵심이다.** 물체 검출에서 어려운 것은 "무엇이
규조각인가" 가 아니라 "무엇이 규조각이 **아닌가**" 인데, 그 판단이 SAM2 가 실제로
헷갈린 것들에 대해 사람 손으로 붙어 있다. 무작위 배경보다 훨씬 값어치가 크다.

되살린 387개는 **지금 파이프라인의 천장을 넘는 자료**다. SAM2 가 못 찾으면 지금은
끝인데, 사람이 찾아 표시해 뒀다. 학습하면 재현율이 SAM2 보다 나아질 수 있다.

P02 가 *"지운 것도 전부 저장한다 — 학습의 어려운 음성 표본이다"* 라고 적고
`geom` 칸을 만들어 둔 것이 여기서 쓰인다. 실제로 **교정 5,021건 전부가 기하를
갖고 있다.**

---

## 자료 실측

### 개체 크기 — 타일 크기를 정하는 근거

원본이 2752×2208 이고 개체 긴 변은 이렇다.

```
 1%   84 px      50%  199 px      95%  556 px
 5%   99 px      75%  306 px      99%  742 px      최대 1331 px
```

원본 그대로 넣으면 중앙값 개체가 화면의 **7.3%** 다. YOLO 는 640 안팎으로 줄여
학습하므로 그대로 넣으면 개체가 46 px 로 뭉개진다. **타일로 잘라야 한다.**

| 타일 | 중앙 개체가 차지 | 큰 개체(95%) | 이미지당 타일 |
|---|---|---|---|
| 512 | 39% | **109% — 잘린다** | 42 |
| **640** | **31%** | 87% | **30** |
| 768 | 26% | 72% | 20 |
| 1024 | 19% | 54% | 12 |

**640 을 기본으로 한다.** 큰 개체가 87% 라 겹침 25% 면 어느 타일에는 온전히 들어온다.
1% 에 해당하는 742 px 이상은 타일을 넘으므로, 그런 것은 원본 축소본에서 따로
잡거나(2단 추론) 그냥 놓치는 것을 감수한다 — 전체의 1% 다.

231 이미지 × 30 타일 = **약 7,000 타일.** 개체가 없는 타일이 많겠지만 그것도
배경 표본이라 버릴 이유가 없다(비율은 조정한다).

### 슬라이드별 — 나누기의 제약

| 슬라이드 | 양성 | 음성 | 이미지 |
|---|---|---|---|
| RS23-GC03 369cm | **829** | 1,624 | 66 |
| RS23-GC03 71cm | 240 | 632 | 34 |
| WAP13-GC47 450cm | 201 | 923 | 43 |
| WAP13-GC47 116cm | 153 | 536 | 47 |
| AM22-GC10B 25cm | 34 | 71 | 26 |
| RS23-GC03 231cm | 25 | 245 | 19 |
| AM22-GC10B 261cm | 3 | 96 | 27 |

**RS23 이 1,094개로 74% 다.** AM22 는 37개뿐이다. 해역이 다르면 쇄설물 배경도
다르므로, 지금 학습하면 RS23 에 맞춰진다. 이것은 자료를 더 모아야 풀리는 문제이고
계획에 그렇게 적어 둔다.

### 분류

```
rod  509 · round_frag 410 · rod_frag 252 · round 228 · eucampia 67 · 미분류 7
```

`eucampia` 가 다른 것의 8분의 1이다. 처음부터 5분류로 가면 이 분류만 성능이
안 나오고, 그 사실이 전체 지표에 묻힌다.

## 단계

### 0단계 — 재현율 기준선부터 (가장 먼저)

**지금 재현율을 모른다.** 3차 보고서 §9.4 가 적어 둔 그대로다. 정밀도는 실측했지만
(26%), 놓친 것의 비율은 되살림 387건이 있을 뿐 전수가 아니다.

기준선이 없으면 **학습한 모델이 나아졌는지 말할 수 없다.** "SAM2 보다 좋다" 를
숫자로 못 하면 이 작업의 값어치를 증명할 수 없다.

시야 **10~15개**를 골라 사람이 규조각을 **전수 표시**한다. 검출 결과를 켜지 않은
채로 보는 것이 낫다 — 이미 그려진 상자를 보면 그것에 끌린다.

- 슬라이드를 섞어 고른다(RS23·WAP13·AM22 각각)
- 이 시야들은 **평가 전용**으로 못 박는다. 학습에 넣지 않는다
- 뷰어에 "전수 표시 모드" 가 필요할 수 있다 — 지금 도구로 되는지 먼저 본다

### 1단계 — 내보내기 (`export_yolo.py`)

DB → YOLO 형식. 파이프라인 스크립트와 같은 갈래로 만든다(`Run(kind=export)`).

```
datasets/yolo/<판>/
  images/{train,val}/<슬라이드>_<시야>_<타일좌표>.jpg
  labels/{train,val}/…txt
  data.yaml
  MANIFEST.json      ← 무엇으로 만들었는지
```

**무엇을 라벨로 삼는가** — 이것이 이 단계의 핵심 판단이다.

| 자료 | 라벨 | 왜 |
|---|---|---|
| 통과 개체 (지워지지 않은 것) | **양성** | 사람이 남긴 것 |
| 사람이 되살린 것 | **양성** | 검출기가 놓쳤지만 규조각이다 |
| 사람이 지운 것 | **아무것도 안 씀** | 라벨이 없으면 YOLO 가 배경으로 배운다 |
| 검토 안 한 시야 | **통째로 제외** | 라벨의 신뢰도가 다르다 |

마지막 줄이 중요하다. 검토하지 않은 시야를 넣으면 "SAM2 가 통과시킨 것 = 정답"
이 되어 **SAM2 의 오검출까지 그대로 배운다.** 사람이 본 231 시야만 쓴다.

- **`Detection.is_current` 인 것만.** 옛 검출을 섞으면 같은 시야가 두 번 들어간다
- **폴리곤을 함께 낸다.** 통과 개체 5,428개 전부가 폴리곤을 갖고 있어
  분할(`-seg`) 학습도 가능하다. 상자만 쓰더라도 폴리곤에서 만드는 편이 정확하다
- 타일 경계에 걸친 개체는 **면적의 절반 이상이 남을 때만** 라벨로 낸다.
  조각만 남은 것을 규조각이라고 가르치면 안 된다
- `MANIFEST.json` 에 슬라이드·시야·문턱·커밋 해시를 적는다. **어떤 자료로 학습한
  모델인지 나중에 반드시 묻게 된다**

### 2단계 — 나누기

**슬라이드 단위로 가른다.** 타일이나 개체를 무작위로 나누면 같은 시야의 것이
학습과 검증에 갈라져 들어가 성능이 부풀려진다 — 같은 규조각의 다른 타일이
양쪽에 있게 된다.

슬라이드가 7장뿐이라 빠듯하다. 시작은 이렇게 본다.

```
학습:  RS23 71cm · RS23 231cm · WAP13 116cm · AM22 25cm · AM22 261cm
검증:  RS23 369cm (829개)
평가:  0단계의 전수 표시 시야 (학습·검증 어디에도 안 넣는다)
```

RS23 369cm 이 가장 크지만 검증에 쓴다 — 검증이 너무 작으면 지표가 흔들린다.

### 3단계 — 단일 분류로 먼저

```
1. diatom 하나        ← 검출이 되는가
2. rod / round        ← 형태를 가르는가
3. + 파편(_frag)      ← 온전한 것과 조각을 가르는가
4. + eucampia         ← 속 수준
```

**단계마다 재현율·정밀도를 실측한다.** 한 번에 5분류로 가면 어디서 막히는지 모른다.
`eucampia` 67개로는 지금 안 될 가능성이 크고, 그것은 자료를 더 모아야 하는 문제지
학습 설정 문제가 아니다.

### 4단계 — 학습

`ultralytics` 8.4 대를 쓴다(사내망에서 PyPI 접근 확인함). 파이프라인 이미지에
얹으면 torch 가 이미 있어 추가 부담이 적다.

**이 장비는 3060 Ti 8 GB 다.** 검출에서 `points-per-batch` 를 64 → 16 으로 내려야
했던 것과 같은 제약이 걸린다. `yolo11s` 정도에서 시작하고 배치를 보수적으로 잡는다.
큰 모델은 자료가 1,473개뿐이라 어차피 과적합한다.

**GPU 잠금(`segment_diatoms.gpu_lock`)을 함께 잡는다.** 학습이 몇 시간 도는데
그동안 폴러가 검출을 시작하면 둘 다 죽는다.

### 5단계 — 견주기

같은 평가 시야에서 SAM2+judge 와 YOLO 를 나란히 잰다.

| | 재현율 | 정밀도 | 시야당 시간 |
|---|---|---|---|
| SAM2 + judge (지금) | ? | 26% | 23초 |
| YOLO | ? | ? | ? |

속도도 함께 잰다. YOLO 가 나으면 파이프라인의 검출 단계를 바꾸는 것이 목표인데,
그러면 시야당 23초가 얼마로 줄어드는지가 실질적인 이득이다.

### 6단계 — 파이프라인에 넣는다 (성능이 증명되면)

`segment_diatoms.py` 가 백엔드를 고를 수 있게 되어 있다(`--backend sam2|sam3`).
`yolo` 를 더한다. **검출은 덮어쓰지 않고 쌓이므로**(`Detection.is_current`) 같은
시야에서 두 엔진을 나란히 비교할 수 있다 — P01 §3 이 그러라고 만든 구조다.

교정 재바인딩(`rebind.py`)이 여기서 결정적이다. 엔진을 갈면 `mask_key` 가 거의
전부 어긋나므로 IoU 로 다시 맺어야 사람의 판단이 살아남는다. **011 에서 같은
설정으로 재검출해도 exact 가 26/67 밖에 안 됐다** — 엔진을 갈면 훨씬 낮을 것이고,
그때 `bind_method="orphan"` 이 얼마나 나오는지가 이 장치의 시험대다.

## 유의

- **평가 시야를 학습에 넣지 않는다.** 한 번 섞이면 그 뒤의 모든 숫자가 무의미해지고,
  섞였다는 사실은 눈에 띄지 않는다. `MANIFEST.json` 에 어느 시야를 썼는지 적고
  `check_db.py` 같은 검사로 겹침을 막는 것을 검토한다
- **자료가 RS23 에 74% 쏠려 있다.** 다른 해역 슬라이드가 들어오면 다시 학습한다
- **`eucampia` 67개는 아직 부족하다.** 3단계에서 억지로 넣지 않는다
- 학습 자료를 만든 뒤 원본이 바뀌면(재검출·재검토) 자료와 모델이 어긋난다.
  `MANIFEST.json` 의 커밋 해시와 시야 목록이 그것을 추적하는 유일한 수단이다
- **`export_review.py`(P02 5단계)가 아직 없다.** 교정이 DB 에만 있으므로 학습
  자료의 원본도 DB 뿐이다. NAS 백업이 유일한 안전망인 상태가 계속된다

## 먼저 할 것

**0단계(재현율 기준선)를 1단계보다 먼저 한다.** 내보내기 도구는 만들면 되지만,
기준선은 사람의 시간이 드는 일이고 그것 없이는 뒤의 모든 숫자가 "좋아진 것 같다"
수준에 머문다.
