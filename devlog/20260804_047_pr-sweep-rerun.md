# 047 — P–R 곡선을 다시 뽑았다. 숫자는 그대로였고, 운영점이 하나 보인다

2026-08-04 밤. `yolo-3차` 를 새로 뽑은 김에(046) 견주기 표도 다시 만들려 했다.

## 1. 먼저 틀린 생각을 하나 버렸다

"자료를 새로 뽑았으니 P–R 곡선도 바뀔 것" 이라고 적었는데 **틀렸다.**
`pr_sweep.py` 는 **DB 를 보지 않는다** — 모델 가중치를 내보낸 데이터셋
(`datasets/yolo-v1-seg`)의 라벨과 직접 견준다. 모델도 데이터셋도 그대로이므로
숫자가 바뀔 이유가 없다.

`yolo-3차` 가 바꾼 것은 **DB 안의 검출**이고, `pr_sweep` 이 재는 것은 **모델
자체**다. 층이 다르다. 025 가 "숫자를 견줄 때는 양쪽이 같은 층인지 본다" 고
적어 둔 것을 또 밟았다.

그래도 돌린 값은 있었다 — 025 §8 의 숫자를 **지금 코드로 재확인**한 것이 된다.

## 3. 새로 보이는 것 — 계수라면 conf 0.29~0.30 이다

**최대 F1 점(conf 0.294)에서 개수비가 0.96 이다.**

`pr_sweep` 머리말이 개수비를 따로 내는 이유를 이렇게 적어 뒀다 — *"이 과제의
목적은 계수다. 개체 하나하나의 정오보다 총 개수가 맞는지가 군집 조성에 직결된다.
놓친 것과 헛본 것이 상쇄되는 자리가 있고, **그 자리는 F1 최대점과 다르다**."*

**이 모델에서는 두 자리가 거의 겹친다.** conf 0.294 에서 F1 이 최대이면서 개수비
0.96, conf 0.30 에서 0.94 다. 놓친 83개와 헛본 70개가 서로 상쇄된다.

반면 HANDOFF 가 운영점 후보로 들던 **conf 0.033 은 재현율을 SAM2 와 맞춘 자리**라
개수비가 4배 가까이 부푼다. 그 값은 "같은 재현율에서 정밀도가 1.7배" 를 말하려고
고른 **비교용 좌표**이지 운영점이 아니다. 둘을 섞어 읽으면 안 된다.

> **다만 이 개수비는 `val_slide` 한 장의 것이다.** 슬라이드마다 개체 밀도가
> 다르고, judge 의 정밀도가 AM261 에서 1.0% 인 것처럼 **한 문턱이 전부에 맞지
> 않는 것이 이 자료의 성질**이다. 운영점을 정하기 전에 AM 계열에서 재 봐야 한다
> (HANDOFF 4.2 의 4번, 아직 안 했다).

## 4. 돌리는 법 (이 머신에서)

`pr_sweep.py` 는 `ultralytics` 가 필요해 **파이프라인 컨테이너에서** 돈다.
경로 기준이 `Path(__file__).parent` 라 컨테이너 안에서는 `/app` 이 되는데,
**데이터셋은 이미지에 없다** — 물려 줘야 한다.

```bash
cd /srv/diatom && docker compose run --rm \
  -v /data3/diatom/datasets:/app/datasets:ro pipeline \
  python pr_sweep.py --models seg --split val_slide \
  --json /data3/diatom/logs/pr_seg_valslide.json
```

**`detect` 모델은 이 머신에 없다**(`/app/runs/detect` 없음, `segment` 만 있다).
가져오지 않기로 했다 — 025 가 이미 seg 를 기본으로 정했고
(mAP50-95 가 detect 0.39 → seg 0.52), detect 는 견줄 이유가 없다.
`--models seg` 를 명시해야 하는 이유가 그것이다.

곡선 전체는 `/data3/diatom/logs/pr_seg_valslide.json` (저장소 밖).
