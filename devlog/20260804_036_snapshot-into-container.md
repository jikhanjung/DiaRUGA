# 036 — 배포 전 스냅샷을 컨테이너 안으로, 그리고 딸려 나온 것 셋

2026-08-04

035 에서 "DB 를 만지는 일은 한 문으로만" 을 세웠는데 구멍이 하나 남아 있었다.
`deploy.sh` 의 배포 전 스냅샷이 호스트 venv 로 `backup_db.py` 를 부르고 있었다.
그것을 `dbrun.sh` 로 옮겼다. 옮기고 나서 셋이 더 나왔다 — **문을 하나로 모으니
그동안 안 보이던 것들이 한자리에 모여 보였다.**

## 1. 옆 모듈까지 따라가야 한다

`backup_db.py` 는 `db_sentinel` 을 부른다. 스크립트 하나만 옮겨 놓으니
컨테이너 안에서 `ModuleNotFoundError` 로 죽었다.

`dbsync.sh` 가 **최상위 임포트를 훑어 저장소에 있는 것만 따라간다.** 지금은
`backup_db.py → db_sentinel.py`, `check_db.py → judge.py` 가 자동으로 함께 간다.
Django 앱(`viewer` 등)은 따라가지 않는다 — 그건 이미지 안의 `/app` 에서 온다.

들여쓰인 임포트(함수 안의 늦은 임포트)는 보지 않는다. 그건 Django 를 세운 뒤에
부르는 것이라 역시 `/app` 에서 온다.

## 2. 컨테이너가 UTC 라 사본 이름이 아홉 시간 어긋났다

첫 시험 사본의 이름이 `diatom_20260804_041906_…` 이었다. 호스트는 13:19 였다.
`Django` 의 `TIME_ZONE = "Asia/Seoul"` 은 Django 의 시각에만 미치고,
`backup_db.py` 의 `time.strftime` 은 OS 시간대를 본다.

**이름만 어긋나는 문제가 아니다.** 정리 규칙이 이름순 정렬이라

```python
old = sorted(OUT.glob(pat))[: -args.keep]
```

UTC 이름(04:19)과 KST 이름(13:16)이 한 디렉토리에 섞이면 **나중에 뜬 것이 앞에
정렬되어 가장 새 사본을 지우고 옛것을 남긴다.**

`compose` 의 `x-common` 에 `TZ: Asia/Seoul` 을 넣어 컨테이너 전부를 호스트에
맞췄다. `dbtool` 은 `environment:` 를 따로 두어 앵커를 통째로 덮으므로 **거기에
다시 적어야 한다** — 빠뜨리면 그 컨테이너만 UTC 로 돈다.

## 3. `--keep 20` 이 아무것도 안 걷고 있었다

배포 전 스냅샷이 24장까지 쌓여 있었다. `--keep 20` 을 주는데도 그랬다.

```python
AUTO_GLOB = "diatom_????????_??????.db"      # 꼬리말 없는 이름만
```

로테이션은 시간별 자동 사본만 굴린다. 사람이 `--note` 로 뜬 것은 작업 중에
되돌릴 지점이라 걷어 가면 안 되기 때문이고, 그 판단은 옳다. 그런데 배포 전
스냅샷은 `_pre-deploy-v0.1.9` 라는 꼬리말이 붙어 이 glob 에 안 걸린다.

`--flat` 은 "이 디렉토리는 이 종류 전용이다" 는 뜻이다(`pre_deploy/`). 그때는
꼬리말이 붙은 것도 굴린다. 26장 → 20장으로 떨어졌다. `.part`·`.corrupt` 는
`.db` 로 끝나지 않아 이 glob 에 안 걸린다.

곁들여, 배포 넷이 `pre_deploy/manual/` 로 새어 있던 것도 올려 두었다 —
`/srv/diatom/bin/deploy.sh` 가 `--flat` 이 붙기 전 판이었다. 거기 있으면
로테이션의 glob 이 애초에 안 내려간다.

## 배포가 이미지에 매이게 됐다

스냅샷이 `dbtool` 로 도니 **배포 전 스냅샷이 이미지를 필요로 한다.** 이 자리에서는
`.env` 의 `IMAGE_TAG` 가 이미 새 판이고 이미지도 받아 둔 뒤라 문제가 없고,
`backup_db.py` 는 Django 를 안 쓰고 sqlite3 백업 API 만 쓰므로 어느 판의
이미지든 하는 일이 같다. 실패하면 `DIATOM_SKIP_SNAPSHOT=1` 로만 넘어간다 —
스냅샷은 되돌아올 지점이라 조용히 건너뛰지 않는다.
