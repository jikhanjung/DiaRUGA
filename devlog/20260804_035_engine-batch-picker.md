# 035 — 검출 화면에서 묶음을 고른다, 겹친 검출을 정리한다

2026-08-04

## 하려던 것

검출 화면(`/engine/`)에서 **같은 시야를 그대로 두고 엔진만 갈아 끼우는 것.**
지금까지는 묶음을 바꾸려면 목록으로 나갔다 다시 들어와야 했고, 그러면 어느
시야를 보고 있었는지 잃었다. 견주기는 같은 자리를 번갈아 보는 일이라 그
왕복이 곧 견주기를 못 하게 만든다.

## 붙이고 나서야 드러난 것

칸 셋을 그려 놓고 눌러 보니 **SAM2 칸이 빈 화면**이었다. 두 가지가 겹쳐 있었다.

### 1. 화면이 "쌓아 둔 것" 만 보고 있었다

이 화면은 처음부터 `is_current=False` 인 검출만 봤다. 검토 화면과 겹치지 않게
하려는 뜻이었고, YOLO 를 `--keep-current` 로 넣어 견주던 동안은 맞는 규칙이었다.

그런데 **SAM2 묶음은 결과의 대부분이 현재로 올라가 있다** (448건이 현재, 324건이
쌓인 것). 묶음을 고를 수 있게 되자 사람이 그 규칙의 뒷면을 직접 누르게 됐다.

묶음이 **낸 것 전부**를 보이도록 바꿨다. 읽기 전용이고 교정을 얹지 않으므로
검토 화면을 건드리지 않는다. 목록의 "쌓인 검출" 칸은 "검출 (N 현재)" 가 됐다.

### 2. 엔진마다 검출을 다는 자리가 다르다

SAM2 는 합성본 한 장에만 달고, YOLO 는 프레임마다 + 합성본에도 단다. 화면은
프레임만 그리고 있어서 SAM2 묶음은 그릴 것이 없었다. 합성본도 프레임과 같은
자격으로 캐러셀에 넣었다(`STACK_KEY = "__stack__"` — `Snap-…` 과 겹칠 수 없다).

## 칸의 수와 화면의 수가 어긋났다

칸에 개체 수를 적고 나니 칸은 552, 화면은 151 이었다. 원인이 둘이다.

- **칸은 원시 후보를 셌고 화면은 통과한 것만 그린다.** 칸도 `passed=True` 만 센다
- **같은 자리에 검출이 둘씩 쌓여 있었다.** 화면은 그중 하나를 고르고, 칸은 다 더했다

고르는 규칙을 `data._engine_pick` 하나로 모았다 — **현재로 올라간 것, 그 다음
번호가 큰 것.** 시야 화면·시야 목록·묶음 칸이 모두 그것을 쓴다. 다섯 시야 ×
세 묶음에서 칸과 화면이 전부 같아졌다.

## 겹친 검출을 지웠다 (`prune_detections.py`)

검출은 덮어쓰지 않고 쌓는 것이 원칙이지만, **같은 묶음 안에서 같은 이미지에
둘씩 쌓인 것은 기록이 아니라 찌꺼기다.** 두 경로로 생겼다.

- 빠진 프레임만 다시 돌려도 `--keep-current` 는 이미 끝난 것까지 다시 쌓는다
- 첫 시도가 죽어 다시 돌린 것이 남았다 (SAM2 #37 → #39)

둘 다 같은 엔진이 같은 이미지를 같은 설정으로 본 것이라 나중 것이 앞의 것을
온전히 대신한다. **묶음을 넘어서는 지우지 않는다** — 서로 다른 엔진이 같은
이미지를 본 것을 나란히 두는 것이 이 화면의 목적 전부다.

지운 것: 검출 2,107건 · 후보 69,863건. 전부 `is_current=False` 였다.

| 묶음 | 지운 검출 | 남은 검출 |
|---|---|---|
| sam2-전수 | 79 | 324 (+448 현재) |
| yolo-1차 | 131 | 1,632 |
| yolo-2차 | 1,897 | 1,625 |

`superseded_by` 가 `SET_NULL` 이라 옛 검출을 지워도 현재 검출이 딸려 가지
않는다. 교정은 `mask_key` 로 붙어 있어 `Candidate` 가 지워져도 남는다. 그래도
지우는 것은 지우는 것이라 `--apply` 는 사본을 뜬 뒤에 돌렸고, `check_db.py` 로
확인했다.

## DB 를 만지는 문을 하나로 (`dbtool` · `dbrun.sh` · `dbsync.sh`)

사용자가 겪은 것: **컨테이너 안팎에서 번갈아 DB 작업을 하면 깨지곤 한다.**

원인이 "안/밖" 자체는 아니다 — 어느 쪽이든 같은 ext4 파일이고 SQLite 잠금은
정상으로 작동한다. 이 저장소가 실제로 당한 것은 둘이고, 둘 다 **환경이 두 벌**
이어서 생겼다.

- **코드 판이 어긋났다.** 컨테이너의 낡은 `models.py` 가 `Site.area` 를 몰라
  NAS 반입이 죽었다 (→ `db_default`)
- **소유자가 바뀌었다.** root 로 돈 컨테이너가 `diatom.db` 를 가져가 호스트
  스크립트가 못 쓰게 됐다 (→ `user: "1000:1000"`)

### 첫 판은 틀렸다 — 저장소를 `/app` 에 덮어 물렸다

처음에는 저장소를 `/app` 에 물렸다. 새 스크립트를 쓸 때마다 7 GB 이미지를 다시
굽지 않으려는 뜻이었는데, **그러면 컨테이너가 배포된 코드가 아니라 편집 중인
작업 트리로 DB 를 만진다.** 막으려던 "환경이 두 벌" 을 이름만 바꿔 다시 만든
꼴이다. 작업 트리의 `models.py` 가 아직 마이그레이션하지 않은 칼럼을 들고 있으면
그대로 프로덕션 DB 에 닿는다.

### 고친 판 — `/app` 은 이미지 것, 스크립트만 밖에서

```
/app                     이미지 안. Django·모델 — 뷰어 컨테이너가 쓰는 그것
/srv/diatom/scripts      밖에서 물린다. 스크립트 파일뿐 (읽기 전용)
DIATOM_APP=/app          스크립트가 Django 를 어디서 찾을지
```

```bash
deploy/host/dbsync.sh check_db.py     # 저장소 → /srv/diatom/scripts
deploy/host/dbrun.sh  check_db.py     # 컨테이너 안에서 돈다
deploy/host/dbsync.sh --list          # 옮겨 둔 것이 저장소와 어긋났는가
```

**옮겨 놓은 것만 돌아간다.** 저장소에서 고친 것이 곧바로 프로덕션 DB 에 닿지
않는다 — `docker-compose.yml` 을 `/srv` 로 복사해 쓰는 것과 같은 갈래다.
저장소는 만들고, `/srv` 는 돌린다. 어긋나면 `dbrun.sh` 가 알리되 막지는 않는다
(일부러 옛 판을 돌리는 일이 있고, 무엇이 도는지만 알면 된다).

확인:

```
django    5.2.16 /usr/local/lib/python3.12/site-packages/django/__init__.py
models    /app/web/viewer/models.py
DB        /srv/diatom/db/diatom.db
저장소가 물려 있나: False
```

**딸려 오는 제약이 하나 있다.** `/app` 은 `IMAGE_TAG` 가 가리키는 판이라, 아직
배포하지 않은 모델 변경이 필요한 스크립트는 여기서 못 돈다. 조용히 어긋나는
것보다 낫다 — 그러라고 이렇게 둔 것이다.

### 스크립트가 저장소 밖에서도 Django 를 찾게

부트스트랩이 `Path(__file__).parent / "web"` 이라 스크립트를 옮기면 깨졌다.
`django.setup()` 을 하는 12개 전부를 고쳤다.

```python
APP = Path(os.environ.get("DIATOM_APP") or Path(__file__).resolve().parent)
```

저장소에서 그냥 돌리면 예전과 같다. 덤으로 `verify_db.py` 의 버그가 하나
드러났다 — 뒤쪽에서 `ROOT / "web"` 을 넣고 있었는데 `ROOT` 는 저장소가 아니라
`DATA_ROOT`(`/data3/diatom`) 였다.

## 데이터셋 속성 페이지를 탭으로

슬라이드·코어·지역 셋이 세로로 길게 늘어서 있었다. 탭으로 갈랐다.

**폼은 하나 그대로다.** 탭은 보이고 안 보이고만 가르고 저장은 세 칸을 함께
보낸다 — 폼 셋으로 쪼개면 지역을 고치려다 슬라이드에 적어 둔 것이 날아간다.
자바스크립트가 없으면 셋 다 펼쳐진 예전 모습이 된다(`.tabbed` 를 JS 가 붙이고
감추는 규칙은 그 클래스 아래에만 있다). 보던 탭은 주소의 `#` 에 남긴다.
