## 덮어써지던 것을 확인했다

`stack_report.json` 은 출력 디렉토리에 **하나만** 쓰였다. `stacked/` 를 세
슬라이드가 공유하므로 나중에 돌린 것이 앞의 것을 지웠다. HANDOFF 에 "덮어써졌다"고
적혀 있었지만 얼마나인지는 몰랐는데, 세어 보니 이렇다:

| 슬라이드 | 합성본 | 품질 지표 |
|---|---|---|
| rs23 | 28 | **전부 없음** |
| wap13-gc47_116cm | 21 | **전부 없음** |
| wap13-gc47_450cm | 32 | 있음 (마지막에 돌린 것) |

**81개 중 49개가 `align_failed`·`object_px_frac`·`sharpness_*`·`gain`·`ref_frame`
을 잃은 상태였다.** 합성이 잘 됐는지 판단할 근거가 없었다는 뜻이다.

이제 시야마다 `Stack` 행이라 덮어쓸 자리가 없다. 다시 합성해서 49개를 되찾았다.

## 경로는 DB 가 안다

`groups_*.json` 의 `dir` 이 `260729/RS23-GC03 71cm` 를 가리킨 채 남아 있었다 —
사진을 `/data3/diatom/photos/260729/…` 로 옮겼는데(P03) JSON 은 그대로였다.
git 이 추적하는 파일이라 조용히 낡아 있었던 것이다.

그래서 **경로를 JSON 에서 읽지 않기로 했다.** `dir` 은 어느 슬라이드인지 알아내는
데만 쓰고(폴더 이름으로 `Slide` 를 찾는다), 실제 파일 위치는 `slide.image_dir` 에서
얻는다. 사진을 또 옮겨도 JSON 을 고칠 필요가 없다.

폴더 이름이 겹치면(같은 슬라이드를 다른 날 다시 촬영하면 — `photos/<촬영일>/<슬라이드>/`
구조라 실제로 가능하다) 조용히 하나를 고르지 않고 `--slide` 로 물어본다.

## 이미 합성한 것은 스스로 건너뛴다

예전에는 `run_batch.sh` 가 `stacked/<tag>_focused.jpg` 가 있는지 봐서 건너뛸
그룹을 골라 `--only` 로 넘겼다. 이제 스크립트가 DB 에 `Stack` 행이 있는지 묻는다.
셸에서 20줄이 사라졌고, 자동 수집(P03 5단계)에서 중간에 끊긴 작업을 이어 돌리기가
쉬워진다. 다시 합성하려면 `--force`.

## 그룹 하나마다 커밋한다

합성이 그룹당 12초쯤 걸린다. 전체를 한 트랜잭션으로 묶으면 그동안 뷰어의 쓰기가
막히고, 중간에 끊기면 한 시간치를 통째로 잃는다. `Run` 행은 시작할 때 만들고
끝에 `done` 으로 닫되, `Stack` 행은 그룹마다 짧게 커밋한다.

`segment_diatoms.py` 는 이렇게 하면 **안 된다** — `is_current` 이동과 교정
재바인딩은 한 트랜잭션이어야 한다. 성격이 다른 작업이다.

## 밟은 것 — 배율을 반올림할 뻔했다

`stack_group()` 이 JSON 리포트용으로 `round(um_per_pixel, 8)` 을 하고 있었다.
그 반환값을 그대로 `Stack` 에 넣었더니 사이드카·`Frame` 의 전정밀도 값과 어긋났다.

```
Frame.um_per_pixel = 0.11259920634920635
Stack.um_per_pixel = 0.11259921            ← 반올림된 값이 들어감
```

값 자체는 상대오차 1e-8 이라 계측 결과가 달라지지 않지만, `check_db.py` 의
**"배율이 하나다"** 검사가 둘로 갈라진다. 배율은 계측의 기준이라 반올림하지
않기로 했다. 진단용 수치(`sharpness_*`, `object_px_frac`)는 그대로 반올림한다.

이전/이후를 칸별로 찍어 대조하지 않았으면 못 봤을 것이다.
