**작성일** 2026-07-31
**커밋** `ae078aa` … `0fef61a` (8건)

006 에서 데이터를 DB 로 옮겼다. 이번에는 그 위에서 두 가지를 했다 — **파이프라인
스크립트를 DB 로 옮기기 시작**했고(P02 6단계), 그 첫 조각인 `refilter` 를 **웹으로

```
image → run → 검출 base → threshold filter → filtered 결과 → 사용자 작업 → 최종
              (불변)        ← 이번에 surface →   (파생)        (사람)
```

## 1. `refilter.py` 를 DB 로 (P02 6단계 시작)

가장 작고(119줄), 이득이 바로 생기고, `segment_diatoms.py` 에 필요한 조각을 먼저
검증할 수 있어서 여기부터 했다.

### 판정 규칙을 `judge.py` 로 떼어냈다

`classify`·`dedupe`·문턱 기본값이 `segment_diatoms.py` 안에 있어서 `refilter` 가
그것을 import 했다. **문턱만 바꾸는 일에 torch·cv2 를 통째로 끌고 오는 셈**이다.

- 두 스크립트가 **같은 함수**를 쓴다 — 두 곳에 적으면 "다시 걸렀더니 결과가
  달라졌다" 가 조용히 생긴다
- torch 없이 import 된다. 뷰어와 처리를 갈라 담을 때(P01 §5) 이 규칙은 가벼운
  쪽에 있어야 한다
- 문턱 기본값 11개도 여기가 유일한 정의다

### UPDATE 한 번이 됐다

통과분·탈락분을 도로 합치던 코드가 **통째로 사라졌다** — 한 표에 `passed` 칼럼이기
때문이다. 스키마에서 두 무리를 합친 이유가 여기서 회수됐다.

```
124 시야 재적용: 2초 → 0.9초
```

속도보다 중요한 것은 **문턱이 `ThresholdSet` 행으로 남고 실행이 `Run` 에 기록된다**는
점이다. 예전에는 결과 JSON 마다 문턱이 복사됐고 다시 거르면 덮어써져서, "원형
669 → 514 가 언제 무슨 문턱으로 바뀌었나" 에 답할 수 없었다.

**주지 않은 문턱은 그 검출이 지금 쓰는 값 그대로다.** `--round-texture-min` 하나를
바꾸려다 나머지 열 개가 조용히 초기화되면 안 된다.

## 2. 문턱 조정을 웹으로

### 풀어야 했던 문제

로드맵 P01 §6 에 "문턱 조정 UI" 가 있었지만, 그대로 만들면 쓸모가 없다. 사용자가
정확히 짚었다.

> 문턱값 조정은 시야 하나를 보면서 하게 될 텐데, 그 조정에 의해 다른 시야들도
> 영향을 받잖아. 그걸 바로 확인할 수가 없으니 여러 시야를 일일이 확인해야 되는 거지.

### 재 보니 답이 나왔다

| | |
|---|---|
| 전체 재판정 (개체 18,936) | **50 ms** |
| 문턱을 바꿔도 판정이 뒤집히는 개체 | 전체의 **0.4~3.3%** |
| areolae 1500 → 2000 일 때 영향받는 시야 | **57/124** — 나머지 67개는 볼 이유가 없다 |
| 시야 하나 폴리곤 | 29 KB · 판정만 돌려주면 2.8 KB |

**124 시야를 다 볼 게 아니라 바뀌는 것만 보면 된다.** 그리고 그것을 즉시 보여줄
만큼 빠르다.

### 화면 — 시야를 2컬럼으로, 영향 큰 순으로

사용자가 제안한 형태다. 크롭만 보여주는 것보다 낫다 — **맥락이 남는다.** "이게
규조각인가" 를 판단하려면 주변 쇄설물과의 대비가 보여야 하는데, 크롭은 그것을
잘라 낸다.

```
┌ 슬라이더 11개 ──────────────┐ ┌ 요약 ─────────────┐
│ 원형 areolae ▁▃▅▇ 2000      │ │ 2522 → 2440 -82   │
└─────────────────────────────┘ │ 영향 시야 57/124  │
                                 │ [지금값][기본값][적용]│
┌ g39  20→16 −4 ┐ ┌ g1  48→44 −4 ┐
│ [사진 + 마스크] │ │ [사진 + 마스크]│    ← 영향 큰 순
└────────────────┘ └───────────────┘
```

**판정은 서버가 한다**(`judge.py` 하나). 규칙을 JS 로 복사하면 두 곳이 어긋나는데,
방금 `judge.py` 로 하나로 모은 것과 정반대가 된다. 폴리곤은 시야마다 한 번만 받아
캐시하고, 슬라이더를 움직일 때는 **판정만**(`mask_key → cls`) 다시 받아 색을 바꾼다.
미리보기 왕복 **212 ms**.

미리보기와 적용이 **같은 함수**를 쓴다 — 갈라지면 "보고 정한 것과 다른 결과" 가
나온다.

### 적용 단위 — 시야마다 다르게 두지 않는다

"시야별로 조정할 수도 있잖아" 라는 물음에 데이터로 답했다.

| 슬라이드 | 텍스처 중앙 | IoU 중앙 | 장축 중앙 |
|---|---|---|---|
| RS23-GC03 71cm | 4,137 | 0.836 | 19.7 µm |
| WAP13-GC47 116cm | 2,620 | 0.851 | 18.8 µm |
| WAP13-GC47 450cm | 3,143 | 0.854 | 16.4 µm |

그리고 **같은 슬라이드 안에서도 시야별 텍스처 중앙값이 1,830 ~ 11,551 로 6배 넘게
벌어진다.** 이것은 촬영 조건 차이가 아니라 **그 시야에 무엇이 들어 있느냐**의
차이다 — 큰 규조각이 많으면 높고 작은 것만 있으면 낮다.

문턱을 시야마다 맞추면 **바로 그 차이를 지운다.** 각 시야에서 비슷한 개수가
나오도록 조정하는 셈이고, 그러면 깊이별·지역별 비교가 *측정이 아니라 조정의
산물*이 된다. 이 시료의 목적이 그 비교인데 신호를 문턱으로 평평하게 만드는 것이다.

배율도 전부 같다(0.112599 µm/px, scale 1.0) — 한 세션·같은 광학계다. 슬라이드
단위로 가를 근거조차 지금은 없다.

**결론**: 적용은 전역 또는 슬라이드. 시야 단위는 미리보기에만. 문턱이 갈라져 있으면
화면이 경고한다. 스키마는 시야 단위 문턱을 계속 허용한다(이력과 예외를 정직하게
기록하려고) — **정책은 UI 가 지킨다.**

시야 하나를 빼야 할 때는 문턱을 흔들지 말고 **제외 표시**가 맞다. 문턱을 바꾸면 그
시야만 기준이 달라진 채 집계에 섞이지만, 제외하면 빠지고 이유가 남는다.

### 쓰면서 고친 것 셋

만들자마자 사용자가 써 보고 지적한 것들이다. 셋 다 **만든 사람은 모르는** 종류다.

**1. "영향받는 것만" 체크박스가 헛돌았다.** 서버가 이미 영향 큰 순으로 잘라 보내는데
클라이언트가 또 걸렀다. 영향받는 시야가 24개를 넘으면 잘려 온 것이 이미 전부
영향받는 것이라 필터가 아무것도 안 하고, 영향이 0개면 켜는 순간 화면이 텅 빈다
(첫 화면이 바로 그 경우다). **무엇을 보여줄지는 서버가 정하게** 했다. 끄면 영향
없는 시야도 섞이게 했다 — 안 그러면 켠 것과 구분이 안 된다.

**2. 들어오는 검출이 안 보였다.** 초록 테두리로 두었는데 **원형 마스크가 초록**이라
그 위에서 묻혔다. 분류에 쓰는 색이 여섯 가지(파랑·초록·보라·청록·분홍·빨강)라
그중 하나를 고르면 반드시 어딘가와 겹친다. **노랑**(`#ffd23f`)이 유일하게 안 겹치고,
이 앱에서 선택 표시에 쓰는 색이라 "지금 볼 것" 이라는 뜻도 맞는다. 거기에 어두운
후광을 먼저 깔았다(폴리곤을 두 번 그린다) — 밝은 배경에서는 노랑도 묻힌다.

**3. 기존 검출을 끌 수 있어야 했다.** 끄면 바뀌는 것만 남아 찾기가 훨씬 쉽다.

## 3. 무결성 검사 (`check_db.py`)

### 왜 필요해졌나

문턱을 사람 손에 넘기면서 **한 가지가 분명해졌다.**

`passed`·`cls`·`reject` 는 저장된 사실이 아니라 **순수 함수의 캐시**다.

```
검출 base (지표, 불변)  +  threshold filter (파라미터)  ──→  filtered 결과 (파생)
```

확인해 보니 저장된 판정과 다시 계산한 판정이 **18,936개 전부 일치**했다. 즉 지우고
다시 계산해도 같다 — 그래서 문턱 실험이 안전하고, 되돌리기가 손실 없이 된다.

**캐시라면 어긋날 수 있다.** 어긋나는 자리가 셋이다.

1. **부분 갱신 후 중단** — `refilter` 가 도는 중에 죽으면 앞쪽은 새 문턱, 뒤쪽은
   옛 문턱
2. **`Detection.thresholds` 만 바꾸고 `Candidate` 를 안 고침**(또는 반대) —
   "1500 이라고 적혀 있는데 실제 판정은 2000 짜리" 가 된다
3. **`judge.py` 규칙을 고치고 재판정을 잊음** — 옛 규칙의 결과가 남는다

**이 종류는 예외가 나지 않고 그냥 틀린 숫자를 보여준다.** 개수도 그럴듯하고 화면도
멀쩡하다. 그리고 그 숫자가 논문에 실릴 개수다.

### 검사 여섯 가지 — 1초

```
1. 판정 == 지표 + 문턱          캐시가 맞는가
2. 시야마다 현재 검출이 하나      둘이면 뷰어가 어느 것을 보여줄지 모른다
3. 교정이 붙어 있다 · 링크 · geom  고아·기하 누락
4. 분류가 ClassDef 에 있다       정의 없는 분류는 이름도 색도 없이 나온다
5. 파일이 있다 · 배율이 있다·섞이지 않았다
6. 문턱이 갈라져 있지 않다
```

### 통과만 하는 검사는 쓸모가 없다

일부러 네 곳을 깨뜨려 확인했다. 넷 다 잡혔고, 특히 2번 시나리오를 이렇게 짚는다.

```
!! 판정 == 지표 + 문턱          4건
   738_1166_88_103:  저장 (True, 'round', '') != 계산 (False, '', '원형areolae부족')
   574_409_157_317:  저장 (False, '', '원형기준미달') != 계산 (False, '', '원형areolae부족')
```

**탈락 사유까지 비교**하므로 개수는 같은데 사유만 틀린 경우도 걸린다.

처음 고른 시야에서는 문턱을 2000 으로 바꿔도 판정이 안 바뀌었다(1500~2000 사이
텍스처를 가진 원형이 그 시야에 없었다). 판정이 실제로 달라지는 시야를 골라 다시
시험해야 했다 — **검사가 잡는지 보려면 잡힐 조건을 만들어야 한다.**

### `verify_db.py` 와의 관계

두 스크립트의 역할이 갈렸다.

| | |
|---|---|
| `check_db.py` | **DB 스스로 앞뒤가 맞는가.** JSON 과 무관하므로 계속 유효하다 |
| `verify_db.py` | **이전 직후 한 번.** 7단계가 끝나면 역할이 사라진다 |

그리고 **`verify_db` 의 교정 항목이 어긋나는 것은 이제 정상이다.** DB 가 원본이고
`review/*.json` 은 이전 시점 스냅샷이라, 그 뒤로 사람이 교정한 만큼 벌어진다.
실제로 오늘 하루에 교정이 1,338건 바뀌고 라벨이 174 → **291개**로 늘었다
(`round_frag` 54→119, `eucampia` 12→21). 그 뜻을 코드에 적어 두었다.

## 4. 목록 화면 다듬기

- **싱글턴 배지를 없애고 반대로 표시했다.** 34개 중 28개가 사진 여럿이라 그쪽에
  배지를 달면 목록이 배지로 덮인다. 썸네일 우상단에 **인스타그램 방식 아이콘**
  (앞 장은 둥근 네모, 뒤 장은 위·오른쪽 모서리만)을 넣었다. 이 형태가 "여러 장"
  이라는 뜻으로 이미 널리 읽히므로 설명이 필요 없다
- 판을 깔지 않고 **그림자로 띄웠다.** 썸네일은 밝기가 제각각이라 흰 선만으로는
  밝은 사진에서 묻히는데, `drop-shadow` 는 어두운 사진에서도 거슬리지 않는다
  (검은 판은 어두운 사진 위에서 네모난 얼룩이 된다)
- **검토 완료 배지를 빨강으로.** 합성됨·개수 배지가 초록이라 그 사이에서 안 보였다
- 문턱 이력에 **바뀐 것만** 보여준다. 웹에서 적용하면 슬라이더 11개가 통째로
  기록되는데 그대로 늘어놓으면 무엇을 바꿨는지 안 보인다. 불러올 때는 11개를 다 쓴다
