# 목록 화면이 1.3초 걸리던 것 — 개수를 세려고 개체를 다 올리고 있었다

**작성일** 2026-08-03

---

## 증상

`/diatom/` 이 눈에 띄게 느렸다. 재 보니 **1.32초**이고 전부 서버 쪽이다
(첫 바이트까지 1.32초, 전송은 80 KB).

## 어디에 쓰였나

```
datasets()      1.23초 · 질의 606개 · DB 0.05초
map_points()    0.01초 · 질의  24개
```

**질의는 606개인데 DB 시간은 0.05초다.** SQL 이 느린 것이 아니라 파이썬이 일을
하고 있었다. 프로파일러가 가리킨 곳:

```
datasets()                1.23s
 └ _slide_summary()       1.21s   (슬라이드 7장)
    └ detection_for_viewpoint()  0.64s   (시야 270개)
       └ _apply_review()         0.51s
```

`_slide_summary` 는 목록의 숫자 열 몇 개(검출·봉상·원형·사람지정)를 낸다. 그런데
그것을 얻으려고 **시야마다 검출 dict 를 통째로 만들고 있었다** — 개체 34,219개를
폴리곤까지 파이썬 dict 로 올린다. 폴리곤만 9 MB 다.

개수를 세려고 자료를 전부 물질화한 것이다. 그리고 이 비용은 **슬라이드 수에
선형으로 는다** — 지금 7장에 1.2초면 20장이면 3.5초다.

## 고친 것 — 세는 일은 SQL 이 한다

`_summary_by_sql()` 을 두고 개수를 집계로 낸다. dict 를 만들지 않는다.

```
전부 올리기   0.67초
폴리곤 빼고   0.52초
SQL 집계만    0.00초
```

어려운 부분은 **판정 규칙이 `_apply_review` 와 같아야 한다**는 것이다. 다르면
목록과 상세 화면의 숫자가 어긋나고, 그 숫자가 보고서에 실린다. 규칙은 셋이다.

```
남는 개체 = 통과분 − 사람이 지운 것 + 탈락분 중 사람이 되살린 것
분류     = 사람이 지정한 것 > (되살린 것은 신장비로 짐작) > 자동 판정
사람지정 = 통과분만 센다
```

`Exists` 서브쿼리로 지움·되살림을, `Subquery` 로 사람이 지정한 분류를,
`Case/When` 으로 표시 분류를 낸다. 되살린 개체의 짐작 규칙(`_guess_cls`)은
경계값까지 그대로 옮겼다 — 1.4 미만이면 원형, 2.0~20.0 이면 봉상.

### 숫자가 같은지 대조했다

성능을 고치면서 값이 조용히 바뀌는 것이 가장 무섭다. 슬라이드 일곱 장에 대해
옛 방식과 SQL 방식을 나란히 돌려 여덟 항목을 맞춰 봤다.

```
n_detected · n_auto · n_labeled · n_rod · n_round
detected_groups · mean_detected · class_counts
```

**7장 × 8항목 전부 일치.**

## 상세 화면은 그대로 뒀다

`dataset_detail` 은 시야마다 개체를 실제로 그려야 하므로 dict 가 필요하다. 거기서
이미 훑은 결과를 `_slide_summary(slide, details)` 로 넘기는 길도 그대로 남겼다 —
두 번 세지 않는다.

```
/                        0.31초
/d/rs23/                 0.16초
/d/…369cm/               0.51초   (시야 74개, 375 KB)
```

## 되짚어 보면

이 함수는 슬라이드가 3장일 때 쓴 것이다. 그때는 개체가 18,936개였고 목록이
0.3초쯤이었을 테니 아무도 느리다고 하지 않았다. **자료가 늘면서 설계가 뒤늦게
드러난 경우**다.

같은 모양이 하나 더 있을 수 있다 — `_candidate_rows()` 가 `/detections/` 와
`/crops/` 에서 데이터셋 전체의 개체를 한 목록으로 모은다. 거기는 개체를 실제로
쓰므로 dict 가 필요하지만, 페이지 나눔 없이 전부 만든다면 같은 문제가 된다.
369cm 슬라이드(2,462 통과)에서 확인해 볼 것.

## 이어서 — 계측 표·크롭 화면도 같은 모양이었다

위에서 "같은 모양이 하나 더 있을 수 있다" 고 적어 둔 것을 확인했다. **있었다.**
그런데 페이지 나눔은 셋 중 하나였고, 나머지 둘이 더 컸다.

```
/d/…369cm/detections/   1.35초 · 371 KB
/d/…369cm/crops/        1.38초
```

### 1. 같은 것을 두 번 캤다 (0.67초)

```
dataset_detail()    0.45초   ← 시야 74개를 훑는다
_candidate_rows()   0.67초   ← 그룹마다 group_detail() 을 또 부른다
```

`_candidate_rows` 는 `ds["groups"]` 를 돌면서 그룹마다 `data.group_detail()` 을
불렀다. 그런데 `dataset_detail()` 이 방금 같은 시야들을 이미 훑었다. **뒤의 것이
통째로 군더더기**였다.

시야를 한 번만 훑는 `data.candidate_rows(slug)` 로 옮겼다. 1.13초 → 0.43초.

대조는 앞과 같은 방식으로 했다 — 개체 집합이 같은지(1,166줄, 키까지 일치)와
7개 항목(`long_side_um`·`major_um`·`cls`·`image_rel`·`overlay_rel`·
`um_per_pixel`·`reviewed`)이 같은지. **전부 일치.**

### 2. 이름 하나 때문에 0.45초 (더 어이없는 쪽)

계측 표와 크롭 화면이 `dataset_detail()` 을 부르는데, 정작 쓰는 것은
`ds["label"]` **하나뿐**이었다. 머리글에 시료 이름을 적으려고 시야 74개를 훑은
것이다.

```python
label = data.slide_label(slug)     # values_list("name").first()
```

`dataset_detail()` 의 `None` 반환을 404 판정에도 쓰고 있어서 그 역할까지 옮겼다.

### 3. 페이지 나눔 (300줄)

계측 표가 1,166줄을 통째로 냈다. 크롭은 이미 500개씩 나누고 있었는데 표만
빠져 있었다.

**요약은 전부를 기준으로 낸다.** 보고 있는 쪽만 세면 페이지를 넘길 때마다
중앙값이 달라져서, 그 값이 무엇의 중앙값인지 알 수 없게 된다. 1페이지와
4페이지 모두 22.4 로 같은 것을 확인했다.

| 계측 표 (369cm, 1,166개) | 1.35초 · 371 KB | **0.48초 · 129 KB** |
| 크롭 (369cm) | 1.38초 | **0.63초** |

## 세 번 다 같은 뿌리였다

목록의 집계, 계측 표의 중복 조회, 이름 하나를 위한 전체 조회 — **원하는 것보다
훨씬 많이 가져와서 파이썬에서 버리는** 모양이다. 슬라이드가 3장이고 개체가
18,936개일 때는 아무도 눈치채지 못했다.

쓰는 쪽에서 "이 함수가 무엇을 하는가" 만 보고 부르면 이렇게 된다.
`dataset_detail()` 은 이름도 주지만 그것을 얻자고 부를 함수가 아니다. **비싼
함수는 비싸다고 적어 두는 편이 낫다** — `slide_label()` 과 `_summary_by_sql()`
머리말에 그렇게 남겼다.

## 이어서 2 — 문턱 조정 화면, 그리고 내 측정이 틀렸다

### 화면 로딩: 0.80초 → 0.02초

앞의 둘과 **똑같은 뿌리**였다.

| 원인 | 비용 |
|---|---|
| 이름 하나 얻으려고 `dataset_detail()` | 0.46초 |
| **`datasets()` — 그런데 템플릿이 이 변수를 쓰지 않는다** | 0.27초 |

두 번째는 순전한 낭비다. 목록을 만들어 context 에 넣는데 `thresholds.html` 에
`datasets` 가 한 번도 안 나온다. 언젠가 데이터셋 고르는 메뉴를 두려다 만 흔적일
것이다. **화면에 안 나오는 것은 아무도 이상하다고 느끼지 못한다** — 020 에서 죽어
있던 `<style>` 과 같은 종류다.

### 미리보기 API: 판정을 두 번 걸고 있었다

이 화면은 슬라이더를 움직일 때마다 `/api/threshold/preview` 를 부른다. 프로파일에
`judge.apply` 가 **148번** 찍혔다 — 검출이 74개인데 두 배다.

```
preview()       전체를 판정
class_counts()  전체를 다시 판정   ← 같은 일
```

`preview` 가 이미 `verdict`(개체 키 → 분류)를 들고 있으므로 그것을 세면 된다.
`class_counts_from(per_det)` 를 두고 값이 같은 것을 확인했다(`rod 1944 ·
round 518`). 판정 횟수가 절반이 됐다.

### 그리고 설명이 안 되던 간격 — 내 측정이 틀렸다

고친 뒤에도 이상한 것이 남아 있었다.

```
컨테이너 안에서 직접 호출   0.21초
같은 컨테이너, HTTP        0.51초
```

같은 코드·같은 요청인데 2.4배. nginx 를 의심해 우회해 봤고(같음), gunicorn 워커
수를 1로 줄여 봤고(같음), 요청 고정비를 쟀다(`/healthz` 1 ms). 전부 아니었다.

뷰 안에 시간을 심고서야 보였다 — WSGI 안에서 `preview` 가 **0.448초**, 직접 부르면
**0.147초**. `cpu == wall` 이라 기다리는 것이 아니라 정말 계산을 세 배 하고 있었다.

원인은 **내가 두 측정에 서로 다른 문턱을 준 것**이었다. curl 본문에 손으로 적어
넣은 값이 실제 기본값과 달랐다.

```
직접 호출:  통과 2,462개 → 0.147초
HTTP:      통과 4,177개 → 0.436초
```

같은 코드가 **다른 일**을 하고 있었다. 성능 문제는 없었다.

**교훈:** 두 경로를 비교할 때는 입력이 같은지 먼저 확인한다. 나는 "같은 요청" 이라고
믿고 gunicorn·nginx·워커 수를 세 번 의심했다. 계측값이 이상하면 **계측 자체를
먼저 의심할 것** — 015 의 배율 사고와 같은 모양이다.

## 덤으로 찾은 것 — `dedupe` 가 O(n²)

측정 실수 덕에 드러났다. 통과 개체가 **1.7배면 시간이 3배**다.

```
통과 2,462개 → 0.15초
통과 4,177개 → 0.44초
```

`judge.dedupe()` 가 통과분끼리 상호 포함율을 재기 때문이다(`_cover` 292,576번).
문턱을 **느슨하게 내리는 쪽**으로 슬라이더를 움직일 때가 가장 느리다 — 하필
사람이 "얼마나 더 잡히나" 를 볼 때다.

지금은 견딜 만하지만 슬라이드가 늘면 이 구간이 먼저 아프다. 고칠 때는 격자
분할이나 bbox 정렬로 후보 쌍을 줄이는 쪽이 될 것이다.
