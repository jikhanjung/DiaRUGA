# 시험용 화면이 교정 37건을 지웠다 — "읽기 전용" 이라고 적어 놓고

**날짜** 2026-08-03
**앞선 문서** `20260803_025_yolo-first-training.md` (YOLO), P02 §2 (교정 스키마)

`/engine/` 을 만들며 문서와 커밋 메시지에 **"읽기 전용이다"** 라고 적었다.
아니었다. **369cm g32 의 교정 37건이 지워졌다.**

---

## 1. 무슨 일이 있었나

```
17:11  /engine/61/…/g32 에서 YOLO 마스크를 클릭
       → save() → POST /review  { removed: ["1981_0_771_871"] }
       → 서버가 그 시야의 교정을 그 키 하나로 갈아치움
       → SAM2 교정 37건 삭제 · ViewpointReview.done 해제
17:19  backup_db.py 가 objectreview 5260 → 5224 로 찍어 알아챔
```

**백업 숫자가 아니었으면 몰랐을 것이다.** 화면에는 아무 표시도 없었다.

## 2. 왜 막히지 않았나

**CSS 로 도구를 감췄다.**

```css
.tools, .donebar, .layers, .notebox { display: none; }
```

감춘 것은 버튼이다. **마스크 자체가 클릭 대상이고, 클릭이 `save()` 를 부른다.**
`_detection.html` 안에서 `save()` 를 부르는 곳이 12군데다 — 버튼만 감춰서는
어디도 막히지 않는다.

**보이지 않는 것과 동작하지 않는 것은 다르다.** 이걸 몰라서가 아니라, "도구만
안 보이면 되지" 라는 앞선 요구를 그대로 CSS 로 옮기면서 검증을 안 했다.

## 3. 왜 한 번의 클릭이 37건을 지웠나

`data.save_review()` 의 마지막 줄이다.

```python
ObjectReview.objects.filter(viewpoint=vp).exclude(mask_key__in=keys).delete()
```

**뷰어는 늘 그 시야의 교정 전체를 보낸다**는 전제다. 그래야 "교정 전체 초기화"
가 깨끗하게 되고, 그 설계 자체는 맞다. 다만 전제가 깨지면 — 키 하나만 담긴
POST 가 오면 — **나머지를 전부 지운다.**

같은 함수에 같은 이유로 이미 한 번 데었다. 그때는 빈 키 목록을 운영 DB 로
보내 14건을 지웠고, 얻은 교훈은 "파괴적 엔드포인트는 사본 DB 로 시험한다"
였다. 이번에는 **시험이 아니라 화면이** 그 POST 를 보냈다.

## 4. 복구

`before-yolo-full` 백업(16:58)에서 37건을 **행 단위로** 되살렸다. DB 를 통째로
되돌리지 않은 이유: 그 사이 YOLO 검출 1,000여 개가 들어와 있어 함께 날아간다.

```
사라진 것 0 · 값이 달라진 것 0 · 검토완료 상태가 다른 시야 0
```

잘못된 저장이 만든 행 하나(`1981_0_771_871`, YOLO 키, `bind=orphan`,
`geom` 없음)는 지웠다 — 사람의 판단이 아니라 사고의 부산물이다.

## 5. 고친 것 — 두 겹

**한 겹으로는 안 된다.** 화면 쪽만 막으면 다음에 또 다른 화면을 만들 때 같은
일이 난다. 서버 쪽만 막으면 화면이 "저장됨" 이라고 거짓말한다.

### 화면 — 아예 보내지 않는다

```js
var readOnly = document.getElementById('ro-' + uid) !== null;
function postReview(keepalive) {
  if (readOnly) { saveState.textContent = '시험용 화면 — 저장하지 않습니다'; return …; }
```

`save()` 를 부르는 12곳을 각각 막지 않는다. **나가는 문 하나를 잠근다.**

### 서버 — 남의 검출 키를 받지 않는다

```python
known = 현재 검출의 후보 키 | 이미 교정 행이 있는 키
if keys - known:
    raise ValueError(...)          # 409, 아무것도 바꾸지 않는다
```

**사람은 화면에 있는 것만 표시할 수 있고, 화면은 현재 검출을 그린다.** 그
밖의 키가 섞여 오면 다른 검출을 보고 보낸 것이다. 이미 교정 행이 있는 키를
통과시키는 것은 재바인딩에서 고아가 된 것들 때문이다 — 그것들도 사람이
화면에서 지울 수 있어야 한다.

사본 DB 로 확인했다.

```
남의 검출 키 POST  → 409 · 교정 37건 그대로
정상 키 전체 POST  → 200 · 정상 저장
```

## 6. 남는 것

- **빈 키 목록으로 오는 POST 는 여전히 전부 지운다.** 그것이 "초기화" 의
  정상 경로이기 때문이다. 새 관문은 *남의 키*를 막을 뿐 *빈 요청*은 못 막는다.
  두 번 다 그 자리에서 데었으므로 언젠가 확인 절차를 붙여야 한다
- **알아챈 것이 백업 숫자였다.** `backup_db.py` 가 매번 카운트를 찍어 준 덕이다.
  026 이 적은 "실패를 아무도 모른다" 와 같은 문제다 — 교정 수가 줄면 눈에
  띄어야 한다. `check_db.py` 에 "직전 백업 대비 교정 수" 를 넣는 것을 검토한다
- **`/engine/` 은 아직 배포하지 않았다.** 개발 서버에서만 띄웠고, 사고를 확인한
  즉시 내렸다
