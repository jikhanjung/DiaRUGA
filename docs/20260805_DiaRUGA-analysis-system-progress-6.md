## 1. 요약

5차 보고서는 **사람이 만지는 화면과 자료를 지키는 장치**를 다듬은 차수였다.
이번 차수는 그 아래를 손봤다 — **이름 · 스키마 · 그리고 판(version)을 다루는
방식**이다. 하루에 아홉 판이 나갔고, 그중 셋은 "만들다가 드러난 것" 을 막는
판이었다.

**첫째, 이름이 한 겹이 됐다.** 화면은 `DiaRUGA` 인데 주소는 `/diatom/` 이고
디렉토리는 `/srv/diatom` 이던 상태를 정리했다. 저장소·경로·URL·DB·환경변수까지
전부 `DiaRUGA` 다. **정지 시간 4분**으로 끝냈다.

**둘째, 스키마의 빠진 조각을 찾았다.** 사용자가 "정규화가 되어 있으면 일어나지
않을 일 같다" 고 지적한 자리가 실제로 빠진 정규화였다. `Detection` 이 문자열
판별자로 **다형 연관을 흉내 내던 것**을 `Image` 테이블로 바꿨다. 마이그레이션
넷을 넓히고-채우고-옮기고-조이는 순서로 나눠, 조이기 전까지는 언제든 되돌릴 수
있게 했다.

**셋째, 사람의 교정을 지키는 일이 또 한 번 있었다.** 검토 저장이 **다른
슬라이드의 시야를 지우고 있었다** — 프레임 이름이 슬라이드끼리 겹치는데 이름
하나로 시야를 찾은 탓이다. 실제로 터진 적은 없다는 것을 백업 아홉 판으로
확인했고, 저장이 `(슬러그, 시야번호)` 로 대상을 짚도록 고쳤다.

**넷째, 엔진 비교가 제자리에서 된다.** SAM2 와 YOLO 를 비교하려면 검토 화면을
나갔다 들어와야 했다. 이제 라디오 하나로 갈린다. **YOLO 쪽은 읽기 전용이고,
그것을 세 겹으로 막았다** — 저장만 잠그면 화면이 "되는 것처럼" 보여서 사람이 한
시야를 헛검토한다.

**다섯째, 한 시료에 관찰을 여럿 둘 수 있게 됐다.** 산처리한 것과 안 한 것을
같은 시료에서 따로 촬영해 비교하는 구조다. 폴더 접미사 `(1)`·`(2)` 로 들어오고,
목록에서 숨기거나 합계에서 빼는 것을 사람이 고른다.

**여섯째, 검토 도구를 데스크탑 앱으로 내는 계획을 세웠다.** GPU 없는 PC 에서
검출이 도는지를 **추정하지 않고 쟀다** — YOLO 는 시야당 1.7초, SAM2 는 3.4분.
결과는 GPU 와 같고 느리기만 하다. 그 측정이 "서버가 없는 연구자에게 이 도구를
줄 수 있는가" 를 답했고, 계획의 전제가 바뀌었다.

**일곱째, 라이선스를 AGPL-3.0 으로 정했다.** 검출 백엔드의 ultralytics 가
AGPL 이라 합쳐지는 이 저장소도 같이 간다.

**여덟째, 하루의 마지막에 장애가 하나 났다.** 슬러그 규칙을 고친 코드가
**파이프라인 이미지에 아직 반영되지 않은 상태**에서 그 규칙이 필요한 폴더가

## 2. 이름을 한 겹으로 모았다 (048)

041 에서 뷰어 이름을 `DiaRUGA` 로 정할 때는 **저장소·경로·DB·URL 을 `diatom` 으로
두기로** 했었다. 그 결정을 뒤집었다. 이름이 두 겹인 상태가 석 달째였고,
"화면은 DiaRUGA 인데 주소는 /diatom/" 을 설명하는 비용이 계속 들었다.

원칙 하나로 정리했다 — **프로젝트 정체성은 `DiaRUGA`, 기술이 소문자를 강제하는
자리만 `diaruga`.** GitHub·작업 디렉토리·`/srv`·`/data3`·venv·NAS 공유·DB 파일·
URL·파이썬 패키지·환경변수·`localStorage` 키가 모두 바뀌었다. Docker Hub 이미지
이름만 소문자다(`honestjung/diaruga`).

### `diatom` 을 남긴 자리가 핵심이다

`diatom` 은 프로젝트 이름이면서 **규조류라는 생물의 이름**이다. 무차별 치환은
분석 대상 자체를 지운다. 패턴 허용목록으로 쓸어내고 **남은 잔여물을 손으로
판단**했다. 남긴 것: `segment_diatoms.py`(하는 일이 규조류 검출이다) ·
`export_yolo.py` 의 YOLO 클래스 `diatom`(바꾸면 학습한 가중치와 어긋난다) ·
NAS 원본 폴더 `DiatomPhotos/`(우리가 만든 것이 아니다) · 지난 devlog 와 보고서.

### 밟을 뻔한 것들

- **URL 은 대소문자를 가린다.** `/diaruga/` 로 친 사람이 404 를 보지 않도록
  301 을 걸었는데, 그냥 걸면 **무한 루프**였다 — nginx 는 접두 location 보다
  정규식을 먼저 본다. `location ^~` 로 멈춘다
- **`localStorage` 키를 갈아치우면 사람의 설정이 조용히 초기화된다.** 꺼 둔
  레이어가 되살아나고 "늘 이동" 을 고른 사람에게 다시 묻는다. 읽는 자리마다
  **옛 키를 대체로 읽게** 했다
- **`/healthz` 가 곧바로 degraded 를 냈다.** 사본을 `DiaRUGA_*.db` 로 찾는데 그
  이름을 가진 것이 하나도 없었다. **안전망이 이름으로 대상을 찾고 있으면 이름을
  바꿀 때 같이 눈이 먼다**
- **순서를 뒤집어 정지 시간을 줄였다.** `경로 이동 → 이미지 굽기` 로 가면 굽는
  동안 뷰어가 내려가 있다. 먼저 굽고 나중에 옮겼다 — 실제 정지 **4분**

## 3. 검토 화면과 목록 (049 · 052)

08-04 에 담아 둔 다섯을 전부 만들고, 그 위에 코어 페이지가 붙었다.

### 3.1 가장 많이 하는 조작에 키가 없었다

교정 6,753건 중 **삭제가 5,467건**인데 삭제만 우클릭 메뉴로 남아 있었다. 시야
하나에 개체가 수십이라 메뉴를 여닫는 왕복이 곧 검토 속도다. 스페이스바를 줬다.

만들면서 **"이미 지운 것에 다시 누르면 되살림" 이 성립할 수 없다**는 것이
드러났다 — 지운 개체를 선택 상태에 넣을 방법이 아예 없었다. 범위 선택이 걸러
내고, 유령을 클릭하면 곧바로 되살아난다. `Shift+클릭` 이 되살리기보다 먼저
가도록 순서를 바꿔 "유령을 골라 둘 수 있는" 길을 냈다.

### 3.2 노두 시료의 위치 칸

노두에는 깊이가 없다. 비워 두면 화면에 `—` 로 나와 **"깊이가 없는 시료" 와
"아직 안 채운 시료" 가 구별되지 않는다.** `depth_cm` 을 문자열로 바꾸지 않고
(정렬과 인덱스가 이 값으로 선다) 시료 종류를 따로 뒀다. 칸 이름은 "깊이" 가
아니라 **"위치"** 이고 시추코어는 `cm`, 노두는 `OC` 다.

`NOT NULL` 칸이라 **`db_default` 를 함께 줬다** — Django 의 `default` 는 파이썬
쪽이라 판이 다른 옛 파이프라인 이미지의 INSERT 에는 칼럼이 안 들어간다.

### 3.3 목록을 코어로 묶고, 코어 페이지를 열었다

지금까지 목록은 **정렬만 되어 있고 묶여 있지 않았다.** 코어로 묶어 접었다.
묶는 열쇠는 지역이 아니라 **코어**이고(한 코어에 슬라이드가 여럿 되는 일이 먼저
온다 — 이미 RS23-GC03 이 셋이다), 이름이 아니라 **코드**로 묶는다(이름은 사람이
고칠 수 있고, 고치는 순간 접어 둔 것이 풀린다).

그 위에 `/core/<지역>/<코어>/` 를 열었다. **깊이 축은 진짜다** — 값이 DB 에
있어 눈금도 시료 위치도 실제다. 위가 얕고 아래로 깊어지는 코어 로그의 관례를
따르고, 축은 늘 0 에서 시작한다(가장 얕은 시료부터 그리면 그 위 구간이 없는 것
처럼 보인다).

**암상은 모델을 만들지 않았다.** 구간 상·하한·암상 코드·색·조직 같은 칸이
정해져야 표가 서는데 **그 기재 규칙이 아직 없다.** 축과 자리만 잡고 띠는 빗금
으로 비워 뒀다 — 그럴듯한 가짜 암상을 그리지 않는다.

### 3.4 판 번호는 사람이 정한다

`v0.4.0 → v0.5.0`. PATCH 를 기본으로 제안하고 물었고 MINOR 가 답이었다. 근거는
새 화면·새 URL·스키마 변경·목록 구조 자체의 변화였다. **규칙이 바뀐 것이
아니라, 판 번호는 프로젝트의 단락을 사람이 어떻게 보는지를 담는 값이다.**

## 4. 엔진 비교를 검토 화면 안으로 (051 · 054)

검출 엔진을 고르는 일이 `/engine/` 이라는 다른 화면에만 있었다. **비교는 같은
자리를 번갈아 보는 일인데** 화면을 나갔다 들어오면 어느 시야를 보고 있었는지
잃는다. `?batch=<실행>` 쿼리 하나로 갈리게 하고, 검토 화면에 라디오를 뒀다 —
`◉ SAM 0` · `○ YOLO 3 |읽기 전용|`.

**드롭다운이 아니라 라디오인 이유**는 닫힌 드롭다운은 **고르지 않은 쪽을 안
보여주기** 때문이다. YOLO 가 몇 개를 잡았는지가 곧 엔진을 바꾸는 이유인데,
바꾸기 전에는 볼 수 없는 셈이었다.

### 읽기 전용은 세 겹이다 — 화면은 그중 하나도 아니다

027 이 정확히 이 자리에서 났다. "읽기 전용" 이라 적어 놓고 CSS 로 버튼만 감췄더니
마스크 클릭 한 번이 교정 37건을 지웠다. 이번에는 셋으로 막았다.

1. **JS** — 표식이 있으면 저장 타이머조차 걸지 않는다
2. **서버** — 현재 검출에 없는 키를 거절한다(409)
3. **화면** — 도구·완료단추·시야 가르기를 감춘다. **앞의 둘이 없으면 이건
   아무것도 아니다**

그런데 배포 직후 사용자가 눌러 보고 바로 걸렸다. **"read only 인데 화면에서
작동은 하는 것처럼 보이네."** 키보드는 막았는데 **우클릭 메뉴가 살아 있었다** —
누르면 마스크가 지워지고 분류가 바뀐다. 저장만 안 나간다. 그렇게 한 시야를
검토하고 새로고침하면 판단이 통째로 사라진다.

**되는 것처럼 보이는 것이 안 되는 것보다 나쁘다.** 우클릭 메뉴·탈락 펼침판·
안내 줄까지 잠갔다(v0.5.2).

### 눌러 보고서야 나온 고장

`.tools { display: none }` 이 **한 번도 먹은 적이 없었다.** `base.html` 의
`.detview .tools { display: flex }` 가 특이도에서 이긴다. 세 화면이 도구를 감춘
줄 알고 계속 내보이고 있었다. **예외도 경고도 없는 종류의 고장**이라 렌더 결과를
브라우저에 물려 `getComputedStyle` 로 보기 전까지는 안 보인다.

## 5. 검토 저장이 남의 시야를 지우고 있었다 (053)

이번 차수에서 가장 중요한 항목이다. 051 을 확인하다 사용자가 **"지금 실제
`frame` 에는 어떤 값이 들어가지?"** 라고 물었고, 그 칸을 따라가다 터져 있는 곳에
닿았다.

### 무엇이 터져 있었나

저장이 **프레임 이름 하나로 시야를 찾았다.** 그런데 **프레임 이름은 슬라이드
끼리 겹친다** — 카메라 일련번호라 같은 날 이어 찍으면 번호대가 이어진다(실측
143종). 이건 이미 알고 있던 함정이고, `Frame` 에 `(slide, name)` 유일 제약까지
있었다. **제약은 있는데 조회가 그걸 안 썼다** — `.first()` 로 아무거나 집었다.

```
싱글턴 시야 135개 중 자기 이름으로 자기를 못 찾는 것: 12개
  260803_gc03-c1_72cm g1 → 실제로 열리는 시야: bp09-0901 g2 (교정 7행)
  ...                      노출된 교정 합계 138행
```

### 왜 조용히 지워지는가

`/review` POST 는 **그 시야의 교정 전체를 갈아치우는** 설계다. "현재 검출에 없는
키가 섞이면 409" 라는 방어가 앞에 있었지만, **키가 하나도 없으면 그 검사가
통과한다.** 즉 개체는 하나도 안 건드리고 **"검토 완료" 만 눌러도** 방어가 전부
비껴간다. 사본에서 재현했다 — 200 이 돌아오고 화면에는 "저장됨" 이라고 뜨는데,
다른 슬라이드의 교정 7행이 사라졌다.

### 고친 것과, 확인한 것

- 이름으로 찾을 때 **모호하면 거절한다**(409). 아무거나 집는 길을 없앴다
- 저장 요청이 **`(슬러그, 시야번호)`** 로 대상을 짚는다. 이름은 검증용으로만
  남겼다 — 화면과 저장 대상이 어긋나면 받지 않는다
- **실제로 터진 적은 없다.** 교정은 재생성 불가라 백업 이력으로 확인했다.
  노출됐던 시야 10개의 교정 수를 08-04 11:44 부터 백업 아홉 판에서 훑었고,
  `[7, 12, 13, 9, 18, 11, 21, 6, 13, 10]` 이 한 번도 변한 적이 없었다

### 교훈

**제약이 있다는 것과 조회가 그걸 쓴다는 것은 다르다.** 제약을 넣을 때 그 이름
으로 찾는 자리를 전부 세어 봤어야 한다. 그리고 **방어는 "무엇을 보내는가" 가
아니라 "어디에 쓰는가" 에도 걸어야 한다** — 027 이후 넣은 방어는 키를 검사했지
대상은 검사하지 않았다.

## 6. 스키마 — `Image` 를 뽑았다 (055 · P06)

프레임별 YOLO 검출도 검토하려면 교정이 **어느 이미지에 붙는지**가 있어야 한다.
그 칸을 어떻게 둘지 이야기하다 사용자가 물었다.

> *"테이블들이 정규화가 잘 되어 있으면 일어나지 않을 일 같거든. 슬라이드 1:N
> 시야 1:N 프레임 1:N 검출결과 1:1 검토결과 이런 식이어야 하잖아."*

맞는 말이었고, 그 사슬이 성립하지 않는 이유는 하나였다 — **합성본은 프레임이
아니다.** 검출이 도는 이미지가 `Stack.focused_path` 아니면 `Frame.path` 라 표가
둘이고, 그래서 `Detection` 이 판별자 문자열 + nullable FK 로 **다형 연관을 흉내
내고** 있었다. 빠진 것은 `Image` 테이블이었다.

### 먼저 안전망을 만들었다

이 이사는 교정 6,732행을 만지는데 안전망이 백업 하나였다. **백업은 "몇 행이었나"
는 알려 주지만 "무엇이 달라졌나" 는 못 알려 준다.** 그래서 `export_review.py`
를 먼저 만들었다 — 교정을 `review/<슬라이드>/g<n>.json` 으로 내보내 **git 에
남는 감사 기록**으로 만들고, `--check` 로 DB 와 대조한다. Django 를 임포트하지
않고 sqlite3 로 읽기 전용이라 **스키마가 바뀌는 동안에도 같은 도구로 비교할 수
있다.** 이 성질이 이번 이사에서 값을 했다.

### 넓히고 → 채우고 → 옮기고 → 조인다

```
0019  Image 테이블 + nullable FK        이미지 1,952 · 검출 2,076 · 교정 6,738
0020  Image.viewpoint  CASCADE → SET_NULL
0021  Image.stack      SET_NULL → CASCADE
0022  판별자·nullable FK 제거 · NOT NULL · UNIQUE (image, mask_key)
```

**조이기 전까지는 전부 되돌릴 수 있었다.** 0020·0021 의 방향이 반대인 것이
요점이다 — **프레임은 원본 사진이라** 시야를 갈라도 살아남고(`SET_NULL`),
**합성본·깊이맵은 그 묶음에서 나온 것이라** 묶음이 갈리면 무효다(`CASCADE`).

### "조인 뒤에 돌려야 안다" — 사용자가 맞았다

조이기 전에 파이프라인을 돌려 보자고 했더니 사용자가 물었다. *"어차피 조이고
나서 돌려봐야 진짜 문제가 있는지 알 수 있는 거 아냐?"* 맞다 — 조이기 전에는
고장 나도 `NULL` 로 조용히 지나간다. **조인 사본에 파이프라인 컨테이너를 붙여**
돌렸고, 그 시험이 바로 잡았다.

```
django.db.utils.OperationalError: table viewer_detection has no column named target
```

배포돼 있던 파이프라인 이미지가 아직 걷어낸 칼럼을 쓰고 있었다. **조이는
마이그레이션과 파이프라인 판은 함께 나간다** — 뷰어와 파이프라인의 판을 갈라
놓은 것(026)이 이번엔 반대로 문 자리다.

### 함께 고친 것

교정을 지우는 범위를 **시야가 아니라 이미지**로 바꿨다. 지금은 시야마다 이미지가
하나라 결과가 같다 — **같아 보일 때 고쳐 두는 것이 요점이다.** 017·027·053 이
전부 이 줄에서 났다.

## 7. 한 시료에 관찰을 여럿 둔다 (056)

지금까지는 **시료 하나 = 슬라이드 하나**였다. 앞으로는 처리 방법을 달리해 같은
시료에서 사진 그룹을 여럿 만든다 — 산처리한 것과 안 한 것, 체 크기를 달리한 것.

**폴더는 숫자 접미사만 받는다.** `(산처리)` 처럼 글자를 받으면 슬러그가 뭉개져
서로 다른 관찰이 같은 슬러그로 부딪히고, **한쪽이 다른 쪽을 조용히 덮어쓴다.**
뜻은 사람이 화면의 `obs_label`(10자)에 적는다 — 폴더도 파일도 안 건드린다.

칸이 넷이다. **자동값(`obs_no`)과 사람 값(`obs_label`)을 가른 이유**는 한 칸이면
폴더에서 다시 읽을 때 사람이 적은 것을 덮기 때문이다. **숨김과 집계 제외를 둘로
가른 것도** 안 보여도 조성에는 들어가야 하는 관찰이 있어서다.

**합계는 숨김을 안 읽는다.** 읽으면 보기 토글 한 번에 같은 자료가 다른 숫자를
낸다. 그 대가로 "보이는 줄의 합 ≠ 합계" 가 생기는데, **그것을 화면이 적는다.**

**색이 주고 기호가 보조다.** 이 목록은 docx 로 구워 NAS 로 나간다 — 색만으로
가르면 흑백 출력에서 두 상태가 통째로 사라진다.

## 9. 데스크탑 앱 — 재고, 정하고, 세었다 (P05 · 049 · 050)

### 9.1 CPU 로 검출이 되는가를 쟀다

**추정으로 답할 이유가 없어서 쟀다.** 운영과 같은 설정, RTX 3060 Ti 대
Ryzen 5 5600G.

| 엔진 | GPU/시야 | CPU/시야 | GPU/슬라이드 | CPU/슬라이드 |
|---|---|---|---|---|
| SAM2.1 `pps=48` | 13.0초 | **3.4분** | 9.8분 | **2.5시간** |
| YOLO11m-seg 1280 | 0.09초 | **1.7초** | 4.2초 | **75초** |

**결과는 같다.** SAM2 는 CPU·GPU 둘 다 마스크 422개, YOLO 는 둘 다 검출 146개다.
**정확도를 잃는 것이 아니라 느리기만 하다.**

SAM2 의 병목은 인코더(2.4초)가 아니라 **점 2,304개를 도는 디코더**다 — 그래서
`--points-per-side` 가 곧 CPU 소요이고 거의 선형이다. YOLO 는 **코어 수에 거의
안 딸려 간다**(12스레드 1.665초 · 4스레드 1.657초). 뒤집으면 **사무용 노트북에서도
같은 속도가 나온다**는 뜻이고, 배포를 생각하면 이쪽이 더 중요한 성질이다.

이 측정이 계획의 전제를 바꿨다. 앞서 쓴 검토 문서는 "연구소 서버가 계속 있다"
를 전제로 검토자 한 명의 속도만 보고 만들지 말자고 했는데, 실제 동기는
**배포 가능성**이었다 — GPU 서버가 없는 연구자에게 이 도구를 주는 것.
**저장은 문제가 아니고**(50 슬라이드도 20 GB) **GPU 도 필수가 아니다.**

### 9.2 라이선스가 성능과 정확히 반대로 걸려 있다

| | 라이선스 |
|---|---|
| **ultralytics** (YOLO11) | **AGPL-3.0** |
| **SAM-2** | Apache 2.0 |

**CPU 에서 쓸 만한 쪽이 AGPL 이고, 라이선스가 자유로운 쪽이 CPU 에서 3.4분이다.**
사내에서 쓰는 지금은 문제가 없지만(AGPL 의 의무는 배포·서비스할 때 걸린다) 밖으로
내는 앱을 만들면 그 순간 걸린다. **AGPL-3.0 으로 공개하는 길을 골랐다** — 학술
도구라면 오히려 자연스럽고, PyQt5(GPL v3)도 그대로 쓸 수 있다.
**`Modan2`(MIT)와는 방향이 있다: MIT → 여기는 되고, 여기 → Modan2 는 안 된다.**

### 9.3 ORM 은 peewee 로, 스키마는 지금 것에 붙인다

계획에 "데스크탑도 Django ORM 을 그대로 쓴다" 고 적었던 것을 뒤집었다. **근거
하나가 틀렸기 때문이다** — "파이썬이라 `judge.py` 를 한 벌로 유지할 수 있다" 는
논거를 GUI 선택과 ORM 선택에 **두 번** 썼는데, 세어 보니 `judge.py` 는 ORM 을
한 줄도 쓰지 않는다(값을 받아 판정만 하는 순수 함수다).

진짜 결정은 ORM 이 아니었다. **같은 DB 파일을 웹(Django)과 앱(peewee)이 둘 다
열 수 있어야 하는가** — 그래야 한다. 그러면 결론은 하나다: **스키마를 옮기지
않고 peewee 모델을 지금 스키마에 붙인다.** 스키마의 원본은 Django 마이그레이션
한 곳이고 앱은 그것을 따라간다.

**옮길 때 잃기 쉬운 것을 추측이 아니라 운영 DB 에서 세었다** — 이름 붙은 유일
제약 6개, JSON 유효성 CHECK 6개, DB 기본값 2개, 외래키 21개의 삭제 규칙,
`auto_now` 3개. 특히 **`ON DELETE CASCADE` 가 스키마에 없다**(Django 가 파이썬에서
흉내 낸다)는 것이 미묘하다 — peewee 에 그대로 적으면 스키마가 달라지고, 안 적으면
**고아가 조용히 쌓인다.** 결론은 "연쇄 삭제를 DB 에 맡기지 말고 파이썬에서
명시한다" 다.

**사람이 표 15개 × 칼럼 수십 개를 눈으로 맞출 수는 없다.** `tools/schema_diff.py`
를 만들어 두 DB 의 스키마를 **의미로** 비교한다(같은 제약도 표현이 다를 수 있어
글자 비교여서는 안 된다). 운영 DB 와 마이그레이션으로 새로 만든 빈 DB 가 **같다**
는 것을 확인했고, 일부러 망가뜨린 사본 4건을 전부 잡았다.

## 10. 오늘의 장애 — 판이 어긋나 뷰어가 섰다 (057)

19:35~19:47, **뷰어 전체가 500** 이었다(요청 7건).

### 원인

056 에서 슬러그 규칙을 고쳤는데 **그 코드가 파이프라인 이미지에 아직 반영되지
않은 상태**에서, 그 규칙이 필요한 폴더(`BP09-0901 (1)`)가 NAS 에서 들어왔다.
슬러그를 만드는 코드는 **파이프라인 쪽**에 있고 그 슬러그를 URL 로 쓰는 코드는
**뷰어 쪽**에 있다.

```
옛 판:  260805_bp09-0901_(1)     ← URL 규칙 [-a-zA-Z0-9_]+ 을 어긴다
새 판:  260805_bp09-0901_1
```

### 왜 404 가 아니라 500 이고, 그 슬라이드만이 아니었나

괄호가 든 주소로 **들어오는** 요청은 404 다. 그러나 목록 템플릿은 슬라이드마다
링크를 **만든다** — 만들 수 없는 슬러그가 하나 섞이면 그 페이지 전체가 500 이
된다. 첫 화면부터 안 뜬다. **들어오는 값의 문제와 나가는 값의 문제는 크기가
다르다.**

그리고 반입만으로 그렇게 됐다. 슬라이드 행은 사진을 복사하기 전에 만들어지므로,
그룹핑·합성·검출까지 갈 것도 없이 **10초 만에** 뷰어가 섰다.

**`/healthz` 는 계속 `ok` 였다.** 링크를 만들지 않는 경로라 이 고장을 통과시킨다.

### 조치

폴러를 `flock` 으로 잡고(crontab 은 안 고친다) → 수동 사본 → **잘못된 슬라이드를
지우고**(사람의 교정이 0건인 것을 걸쇠로 확인했다) → 파이프라인 판을 올리고 →
새 판으로 재처리. 27분 만에 끝났고 결과는 시야 56 · 통과 개체 540 이다.

**슬러그만 DB 에서 고치는 길도 있었다**(27분을 아낀다). 사용자가 지우고 다시
돌리는 쪽을 골랐고, 이유는 시간이 아니라 **출처**다 — 남아 있는 행은 전부 옛
판의 산물이고, 그것이 새 판이 만들었을 것과 같은지는 값마다 사람이 확인해야
한다. **교정이 하나라도 붙어 있었다면 정반대로 판단했을 것이다.**

### 남는 것

- **판을 함께 올려야 하는 축이 하나 더 있다.** 스키마뿐 아니라 **값의 모양을
  정하는 규칙**(슬러그·경로·이름 규칙)도 파이프라인이 만들어 뷰어가 쓴다
- **화면을 보는 검사가 배포에만 붙어 있었다.** `smoke.sh` 는 목록 페이지를
  이미 보고 있었지만(nginx 를 거쳐 `/DiaRUGA/` 를 친다) **배포할 때만 돈다** —
  이 고장은 배포가 아니라 자료가 들어오면서 났다. 그래서 08-06 에 폴러가
  자동 처리 뒤에 같은 검사를 하고, 안 뜨면 `/healthz` 에 깃발을 세우게 했다(061)
