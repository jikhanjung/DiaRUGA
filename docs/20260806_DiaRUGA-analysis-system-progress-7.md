## 1. 요약

사용자가 아침에 **"첫 페이지가 2초 정도 걸리네"** 라고 했다. 그 한 줄에서 시작해
반나절 만에 화면 셋이 10~20배 빨라졌고, 그 과정에서 **어제의 옳은 이사가 남긴
그림자**가 드러났다.

| 화면 | 아침 | 점심 | |
|---|---|---|---|
| 목록 `/` | 2.09초 | **0.12초** | 17배 |
| 시야 목록 `/d/<슬라이드>/` | 0.83초 | **0.08초** | 10배 |
| 지점(코어) 페이지 | 0.99초 | **0.05초** | 20배 |

**첫째, 느려진 원인이 "코드가 나빠서" 가 아니었다.** 어제 스키마를 옳게 고치면서
(`Image` 를 뽑았다 — 055) 교정의 유일 제약이 시야에서 이미지로 옮겨 갔는데,
**그 인덱스를 밟고 서 있던 질의가 따라가지 않았다.** 코드는 한 글자도 안 바뀌었고
발밑의 인덱스만 없어졌다.

**둘째, 인덱스를 되살리는 대신 질의를 옮겼다.** 속도는 같았지만(510 ms vs 522 ms)
방향이 달랐다 — 되살리는 쪽은 어제 걷어낸 것을 성능 때문에 되돌리는 꼴이고,
무엇보다 **프레임별 검토가 붙는 순간 옛 질의는 값도 틀린다.** 지금은 시야마다
이미지가 하나라 결과가 같을 뿐이다. **같아 보일 때 고쳐 두는 것**을 골랐다.

**셋째, 일 자체를 줄였다.** 인덱스를 되찾은 것은 같은 일을 빨리 한 것이지 일을
줄인 것이 아니다. 후보 97,299개마다 교정을 찾는 조회가 **40만 번** 돌고 있었다 —
교정이 `(이미지, 마스크키)` 로 유일하므로 **왼쪽 조인 한 번**이면 된다.

**넷째, 화면이 쓰지도 않는 것을 만들고 있었다.** 시야 목록이 개체 11,048개를
파이썬 객체로 만들어 그중 **370개**를 그렸다. 폴리곤은 그 와중에 세 번 파싱됐다.

**다섯째, 안전망을 자료가 바뀌는 자리로 옮겼다.** 어제의 장애(057)는 배포가
아니라 **반입** 때 났는데, 검사는 배포에만 붙어 있었다. 그리고 그 장애의 원인을
**틀리게 적어 문서 셋에 옮겨 놓은 것**을 발견해 함께 정정했다.

## 2. 첫 페이지 2.09초 — 어제의 이사가 남긴 그림자 (058)

### 먼저 재고 나서 골랐다

컨테이너 안에서 테스트 클라이언트로 첫 페이지를 부르고 질의를 전부 잡았다.

```
status 200 · 2,113 ms · 질의 82개
질의 합계 1,951 ms          ← 페이지 시간의 93%
그중 한 모양 11개가 1,927 ms  (슬라이드마다 하나 — _summary_by_sql)
```

렌더링도 파이썬도 아니고 **SQL 하나**였다.

### 원인

```
055 이전:  UNIQUE (viewpoint_id, mask_key)
지금    :  UNIQUE (image_id,     mask_key)
```

집계 질의는 그대로 `viewpoint` 로 상관하고 있었다. 그래서 실행 계획이
`(viewpoint_id, bind_method)` 인덱스로 **시야까지만** 좁힌 뒤 그 시야의 교정을
전부 훑으며 마스크키를 비교했다. `image` 로 상관하면 유일 인덱스가 **한 번에
짚는다.**

> **055 는 잘못한 것이 없다.** 다형 연관을 걷어내는 옳은 이사였고 스키마 동등성도
> 확인했다. 놓친 것은 **그 인덱스를 짚어 쓰던 질의가 어디인지 세는 일**이었다.
>
> 053 의 교훈("제약이 있다는 것과 조회가 그걸 쓴다는 것은 다르다")의 **반대편**
> 이다. 그때는 제약이 있는데 조회가 안 썼고, 이번엔 제약을 옮겼는데 조회가 안
> 따라왔다.

### 30분을 엉뚱한 길로 갔다 — 시험이 자기 자신을 오염시켰다

원인을 짚기 전에 "사본에서는 같은 질의가 500 ms" 라는 결과가 나왔다. 같은
컨테이너·같은 코드·같은 크기의 파일인데 4배가 달랐다. 파일 배치를 의심해
바이트 사본을 다시 뜨고, `VACUUM` 으로 108 → 58 MB 로 줄이고, `ANALYZE` 도 걸었다.
전부 헛다리였다.

**진짜 이유는 그 "빠른 사본" 에 앞선 측정에서 만들어 둔 인덱스가 남아 있었다는
것이다.** 인덱스 개수를 세고서야(46 vs 47) 알았다.

- **성능을 잰 파일에 무엇을 만들었는지 기억할 것.** 시험이 대상을 바꾸면 그 다음
  측정은 전부 거짓말이 된다. 사본을 다시 뜨는 편이 싸다
- **엉뚱한 답도 재는 값은 진짜였다.** `VACUUM` 이 파일을 절반으로 줄이고도
  0 ms 도 못 줄인 것이 오히려 "배치 문제가 아니다" 를 확정해 줬다

## 3. 조인 한 번으로 (059) — 그리고 버린 길 둘

058 은 **인덱스를 되찾은 것**이지 일을 줄인 것이 아니다. 후보 하나마다 교정을
찾는 상관 서브질의가 넷 돌아 **조회가 40만 번**이었다.

교정은 `(이미지, 마스크키)` 가 **유일**하므로 왼쪽 조인이 후보 하나에 교정 0
또는 1행만 붙인다 — 행이 안 불어나고, 서브질의 넷이 조인 하나가 된다.

```
집계 11개    500 → 77 ms
첫 페이지    547 → 122 ms
지점 페이지  188 → 46 ms
```

### 왜 원시 SQL 인가

**Django ORM 이 이 조인을 낼 수 없다.** 관계가 FK 가 아니라 `(이미지, 마스크키)`
짝이기 때문이다. `ObjectReview.candidate` FK 가 있긴 하지만 **그것을 조인 열쇠로
쓰면 안 된다** — 재검출에서 끊기라고 만든 칸이다.

교정이 `mask_key` 에 붙는 것은 **소유 방향의 선택**이고(재생성 불가한 것이
재생성 가능한 것의 자식이 되면 안 된다), 그 선택의 대가가 "ORM 으로는 조인을 못
쓴다" 이다. 대신 판정 규칙이 SQL 문자열로 들어갔으므로 **경계값까지 파이썬 쪽과
같아야 한다는 사실을 머리말에 적었다.**

### 재 보고 버린 것 둘

- **한 질의로 묶기**(11개를 `GROUP BY` 하나로) — **567 ms 로 오히려 느리다.**
  실행 계획이 이미 필요한 것만 타고 들어가고 있었고, 묶으면 전체를 훑고 나서
  나눈다. **"질의를 줄인다" 가 곧 "일을 줄인다" 는 아니다**
- **SQLite 프라그마** — 캐시를 키워 6%, `mmap` 은 차이 없음. 자료가 108 MB 라
  이미 페이지 캐시에 들어 있다

## 4. 370개를 그리려고 11,048개를 만들었다 (060)

첫 페이지가 0.12초가 되고 나니 다음이 보였다.

```
/d/…369cm/   825 ms · SQL 1 ms · 파이썬 824 ms
```

**질의는 이미 빨랐다.** 겹쳐 있던 것이 둘이었다.

**하나 — 쓰지도 않는 묶음의 후보까지 당겼다.** 이 저장소는 검출 엔진을 두 벌
쌓아 둔다(`sam2-전수` · `yolo-3차`).

```
RS23-GC03 369cm 의 후보 28,697개
  sam2-전수 11,048   ← 화면이 쓰는 것
  yolo-3차  17,649   ← 한 개도 안 쓴다
```

`Candidate.polygon` 이 JSON 이라 **올리는 값이 곧 파싱 비용**이다. 현재 검출만
당기게 하되, **엔진 비교 화면은 그대로 두었다** — 거기는 고른 묶음의 검출을 봐야
해서 현재 것만 당기면 화면이 통째로 빈다. 기본값을 바꾸지 않고 **부르는 쪽이
고르게** 했다.

**둘 — 그러고도 개체를 전부 dict 로 만들었다.** 이 화면이 개체에서 쓰는 것은
표지에 얹을 마스크와 그 수뿐인데(슬라이드 전체로 923개), 11,048개를 만들고
있었다. 남는 것만 뽑는 질의 하나로 바꿨다.

```
825 → 429 → 81 ms
```

### "썸네일에 마스크를 구워 넣으면 안 되나"

사용자가 물었다. **되지만 이 문제의 답은 아니었다.** 비용은 그리는 데 있지
않았다 — 마스크 923개를 SVG 로 내보내는 것은 공짜에 가깝고, 값은 그것을
**고르려고** 개체 11,048개를 만드는 데 있었다. 그 자리를 고치면 구울 이유가
없어진다.

구웠을 때 잃는 것도 적지 않다.

- **사람의 교정이 그림에 박힌다.** 교정은 하루에도 수백 건 바뀌는데, 그때마다
  다시 굽지 않으면 화면이 조용히 낡는다
- **켜고 끌 수 없고 테마를 못 따라간다.** SVG 는 색을 CSS 가 정해 어두운 화면·
  밝은 화면에서 각각 읽히고, 확대하면 원본 화소로 간다
- **어제 걷어낸 overlay JPG 가 정확히 그것이었다** — 1,496장 752 MB 를 구워 두고
  아무도 안 읽었다

그래도 길은 열려 있다. 표지가 훨씬 커지거나 마스크가 시야당 수백 개가 되면 굽는
편이 싸진다.

## 6. 안전망을 자료가 바뀌는 자리로 (061)

### 먼저 — 틀린 진단을 문서 셋에서 걷었다

어제 장애(057)의 "남는 것" 에 **"`smoke.sh` 에 목록 페이지 검사를 더한다"** 고
적어 두었는데, 열어 보니 **이미 있었다.** 사본에 괄호 슬러그를 심어 그 상황을
재현하고 `smoke.sh` 를 걸어 보니 그대로 잡혔다.

```
  ✓ /healthz 200
  ✗ nginx 경유가 200 이 아니다 (받은 것: 500)
smoke 실패 — 종료코드 1
```

**틀린 진단이 devlog · HANDOFF 세 절 · 6차 보고서에 옮겨 적혀 있었다.** 전부
고치고 보고서 docx 도 다시 구워 NAS 공유에 올렸다.

> **026 의 교훈이 정확히 이것이었다** — 원인을 짐작해 적으면 그 진단이 문서에
> 눌러앉아 다음 사람을 엉뚱한 곳으로 보낸다. 그때는 로그 524줄이었고 이번엔
> 문서 셋이다.

### 진짜 구멍

```
검사가 붙어 있던 곳:  배포 (판이 바뀌는 자리)
고장이 난 곳:        반입 (자료가 바뀌는 자리)
```

`smoke.sh` 는 배포할 때만 돈다. 그런데 057 은 배포와 무관하게, **폴러가 NAS 에서
슬라이드를 반입하는 순간** 규칙을 어긴 슬러그가 DB 에 앉으면서 났다. 11분 36초
동안 아무도 몰랐고 **사람이 화면을 열어 보고서야 알았다.**

폴러가 처리를 끝내면 목록 페이지를 한 번 치게 했다. **로그에만 적지 않는다** —
로그는 읽는 사람이 없는 동안 꺼진 안전망이다. 무결성 깃발을 세워 `/healthz` 가
`degraded` 가 되게 했고, 그러면 `smoke.sh` 도 실패한다. **사람이 이미 보고 있는
통로에 싣는다.**

### smoke 에는 한 걸음 더 — 링크를 따라가 본다

**200 은 "떴다" 일 뿐이다.** 목록이 200 을 내면서 링크를 하나도 못 만들 수도
있다(057 이 정확히 그 모양이었다). 목록에서 슬라이드 링크를 하나 뽑아 따라간다.

```
  ✓ nginx 경유 http://127.0.0.1/DiaRUGA/ 200
  ✓ 시야 목록 /DiaRUGA/d/260805_bp09-0901_1/ 200
```

링크가 하나도 없으면 그것도 실패다 — **단, 자료가 있을 때만.** 자료가 없는 경우는
앞 검사가 이미 잡으므로 여기서 또 울리면 한 원인이 두 줄로 번진다.

### 곁들여 — 깃발 문구 한 줄 (062)

깃발을 세우는 주인이 백업만이 아니게 됐는데 `/healthz` 는 무슨 깃발이든
**"백업 실패 깃발"** 이라고 적고 있었다. 폴러가 세운 깃발에 그 말이 붙으면 읽는
사람이 백업을 보러 간다. `무결성 깃발 [poll_nas …]` 로 바꿔 `v0.6.4` 로 냈다.

고장 나 있는 상태가 아니라 **고장 났을 때 잘못 말하는 상태**라 급하지는 않다.
그래도 안전망이 우는 날은 이미 나쁜 날이고, 그날 한 줄 때문에 사람이 다른 데를
파게 만들 이유가 없다.

## 8. 남는 것

- **갤러리 0.42초 · 계측 표 0.43초.** 이 둘은 성격이 다르다 — 개체 하나하나를
  화면에 내는 것이 일이라 물질화가 곧 목적이다. 줄이려면 페이지를 나누는 쪽이지
  질의 쪽이 아니다
- **아무도 아무것도 안 할 때는 여전히 아무 검사도 안 돈다.** 자료가 안 들어오고
  배포도 없으면 화면이 죽어도 모른다. 5분마다 때리는 것이 가장 싸지만, 그건
  "폴러가 멈춘 것을 아무도 안 알려 준다" 와 같은 자리라 **한 화면에 모아 보이는
  쪽**이 낫다
- **판정 규칙이 두 곳(파이썬 · SQL)에 있다.** 경계값까지 같아야 목록과 상세의
  숫자가 어긋나지 않는다 — 셋이 되지 않게 머리말에 못 박아 두었다

## 9. 이 차수에서 얻은 것

**스키마를 옳게 고치는 것과 그 뒤를 세는 것은 다른 일이다.** 055 는 옳았고 검증도
했지만, "그 인덱스를 짚어 쓰던 질의가 어디인가" 는 세지 않았다. 제약을 옮길 때는
**그 제약을 밟고 서 있던 질의 목록**이 함께 나와야 한다.

**성능 작업은 자기 시험을 오염시키기 쉽다.** 잰 파일에 무엇을 만들었는지 기억
못 하면 그 다음 측정이 전부 거짓이 된다.

**안전망은 "고장이 나는 자리" 가 아니라 "자료가 바뀌는 자리" 에 붙인다.** 그리고
로그가 아니라 **사람이 이미 보고 있는 통로**에 싣는다.

**원인을 짐작해 적지 않는다.** 이번에는 그 대가가 문서 셋이었다.
