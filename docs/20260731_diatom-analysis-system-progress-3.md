## 1. 요약

2차 보고서 시점에는 **사람이 손으로 돌리는 파이프라인**이었다. 스크립트를 순서대로
실행하고, 결과 JSON 을 DB 로 넣고, 뷰어를 개발 서버로 띄웠다. 그 이후 네 가지가
달라졌다.

**첫째, 시스템이 스스로 돈다.** NAS 에 새 슬라이드가 올라오면 1분 안에 감지해
복사·그룹핑·합성·검출까지 사람 손 없이 진행한다. 자동 처리가 끝나야 검토 화면이
열린다.

**둘째, 컨테이너로 옮겼다.** 뷰어와 파이프라인이 Docker 컨테이너에서 돌고, 데이터와
배포 구성이 저장소 밖으로 나갔다. 장비를 바꿔도 같은 환경이 선다 — 실제로 이번에
서버를 옮기면서 겪은 문제들이 계기였다.

**셋째, 파이프라인 스크립트 4개가 전부 DB 를 쓴다.** JSON 을 거치는 단계가 사라졌고,
검출을 다시 돌려도 사람의 검토 결과가 개체를 계속 가리키도록 다시 맺어 주는 장치를
만들었다.

**넷째, 자동 수집 첫날 실제 사고를 하나 잡았다.** 새로 들어온 시료의 배율
메타데이터가 실제 광학계와 달라서, 검출 통과율이 1.6% 로 무너져 있었다. 원인을
찾아 고쳤고 재처리 중이다.

## 2. 배경 — 컨테이너란 무엇이고 왜 쓰는가

이 보고서의 상당 부분이 컨테이너 이야기라 용어를 먼저 정리한다.

### 2.1 문제

프로그램은 혼자 돌지 않는다. 파이썬 버전, 라이브러리 수십 개, 그 라이브러리가
기대하는 시스템 파일이 맞아야 한다. 이 조합을 **손으로 맞춰 두면 그 장비에서만
돈다.**

실제로 이번에 서버를 옮기면서 그 대가를 치렀다. 뷰어가 안 뜨고(옛 장비 주소가
설정에 박혀 있었다), 파이썬 가상환경 위치가 문서와 달랐고, 필요한 라이브러리
목록에 Django 가 빠져 있었다. 하나씩 찾아 고쳐야 했다.

### 2.2 컨테이너

**컨테이너는 프로그램과 그것이 필요로 하는 것 전부를 한 덩어리로 묶은 것**이다.
운영체제 위에서 격리된 채로 돌지만, 가상머신과 달리 운영체제를 통째로 복제하지
않아 가볍다(시작이 1초 남짓).

세 가지 용어만 알면 된다.

| 용어 | 무엇 |
|---|---|
| **이미지(image)** | 프로그램 + 라이브러리를 구워 놓은 읽기 전용 틀. 붕어빵 틀 |
| **컨테이너(container)** | 이미지를 실제로 실행한 것. 붕어빵 |
| **볼륨(volume)·마운트** | 컨테이너 안에서 바깥 디렉토리를 들여다보게 연결하는 것 |

이미지에는 **코드만 굽고 데이터는 굽지 않는다.** 데이터를 구우면 이미지를 새로
만들 때마다 데이터가 옛것으로 되돌아간다. 대신 바깥 디렉토리를 **마운트**해서
컨테이너가 들여다보게 한다.

### 2.3 이 프로젝트의 구성

```
NAS (읽기 전용)                /data3/diatom (읽기·쓰기)        컨테이너
DiatomPhotos/<촬영일>/… ──▶ photos/<촬영일>/<슬라이드>/ ─┐
                             stacked/  out/  backup/     ├─▶ web      (뷰어, 상주)
/srv/diatom/ diatom.db ──────────────────────────────────┘   pipeline (검출, 일회성)
```

이미지를 둘로 나눴다.

- **web** (174 MB) — Django 뷰어. 화면을 그리는 데 필요한 것만
- **pipeline** (6.9 GB) — 여기에 PyTorch·SAM2 가 들어간다. GPU 를 쓴다

뷰어는 계산 라이브러리를 하나도 쓰지 않는다는 것을 확인하고 갈랐다. 덕분에 화면을
한 줄 고칠 때 6.9 GB 를 다시 굽지 않는다.

### 2.4 GPU 를 계속 붙잡지 않는다

파이프라인 컨테이너는 **상주하지 않는다.** 일이 있을 때만 뜨고 끝나면 사라진다.

상주시키면 PyTorch 가 한 번 확보한 그래픽카드 메모리를 프로세스가 죽을 때까지
놓지 않는다. 이 장비의 그래픽카드는 8 GB 뿐이라 다른 작업과 부딪힌다. 확인해 본
결과 **컨테이너를 GPU 연결로 띄우는 것 자체는 메모리를 쓰지 않는다**(띄우기 전
77 MiB → 띄운 후 77 MiB). 메모리를 잡는 것은 컨테이너가 아니라 그 안에서 실제로
계산을 시작하는 프로세스다.

## 3. 컨테이너로 옮기기 (devlog 008 · 016)

### 3.1 데이터를 저장소 밖으로

사진과 산출물을 `/data3/diatom` 으로 옮겼다. 시스템 디스크가 74% 차 있었고
슬라이드 하나가 1 GB 대다. 옮기기 전에 저장소·`/data3`·NAS 세 곳이 **690 파일
1,040,300,038 바이트**로 일치하는 것을 확인했다.

사진 폴더 구조는 NAS 를 그대로 비춘다.

```
photos/<촬영일>/<슬라이드>/     예: photos/260729/RS23-GC03 71cm/
```

처음엔 촬영일 층을 없앴다가 되돌렸다. **같은 슬라이드를 다른 날 다시 촬영하면
이름이 부딪힌다.** 초점을 다시 잡거나 시야를 더 찍는 일은 충분히 있다.

### 3.2 예상 못 한 것 — 사내망이 통신을 가로챈다

파이프라인 이미지를 굽는데 PyTorch 내려받기에서 실패했다. 연구소 망이 보안 검사를
위해 암호화 통신을 중간에서 풀었다 다시 묶는데, 그때 쓰는 인증서가 컨테이너 안에
없어서 "믿을 수 없는 상대" 로 판단한 것이다.

확인해 보니 가로채는 대상은 PyTorch 배포 서버 하나뿐이고 나머지는 통과한다.
인증서를 이미지에 넣어 해결했다. 망 밖에서 이 저장소를 쓰면 그 인증서를 지우면
된다는 것도 함께 문서로 남겼다.

### 3.3 뷰어 앞단

바깥에서 오는 접속은 nginx 가 받아 컨테이너로 넘긴다. 컨테이너는 외부에 직접
노출되지 않는다. 쓰던 주소(`172.16.116.98:9090`)는 그대로다.

옮긴 뒤 컨테이너 뷰어와 기존 뷰어의 응답을 대조했다 — **바이트 단위로 같았다.**

### 3.4 배포 규약과 대조 (devlog 016)

형제 프로젝트들이 같은 사고를 겪고 정리해 둔 배포·데이터 안전 규약이 있다.
내 구성을 하나씩 맞춰 보니 **위반이 하나 나왔다** — 컨테이너에 배포 디렉토리를
통째로 연결해서 비밀키가 든 설정 파일이 컨테이너 안에서 읽히고 있었다. DB 만 든
전용 디렉토리로 좁혔다.

규약 중 두 조항은 이 장비에서 구조상 지킬 수 없다 — **한 대가 개발·운영·백업을
겸하기 때문**이다. 못 지키는 것을 못 지킨다고 적어 두는 편이 반쯤 지키고 다 지킨
척하는 것보다 낫다고 보아 그대로 기록했다.

## 4. 사람의 검토 결과를 지키는 장치 (devlog 009 · 011)

이 시스템에서 **다시 만들 수 없는 것은 사람의 검토 결과뿐이다.** 사진은 다시
찍을 수 있고 검출은 다시 돌릴 수 있지만, 124개 시야를 전수 검토해 만든 2,400여
건의 판단은 그렇지 않다.

### 4.1 오프사이트 백업

백업이 전부 같은 디스크에 있었다. 디스크 한 장이 죽으면 전부 잃는다.

NAS 는 물리적으로 별개 장비다. 검증을 통과한 스냅샷만 NAS 로 밀고, **받은 쪽에서
다시 검증한다.** 가장 오래 남는 사본이 가장 덜 검증된 것이 되는 상황을 피하기
위해서다.

안전장치를 실제로 터뜨려 확인했다.

| 시험 | 결과 |
|---|---|
| NAS 가 연결 안 됐을 때 | 거부하고 **디렉토리조차 만들지 않음** |
| 깨진 스냅샷을 섞고 "최근 1개만 유지" 를 걸었을 때 | 증거를 남기고 **정리를 건너뛰어 정상 사본이 생존** |

두 번째가 핵심이다. 정리를 건너뛰지 않았으면 좋은 사본이 쫓겨났을 것이다.

**복구 리허설**도 했다. NAS 사본에서 되살려 무결성 검사·마이그레이션·화면 렌더링까지
통과하는 것을 확인했다. 무결성 검사만으로는 "백업은 멀쩡한데 거기서 시스템을 세우면
죽는" 경우를 못 잡는다.

### 4.2 검출을 다시 돌려도 검토 결과가 따라간다 (devlog 011)

사람의 검토는 개체 하나하나에 붙어 있다. 검출을 다시 돌리면 개체 목록이 통째로
새로 만들어지므로 **연결이 끊긴다.**

다시 맺어 주는 장치(`rebind.py`)를 만들었다. 세 단계로 찾는다.

1. **정확히 같은 위치**에 개체가 있으면 그것
2. 없으면 **충분히 겹치는** 개체를 찾아 연결
3. 그것도 없으면 "고아" 로 표시 — **지우지 않는다.** 검토 행이 스스로 도형 정보를
   들고 있어 나중에 되살릴 수 있다

만들기를 잘했다는 것이 바로 확인됐다. 검토 67건이 달린 시야를 **같은 이미지·같은
설정으로** 다시 검출했더니 정확히 일치한 것은 26건뿐이었다. AI 모델이 미세하게 다른
결과를 낸다. **이 장치가 없었으면 41건이 검토에서 떨어져 나갔을 것이다.**

## 5. 파이프라인이 DB 를 쓴다 (devlog 010 · 011 · 012)

2차 보고서 시점에는 스크립트 4개 중 1개만 DB 를 썼다. 이제 전부 쓴다.

### 5.1 잃어버린 품질 지표를 되찾았다

합성 결과 보고서가 파일 하나에 쓰이고 있었다. 슬라이드 셋이 같은 파일을 공유해서
나중에 돌린 것이 앞의 것을 지웠다. 세어 보니 **합성본 81개 중 49개가 품질 지표를
잃은 상태였다** — 합성이 잘 됐는지 판단할 근거가 없었다.

이제 시야마다 한 행이라 덮어쓸 자리가 없다. 다시 합성해 49개를 되찾았다.

### 5.2 그룹핑 신뢰성을 잰다 (devlog 012)

시야를 묶는 기준이 이 파이프라인의 핵심이다. 사진 여러 장이 같은 위치를 찍은
것인지 판단하는데, **판단 기준이 그 시료에서 의미가 있는지**를 재는 장치를 넣었다.

| 시료 | 같은 시야 최소 유사도 | 다른 시야 최대 유사도 | 여유 |
|---|---|---|---|
| RS23 71cm | 0.936 | 0.350 | 0.586 |
| WAP13 116cm | 0.974 | 0.538 | 0.437 |
| WAP13 450cm | 0.944 | 0.527 | 0.417 |
| RS23 369cm (신규) | 0.901 | 0.346 | 0.554 |

두 값 사이가 넓게 벌어져 있어야 기준선이 의미가 있다. 좁으면 기준선이 분포
한가운데를 자르고 있다는 뜻이고, 그때는 **조용히 잘못 묶인다.** 좁으면 자동으로
넘기지 않고 사람을 부른다.

이 장치가 **1차 보고서 때부터 남아 있던 질문에 답을 줬다.** WAP13 116cm 는 47개
시야 중 26개가 사진 한 장짜리라 "촬영을 덜 한 것인지 기준선이 안 맞는 것인지"
알 수 없었는데, 재 보니 **기준선 문제가 아니다.** 진짜로 한 장씩만 찍은 것이다.

### 5.3 떨어진 조각을 버린다

AI 가 낸 검출 영역에 본체와 떨어진 작은 조각이 섞여 있는 경우가 있다. 이번에 재
보니 **마스크 279개 중 106개(38%)** 가 그랬다. 떠돌이 점 하나가 개체의 경계 상자를
넓혀서, 중복 정리가 제대로 걸리지 않고 있었다.

본체만 남기도록 바꿨다. 통과분이 62 → 55 로 줄었는데 경계 상자가 조여지면서 중복
정리가 제 일을 한 결과다.

**기존 시료에는 적용하지 않는다.** 경계 상자가 검토 기록의 열쇠라, 전수 검토를
마친 자료의 열쇠를 흔들면 2,400여 건을 다시 맺어야 한다. 검토 기록이 있는 시야는
명시적으로 지시하지 않는 한 다시 검출하지 않도록 막아 뒀다.

## 6. NAS 자동 수집 (devlog 013 · 014)

```
NAS 감지 → 로컬 복사 → 시야 묶기 → 합성 → 검출 → 검토 열림
```

호스트가 1분마다 확인한다. 할 일이 없으면 1~2초에 끝나고 **GPU 를 건드리지
않는다.** 아무 일도 없으면 로그도 남기지 않는다 — 하루 1,440번인데 매번 적으면
정작 사고가 났을 때 그 줄을 못 찾는다.

### 6.1 복사가 끝났는지 판단하는 법

**아직 들어오는 중인 폴더를 건드리면 안 된다.** 절반만 가져가면 시야를 잘못 묶고,
그 위에 검출과 검토가 쌓인 뒤에 되돌리는 것은 훨씬 비싸다.

처음엔 "파일 시각이 한동안 안 바뀌면 끝난 것" 으로 판단했다. 그런데 흔히 쓰는 복사
명령은 **원본의 시각을 그대로 보존한다.** 한창 들어오는 중인데도 "몇 시간째 조용함"
으로 보인다. 실제로 첫 확인에서 이미 있던 폴더가 "2,949분째 조용" 으로 나왔는데,
그건 파일이 언제 도착했는지가 아니라 **언제 촬영됐는지**였다.

그래서 **본 것을 기억하도록** 바꿨다. 폴더의 (파일 수·총 용량)을 지문으로 적어 두고,
정해진 시간 동안 한 번도 안 바뀌었을 때만 가져온다. 복사 상황을 흉내 내 확인했다 —
파일 시각이 3시간 전 그대로인데 내용이 늘어난 경우를 잡아낸다.

### 6.2 검토는 슬라이드 단위로 연다

자동 처리가 다 끝나기 전에는 사람이 검토하지 못하게 했다. 반쯤 처리된 시료를
검토하면 **아직 안 돌아간 시야의 검출이 뒤늦게 들어오면서 이미 본 화면이 바뀐다.**

두 겹으로 막는다. 서버가 저장을 거절하고, 화면에서도 안내와 함께 검토 도구를
잠근다. 사진은 그대로 볼 수 있다 — 막을 것은 도구지 화면이 아니다.

### 6.3 실제로 돌았다

새 시료(`260731/RS23-GC03 369cm`, 사진 412장)로 전 과정을 확인했다.

```
감지 → 반입 824개 파일 1.37 GB → 시야 74개 → 합성 73개 → 검출 74개
그룹핑 직후  processing (검토 막힘)
검출 완료 후 done       (검토 열림)
```

## 7. 자동 수집 첫날 잡은 사고 — 배율 (devlog 015)

새 시료의 검출 통과율이 **1.6%** 였다. 기존 시료는 18.6% 다.

지표를 갈라 보니 크기와 형태 지표는 멀쩡한데 **조직 무늬(texture) 지표만 1,903 →
109 로 무너져 있었다.** 이 지표는 규조각 표면의 규칙적인 줄무늬를 재는 것으로,
규조각과 흙먼지를 가르는 1차 관문이다.

### 7.1 원인

사진에 딸려 오는 메타데이터에 **대물렌즈가 100배로 기록**돼 있었다. 기존 시료는
40배다. 메타데이터 안에서 계산이 앞뒤로 맞았고(네 시료 모두 오차 0.0000%), 그래서
처음엔 "배율이 진짜로 다르다" 고 판단했다.

**그런데 촬영하는 쪽에서는 규조류를 40배로만 찍는다고 한다.** 현미경 소프트웨어는
*소프트웨어에서 선택된* 렌즈로 계산하므로, 렌즈 교환대가 수동이면 실제와 어긋날 수
있다. 검산은 메타데이터 안의 일관성만 확인해 줄 뿐이다.

같은 사진에 배율 가정만 바꿔 다시 재서 확정했다.

| 새 시료 개체 60개 | 중앙값 |
|---|---|
| 메타데이터가 말하는 배율로 | **83** |
| 실제 40배로 | **2,659** |
| (대조) 기존 시료 | 1,872 |

배율을 바로잡으면 오히려 기존 시료보다 높다. 정상이다.

### 7.2 왜 이 지표만 무너졌나

조직 무늬 지표는 **줄무늬 간격을 실제 길이(µm)로 정의해 두고 픽셀로 환산해서**
이미지의 어느 성분을 볼지 정한다. 배율이 2.5배 틀리면 실제와 20% 밖에 안 겹치는
엉뚱한 곳을 뒤진다.

**지표마다 고장 나는 방식이 다르다는 것이 이 사고의 교훈이다.**

| 지표 | 배율이 틀리면 |
|---|---|
| 형태 비율 (원형도·볼록성 등) | 영향 없음 |
| 크기 (µm) | 비례해서 틀림 — 나중에 고칠 수 있고 눈에도 띈다 |
| **조직 무늬** | **무너진다** — "규조각이 아니다" 라는 그럴듯한 답으로 나온다 |

앞의 둘은 회복 가능하다. 그런데 조직 무늬는 예외도 경고도 없이 **그럴듯하게
틀린다.** 통과율 1.6% 라는 숫자만 아니었으면 못 봤을 것이다.

### 7.3 고친 것

**따로 지정하지 않으면 40배로 계산한다.** 메타데이터의 렌즈 배율을 그대로 믿지
않고, 카메라·중간 렌즈 정보는 그대로 쓰되 대물렌즈만 40배로 고정해 다시 계산한다.
다른 배율로 찍었다면 사람이 알려 줘야 한다 — 자동으로 알아내려 하지 않는다.
그러려다 두 번 틀렸다.

지정하는 수단은 둘이다. 명령줄 인자, 그리고 **시료 속성 화면의 배율 칸**(7.4).

### 7.4 시료 정보를 사람이 채운다 (devlog 017)

지역명·좌표·수심·채취일 칸은 설계 때 만들어 두고 비워 뒀던 것이다 — *"코드만으로는
단정할 수 없으니 사람이 채운다"* 는 판단이었다. 이제 채울 화면을 만들었다
(`/d/<시료>/edit/`).

폴더 이름에서 뽑히는 것(지역 코드·코어 코드·깊이)은 이미 채워져 있고, `RS = 로스해`
같은 것은 **추천으로만 보여 주고 사람이 확인해 넣는다.** 지역과 코어는 여러 시료가
공유하므로 몇 개가 함께 바뀌는지 미리 알린다.

## 8. 뷰어 개선 (devlog 007 · 012 · 017)

- **문턱 조정 화면** — 판정 기준을 화면에서 조정하고, 바뀌는 시야를 영향 큰 순으로
  미리 본다. 배율이 다른 시료가 섞이면 경고한다(조직 무늬 기준은 배율에 딸려 간다)
- **검출 영역 표시** — 채우기를 끄고 테두리만 그릴 수 있게 했다. 채우면 정작
  "이게 규조각인가" 를 판단할 수 없을 때가 있다
- **검토 전 화면** — 검출 전이라도 합성 사진과 원본을 볼 수 있다. 도구만 잠근다
- **무결성 검사** — 시료마다 배율·판정 기준이 하나인지 본다. 시료끼리 다른 것은
  정상으로 처리한다

## 9. 현재 상태와 남은 것

### 9.1 지금 돌아가는 것

| | |
|---|---|
| 시료 | 4개 (RS23 71cm·369cm, WAP13 116cm·450cm) |
| 사진 / 시야 | 757 / 198 |
| 사람의 검토 | 2,416건 (첫 3개 시료 전수 검토 완료) |
| 자동 수집 | 1분 주기, 동작 확인 완료 |
| 백업 | 로컬 + NAS, 복구 리허설 완료 |

### 9.2 진행 중

**새 시료 재처리.** 배율을 바로잡아 합성부터 다시 돌리고 있다. 검토 기록이 아직
없어 지금이 가장 싼 시점이다. 통과율이 기존 시료 수준(18% 안팎)으로 올라올 것으로
본다.

### 9.3 남은 것

1. **촬영 쪽 확인** — 현미경 소프트웨어의 렌즈 설정이 실제 교환대와 어긋나 있다.
   다음 촬영 전에 맞춰 두면 이런 일이 다시 안 생긴다
2. **배율이 기존과 다른 시료를 자동으로 세우는 장치** — 지금은 경고만 찍고 넘어간다
3. **고아 검토 화면** — 검출이 바뀌어 연결이 끊긴 검토를 사람이 다시 맺어 줄 화면
4. **검토 기록 내보내기** — 검토가 DB 에만 있다. 사람이 읽고 비교할 수 있는 형식으로
   내보내면 백업 외에 한 겹이 더 생긴다
5. **자동 실행 실패 알림** — 지금은 로그를 봐야 안다

### 9.4 재현율은 아직 실측되지 않았다

2차 보고서에서 정밀도를 26%로 실측했다. **재현율(놓친 것의 비율)은 여전히 추정이다.**
사람이 사진을 보고 "여기 규조각이 있는데 검출이 못 잡았다" 를 표시하는 도구는 있지만
(되살림 133건), 전수로 하지 않으면 재현율이 나오지 않는다. 이 값이 없으면 개수를
논문에 쓸 때 보정을 못 한다.

## 부록 — 오늘 기록한 판단 착오

이번 작업에서 내가 틀린 것들을 개발 로그에 남겼다. 같은 함정을 다시 밟지 않기
위해서다.

- **비교용 이미지를 만들 때 한쪽만 크게 축소**해서, 그 이미지가 결론을 바꿨다.
  사람이 "오른쪽이 흐리다" 고 한 것은 맞았고 원인이 내 이미지였다 (015)
- **잘못된 전제로 설계한 실험은 그 전제를 확인해 줄 뿐**이었다. 배율이 맞다고
  가정하고 만든 검증이 그 가정을 뒷받침하는 결과를 냈다 (015)
- **검산이 맞는다고 입력까지 맞다고 봤다.** 네 시료가 소수점까지 맞아떨어지는 것을
  보고 확신했는데, 검산은 메타데이터 안의 일관성만 본다 (015)
- **파괴적 기능을 실제 데이터에 대고 시험**해 검토 14건을 지웠다. 30분 전 백업에서
  복구했고, 그 뒤로는 사본 DB 로 시험한다 (017)

공통점은 하나다 — **계측이 사람의 눈과 어긋났을 때 계측을 먼저 믿었다.** 이번에는
사람이 맞았다.
