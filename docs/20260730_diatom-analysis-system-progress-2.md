## 1. 요약

1차 보고서 시점에는 시료 하나(34개 시야)에만 파이프라인을 적용한 상태였고, 가장
큰 과제가 "재현율 50~60%(육안 추정)" 였다. 그 이후 세 가지가 달라졌다.

**첫째, 전량 처리를 마쳤다.** 3개 시료 124개 시야 전부에 합성·검출을 적용했다.

**둘째, 사람이 전수 검토를 끝냈다.** 124개 시야를 모두 검토해 자동 검출 2,522개
중 2,044개를 오검출로 지우고, 133개를 문턱에서 되살렸으며, 174개의 분류를 직접
지정했다. **이로써 정밀도가 추정에서 실측으로 바뀌었다 — 26%다.**

**셋째, 데이터와 설정을 SQLite 로 옮기는 중이다.** JSON 파일이 원본이던 구조를
DB 로 바꿨다. 뷰어는 이미 DB 로만 돌고, 파이프라인 스크립트는 아직 JSON 을 쓴다.

이 과정에서 뷰어가 "결과를 보는 화면" 에서 **"검토를 실제로 돌리는 도구"** 로
바뀌었다. 분류를 직접 지정하고, 개체·시야마다 코멘트를 달고, 검출된 개체만 방향을
세워 훑고, 문턱에서 떨어진 후보를 겹쳐 볼 수 있다.

남은 최우선 과제는 여전히 **재현율**이다. 다만 이제 추정이 아니라 **측정할 수단이
갖춰졌다**(§5.2).

## 3. 이번 기간의 작업

### 3.1 계측 기준을 상수에서 메타데이터로 (devlog 004)

`segment_diatoms.py` 에 `UM_PER_PIXEL = 0.11259920634920635` 가 박혀 있었다.
여기에 계측값만 걸린 것이 아니라 **크기 관문(10~150 µm)과 텍스처 대역(0.4~1.6 µm)**
이 함께 걸려 있었다. 촬영 조건이 바뀌면 예외도 경고도 없이 결과 전체가 배율만큼
어긋난다.

`zen_meta.py` 를 만들어 사진 옆 XML(`Scaling/Items/Distance`)에서 읽는다.
합성본은 XML 이 따라오지 않으므로 `focus_stack.py` 가 사이드카로 물려준다.
결정 순서는 `XML > 사이드카 > 기본값` 이고, 기본값으로 물러나거나 한 실행에서
배율이 섞이면 경고한다. 결과 JSON 에 출처(`um_per_pixel_source`)를 남긴다.

**실제 ZEN XML 345개로 확인했다** — 전부 `source='xml'`, 0.112599 µm/px.
004 시점에는 촬영 데이터가 없는 머신이라 합성 XML 로만 검증했는데, 그 숙제를
005 에서 닫았다. 전량 배치가 `zen_meta.py` 도입 이전에 돌아 출처가 없던 결과
124개는 `backfill_scale_source.py` 로 재추론 없이 채웠다(합성본 81개는 없던
사이드카를 만들어 물려주었다).

### 3.2 areolae 를 원형 판정에서 더 무겁게 (devlog 005)

"원형으로 인식됐는데 areolae 가 뚜렷하지 않은 것을 걸러내고 싶다" 는 요구였다.
형태 문턱을 조이는 것이 먼저 떠오르지만, 실측해 보니 **형태로는 가려낼 수 없었다.**

| 텍스처 구간 | 개수 | 타원 IoU 중앙 | 볼록성 중앙 | 장축 중앙 |
|---|---|---|---|---|
| 1000~1500 | 159 | 0.887 | 0.962 | 14.2 µm |
| 1500~2000 | 82 | 0.896 | 0.957 | 14.2 µm |
| 2000~3000 | 121 | 0.886 | 0.960 | 15.2 µm |
| 3000~5000 | 124 | 0.891 | 0.959 | 16.6 µm |
| 5000+ | 183 | 0.898 | 0.966 | 18.4 µm |

IoU 0.886~0.898, 볼록성 0.957~0.966 — **거의 평평하다.** 형태 문턱을 어디에 두어도
areolae 가 약한 원반과 뚜렷한 중심목이 갈리지 않는다. 그래서 areolae 세기 자체를
관문으로 두었다.

`--round-texture-min`(기본 1500)을 원형에만 걸었다(봉상은 1000 그대로).
**원형 669 → 514.** 탈락분은 `원형areolae부족` 사유로 남아 뷰어에서 되살릴 수
있고, 문턱은 `refilter.py` 로 2초에 다시 잡는다.

**유의**: 텍스처는 크기와 같이 움직인다(위 표의 장축 14.2 → 18.4 µm). 작은 개체는
areolae 를 담는 화소가 적어 점수가 낮으므로, **이 문턱은 작은 중심목을 먼저
떨어뜨린다.** 문턱값 자체는 실물로 검증해야 한다(§5.1).

### 3.3 뷰어를 검토 도구로 (devlog 003·005)

이번 기간 작업량의 절반 이상이 여기다. 뷰어가 "결과를 보는 화면" 에서 **"검토를
실제로 돌리는 도구"** 로 바뀌었다.

| | 1차 보고서 시점 | 지금 |
|---|---|---|
| `_detection.html` | 794줄 | **1,576줄** |
| `base.html` (스타일) | 291줄 | **573줄** |
| `views.py` | 182줄 | **483줄** |
| `crops.html` | — | 75줄 (신규 화면) |

중요한 것은 분량이 아니라 **고친 것 대부분이 실제로 검토를 돌리다 막혀서 나왔다**는
점이다. 124개 시야를 사람이 하나씩 넘겨보는 일을 실제로 해 보지 않으면 알 수 없는
것들이었다.

#### 시야를 넘기는 흐름 — 124번 반복되는 동작

전수 검토는 같은 조작을 124번 반복하는 일이다. 한 번에 몇 초씩 걸리던 것이 전체
작업 시간을 지배한다.

| 조작 | 동작 |
|---|---|
| `← →` 또는 `‹ ›` | 캐러셀 앞뒤 **사진** (합성본 · 깊이맵 · 원본 프레임) |
| 끝에서 한 번 더 | 이웃 시야로 넘어갈지 **묻는다** — "다시 묻지 않기" 를 고르면 이후 바로 |
| `Ctrl+← →` 또는 `« »` | 곧바로 이웃 **시야** (묻지 않는다) |
| **검토 완료** | 표시를 저장하고 **다음 시야로 넘어간다** |

세 가지를 신경 썼다.

- **검토 완료가 다음 시야로 이어진다.** 검토는 연달아 하는 일이고 누른 사람의 뜻이
  분명하므로 묻지 않는다. 반대로 **해제할 때는 한 번 더 묻는다** — 잘못 눌러 풀리면
  "다 본 시야" 표시가 조용히 사라지고, 그것이 학습 데이터 선별의 근거다
- 이전 시야로 거슬러 갈 때는 **그 시야의 마지막 사진**에서 시작한다. 그러지 않으면
  `←` 로 되돌아갔다가 다시 `→` 를 누르는 왕복이 끊긴다
- **시야를 떠나기 전에 지연 저장 중인 교정을 밀어낸다**(`keepalive`). 지우고 곧바로
  `→` 를 누르면 그 교정이 사라지고 있었다

#### 사진 위에서 조작한다

교정 버튼 여섯 개를 사진 좌상단으로, **검토 완료**를 하단 가운데로 올렸다. 사진에서
눈을 떼지 않고 조작해야 하기 때문이다. 네 귀퉁이가 각각 쓰인다 — 좌상 교정 도구,
우상 레이어 토글, 우하 스케일바, 하단 가운데 검토 완료, 배율은 남은 좌하단.

머리글도 줄였다. 경로·그룹·태그·최선 프레임을 제목 옆 한 줄로 올려 본문의 세 줄을
걷어냈고, 헤더-탭 간격을 15 px → 5 px 로 좁혔다. 촬영 소요 초처럼 판단에 쓰이지
않는 값은 뺐다.

```
규조류 뷰어  데이터셋 / RS23-GC03 71cm / g1 · 5장 · g001_Snap-21371-21375 · 최선 …  ← g0  g2 →
[검출 화면 (합성본)] [개체 목록 45]        후보 45개 (봉상 36, 원형 9) · 0.1126 µm/px
```

#### 무엇을 눌렀는지 어긋나지 않게 — 실측이 필요했던 곳

여기가 가장 손이 많이 간 부분이다. **눌렀는데 다른 것이 잡히거나, 아무것도 없는데
뭔가 뜨는** 문제가 셋 있었고 전부 측정으로 원인을 찾았다.

**1. bbox 를 끄면 클릭 판정도 마스크로 바뀐다.** bbox 를 끄면 화면에 보이는 것은
마스크뿐인데 판정은 여전히 bbox 로 하고 있었다 — 큰 물체의 빈 자리를 눌러도 잡혔다.
폴리곤 내부 판정(ray casting)으로 바꿨고, hover 팝업도 같은 규칙을 쓴다.

**2. 겹친 개체는 다시 클릭하면 순환한다.** SAM 은 한 자리에 여러 스케일의 마스크를
내므로 bbox 가 예사로 겹친다(후보의 84%가 더 큰 마스크 안에 든다). 맨 위의 것만
잡히면 아래 것을 고를 방법이 없었다. **작은 것부터** 돌고, 선택 정보에
`이 자리에 3개 겹침 (2/3)` 으로 몇 번째인지 나온다.

**3. 탈락 후보는 마스크로만 판정한다.** "빈 곳을 눌렀는데 탈락 후보가 뜬다" 는
지적으로 시작해 덮는 면적을 재 봤다.

| 시야당 탈락 후보 133개(중앙)가 덮는 면적 | |
|---|---|
| bbox 합집합 (옛 판정 기준) | **46.6%** (최대 63%) |
| 마스크 합집합 | 19.5% (최대 32%) |
| 차이 — 아무것도 없는데 bbox 안 | **25.3%p** |

무작위 점으로는 48%의 위치에서 뭔가 떴다(마스크 기준이면 17%). 탈락분은 화면에
그려지지도 않으니 **왜 떴는지 알 방법이 없었다.** 폴리곤 판정으로 바꿨다(폴리곤이
없는 탈락 후보는 16,414개 중 0개라 잃는 것도 없다).

#### 판정을 사람이 고친다

자동 판정은 봉상·원형 둘뿐인데 조각난 규조각이 그 둘로 잘못 들어간다. 우클릭으로
직접 지정한다.

```
형태     원형 · 원형 파편 · 봉상 · 봉상 파편
──────────────────────────────
분류학   Eucampia
```

- **형태 칸과 분류학 칸을 줄로 나눴다.** Eucampia 는 형태가 아니라 속(屬)으로
  알아보는 것이라 같은 칸에 묶을 수 없다
- 사람의 지정이 자동 판정을 덮어쓰되 **원래 값을 남긴다**(툴팁에 `자동 판정: 원형`)
- 파편은 별도 색이고 사람이 지정한 것은 테두리가 점선이라 자동 판정과 구분된다
- 분류 정의를 한 곳(`CLASS_LABELS`, 지금은 `ClassDef` 표)으로 모아 **분류를 더할 때
  한 줄만 고치면 된다** — 메뉴·배지·필터·집계가 모두 그것을 읽는다. Eucampia 추가가
  그 첫 사례였다

실제로 174개를 지정했다: `봉상 파편 100 · 원형 파편 54 · Eucampia 12 · 봉상 6 ·
원형 2`. **파편이 154개** 로 가장 많다 — 조각난 개체를 온전한 것과 섞지 않겠다는
것이 이 기능의 목적이었고, 그만큼 실제로 있었다.

#### 코멘트 — 판단의 근거를 남긴다

개체마다 코멘트를 달 수 있고 **사진 오른쪽에 목록으로 나열된다.** 목록에 커서를
올리면 그 개체가 선택되고, 반대로 개체를 고르면 그 코멘트가 강조된다 — 메모를
읽으면서 어느 것에 대한 말인지 바로 짚어야 한다.

시야 전체 코멘트는 그 아래 **고정 높이 칸에서 그 자리로 적는다**(팝업을 열지 않는다).
개체에 붙지 않는 이야기 — 초점 상태, 판정을 보류한 이유 같은 것 — 를 적는 곳이다.
위·아래 두 칸이 각각 스크롤되고, 아래 칸은 높이가 고정이라 개체 코멘트가 길어져도
밀려나지 않는다.

#### 검출 결과만 보는 화면 (`/crops/`)

시야를 하나씩 넘겨보지 않고 **"이것들이 정말 규조각인가" 를 한 화면에서 훑는** 화면.
검출된 개체만 bbox 로 잘라 썸네일 격자로 늘어놓는다. 크기 내림차순이라 의심스러운
것(작고 밋밋한 것)이 뒤쪽에 모인다.

**방향을 세운다.** 마스크 폴리곤의 **면적 모멘트**로 주축을 구해 장축을 세로로
돌린다 — 방향이 통일되면 형태를 나란히 비교할 수 있다. 꼭짓점만 PCA 하면
`approxPolyDP` 로 단순화된 점 간격이 고르지 않아 결과가 치우치므로, 채워진 영역의
2차 모멘트를 닫힌 해로 구했다. 회전과 자르기는 한 번의 affine 으로 함께 한다
(잘라서 돌리면 모서리가 비고 두 번 보간한다).

검증은 **결과를 다시 재서** 했다. 합성 타원을 0·20·45·70·110·160°로 넣고 결과
이미지의 방향을 측정하니 전부 90°(세로)로 섰다(오차 0.06° 이내). 축 비율이 1.15
미만인 것(원형처럼 방향이 뜻 없는 것)은 돌리지 않는다 — RS23 259개 중 235개가
회전된다.

**썸네일마다 스케일바가 붙는다**(1·2·5 눈금, 이미지 폭의 40%를 넘지 않게 내림).
바는 칸이 아니라 **이미지에** 붙인다 — `object-fit` 여백만큼 길이가 어긋나기
때문이다. 크롭이 몇 µm 폭인지 알 수 있는 것은 회전량과 결과 크기를 자르기 전에
여백까지 포함해 확정해 두기 때문이다.

형태·사람지정·코멘트 유무로 거를 수 있고, 개체가 데이터셋마다 700~1,100개라 한
페이지에 500개까지만 그린다(잘린 개수를 화면에 적는다).

#### 재현율을 눈으로 세는 도구

우상단 **탈락** 체크박스를 켜면 문턱에서 떨어진 후보가 **빨간 점선 테두리**로 보인다
(채우지 않는다 — 사진이 가려지면 정작 규조각인지 판단할 수 없다). 시야당 100개가
넘어 기본값은 꺼짐이다.

**이것이 재현율 측정의 도구다**(§5.2). 보이는 규조각 중 점선만 있는 것은 문턱이
놓친 것, 점선조차 없는 것은 분할이 놓친 것이다.

#### 화면을 사진에 내준다 — 확대와 화소

**확대해도 원본이 아니었다.** 뷰어가 1600 px 축소본을 띄우고 그것을 확대하고
있었다(원본 2752 px). 고밀도 화면에서는 1배에서도 화소가 부족했다. areolae 세기로
판정하는 화면인데 정작 눈으로 확인할 화소가 없었던 셈이다.

- 그려지는 폭이 지금 이미지의 실제 화소를 넘는 순간 **원본으로 갈아 끼운다**
  (`naturalWidth` 로 재므로 축소본 폭을 코드에 박지 않는다). 미리 받아 두고 바꾸므로
  깜빡임 없이 배율·선택·검출 레이어가 유지된다
- **배율 표시를 원본 기준으로** 바꿨다. 화면에 맞춘 상태를 100%라 하면 "지금 원본을
  다 보고 있는가" 를 알 수 없다 — 실제로는 `53%` 다. `100%` 는 원본 1화소가 화면
  1화소라는 뜻이고, 원본을 받아 온 뒤에는 `· 원본` 이 붙는다
- **선 두께가 확대에 따라 두꺼워지고 있었다.** 보상 코드가 있었지만
  `Math.max(1, 2/k)` 의 하한 때문에 2배를 넘는 순간 1 px 에 고정되어, 그 뒤로는
  배율만큼 두꺼워졌다(12배에서 12 px). CSS 변수(`--inv`)로 역수를 곱하게 바꿨다.
  hover 후광과 유령 ✕ 표시도 함께 정리됐고(보상이 아예 없었다), 인라인 스타일에
  덮여 죽어 있던 선택 테두리 규칙도 살아났다

#### 목록 화면 — 무엇이 잡혔는지 목록에서 보인다

- 표지를 **합성본**으로 바꿨다(합성본이 없으면 그 프레임). 목록의 대표 그림이
  검출을 돌린 그림과 같아야 목록과 상세가 어긋나지 않는다
- 표지 위에 **검출 마스크를 얹었다**(34개 타일에 폴리곤 726개). 검출을 돌린 이미지와
  표지가 같을 때만 그린다 — 다른 이미지의 좌표를 얹으면 조용히 어긋난 그림이 된다
- **검토 완료 배지**(`✓ 검토`)와 진척 카운터를 세 곳에 넣었다
- 데이터셋 화면에 진척을 한 줄로 넣었다. **자동 검출과 교정 후 개수를 함께** 보여야
  뜻이 통한다 — 하나만 보면 문턱이 센 것인지 사람이 많이 지운 것인지 알 수 없다

```
검출 811 → 교정 후 264개 (원형 38 · 원형 파편 31 · 봉상 119 · 봉상 파편 63 · Eucampia 8)
· 시야당 7.8 · 교정: 삭제 608 · 되살림 47 · 분류 지정 109 · 코멘트 2 (+시야 1)
```

#### 이미지 캐시 — 옛 화면이 남지 않게

목록의 마스크·배지·개수는 요청마다 다시 계산하므로 교정하고 목록으로 오면 그 자리에
반영된다. 다만 두 군데서 옛 화면이 남을 수 있어 막았다.

- 이미지 응답에 **캐시 검증자가 하나도 없었다.** 주소가 그대로여서 합성본을 다시
  만들어도 브라우저가 옛 그림을 붙잡을 수 있었다 → 주소에 원본 mtime(`v=`)을 박고
  `Cache-Control: immutable` 로 보낸다. 내용이 바뀌면 주소가 바뀌므로 늘 맞고,
  두 번째 방문은 오히려 빨라진다
- **뒤로 가기**(bfcache)로 돌아오면 캐시된 화면이 되살아난다 → `pageshow` 에서 다시
  받는다

### 3.4 데이터와 설정을 SQLite 로 (devlog 006)

JSON 이 원본이던 구조를 DB 로 바꿨다. 성능도 이유지만(슬라이드 3장에 첫 화면이
파일 251개를 열었다) **결정적인 것은 둘 곳이 없던 것들**이었다.

- **실행 이력** — `stack_report.json` 이 합성본 81개인데 32항목만 남아 있다.
  실행마다 덮어써서 앞의 기록이 사라졌다
- **문턱 이력** — `refilter` 가 판정을 덮어쓰므로 "원형 669 → 514 가 언제 무슨
  문턱으로" 에 답할 수 없다. 문턱 11개가 결과 124개에 복사돼 있었다
- **처리 상태** — NAS 를 붙이면 대기/복사중/처리중/완료/실패가 필요하다
- **시료의 출처** — 아래 §4

1~4단계(모델·이전·대조·뷰어)를 끝냈다. 대조는 두 단계로 했다.

| 대조 | 결과 |
|---|---|
| `verify_db.py` — DB ↔ JSON | 검사 37개 전부 일치 (지표 합까지: `texture` 54,051,089, 폴리곤 좌표 882,880) |
| JSON 판 `data.py` ↔ DB 판 | 124개 시야 전부, **개체 dict 하나하나까지** 같은 값 |

두 번째 대조가 눈으로는 못 볼 세 가지를 잡았다 — 유령(지운 것)은 파일에 적혀 있던
`id` 를 유지해야 하고, 중첩정리로 떨어진 126개는 탈락분인데도 `cls` 를 갖고 있으며,
`n_labeled` 는 통과분만 세야 다른 화면과 정의가 같아진다.

## 5. 검증 상태 — 정직한 기록

### 5.1 정밀도는 실측됐다. 문턱은 아니다

전수 검토로 **정밀도 26%** 가 나왔다(자동 2,522 중 사람이 남긴 627). 1차 보고서의
"판정 기준을 실측으로 수립했다" 는 서술이 이제 사람의 검토로 뒷받침된다.

다만 **원형 판정 문턱(`round_texture_min=1500`)은 실물로 검증되지 않았다.**
오검출을 걸러내며 정한 값이고, 텍스처가 크기와 같이 움직이므로 작은 중심목을
함께 떨어뜨릴 수 있다. 크롭 갤러리에서 방향을 세워 훑으면 확인할 수 있다 —
**최우선 과제다.**

### 5.2 재현율은 이제 측정할 수 있다

여전히 육안 추정(50~60%)이지만, 측정 수단이 갖춰졌다. 뷰어의 `탈락` 레이어를 켜고
보이는 규조각을 세 갈래로 가르면 된다.

| 무엇이 보이나 | 뜻 | 고치는 비용 |
|---|---|---|
| 실선 마스크 | 검출됨 | — |
| **점선만 있다** | 문턱이 놓쳤다 | `refilter.py` 2초 |
| **점선조차 없다** | 분할이 놓쳤다 | 분할 단계를 고쳐야 한다 |

**두 숫자를 갈라 세는 것이 중요하다** — 앞은 문턱 조정으로 되찾고, 뒤는 근본
수정이 필요하므로 투자 판단이 갈린다. 되살림 133개가 이미 "문턱이 놓친 것" 의
부분 실측값이다.

### 5.3 진단만 하고 적용하지 않은 것

**bbox 를 부풀리는 떠돌이 픽셀.** "마스크는 같은데 bbox 만 다른 개체가 있다" 는
관찰에서 시작해 사진 한 장을 다시 돌려 원본 마스크를 뜯어봤다.

```
SAM bbox (2293, 257, 163, 161)  마스크면적 13003
  성분 1: 면적 13,002  bbox (2293, 257, 139, 162)   <- 본체
  성분 2: 면적      1  bbox (2456, 349,   1,   1)   <- 24 px 떨어진 픽셀 하나
```

bbox 는 SAM 이 준 것(마스크의 **모든** 픽셀)이고 폴리곤·형태 지표는 **가장 큰 윤곽
하나만** 쓴다. 후처리를 껐으므로 작은 분리 조각이 남는다. 통과분의 **27.5%** 가
본체보다 10 px 넘게 큰 bbox 를 갖고 있다.

**그리고 이것이 중복 정리를 무력화한다.** 상호 포함율 0.8 문턱을 bbox 로 재는데,
실제로 0.794 로 아슬아슬하게 피해 중복이 살아남는 사례를 확인했다.

`tighten_bbox.py` 를 만들어 dry-run 까지 했으나(개체 18,936 중 11,472의 bbox 가
줄고, 중복 정리를 다시 돌리면 2,522 → 2,193) **적용하지 않았다.** `bbox` 가 교정
기록의 키이고, 전수 검토를 막 끝낸 직후에 키를 흔드는 것은 순서가 아니라고 보았다.
DB 이전이 끝난 뒤 재바인딩과 함께 한 번에 푸는 것이 낫다.

### 5.4 검토 중에 드러난 버그 (devlog 005 §4)

도구를 실제로 쓰기 시작하니 **예외가 나지 않고 그냥 틀린 결과를 보여주던 것들**이
드러났다. 7건을 고쳤다. 성격을 보여주는 두 가지만 적는다.

- **지운 개체가 저장할 때마다 되살아났다.** 문턱을 올리면 사람이 지워 둔 개체가
  탈락분으로 옮겨가는데(실제로 12개), 그때 클라이언트가 복구 목록을 잘못 되짚어
  같은 개체가 "지움" 과 "복구" 양쪽에 들어갔다. 새로고침하면 지운 것이 살아났다
- **교정을 되돌려도 옛 상태가 따라붙었다.** 캐시에 담긴 원본 dict 를 직접 고치고
  있어서, 되살리거나 분류를 지워도 옛 값이 남았다. 파일에는 제대로 지워져 있어
  화면만 보고는 원인을 짚을 수 없는 종류다

그 밖에: 여러 줄 `{# #}` 주석이 화면에 그대로 나왔고(Django 는 한 줄만 주석이다),
확대하면 bbox 선이 두꺼워졌고(보상 코드의 하한이 거꾸로 작동했다), 목록 타일에서
사람이 지정한 분류가 다른 색에 덮였고, 이미지 응답에 캐시 검증자가 없었다.

### 5.5 이 환경에서 검증할 수 없는 것

- **JS 를 실행할 수 없다** — node·브라우저가 없다. 렌더한 인라인 스크립트를 뽑아
  구문·미선언 참조 검사로 확인해 왔다(그 검사가 실제 버그를 잡았다). 실제 동작은
  사용자가 뷰어를 쓰면서 확인했고, 고친 것 상당수가 그 과정에서 나왔다
- **기하 계산은 결과를 다시 재서** 확인했다(방향 세우기·스케일바). 부호 규약을
  추측하지 않는 것이 요령이다

