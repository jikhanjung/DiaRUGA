## 2. 같은 개체 묶기 (P11 · `v0.9.0`)

### 2.1 실측이 설계를 확인했다 (090 — 0단계)

`yolo-3차` 의 이웃 이미지 쌍 **13,523곳**에서 쟀다(`tools/measure_link_thresholds.py`,
읽기 전용).

| 무엇 | 값 |
|---|---|
| 근접 창(기준 bbox 1.5배) 안 후보 수 | 0개 46.0% · 1개 37.5% · 2개 13.2% · 3개 2.5% · 4개+ 0.8% |
| 최선 후보 IoU (겹침 있는 것만) | 중앙 0.83 · IoU ≥ 0.5 가 77.4% |
| 최선-차선 간격 | 간격 < 0.2 (헷갈리는 자리) 21.4% |

읽는 법이 셋이다.

- **사용자의 직감이 맞았다** — "프레임마다 하나씩, 많아야 두셋". 4개 이상은
  0.8% 뿐이라 팝업의 줄 길이가 실제로 짧다. 창을 2.0배로 넓혀도 "0개" 가
  46 → 42% 로 거의 안 줄고 잡음만 늘어 **K=1.5 로 확정**했다
- **0개가 46% 다.** 이웃 프레임에서 같은 개체가 안 잡힌 경우가 절반이다 —
  초점면이 다르면 검출이 안 되는 것이 자연스럽다. **"(없음)" 이 일급 선택지**
  여야 한다는 근거가 여기서 나왔다
- **미리 고르기는 보수적으로** — `IoU ≥ 0.5 이고 차선과의 간격 ≥ 0.3` 일 때만
  ✓ 를 미리 찍는다(맞을 수 있는 것의 2/3). **헷갈리는 21% 는 사람 손에 남긴다** —
  자동값이 사람의 판단을 오염시키는 자리다

### 2.2 핵심 결정 — 이것은 교정과 같은 무게다

`TODOs.md` 의 원안(2026-08-05)은 "IoU 로 자동 계산하는 층, 재검출하면 다시
계산" 이었고 그래서 `Candidate` FK + CASCADE 로 충분했다. **사람이 고르는 순간
그 전제가 무너진다.**

| 원안 | 실제 |
|---|---|
| 산수 — 재검출하면 다시 계산 | **사람의 판단 — 재생성 불가** |
| `Candidate` 를 FK 로 | `(image, batch, mask_key)` 로 짚는다 |
| 검출이 지워지면 CASCADE | 검출이 바뀌어도 남는다 · `geom` 을 스스로 든다 |
| 내보낼 것 없음 | `export_review.py` **FORMAT 4** 로 git 감사 기록에 실린다 |

**계획서가 스스로 뒤집힌 기록을 남겼다는 점이 중요하다** — 같은 자리를 다음에
또 지나가기 때문이다(회차를 넘는 묶기가 정확히 그 자리다, 8절).

### 2.3 화면 (091·099 — 2·3단계)

우클릭 → **[⛓ 동일 개체 묶기]** → 팝업. 판마다 닻 근처의 살아 있는 후보를
거리순 3개까지 펼치고, 하나씩 고르고, 별로 대표를 세운다.

- **후보 계산은 화면이 한다** — 새 조회 API 가 없다. 검토 화면이 프레임마다의
  검출을 이미 들고 있다(P09 캐러셀). 서버가 더한 것은 크롭 경로 하나뿐이다
- **화면의 지금 상태를 본다** — 서버가 준 초기 상태가 아니다. 방금 지운 마스크는
  후보에서 빠지고 방금 그린 마스크는 든다
- **서버가 다시 검사한다** — 시야 밖 이미지 · 없는 마스크 · 오검출로 지운
  마스크 · 대표 0/2개 · 멤버 1개 · 이미 다른 묶음에 속한 마스크(409).
  **기하는 서버가 스스로 뜬다** — 화면이 보낸 것을 믿지 않는다
- **사슬 배지 ⛓ 와 캐러셀 따라가기** — 묶인 개체를 고른 채 판을 넘기면 다음 판의
  짝이 1.4초 밝아진다. 마스크 색은 안 건드린다(색은 분류가 말하고, 묶임은 정체에
  대한 다른 축이다)

> **브라우저 레이어가 잡은 것** — 미리 고르기를 `render()` 안에 두었더니
> **"(없음)" 으로 뺀 판을 다음 그리기가 도로 찍었다.** 그리기가 상태를 만들면
> 사람의 선택이 진다 — **그리기는 상태를 읽기만 해야 한다.** 서버 시험 11개는
> 이것을 못 잡는다(서버는 화면이 무엇을 보냈는지만 본다).

## 3. 2차 검토가 만든 것 (092~095)

### 3.1 완료 표시를 걷었다 (092)

직접 그리기(P09)가 열리기 전에 검토한 시야는 **엔진이 낸 것 중에서 고르는 일**만
거쳤다. 검토자가 기능을 써 보고(18건) 남극 시료를 다시 보기로 했다 — 남극 9개
슬라이드 366 시야의 완료 표시를 걷었다.

**새 칸을 만들지 않았다.** 검토자 판단이 "구분할 필요는 없지만 진척은 보고
싶다" 였고, 그래서:

- 1차의 기록은 **git 에 이미 있다**(`review/` 감사 기록과 그 시점의 백업)
- 걷은 시점(08-09 15:14)이 분수령이라 **지금부터 붙는 완료가 곧 2차다**
- 직접 그린 개체는 저장부터 구분돼 있다(`batch IS NULL`)

교정 7,493건과 시야 코멘트는 안 건드렸다 — 체크만 풀었다.

### 3.2 `Chaetoceros` 가 1건에서 199건이 됐다 (093·094)

| 시점 | `chaetoceros` 교정 |
|---|---|
| 1차 검토까지 | **1건** |
| 2차 검토 중간 (08-09) | 74건 |
| 지금 | **199건** |

**왜 이제서야 쓰였나.** 분류 자체는 038~040 무렵에 만들어 뒀지만, **강모(seta)가
가늘고 길어 엔진이 개체로 못 잡거나 조각으로만 잡았다.** 검토가 "엔진이 낸 것
중에서 고르는 일" 이던 동안에는 봉상(`rod`)으로 분류해 두는 것이 손댈 수 있는
전부였다.

`wap13-gc47 116cm` 한 슬라이드에서만:

- **96건은 손으로 그렸다** — 엔진이 아예 못 낸 개체들
- **89건은 기존 검출에 라벨만 붙였다** — 형태는 잡혔는데 분류가 없거나 틀렸던 것
- **`rod` 6 · `round` 1 · `rod_frag` 1 이 재분류됐다** — 1차 때 봉상으로 밀어
  넣었던 것들이 제 이름을 찾았다

`gc03-c1 72cm` 은 결이 달라 **조각이 대부분**이었다(`round_frag` 27 ·
`rod_frag` 25 · `chaetoceros` 11). 시료 차이로 읽힌다.

> **여기서 나온 주의 하나** — 2차 검토를 거친 슬라이드와 아직 안 거친 슬라이드는
> **조성을 비교하면 안 된다.** 분류 구성이 검토 회차에 따라 달라져 있다.

### 3.3 `?` 하나를 데이터로 고쳤다 (095)

검토 구분 라디오가 세 슬라이드에서 `◉ ?` 로 나왔다. 이름은
`Run.params["backend"]` 에서 오는데, P02 이전에 계산된 260729 세 슬라이드의
검출은 **ingest 실행 #19** 로 들어와 backend 가 기록된 적이 없었다.

**코드 폴백(묶음 이름에서 추정)을 버렸다** — 화면에서 "모르는 것" 과 "아는 것"
이 같아 보이게 된다. `?` 는 기록이 없다는 정직한 표시이고, **기록이 실제로 있는
자리는 데이터를 채우는 것이 맞다.** 백업 → dbsync → dry-run → `--apply` 규약대로
갔다.

## 4. 조용히 죽어 있던 것 둘, 그리고 그 답 (096~098)

### 4.1 저장이 한 번 미끄러지면 그 뒤로 아무것도 저장되지 않았다 (096)

실사용 보고에서 시작했다 — 봉상 다섯을 지우고 새로 그려 가며 검토하다 묶기를
눌렀는데 그린 마스크 하나를 서버가 거절했다. DB 를 보니 **그 마스크만
`ObjectReview` 에 없었다.**

```js
function postReview(keepalive) {
  savePending = false;          // ← 첫 줄에서 끈다
  ...fetch...
  .catch(() => saveState.textContent = '저장하지 못했습니다');  // 안 되살린다
}
```

저장이 한 번 미끄러지면 `savePending` 이 꺼진 채라 그 뒤의 `flushSave` 가
**"할 일이 없다" 고 판단한다.** 상태 줄의 작은 글씨 하나가 유일한 흔적이고,
사람은 계속 검토한다.

고침 셋: **실패는 다시 저장할 것으로 남긴다** · **묶기 팝업이 열릴 때 밀린
저장부터 밀어낸다** · **`keepalive` 는 정말 떠날 때만**(브라우저가 본문 64KB 를
넘으면 보내 보지도 않고 거절한다 — 교정이 많은 시야가 정확히 그 크기다).

### 4.2 폴러 3단계가 사흘째 죽어 있었다 (097)

증상은 "사진이 안 왔다" 였지만 사진은 **와 있었다**(774개 파일 1.3 GB). 슬라이드가
`pending` 에서 멈춰 그룹핑부터가 안 돈 것이다.

뿌리는 **079 가 붙인 `</dev/null`** 이었다. 묶음 루프 안에서 docker 가 루프의
stdin 을 삼키는 것을 막으려던 것인데, **3단계의 밀린 일 조회가 heredoc(stdin)으로
파이썬을 먹이고 있었다.**

```sh
run() { timeout "$1" docker compose run --rm -T pipeline "${@:2}" </dev/null; }
TODO=$(run "$T_SCAN" python - <<'PY' 2>/dev/null ...
```

`python -` 이 빈 stdin 을 받아 **조용히 성공(빈 출력)** 하고, 빈 결과는 "할 일
없음" 이다. `2>/dev/null` 이라 흔적도 없었다. **죽은 날(08-07 오후)과 드러난
날(08-10) 사이가 사흘**이다 — 그사이 새 슬라이드가 없어서다.

고친 뒤 **밀린 일 조회를 스크립트로 뺐다**(`pending_slides.py`) — heredoc 으로
파이썬을 먹이는 모양 자체를 없앴다. 그리고 **정찰 JSON 파싱 실패를 "새것 없음"
으로 접지 않게** 했다: *조용히 성공한 빈 결과와 실패를 한 갈래로 접으면 안 된다.*

### 4.3 그 답 — 파이프라인이 살아 있는가를 화면이 말한다 (098)

`/system-settings/pipeline/` 이 셋을 낸다: **정찰**(`last_scan.json` 의 나이가
곧 "폴러가 살아 있는가") · **끝나지 않은 슬라이드**(단계별 진행과 파이프라인이
적은 문장) · **최근 실행 12개**.

**해석은 화면이 먼저 한다** — 경고 줄이 맨 위다.

- 정찰이 5분 넘게 없다 (폴러 자체가 멈춤)
- 밀린 슬라이드가 있는데 도는 실행이 없고 마지막 완료가 15분 전보다 이르다 —
  **097 의 그 모양**("대기 중인데 아무도 데리러 오지 않는다")

> **첫 화면부터 거짓 경고를 냈다.** 폴러가 죽어서가 아니라 **한 주기가 잠금을
> 쥐고 긴 합성을 도는 중**이라 다음 정찰이 밀린 것이었다(설계상 정상). **도는
> 실행이 있으면 정찰 나이 경고를 접는다** — 늘 우는 경고는 곧 아무도 안 읽는
> 경고다.

## 5. 저장소를 넷으로, 운영을 `/srv` 하나로 (100·101 · `v0.9.1`)

시작은 정리였다("repo 루트에 파이썬 스크립트가 너무 많네" — 루트에 `.py` 가
35개였다). **설계를 바꾼 것은 마지막 한마디다** — *"운영 서버에 repo 가 없을
수도 있다."*

| 디렉토리 | 무엇이 | 개수 | `/srv` 로 |
|---|---|---|---|
| `pipeline/` | 컨테이너 안에서 도는 것 + 그들이 쓰는 모듈 | 11 | **간다** |
| `ops/` | 주기적으로 돌거나 상태를 보는 것 | 10 | **간다** |
| `migrate/` | 이전기·일회성 | 9 | 안 간다 |
| `tools/` | 개발 도구 | +5 | 안 간다 |

저장소를 붙잡고 있던 자리 셋(cron 세 줄)과 폴러 안의 `REPO=` 를 전부 끊었다.
이제 cron 은 `/srv/DiaRUGA/bin/` 과 `/srv/DiaRUGA/scripts/` 만 본다.

**파이프라인 스크립트도 `/srv` 것이 돈다** — 이미지 안의 `/app` 사본이 아니다.
이득이 크다: **스크립트 한 줄을 고치는 데 7.2 GB 를 다시 굽지 않는다.** 이미지를
다시 굽는 것은 의존성이 바뀔 때뿐이다.

> **배포 직전에 사용자가 물어서 고장 하나를 잡았다** — "파이프라인은 여전히
> 손댈 거 없어?" 스크립트는 `/srv` 것이 도는데 그 안의 `judge`·`zen_meta`·
> `runlog` 는 **이미지 것을 물고 있었다**(`sys.path.insert(0, APP)`). `APP` 을
> `sys.path` **뒤에** 붙이는 것으로 고쳤다. 실제로 그 상태로 돌고 있었다.

`deploy.sh` 에 8단계가 붙었다 — 배포 뒤 `sync_to_srv.sh --from-image` 가 `/srv`
를 그 판에 맞춘다. **앞으로 판을 올릴 때마다 `/srv` 가 자동으로 맞는다.**

## 6. 개체 카탈로그 — 번호와 동정 (105 · `v0.10.0`)

> "카탈로그 번호를 붙이고, 각각에 대한 동정 결과를 좀 채워넣어야 하는 시점이라고
> 생각해. 규조 객체 각각에 페이지를 만드는 것은 부적합해보이고, 관찰 하나당 카드
> 형태로 보여주는 페이지를 만들어주자."

### 6.1 없던 것 — 개체를 부르는 이름

검출된 개체는 지금까지 `mask_key`(bbox 를 이어 붙인 문자열)로만 짚었다. 그것은
**이미지 한 장 안에서만 유일한 내부 열쇠**다. 논문에 개체를 인용하거나 표본
목록을 만들려면 사람이 읽고 적을 수 있는 고정 번호가 있어야 한다.

동정을 적을 자리도 없었다. `ObjectReview.label` 은 `ClassDef` 가 정한 목록에서
고르는 것이라 **종 수준을 담지 못한다** — 종은 목록으로 가둘 수 없다(`var.`·`f.`·
명명자가 붙고 검토 중에 이름이 바뀐다).

### 6.2 번호는 저장하지 않는다

```
<지역>-<지점>-<시료>[-<관찰>]-g<시야>[-f<프레임>]-<위치>-<묶음>

RS23-GC03-071-g03-1204_856_132_97-S1        남극 · SAM2 · 합성본
RS23-GC03-071-g03-f28-1198_861_130_99-Y3    남극 · YOLO 3차 · 프레임 28
BP-BP09-0901-g12-f27-843_1502_96_210-S1     육상 · 단독 프레임
```

칼럼에 넣으면 층을 고치거나 재검출을 돌릴 때 저장된 값과 실제가 어긋나고,
**어긋난 것은 예외가 안 나고 그냥 틀린다.** 파생이면 어긋날 수가 없다.

**위치를 줄이려다 세 번 걸렸다.** 짧게 만들려고 자른 후보가 전부 실측에서
부딪혔다(이미지 한 장에 개체가 최대 106개다).

| 후보 | SAM 충돌 | YOLO 충돌 |
|---|---:|---:|
| x,y | 90 | 270 |
| x,y,너비 | 10 | 30 |
| 중심 좌표 | 0 | 30 |
| 해시 4자 | 2 | 0 |
| **bbox 전체** | **0** | **0** |

**해시 5자도 오늘 0 이지만 그것은 재 봐서 0 인 것**이고, bbox 전체는
`Candidate` 의 유일 제약이 **보장한다.** 4자 해시가 실제로 2건 부딪힌 것을 보면
자료가 늘면 5자도 언젠가 부딪힌다 — 길이보다 이쪽을 골랐다.

실제 자료로 통과 개체 **32,480건에 번호를 매겨 전부 서로 달랐고, 못 만든 것은
0건**이었다.

### 6.3 화면과 안전망

`/d/<슬러그>/catalog/` — 카드 하나가 개체 하나이고, 왼쪽에 **세워서 자른**
크롭(방향이 통일돼야 형태를 비교한다), 오른쪽에 번호 · 종명 · 유형 · 코멘트.
검색창과 거르개 칩(형태별 + 수동 복구·사람 지정·코멘트 있음·**동정함·동정 안 함**)이
붙는다.

- **엔진마다 별개이고, 고르는 장치는 없다.** 화면은 **검토 대상 묶음 하나만
  따라간다** — `?batch=` 로 넘어다니는 버튼을 만들었다가 걷었다. 관리 화면에서
  검토 대상을 갈면 검토·크롭·계측·카탈로그가 **함께** 옮겨 가고, 그러면 화면마다
  다른 판을 보는 상태가 아예 안 생긴다(051 이 그 상태에서 났다)
- **`ops/check_db.py` 에 9번을 더했다** — 묶음 코드가 있는가 · `M` 이 아닌가 ·
  층 코드가 번호에서 안 뭉개지는가 · 관찰이 층을 갖고 있는가 · 종명이 붙은 교정이
  묶음에 들어 있는가. **다섯 다 사본을 망가뜨려 걸리는 것을 확인했다**
- **9번은 뷰어 이미지를 올린 뒤에 돈다**(규칙이 뷰어 코드에 있다). 낡은 판에서는
  **크게 적고 넘어간다** — 죽지도, 조용히 건너뛰지도 않는다

### 6.4 밟은 것 — "검토 완료" 한 번이 동정을 지웠다

`/review` POST 는 **그 (이미지, 묶음)의 교정 행 중 payload 에 없는 것을 지운다** —
"뷰어는 늘 전체를 보낸다" 가 전제다. 그런데 **검토 화면은 종명을 모른다.** 그래서
종명만 채운 행은 다른 표시가 전부 비어 있어, 사람이 **아무것도 안 하고 "검토
완료" 만 눌러도 통째로 사라졌다.**

017·027·053 이 전부 그 삭제 줄에서 났고 두 번은 운영 자료를 잃었다(14건·37건).
**시험으로 먼저 재현해 놓고** 막았다 — 삭제 범위를 정할 때 종명이 든 행의 키를
**갈래 없이 늘** 얹는다.

> **응답이 방금 친 글자를 덮은 것은 브라우저 레이어로만 잡혔다.** 세 칸을 잇달아
> 채우니 코멘트만 저장이 안 됐다 — 먼저 보낸 종명 저장의 응답이 돌아오면서 그
> 사이에 친 코멘트를 서버가 아는 빈 값으로 되돌리고 있었다. 서버는 받은 것을
> 정확히 저장했고 200 을 냈다.

## 7. 묶기를 실제로 쓰며 나온 넷 (102·103·104·107)

### 7.1 탈락 후보도 고를 수 있다 — 고르면 되살아난다 (102)

P11 은 탈락 후보를 1판에서 뺐다("묶기(정체)와 되살리기(판정)를 한 팝업에서
겹치면 저장 의미가 복잡해진다"). 실제로 쓰다 보니 **그 프레임에서 가장 좋은
마스크가 문턱에서 떨어져 있는 일**이 있었다 — 초점이 흐린 판은 텍스처가 모자라
탈락한다.

겹침을 피하는 대신 **뜻을 하나로 못 박았다**: 사람이 "이것이 그 개체다" 라고
하면 그것은 **검출이 맞다는 판단이기도 하다.**

- **화면이 먼저 말한다** — 빨간 점선(탈락 레이어와 같은 표시) · `탈락` 딱지 ·
  "탈락 후보 N개를 함께 되살립니다" · 저장 뒤 "묶었습니다 (4장 · 탈락 1개 되살림)"
- **미리 고르기는 탈락을 안 집는다** — 자동으로 골라 두면 사람이 확인하지 않은
  판정이 서 버린다
- **되살리기는 서버가 행 하나만 좁게** 한다 — 화면에서 하려면 그 판에 `/review`
  를 따로 보내야 하고, 그 길은 "그 이미지의 교정 전체를 갈아치운다" 다

### 7.2 프레임 판을 보고 한 교정이 통째로 거절되고 있었다 (103 · `v0.9.3`)

> "22119 프레임에서 같은 자리의 검출 둘을 오검출로 지웠어. (…) 묶은 것은 잘
> 보이지만 **맨 처음에 지운 두 개가 여전히 살아 있네.**"

`/review` 의 덧문이 이렇게 생겼었다.

```python
cur = next((d for d in vp.detections.all() if d.is_current), None)
if cur is not None and Path(cur.image_path).stem != stem:
    return None, "화면과 저장 대상이 어긋난다 …"
```

**시야 하나에 현재 검출이 여럿이다**(합성본에 하나, 프레임마다 하나 — P09·055).
그런데 그중 **아무거나 하나**를 집어 견줬다. 053 의 `.first()` 와 정확히 같은
자리다: *제약이 있다는 것과 조회가 그걸 쓴다는 것은 다르다* 를 이번엔
**"판이 여럿이라는 것과 검사가 그걸 아는 것은 다르다"** 로 다시 밟았다.

세어 보니 **판이 여럿인 시야 417개 중 11개가 프레임 판으로 열리고, 그 열한
화면에서는 어떤 교정도 저장된 적이 없었다.**

고장이 셋이었다.

1. **서버가 갈래를 안 밟았다** — 시험은 "현재 검출이 여럿" 을 일부러 세워 두고
   열두 가지를 확인하는데 **전부 합성본 stem 으로만 보냈다**(086 과 같은 이야기)
2. **화면이 실패를 조용히 흘렸다** — 회색 글씨 한 줄이었고, 409 를 전부 "아직
   검토를 열지 않았습니다" 로 적어 **사람은 안 겪은 문제를 찾으러 간다**
3. **묶기는 그 문을 안 지난다** — 한쪽은 거절, 한쪽은 200. 보고의 문장이 정확히
   그 모양이었다

고친 뒤: 덧문은 **그 시야가 가진 판들**과 견주고, 저장 실패는 **성공할 때까지 안
사라지는 띠**로 서버의 말을 그대로 적으며, **밀린 저장이 실패한 상태에서는 묶지
않는다.** 지금 열한 시야의 검토 기록이 비어 있는 것은 **맞다** — 되살릴 방법이
없어 다시 검토해야 한다.

### 7.3 묶인 개체는 분류를 함께 받는다 (104 · `v0.9.4`)

묶음은 "이 판들의 이것이 같은 개체다" 라는 말이므로, 봉상인지 원형인지는
**개체의 성질**이다. 그런데 분류는 `ObjectReview` 에 판마다 따로 앉아 있었다.

**서버가 번지게 한다.** 화면에서 하면 다른 판의 저장이 안 나간다(사람이 그 판을
열기 전에는 DB 에 안 간다). 그리고 **화면이 그것을 받아야 한다** — 이쪽이 더
위험했다. 화면의 `labels` 는 열릴 때 받은 것이라 방금 번진 분류를 모르고,
**뷰어는 늘 전체를 보낸다.** 서버는 안 온 키를 "표시가 사라진 행" 으로 보고
지운다.

| 번진다 | 안 번진다 |
|---|---|
| 분류(`label`) · 무르는 것(`""`)도 함께 | 오검출 삭제·되살림 — **판정은 판마다 다르다** |
| | 코멘트 · 종명 · 고친 기하 — 그 판을 보고 쓴 글이다 |

### 7.4 묶을 때 엇갈리면 알리고 고르게 한다 (107 · `v0.10.2`)

104 는 *저장할 때* 번지게 하는 것이라 **묶기 전에 판마다 따로 적어 둔 것**은
그대로다 — 실제로 운영의 묶음 셋 중 둘이 어긋나 있었다.

```
분류가 엇갈립니다   [봉상 ×2] [원형] [그대로]
종명               [Eucampia antarctica ×3] [그대로]
```

결정 넷: **기본은 `그대로`**(덮을 판단이 있는 자리에서는 사람이 손을 대야 한다) ·
**하나뿐이면 미리 고른다**(덮을 판단이 없으므로 잃을 것이 없다) · **사람이
지정한 것만 센다**(엔진의 자동 판정을 사람의 분류로 올려 적으면 안 된다) ·
**`안 보냄` 과 `빈 문자열` 이 다르다**(안 건드린다 / 비운다).

서버는 **묶음이 선 뒤 같은 트랜잭션 안에서** 맞춘다 — 밖에서 하면 *묶기가
실패했는데 분류만 바뀌는* 갈래가 생긴다(그 모양을 7.2 에서 겪었다).

## 8. YOLO 에서 전제가 깨진다 (106 · `v0.10.1`)

카탈로그를 "개체 하나 = 마스크 하나" 로 만들었는데 YOLO 에서는 그 전제가 깨진다.

```
SAM     시야 570개 전부 판이 하나 (합성본 417 · 단독 프레임 153)   → 전제가 맞는다
YOLO    합성본 1장 + 프레임 2~10장                                → 전제가 깨진다
```

SAM 에서는 잘 돌았고 **105 의 시험 137개가 전부 통과한 채로** 이 구멍이 남아
있었다. 사용자가 YOLO 로 써 보며 보고한 세 가지가 **한 뿌리**였다.

### 8.1 고친 것 둘

- **카탈로그에서 유형을 바꿔도 묶음에 안 번졌다** — 104 의 전파가 `save_review`
  안에만 있었고 카탈로그의 저장은 개체 하나만 고치는 좁은 문이라 그 자리를 안
  지났다. **저장은 성공으로 보이고 묶음 안이 어긋난다.** 화면이 "저장됨 · 묶음
  3장에 함께" 라고 적게 했다 — 다른 판은 이 화면에 없어서 적지 않으면 번졌는지
  알 방법이 없다
- **기하 스냅샷의 키가 두 벌이었다** — `ObjectReview.geom` 은 `bbox`,
  `ObjectLinkMember.geom` 은 `bbox_xywh` 인데 사람이 그린 멤버는 전자를 그대로
  싣는다. 카탈로그가 한쪽만 읽어 **예외 없이 조용히 원래 상자로 되돌아갔다** —
  다른 판의 그림을 이 개체의 옛 자리로 잘라 냈다. **시험이 통과하고 있던 이유도
  같이 나왔다**: 픽스처가 현실에 없는 모양을 세우고 있었다

### 8.2 못 고친 것 — 카탈로그가 개체의 절반을 못 본다

```
합성본+프레임 둘 다 있는 시야 417개
  프레임 개체 16,782 중 합성본에도 있는 것 11,659
  프레임에만 있는 것              5,123   ← 카탈로그에 아예 안 나온다
  (합성본 통과 개체는             4,444)
```

**저장할 자리는 있다** — 열쇠가 `(이미지, 묶음, mask_key)` 라 프레임 이미지에
동정을 앉힐 수 있고 번호도 `-f<순번>-` 을 낸다. **화면이 안 보여줄 뿐이고, 그래서
저장될 일도 없다.**

"프레임도 다 내자" 로 안 끝나는 이유가 둘이다. 같은 규조각이 초점면마다 잡혀
**카드가 2~10장씩 중복되고**, **번호가 판마다 달라 서로 다른 개체가 된다** —
*이름이 여러 개면 이름이 아니다.* 접으려면 "이 마스크들이 한 개체다" 를 아는
것이 있어야 하고, 그것이 묶음이다.

### 8.3 접은 것 둘 — 근거 없는 숫자와 반쪽 배포

**C 안**("프레임에만 있는 개체 n개가 더 있습니다" 를 화면이 적는다)은 다 만들고
시험까지 통과했는데 **사용자 판단으로 접었다.**

> "생각해보니 그게 같은 개체인지 네가 판단하는 능력이 아직 없을 거야."
> "애초에 묶여있는 개체도 지금 네 개 밖에 안되는데…"

맞는 지적이다. 센 방식이 "중심이 합성본 개체의 상자 안에 드는가" 였는데 그건
결국 **기계가 같은 개체인지 판정한 것**이고, 그 판정을 견줄 근거가 묶음 4개뿐이다.
**화면에 숫자를 내려면 그 숫자를 견줄 근거가 있어야 한다.**

**그린 마스크 번지기**(같은 시야의 모든 판에 복제하고 묶어 준다)는 서버 조각까지
만들고 **커밋도 배포도 하지 않고 접었다.** 복제한 마스크를 다른 판의 화면이
모르는 채 저장하면 그 자리에서 사라진다 — **서버 + 화면 두 조각이고 하나만
넣으면 자료를 잃는다.** 104 가 분류 전파에서 정확히 이 함정을 지났다.
둘 다 `git stash` 에 있고 **메시지로 짚는다**(번호는 밀린다).

## 9. 개체와 판정을 가른다 — 계획 (P12)

104 직후 사용자가 물었다.

> "엄밀히 말하면 `ObjectLink` 에 라벨을 넣고, 그것이 `ObjectReview` 의 라벨에
> 대해 우선권을 가지게 하면 되는 것 같은데."

그때는 **읽는 자리 79곳**을 근거로 비정규화를 택했다. 그런데 105 가 **종명**을
넣으면서 같은 질문이 더 날카롭게 돌아왔고, 파고들어 보니 **경계가 묶음에 있지
않았다.**

**어긋나 있는 다섯**

1. **`ObjectReview` 가 두 가지를 겸한다** — `removed`·`accepted` 는 **그 회차의
   그 마스크**에 대한 판정이고, `label`·`note`·`species` 는 **개체**에 대한
   판단이다(회차를 갈아도 참이다). 뜻은 갈라 놓고 자리는 한 행이다
2. 라벨은 번지고 종명은 안 번진다
3. 전파는 **소급되지 않는다** — 규칙으로 만든 정합성은 규칙이 생기기 전의 자료를
   못 고친다
4. 지워진 마스크가 묶음에 남을 수 있다 (지금 0건이지만 막는 것이 없다)
5. 묶음이 회차를 못 넘는다

**제안**

```
Object          개체 하나 — label · species · note            ← batch 무관
   ▲ N:1
MaskJudgement   (image, batch, mask_key) 의 판정              ← removed · accepted
   ╎                                                            geom · is_rep · bind_*
Candidate       검출이 낸 개체                                 ← 재생성 가능
```

**"묶였나?" 를 조건으로 삼지 않는 것이 요점이다.** 라벨을 `ObjectLink` 로 올리는
안(B)은 **집이 둘이 된다** — 묶인 것은 `ObjectLink`, 아닌 것은 `ObjectReview`
인데 개체 122,333개 중 묶인 것은 열둘이다. 읽는 쪽이 늘 두 갈래를 타야 하고,
**안 고친 자리는 예외 없이 옛 값을 보여준다**(038·040 의 모양).

**아직 아무것도 안 바꿨다.** 스키마는 **YOLO 4차가 들어온 뒤에** 박는다
(사용자 판단) — 회차를 넘는 묶기와 같은 문제이고, P11 이 그랬듯 **자료를 보고
나서 정할 것**이 있다.

## 12. 이 차수에서 되풀이된 교훈

- **되는 것처럼 보이는 것이 안 되는 것보다 나쁘다.** 저장이 미끄러진 뒤의 화면
  (096), 프레임 판의 거절(103), 카탈로그의 유형 전파(106) — 셋 다 화면은
  "됐다" 고 말했고 DB 는 아니었다
- **조용히 성공한 빈 결과와 실패를 한 갈래로 접지 말 것** (097). 폴러가 사흘을
  "할 일 없음" 으로 끝냈다
- **제약이 있다는 것과 조회가 그걸 쓴다는 것은 다르다** (103, 053 의 재판).
  이번 판은 "판이 여럿이라는 것과 검사가 그걸 아는 것은 다르다"
- **픽스처가 현실에 없는 모양을 세우면 시험이 옛 규칙을 증언한다** (106).
  105 의 시험 137개가 전부 초록인 채로 구멍이 남아 있었다
- **화면에 숫자를 내려면 그 숫자를 견줄 근거가 있어야 한다** (106 의 C 안).
  목적이 옳아도 수단이 스스로 판정을 하나 만들어 버릴 수 있다
- **자동값이 사람이 채운 것을 덮으면 안 된다** — 묶기의 미리 고르기(090),
  탈락 후보를 미리 안 집는 것(102), 엔진의 자동 판정을 사람의 분류로 올려 적지
  않는 것(107). 같은 규칙의 세 얼굴이다
- **서버와 화면이 짝인 변경은 반쪽으로 내보내지 않는다** (104·106). 전파는 서버가
  하고 화면이 받아야 하며, 하나만 넣으면 다음 저장이 자료를 지운다
