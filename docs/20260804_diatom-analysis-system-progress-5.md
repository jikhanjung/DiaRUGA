## 1. 요약

4차 보고서는 **검출기를 학습시킨** 차수였다. 이번 차수에는 새 능력이 붙지
않았다. 대신 **사람이 실제로 만지는 화면**과 **자료를 지키는 장치**를 다듬었다.
새 기능이 아니라 **지금 있는 것을 쓸 만하게 만드는 일**이다.

**첫째, 분류 체계가 화면을 지배하게 됐다.** `ClassDef` 표를 만들어 둔 목적이
"분류를 더할 때 배포가 필요 없게" 였는데, 실제로 속(genus) 하나를 넣어 보니
**코드에 박힌 자리가 여섯 군데 남아 있었다.** 그것을 표로 끌어오면서 검토 화면이
함께 정리됐다 — 세는 분류, 색 가족, 단축키, 약칭.

**둘째, 검토가 손에 붙었다.** 개체를 고르고 `q`·`w`·`e`·`r` 로 분류가 지정된다.
그전에는 개체마다 우클릭 → 메뉴 왕복이었고, **시야 하나에 개체가 수십이라 그
왕복이 곧 검토 속도였다.**

**셋째, 안전망이 스스로를 알린다.** 백업 실패가 로그에만 남던 것을 `/healthz` 로
이었고(`db_sentinel.py`), 배포 뒤 `smoke.sh` 가 판·행 수까지 본다. 시간별 백업을
cron 에 걸었고 오프사이트 보관을 개수가 아니라 **나이**로 바꿨다.

**넷째, DB 를 만지는 문을 하나로 모았다.** 호스트와 컨테이너가 같은 파일을 번갈아

돈다 — **저장소는 만들고, `/srv` 는 돌린다.**

**다섯째, 이름이 생겼다.** 뷰어는 **DiaRUGA** 다(Diatom Refocusing Using
Genus-level AI). 로고를 심고, `v0.3.0` 으로 내보냈다.

**여섯째, 앞으로 할 일을 "밟을 곳" 까지 적었다.** `TODOs.md` 에 화면 쪽 항목

## 2. 검토 화면 — 분류를 표가 정하게 했다

이번 차수의 절반이 여기에 있다. 시작은 작은 물음이었다. **"목록의 검출 수는
무엇을 세는가."**

### 2.1 파편을 개체로 세면 밀도가 부푼다 (037)

첫 화면의 **검출** 칸은 검토 후 남은 개체를 전부 세고 있었다. 파편도 미분류도
한 개다. 그런데 이 숫자를 실제로 쓰는 자리는 "이 슬라이드에 규조가 몇 개 있나"
이고, 거기서 깨진 조각 하나를 개체 하나로 세면 값이 부푼다.

```
RS23-GC03 369cm    923  →  444        전체 합계  2,132 → 1,197
```

**두 배 넘게 차이 난다.** 세는 것은 봉상·원형·Eucampia·Chaetoceros 넷이고,
파편(봉상 파편·원형 파편)과 미분류는 뺀다.

**가장 짧은 길은 `data.py` 어딘가에 세 키를 적는 것이었다. 그러지 않았다.**
표를 만든 목적이 배포 없이 분류를 더하는 것인데, 세는 목록을 코드에 박으면 새
속을 넣을 때마다 다시 배포해야 한다. 넣고 나서 "왜 검출 수가 안 늘지" 로 한 번
헤맬 자리다. `ClassDef.counted` 칸을 뒀다.

같은 이유로 **열도 표가 정한다.** 검출 수가 넷의 합이 된 이상 넷이 다 보여야
한다 — 안 그러면 화면의 숫자가 **분해되지 않는다**(합만 있고 무엇이 얼마인지가
없다).

**상세 화면은 안 건드렸다.** 거기 "검출 N → 검토 후 M" 은 개체 수가 아니라
검토가 얼마나 걸러 냈는가를 보는 줄이라 파편도 세어야 뜻이 맞는다. 대신 목록의
검출 칸에 `title` 로 전체 개체 수를 달아 **두 화면의 숫자가 다른 것이 어긋남이
아니라는 것**이 그 자리에서 읽히게 했다.

### 2.2 속 하나를 넣어 보고 나서야 남은 자리가 보였다 (038)

`Chaetoceros` 를 Eucampia 와 같은 층(속)으로 더했다. **표에 행 하나면 끝나야
했다.** 그렇지 않았다.

표만으로 따라온 것 — 분류 지정 메뉴, `/crops/` 의 형태별 갈래, `/review` POST 의
라벨 검증, 목록의 분류 열과 검출 수 합산. 따라오지 **않은** 것 둘:

- **색이 CSS 에 박혀 있다.** `ClassDef.color` 칸이 있는데 아무도 그 값을 쓰지
  않고, 색은 `base.html` 이 키로 잡는다. 규칙이 여섯 자리(썸네일 마스크·시야
  마스크·크롭 테두리·검출 마스크·테두리·bbox)에 분류마다 하나씩 있다.
  **행만 넣었으면 Chaetoceros 만 색 없이 그려졌을 것이다** — 마스크가 투명해서
  "지정은 되는데 화면에서 안 보이는" 상태가 된다
- **검출 화면 머리의 개수 줄**에 분류 이름이 손으로 적혀 있었다. `data.py` 가
  표 순서대로 만들게 바꿨다

이것이 이 차수에서 가장 값어치 있는 발견이다. **예외가 안 나고 그 분류만 조용히
다르게 굴러가는** 종류의 고장이라, 사람이 눈으로 보기 전까지 아무도 모른다.

### 2.3 색이 분류 체계를 말하게 (039)

038 에서 색을 "색상환의 빈자리를 찾아 채우는" 방식으로 골랐다. 여섯이 되고 나니
**색이 분류 체계를 하나도 반영하지 않는다**는 것이 드러났다.

```
전    봉상 파랑 217°  ·  봉상 파편 보라 258°  ·  원형 초록 150°  ·  원형 파편 청록 180°
후    봉상 70,140,255 진한 파랑     봉상 파편 120,195,255 옅은 파랑   ← 같은 217°
      원형 60,220,120 진한 초록     원형 파편 140,235,170 옅은 초록   ← 같은 150°
```

**색상이 "무엇인가", 진하기가 "온전한가" 를 말한다.** 축이 둘로 갈라져 분류가
늘어도 규칙이 그대로 선다. 넷을 따로 외우던 것이 둘로 줄었다.

**너무 옅게는 안 잡았다.** 마스크는 밝은 규조각 위에 42% 로 얹히므로 흰색에
가까워지면 *마스크가 안 걸린 것*과 구분이 안 된다. 파스텔로 밀었다가 그 지점에서
되돌렸다.

배지 색도 마스크에 맞췄다 — **사진에서 파랗던 것이 목록에서도 파랗다.** 이때
파편 둘이 배지 키 하나를 같이 쓰던 것과, 원형이 일반 배지(`on`)에 얹혀 우연히
맞아 보이던 것이 함께 드러났다.

색이 `ClassDef.color` 와 `base.html` 두 곳에 있으므로, **표와 CSS 가 어긋나지
않는지를 기계로 본다** — `check_db.py` 가 키마다 CSS 에서 rgb 를 긁어 표의 값과
대조한다.

### 2.4 단축키 — 메뉴 왕복이 곧 검토 속도다 (040)

```
q → 원형 → 원형 파편 → 원형 …        w → 봉상 → 봉상 파편 → 봉상 …
e → Eucampia                          r → Chaetoceros (CRS)
```

**본체와 파편이 한 키를 나눠 가진다.** 손가락을 옮기지 않고 **누른 횟수**로
온전한 것과 깨진 것을 가른다 — 039 에서 색을 그렇게 묶었으니(색상은 본체,
진하기는 온전한가) 조작도 같은 모양이어야 한다.

여럿을 고른 채 눌렀을 때는 **전부 같은 분류일 때만** 다음으로 넘어가고, 섞여
있으면 처음 것으로 모은다. 여럿을 한 번에 눌렀는데 결과가 개체마다 다르면 그건
도구가 아니다.

배정은 `ClassDef.hotkey` 다. **코드에 목록을 적지 않았다** — 분류를 더하면서 한
자리만 옛 목록으로 남는 일이 이미 두 번 있었다. 키를 안 준 분류는 화면 안내에도
안 나오고, 그것이 곧 "아직 배정 안 했다" 는 표시다.

**읽기 전용 화면(`/engine/`)에서는 키도 안내도 내지 않는다.** 예전에 "읽기
전용" 이라 적어 놓고 CSS 로 버튼만 감췄다가 교정 37건을 잃었다(4차 §4). 있는
기능인 줄 알고 눌러 보다 "안 되네" 가 되는 쪽이 아예 안 보이는 것보다 나쁘다.

**속명은 길다.** `Chaetoceros` 하나가 목록 표의 열을 두 배로 넓힌다.
`ClassDef.short` 로 `CRS` 를 넣되 **자리가 좁은 곳만** 줄인다 — 말풍선과 분류
지정 메뉴는 전체 이름이다. 고르는 자리에서까지 줄이면 무엇을 지정하는지가
흐려진다.

### 2.5 이 차수의 산물 — "분류를 더할 때 채울 것 여덟"

037~040 을 지나며 같은 종류의 누락을 세 번 겪었다. 그래서 `ClassDef` 머리말에
목록으로 못 박았다.

> `label` · `short` · `badge` · `color` · `hotkey` · `counted` · `is_taxon` ·
> `sort_order`, 그리고 **`base.html` 의 CSS**

**하나라도 비면 예외는 안 나고 그 분류만 조용히 다르게 굴러간다.**
`check_db.py` 가 단축키·색 둘은 기계로 잡는다.

그리고 **되돌릴 때는 지우지 않고 `active=False` 로 끈다.** 행을 지우면 그
분류로 붙인 교정이 이름 없는 분류가 되어 화면에서 안 읽힌다.

### 2.6 브라우저가 없는 채로 확인한 방법, 그리고 못 한 것

이 머신에는 브라우저가 없다. Django 테스트 클라이언트로 전 화면 200 을 보는
것으로는 **조건이 갈리는 코드**를 못 본다.

키 순환은 **렌더한 페이지에서 그 조각을 그대로 떼어 내** node 에서 12가지를
돌렸다. 손으로 옮겨 적으면 시험이 아니라 사본을 시험하는 것이 된다.

```
OK  q · [round] -> round_frag      OK  q · [round,round_frag] -> round
OK  q · [round_frag] -> round      OK  e · [eucampia] -> eucampia
OK  q · [rod] -> round             OK  r · [round] -> chaetoceros
```

**못 한 것은 적어 두었다** — 이벤트 배선(활성 패널 판정, 입력칸 안에서 안 듣기)과
로고의 크기·굵기다. 이 둘은 배포 뒤 사람이 한 번 열어 보는 수밖에 없다.
**"200 이 뜬다" 로 덮이지 않는 자리가 어디인지를 배포마다 적는 편이 낫다.**

## 3. 검출 화면과 속성 편집 (035)

**같은 시야를 그대로 두고 엔진만 갈아 끼울 수 있게 했다.** 그전에는 묶음을
바꾸려면 목록으로 나갔다 다시 들어와야 했고, 그러면 어느 시야를 보고 있었는지
잃었다. 견주기는 같은 자리를 번갈아 보는 일이라 **그 왕복이 곧 견주기를 못 하게
만든다.**

붙이고 나서야 드러난 것이 둘이다.

- **화면이 "쌓아 둔 것" 만 보고 있었다.** `is_current=False` 만 그리는 규칙이라
  SAM2 묶음은 대부분이 현재로 올라가 있어 빈 화면이 됐다. 묶음이 낸 것 전부를
  보이게 바꿨다
- **엔진마다 검출을 다는 자리가 다르다.** SAM2 는 합성본 한 장에만, YOLO 는
  프레임마다 + 합성본에도 단다. 합성본을 프레임과 같은 자격으로 캐러셀에 넣었다

**칸의 수와 화면의 수가 어긋났다** — 칸 552, 화면 151. 칸은 원시 후보를 세고
화면은 통과한 것만 그렸으며, 같은 자리에 검출이 둘씩 쌓여 있었다. 고르는 규칙을
`data._engine_pick` 하나로 모아 시야 화면·시야 목록·묶음 칸이 전부 그것을 쓰게
했다.

**찌꺼기 검출을 지웠다**(`prune_detections.py`) — 검출 2,107건 · 후보 69,863건.
검출은 덮어쓰지 않고 쌓는 것이 원칙이지만, **같은 묶음 안에서 같은 이미지에
둘씩 쌓인 것은 기록이 아니라 찌꺼기다.** 묶음을 넘어서는 지우지 않는다 — 서로
다른 엔진이 같은 이미지를 본 것을 나란히 두는 것이 이 화면의 목적 전부다.

**시료 속성 편집은 탭으로 갈랐다.** 폼은 하나 그대로다 — 셋으로 쪼개면 지역을
고치려다 슬라이드에 적어 둔 것이 날아간다. 자바스크립트가 없으면 셋 다 펼쳐진
예전 모습이 된다.

## 4. 이름과 로고 — DiaRUGA (041)

`규조류 뷰어` 를 **DiaRUGA** 로 바꿨다. Diatom Refocusing Using Genus-level AI
의 약자이고, **화면에는 풀어 쓰지 않는다.** 이름은 이름으로 서는 편이 낫다.

**표기는 `DiaRUGA` 하나다** — 대문자 자리가 곧 약자의 자리다(Dia / R·U·G·A).
이 화면에는 `text-transform: uppercase` 가 두 군데 걸려 있어 **거기에 이름을
넣으면 CSS 가 `DIARUGA` 로 만든다.** 그 사실을 CSS 옆에 적어 뒀다.

받은 SVG 를 그대로 쓰지 않았다. **워드마크가 `<text>` 인데 서버에 Montserrat 이
없고 사내망이라 웹폰트도 못 받는다** — 그대로 쓰면 보는 기기마다 다른 글꼴로
나온다. 로고가 기기마다 달라지는 것은 로고가 아니다. 글자는 HTML 로 쓰고 SVG 에는
규조 마크만 남겼다. 색도 `currentColor` 로 바꿔 밝은 테마에서 사라지지 않게 했다.

**파일이 아니라 심었다.** 이 배포에는 정적 파일을 내보내는 길이 없다
(`STATIC_ROOT` 도 nginx 의 static 자리도 없다). 마크는 1 KB 라
`viewer/_logo.html` 로 심는 편이 맞다 — 요청도 한 번 줄고, 서브경로(`/diatom/`)
아래에서 경로가 틀어질 일도 없다.

**작은 자리에서는 덜어내야 형태가 남는다.** 머리글(21 px)에서는 방사 늑골 16개를
그대로 두되 선을 원본보다 굵게 줬고, **탭 아이콘(16 px)은 늑골을 8개로 줄였다** —
16개를 그대로 두면 뭉개져 회색 원반이 된다.

nginx 안내 페이지(`maintenance.html`·`unavailable.html`)는 Django 를 거치지
않으므로 마크를 옮겨 적었다. 로고를 고치면 여기도 같이 고쳐야 한다고 파일 안에
적어 뒀다.

**URL·컨테이너·DB 는 안 건드렸다.** `/diatom/` 그대로이고, devlog 와 `docs/` 의
지난 기록도 그때 이름 그대로 두었다 — 그때의 이름이 그때의 기록이다.

## 6. 안전망이 스스로를 알린다 (034 · 036)

devlog 016·009 가 같은 문장으로 끝나 있었다 — *"무결성 실패를 health 엔드포인트로
잇는 sentinel 이 없다."* 백업 게이트는 이미 깨진 사본을 잡아내고 있었지만 그
사실이 **로그에만 남았다.**

> A cron job that only logs its failure is "the illusion of a check."

### 6.1 깃발은 파일이다

`db_sentinel.py` 가 DB 옆에 `INTEGRITY_FAIL` 한 장을 놓고 `/healthz` 가 그것을
읽는다. **DB 에 적지 않은 것이 요점이다** — 이 깃발이 서는 상황이 곧 DB 를 믿을
수 없는 상황이다. 깨진 DB 에 "DB 가 깨졌다" 고 적을 수는 없다.

**track 마다 한 줄을 쓴다.** 처음에는 깃발 하나를 공유하게 썼다가 되돌렸다 —
나중에 성공한 track 이 남의 실패를 지운다. NAS 사본이 깨졌다는 깃발을 다음 시간별
백업이 조용히 내리는 식이다.

**NAS 가 안 붙은 것은 깃발이 아니다.** 그것은 자료가 상한 것이 아니라 lane 이
잠깐 없는 것이다. 그것까지 세우면 NAS 점검 한 번에 뷰어가 degraded 가 되고 배포
smoke 가 막힌다 — **가장 센 신호가 잡음에 묻히면 안 된다.**

### 6.2 `degraded` 는 503 이 아니라 200 이다

| 상태 | 코드 | 뜻 |
|---|---|---|
| `ok` | 200 | 정상 |
| `degraded` | **200** | 서비스는 되는데 손상이 감지됐다 |
| `unhealthy` | 503 | DB 를 못 열거나 자료가 통째로 없다 |

가장 반직관적인 대목이고, 이유는 실질적이다. **`deploy.sh` 의 기동 게이트가
200 을 기다린다.** degraded 에 503 을 내면 "백업이 깨졌다" 는 신호가 **배포 자체를
못 끝내게** 만든다. 배포를 세우는 판단은 `smoke.sh` 가 `status != ok` 로 한다 —
신호와 조치를 갈랐다.

**빈 DB 는 unhealthy 다.** 마운트가 어긋나 컨테이너가 빈 DB 를 새로 만들어도
"파일이 있는가" 검사는 통과한다. 그때는 손으로 셌고, 이제 게이트가 센다.

인증이 없는 엔드포인트라 **여기서 `integrity_check` 를 돌리지 않는다** — 누구나
부를 수 있는 DoS 표면이 된다. 비싼 검사는 백업이 한 번 하고, 여기서는 그것이
남긴 파일을 읽기만 한다.

### 6.3 게이트를 전부 터뜨려 보고 나서 걸린 둘

*"Mutation-test each gate: remove it and confirm a test fails."* 깃발을 손으로
세우고, 빈 DB 를 물리고, 난수를 DB 인 척 물리고, 판을 틀리게 기대하게 했다.
**둘 다 그러지 않았으면 못 봤을 것들이다.**

- **뜨다 만 사본이 정상 사본의 이름을 달고 있었다.** 반쯤 쓴 파일이
  `diatom_*.db` 라는 이름을 달면 정리 glob 에 걸리고 **가장 새 파일이라
  살아남아 멀쩡한 사본을 하나 밀어낸다** — 백업이 백업을 지우는 형태다. 이제
  **제 이름은 검증을 통과한 뒤에 준다**(그전에는 `.part`)
- **부산물을 이름 바꾼 뒤에 쓸었다.** `.part-wal`·`.part-shm` 이 남았다.
  **연결을 먼저 닫고, 쓸고, 그 다음에 이름을 바꾼다**

**사람이 읽는 문구도 게이트다.** 첫 `smoke.sh` 가 한 가지 원인("응답이 JSON 이
아니다")을 세 줄의 다른 진단으로 번지게 해서 **DB 마운트를 파라고 세 번 말했다.**
응답을 못 읽으면 거기서 멈추고 한 줄만 내게 고쳤다.

### 6.4 백업 lane 을 cron 에 걸고, 나이로 보관한다

```cron
20 * * * *  backup_db.py --keep 24                              → logs/backup.log
40 4 * * *  timeout 600 sync_backup_nas.py --newest-only --prune → logs/nas-sync.log
```

세 track 이 이제 다 있다 — 배포 전 스냅샷 · 시간별 · 일별 오프사이트.
**깃발이 생기고 나서야 걸 값어치가 생겼다** — 그전에는 실패해도 아무도 몰랐다.

**종류를 디렉토리로 가른다**(`backup/` · `manual/` · `pre_deploy/`). 이름
규칙으로도 되고 실제로 처음에는 그렇게 짰는데, **정리 glob 을 한 번 잘못 쓰는
순간 섞인다.** 디렉토리는 glob 이 애초에 안 내려간다. 수동 스냅샷은 작업 중에
되돌릴 지점이지 보관물이 아니므로 **NAS 로 안 가고 로테이션이 안 건드린다.**

**개수가 아니라 나이로 보관한다.** 009 의 `--keep 30` 은 손으로 하루 한두 개
뜨던 시절의 "한 달치" 였다. **시간별이 되면 같은 30 이 30일이 아니라 30시간이
된다** — cron 을 거는 것만으로 오프사이트 보존이 30일에서 1.25일로 조용히 줄어든다.

| 나이 | 남기는 것 |
|---|---|
| 1주일 이내 | 전부 |
| 1주일 ~ 한 달 | 주에 하나 |
| 한 달 이후 | 달에 하나 |

1년치 366개가 **24개**가 된다. 나이는 mtime 이 아니라 **이름**에서 읽는다 —
NAS 로 건너간 사본은 전부 "옮긴 시각" 의 mtime 을 갖는다.

**사진도 같은 일별 실행에 태웠다** — `photos_YYYYMMDD.tar`, 일주일 rolling,
4.0 GB 에 40초. **압축하지 않는다.** 먼저 재 봤고 JPEG 이 이미 압축된 포맷이라
5% 밖에 안 줄었다. 5% 를 얻자고 매일 4 GB 를 갈아 내는 셈이다. 가이드가 권하는
하드링크 스냅샷 트리를 안 쓴 이유는 하나뿐 — **덩어리 하나로 들고 다니고 싶다.**
그래서 **뒤집힐 조건을 적어 뒀다**(사진이 수십 GB 가 되면 트리로).

### 6.5 시간별 백업 cron 은 "문 하나로" 규약의 예외다

§7 의 규약을 세우면서 **시간별 백업만 호스트 venv 로 남겼다.** 근거가 둘이고
두 번째가 결정적이다.

- `backup_db.py` 는 Django 를 임포트하지 않고 원본을 읽기 전용으로 열어 sqlite3
  백업 API 만 쓴다 — 규약이 막으려는 "환경이 두 벌" 이라는 상황 자체가 안 생긴다
- **시간별 안전망이 Docker 가 성한지에 매달리면 안 된다.** 이미지가 안 받아지거나
  데몬이 죽은 날에 백업까지 같이 멈추는 것이 규약이 지키려던 것보다 비싸다

**예외를 두는 것보다 나쁜 것은 예외를 두고 적지 않는 것**이라 `CLAUDE.md` 에 왜
예외인지까지 적었다.

## 7. DB 를 만지는 문을 하나로 (035 · 036)

사용자가 겪은 것은 **컨테이너 안팎에서 번갈아 DB 작업을 하면 깨지곤 한다**는
것이었다. 원인은 "안/밖" 자체가 아니다 — 어느 쪽이든 같은 ext4 파일이고 SQLite
잠금은 정상으로 작동한다. 실제로 당한 것은 둘이고 **둘 다 환경이 두 벌**이라
생겼다.

- 컨테이너의 낡은 `models.py` 가 `Site.area` 를 몰라 **NAS 반입이 죽었다**
- root 로 돈 컨테이너가 `diatom.db` 소유자를 가져가 **호스트 스크립트가 못 쓰게 됐다**

**첫 판은 틀렸다.** 저장소를 `/app` 에 덮어 물렸다 — 새 스크립트를 쓸 때마다
7 GB 이미지를 다시 굽지 않으려는 뜻이었는데, **그러면 컨테이너가 배포된 코드가
아니라 편집 중인 작업 트리로 프로덕션 DB 를 만진다.** 막으려던 것을 이름만 바꿔
다시 만든 꼴이다.

```
/app                     이미지 안. Django·모델 — 뷰어 컨테이너가 쓰는 그것
/srv/diatom/scripts      밖에서 물린다. 스크립트 파일뿐 (읽기 전용)
```

```bash
deploy/host/dbsync.sh check_db.py     # 저장소 → /srv (옆 모듈까지 따라간다)
deploy/host/dbrun.sh  check_db.py     # 컨테이너 안에서 돈다
deploy/host/dbsync.sh --list          # 옮겨 둔 것이 저장소와 어긋났는가
```

**옮겨 놓은 것만 돌아간다.** 어긋나면 알리되 막지는 않는다 — 일부러 옛 판을
돌리는 일이 있고, 무엇이 도는지만 알면 된다. **딸려 오는 제약이 하나 있다**:
`/app` 은 `IMAGE_TAG` 가 가리키는 판이라 아직 배포하지 않은 모델 변경이 필요한
스크립트는 여기서 못 돈다. **조용히 어긋나는 것보다 낫다.**

문을 하나로 모으니 그동안 안 보이던 것 셋이 한자리에 모여 보였다(036).

- **옆 모듈까지 따라가야 한다** — `dbsync.sh` 가 최상위 임포트를 훑어 저장소에
  있는 것만 함께 옮긴다
- **컨테이너가 UTC 라 사본 이름이 아홉 시간 어긋났다.** 이름만의 문제가 아니다 —
  정리가 이름순 정렬이라 **UTC 이름과 KST 이름이 섞이면 가장 새 사본을 지우고
  옛것을 남긴다.** `TZ: Asia/Seoul` 을 컨테이너 전부에 줬다
- **`--keep 20` 이 아무것도 안 걷고 있었다.** 로테이션 glob 이 꼬리말 없는
  이름만 보는데 배포 전 스냅샷에는 `_pre-deploy-v0.1.9` 가 붙는다. `--flat` 을
  뒀다("이 디렉토리는 이 종류 전용이다")

| **카드의 두 줄을 축으로 가르기** | 지금 아랫줄이 "분류별 + 규모 + 진행률" 잡탕이다 | 첫째 = 얼마나 있고 얼마나 봤나 · 둘째 = 무엇이 있었나. 그러면 둘째 줄이 정확히 `ClassDef.counted` 만 남아 **분류를 더하면 저절로 한 칸 는다** |
| **목록을 코어로 묶고 접기** | 지금은 **정렬만 되어 있고 묶여 있지 않다.** 코어가 분석의 단위다 | 표 안에서는 `<details>` 가 안 먹는다 · 접힌 머리줄이 합계를 들어야 하고 **평균은 넣지 않는다**(분모가 달라 다시 더할 수 없다) · 전부 접힌 채 열면 첫 화면이 빈 목록이다 |

여기에 042 에서 둘을 더 넣었다 — **분류 색을 표에서 뿜어내기**(이 판에서 CSS 를
두 번 따라 고쳤다)와, `Identification` 항목의 "표에 속을 더하면 배포 없이" 라는
문구가 **아직 사실이 아니라는 것**(038 이 그것을 보였다).

운영 쪽은 반대로 다섯이 지워졌다 — 백업 lane 을 cron 에, 손으로 뜬 스냅샷과
시간별 스냅샷을 갈라 두기, NAS 의 `manual/` 정리(1.3 GB), 사진 오프사이트,
`/healthz` 가 백업·무결성 상태를 보게.

### 안 하기로 한 것도 근거와 함께 적었다

목록을 코어로 묶는 항목 아래에 **"그러면 코어 페이지로 가면 되지 않나"** 에 대한
답을 길게 적었다. 지금 가면 손해라는 판단이다.

- **지금은 10장이 한 화면에 다 들어온다.** 목록의 값은 표를 통째로 놓고
  슬라이드끼리 견주는 데 있다 — 분류별 열이 나란히 서고 아래 합계 줄이 있는
  이유가 그것이다. **코어 다섯 줄만 내면 지금 되는 일이 클릭 다섯 번이 된다**
- **코어 페이지가 값을 하려면 목록의 부분집합 이상이어야 한다** — 깊이 대 개체수,
  깊이 방향 조성 변화. 새 기능이라 설계가 붙는다
- **묶기는 그 페이지가 생겨도 안 버려진다.** 걷어낼 것은 접기 하나뿐이고 나머지는
  코어 페이지의 머리로 그대로 간다
- **넘어가는 때**: 코어 하나의 슬라이드가 한 화면을 넘거나, 깊이 대 조성을 그려
  달라는 말이 나올 때. 둘 중 먼저 오는 쪽이다

같은 이유로 표 안 스크롤도 하지 않기로 했다 — `table-layout: fixed` 로 열 너비를
못 박아야 하는 수술인데, **코어 페이지가 생기면 이유가 통째로 사라진다. 임시
방편에 되돌리기 번거로운 값을 치르는 꼴이다.**

## 9. 파이프라인 — 성능과 사고

### 9.1 같은 실수를 옆 함수에서 또 했다 (033)

4차 §6 에서 `shape_metrics()` 를 26배 빠르게 고쳤는데 **전체 시간은 개체당
73 ms → 66 ms 밖에 안 줄었다.** 그 함수는 애초에 7 ms 였고, 진짜 병목은 바로
옆에 있었다.

```
largest_body     1,616 ms   35.1 ms/개체   96%
shape_metrics       16 ms    0.3 ms/개체    1%   ← 030 에서 고친 것
texture_score       59 ms    1.3 ms/개체    4%
```

**글자 그대로 같은 실수다** — 개체 하나를 재려고 6백만 화소 배열을 훑고 있었다.
그리고 **자를 자리를 찾느라 또 훑었다**(`np.nonzero`) — 35.1 → 35.1 ms, 하나도
안 줄었다. `bbox` 를 인자로 받게 하니 **11.0 ms** 가 됐다.

중간에 "고쳤는데 하나도 안 빨라진다" 가 두 번 나왔는데 원인은 코드가 아니라
**측정**이었다. `docker compose run pipeline` 이 이미지 안의 `/app` 을 써서
**옛 코드끼리 비교**하고 있었다. **고친 코드가 실제로 도는지부터 확인해야 한다.**

값은 한 자리도 안 바뀌었다 — 옛 구현과 나란히 돌려 개체별로 15개 칸을 전부
대조했다(다른 것 0).

### 9.2 8 GB 카드에서 한 장이 안 들어간다 (043)

YOLO 2차(판정 없는 판)를 돌리다 프레임 몇 장이 조용히 빠졌다.

```
Snap-21379 (rs23)   검출 110개 (conf 0.01)
  마스크 한 벌 = 110 × 2208×2752 × 4바이트 = 2.49 GiB
  혼자 돌려도 최대 예약 6.96 GiB / 카드 7.65 GiB   ← 91%
```

`retina_masks=True` 는 검출 전부를 원본 해상도로 펼쳐 주는 옵션이다. 편해서 켜
뒀는데 **검출이 100개를 넘는 프레임에서는 그것만으로 카드를 채운다.**

**OOM 재시도가 무력했던 이유**를 고쳤다. `except` 블록 안에서 `empty_cache()` 를
불렀는데, **역추적이 살아 있고 역추적은 실패한 호출의 지역변수를 붙들고 있다** —
방금 자리를 못 찾은 그 큰 GPU 텐서들을. 재시도를 `except` 밖으로 빼니
`rs23` 이 146 → 150/151 이 됐다.

**실행이 성공으로 남던 것도 고쳤다.** `Run.STATUS` 에 `partial` 을 더해 한 장이라도
건너뛰면 그것으로 끝난다.

**안 고친 것과 그 이유를 적었다.**

- `retina_masks=False` 는 메모리가 1/4 이지만 **모든 개체의 경계가 달라진다.**
  충실히 재현하려면 ultralytics 내부 구현에 기대야 하고, 그러면 판이 바뀔 때
  조용히 깨진다 — **0.08% 를 위해 치를 대가가 아니다**
- `expandable_segments` 는 PyTorch 가 직접 권하는 설정인데 켜니 오히려 재시도
  성공이 3 → 0 이 됐다. **조각남이 아니라 총량이 모자란 것**이기 때문이다
- conf 를 올리면 검출이 110 → 47 로 줄지만 **2차의 목적이 판정 없이 다 보는
  것**이라 취지가 흐려진다

**1,318장 중 1장이 어떤 방법으로도 안 들어간다.** 코드 문제가 아니라 장비
문제다 — 학습을 돌린 RTX 8000(48 GB)에서는 6.96 GiB 가 아무것도 아니다.

### 9.3 DB 잠금으로 프레임 229장을 잃었다

같은 실행 중에 `database is locked` 로 `bp09-0901` 프레임 229장이 통째로
날아갔다. WAL 이라 읽기는 여럿이 동시에 되지만 **쓰기는 한 번에 하나**다.
파이프라인이 개체 수천 개를 한 트랜잭션으로 넣는 동안 사람이 검토를 저장(31건)하자
20초를 기다리다 죽었다.

트랜잭션을 둘로 나눴다 — 개체를 넣는 것과 `is_current` 를 옮기는 것은 **원자성
요구가 다르다.** 후자만 한 덩어리여야 한다(갈라지면 교정이 안 붙은 검출이 화면에
보인다).

**지금까지 안 터진 이유는 파이프라인이 돌 때 사람이 검토하지 않았기 때문이다.**
그것이 일상이 되면 SQLite 를 다시 볼 문제가 된다.

앞으로도 이 두 종류는 배포 뒤 사람이 한 번 열어 보는 수밖에 없다. **"200 이
