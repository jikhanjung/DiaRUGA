## 1. 요약

다섯이다.

**첫째, 사람이 그린 마스크가 같은 시야의 모든 판에 번진다** (111 · `v0.12.0`).
YOLO 로 갈아타면 시야 하나에 판이 여럿(합성본 1 + 프레임 2~10)이라, 엔진이 놓친
규조각을 넣으려면 **판마다 똑같은 마스크를 다시 그려야** 했다. 되는 근거는
알고리즘이 아니라 **촬영 방식**이다 — 같은 시야는 스테이지가 안 움직이므로 좌표가
그대로 맞는다. *기계가 "같은 개체 같다" 고 판정하는 것이 아니라 찍는 방법이
보장한다.*

**둘째, 등급이 하루 만에 판에서 개체로 옮겨졌다** (`0034` → `0035` · 110 · 111).
11차가 *"축이 반대라 테이블이 갈렸다"* 고 적은 그 결정이 번지기가 들어오면서
깨졌다. 근거는 이랬다 — ***"어느 판이 잘 보이는가" 는 `is_rep`(대표)이 이미 하고
있었다.*** 운영에 등급이 **0건**이라 지금이 옮기기 가장 싼 시점이었다.

**셋째, 코멘트도 개체로 가고 적는 자리가 카탈로그 하나로 모였다**
(`0036` · 112). 사람이 실제로 적은 말이 *"가장자리가 깨졌다"* 처럼 **판이 아니라
규조각에 대한 것**이었고, 번지기 뒤로는 같은 말을 판 넷에 적게 된다.
**등급과 달리 값을 안 버린다** — 사람이 쓴 글은 재생성 불가라 고르지 않고 잇는다.

**넷째, 판 둘을 내보냈다** (114). `v0.11.2`(등급·자세) → `v0.12.0`(번지기 ·
등급·코멘트 이전). **뷰어만 올렸다** — `0035`·`0036` 이 칼럼을 걷지만 사본에 옛
파이프라인 컨테이너를 붙여 **안 닿는 것을 실측**했다.

**다섯째, 병합이 Pull Request 를 지나가게 됐다** (114). CI 트리거가
`push: [main]` 과 `pull_request: [main]` 이라 **`work/*` 브랜치는 CI 를 한 번도
안 지났다.** PR 은 그 순서를 뒤집는다 — `main` 이 깨끗한 채로 결과를 본다.

그 밖에 **도감 연동 계획**(P14 · 113)이 서고, **고아 화면을 YOLO 4차 뒤로
미뤘으며**(P13), **말을 고르는 규칙**이 `CLAUDE.md` 에 자리를 잡았다.

## 2. 그린 마스크가 판마다 번진다 (111 · `v0.12.0`)

106 이 세 안으로 적어 두고 A 안만 남겨 둔 것인데, 그때는 서버 조각만 있었고 그
조각은 08-11 에 **버려졌다**(P12 가 같은 파일을 337줄 고쳐 전제가 달라졌다).
P12 위에서 새로 짰다.

### 복제할 판을 엔진 이름으로 고르지 않는다

*이 회차에 현재 검출이 있는 판*으로 잡는다. 그러면 SAM(시야당 판 하나)과 단독
프레임 시야는 복제할 곳이 없어 **자동으로 지나간다** — *"YOLO 일 때만"* 을 이름으로
판정할 이유가 없다.

**검출이 없는 판에는 넣으면 안 된다.** 그 판의 화면은 마스크를 안 그리고 저장도
못 받아(`save_review` 가 거절한다) **손댈 수 없는 유령**이 된다.

### 반쪽으로 넣으면 자료를 잃는다

복제한 마스크는 **다른 판의 화면이 모른다.** 그 화면은 열릴 때 받은 상태를 들고
있고 `/review` 는 payload 에 없는 그린 개체를 지우므로, 프레임 3에 그리고 프레임
5로 넘어가 저장하면 **복제가 그 자리에서 사라진다.**

그래서 서버 조각과 화면 조각을 **한 커밋으로** 넣었다. 그리고 말로 적어 두는 대신
**브라우저 시험이 확인한다** — 화면 조각만 끄면 셋이 실패한다.

### 곁들여

묶인 그 순간에 **사슬 배지가 뜬다.** `links` 는 페이지가 열릴 때 한 번 받는 값이라
그전에는 새로고침해야 보였다. 방금 그린 것은 잠깐 밝힌다(`linkflash`).
개체로 모으는 규칙은 `data.merge_into_object` 한 문으로 뺐다 — **사람이 묶을 때와
마스크가 번질 때가 같은 문을 지난다.**

## 3. 등급이 판에서 개체로 (`0034` → `0035` · 110 · 111)

11차 보고서가 이렇게 적었다.

> **축이 반대라 테이블이 갈렸다** — 등급은 **판(초점면)** 의 것이라 `ObjectReview`
> 에, 자세는 **개체**의 것이라 `DiatomObject` 에 앉혔다.

그 근거는 *"같은 규조각도 초점면마다 동정키(areolae)가 보이고 안 보인다"* 였다.
사실 자체는 맞다. 그런데 **그 판단을 담는 자리가 이미 있었다** — `is_rep`(대표)다.
어느 판을 이 개체의 얼굴로 삼는가가 곧 어느 판이 잘 보이는가다. 등급을 판마다
따로 매기면 **같은 것을 두 번 적는 셈**이고, 번지기가 들어와 판이 여럿이 되면서
그 부담이 실무에서 드러났다.

**옮기는 값이 0건이었다.** 등급은 `0034` 로 하루 전에 생긴 칸이고 아직 아무도 안
매겼다. 값이 쌓인 뒤였으면 *"판마다 다른 등급을 하나로 접는 규칙"* 을 사람이
정해야 했다.

> **마이그레이션 순서를 지켰다** — **새 칸 → `RunPython` 으로 자료 이동 → 옛 칸
> 걷기.** 자동 생성이 내는 순서(옛 칸을 먼저 지우고 새 칸을 빈 채로 만든다)를
> 그대로 돌리면 사람이 매긴 것이 날아간다(063 에서 `Core` → `Locality` 로 겪을
> 뻔했다). `reverse` 도 함께 적었다 — 배포가 막혀 판을 되돌릴 때 빈 화면이 나오면
> 안 된다.

**결과: 판(초점면)에 대해 사람이 적을 자리는 대표 하나로 모였다.** 판정에 남는
것은 `removed`·`accepted`·`geom`·`is_rep`·`auto_confirmed` — **판정**뿐이다.

## 4. 코멘트를 개체로, 적는 자리를 카탈로그 하나로 (`0036` · 112)

등급 이전의 나머지 반쪽이다. 그런데 한 걸음 더 갔다 — **사는 자리만 옮긴 것이
아니라 적는 화면도 하나로 모았다.**

`ObjectReview.note` 머리말의 전제는 *"판마다 따로 적는 말이다 — 이 판에서는 초점이
안 맞는다 처럼"* 이었다. 둘이 그 전제를 깼다.

1. **사람이 실제로 적은 것은 그 규조각에 대한 말이었다** — *"가장자리가 깨졌다"* ·
   *"다시 봤다"*. 판의 상태가 아니라 개체의 상태다
2. **번지기가 들어왔다** — 같은 말을 판 넷에 적게 되고, 판에만 두면 *어느 판에서
   적었는지*를 사람이 기억해야 그 코멘트를 다시 찾는다

### 등급과 다른 점 — 값을 안 버린다

등급은 판마다 다르면 대표의 것을 골랐다(글자 하나이고 0건이었다). 코멘트는 그럴
수 없다. **사람이 쓴 글은 재생성 불가**이고, 판 셋에 다른 말이 적혀 있으면 그 셋이
전부 이 규조각에 대한 사실이다 — 고르면 둘을 버린다.

그래서 **이어 붙인다.** 대표 먼저, 그다음 적힌 차례, 같은 말은 한 번만, 줄바꿈으로.
**순서를 못 박아야 다시 돌려도 같은 결과가 나고**, 두 DB 를 비교하는 감사 기록
(`ops/export_review.py`)이 거짓말을 안 한다.

### 자리는 이미 있었다

`DiatomObject.note` 가 있었다. `ObjectLink.note`("묶음에 대한 메모")가 `0032` 로
따라온 칸인데 **아무도 읽지도 쓰지도 않았다.** 새 칸을 세우지 않고 그 자리를 넓혀
썼다(`CharField(200)` → `TextField`).

### 검토 화면에서 적는 자리가 사라진다

**사용자 결정이었다.** 개체 코멘트는 개체 카탈로그에서만 적고, **검토 화면은
읽기만 한다.** 목록·팝업·우클릭 항목을 전부 걷었다 — 저장만 잠그는 것으로는 안
된다는 것을 051 에서 배웠다. **시야 코멘트는 다른 칸이라 그대로 남는다.**

> **자료로 확인했다.** 판정 코멘트는 운영에 **2건**뿐이고 둘 다 대표 판에 붙어
> 있어 이어붙이기가 발동할 자료가 없었다. 그리고 **개체 7,913 중 7,908 이 판을
> 하나만 갖는다** — 지금 자료에서는 "판별 코멘트" 와 "개체 코멘트" 가 사실상 같은
> 말이다.
>
> **다만 그 비율은 앞으로 바뀐다.** 프레임에만 있는 개체가 이미 5,123 이다(106).
> 그때가 되면 *"이 판에서만"* 이라고 적고 싶어질 수도 있다 — **이 결정의
> 유효기간은 거기까지다.**

## 5. 판 둘을 내보냈다 (114)

```
08-13 08:06   v0.11.2   등급·자세 (0034)
08-13 09:17   v0.12.0   번지기 · 등급·코멘트를 개체로 (0035·0036)
```

둘 다 **뷰어만** 올렸다(`PIPELINE_TAG=v0.5.2` 그대로). smoke 통과 ·
`ops/check_db.py` 전부 OK.

**한 판에 겹치지 않고 둘로 나눈 것은 사용자 결정이다.** 기술적으로는 겹쳐도 됐다
— `0034`→`0035`→`0036` 이 기동 때 순서대로 다 돌고 옮길 값이 0건이었다. 그래서
오히려 갈라 놓기 좋았다: **되돌릴 일이 생겨도 어느 판으로 돌아갈지가 분명하다.**

### 파이프라인이 새 스키마에서 도는가 — 실측

`0035`·`0036` 이 **칼럼을 걷는다**(`ObjectReview.grade`·`note`). 이 저장소에서
칼럼을 걷은 것은 `0032` 이후 처음이고, 그때는 **옛 파이프라인 이미지가 교정 있는
시야를 지울 때 죽었다**(108). 규약대로 사본에 붙여 봤다 — 백업 사본을 스크래치로
떠서 `0036` 까지 올리고 `diaruga-pipeline:v0.5.2` 를 물렸다(**운영 `db/` 는
마운트하지 않았다**).

| 갈래 | 결과 |
|---|---|
| `ObjectReview` 한 행 읽기 (전체 칼럼 SELECT) | 실패 — `no such column: …note` |
| 교정 22건이 달린 시야 지우기 (108 이 잡은 갈래) | **통과** |
| `batch_plan.py` (폴러가 실제로 부른다) | 통과 |

**갈래가 갈린 이유가 요점이다.** `ObjectReview` 를 가리키는 FK 도 시그널도 없어서
Django 가 **fast-delete** 로 간다 — 지울 행을 안 불러오고 `DELETE … WHERE` 만 낸다.
그래서 없는 칼럼을 짚을 일이 없다.

**그리고 `note` 만 문제였다.** `grade` 는 어제 생긴 칸이라 옛 이미지의 모델이 아예
모른다 — **모르는 칼럼은 SELECT 하지 않는다.** 옛 판이 위험한 것은 걷힌 칼럼을
*아는* 경우뿐이다.

> **파이프라인은 `ObjectReview` 를 만들지 않는다.** 그런데도 확인이 필요한 이유는
> **위험이 쓰기가 아니라 읽기**이기 때문이다 — Django 는 행을 불러올 때 모델이
> 아는 칼럼을 전부 SELECT 하고, **cascade 삭제는 지울 대상을 먼저 불러온다.**
> `group_focus_series.py` 의 재그룹핑이 그 자리다.

**결론은 "뷰어만 올린다" 이지만 유효기간이 있다** — `pipeline/` 에 `ObjectReview`
를 읽는 줄이 하나라도 들어오면 그날로 물린다. **다음에 파이프라인 이미지를 구울 때
함께 올린다.**

### `note` 를 꼭 걷어야 했나 — 다시 물었다

배포 직전에 나온 질문이다. 칼럼을 남기면 옛 판이 안전해지고, 그것이
**expand–contract(parallel change)** 라는 표준 패턴이다. 그런데 이 저장소에서는
남기는 쪽이 더 비쌌다 — `0036` 이 코멘트를 **복사만 하고 원본을 안 지우므로**
같은 말이 두 자리에 앉고, `/review` 의 빈 껍데기 청소가 헷갈리고,
`ops/export_review.py` 가 같은 말을 두 번 싣는다. 남기려면 원본을 비우는 일까지
해야 하고 그러면 *"일부러 비워 둔 칼럼"* 과 그것을 지키는 불변식이 는다.

**미루고 얻는 안전이 이미 실측으로 확보돼 있었다.** 그래서 걷는 쪽으로 갔다 —
**판단이 갈릴 수 있는 자리라 devlog 에 적어 두었다.**

## 6. 병합이 Pull Request 를 지나가게 됐다 (114)

**이 저장소의 첫 PR 이다**(`#1`). 계기는 CI 트리거였다.

```yaml
on:
  push:
    branches: [main]        # ← work/* 는 아니다
    tags: ['v*']
  pull_request:
    branches: [main]        # ← PR 을 열면 돈다
```

**`work/*` 를 push 한 것만으로는 CI 가 한 번도 안 돌았다.** 브랜치 문서가 적어 둔
절차(`main` 에 병합 → push 가 CI 를 돌린다)는 틀리지 않다 — 태그 전이라 배포에 안
닿는다. 다만 **깨진 코드가 이미 `main` 에 앉은 뒤에 알게 된다.** PR 은 그 순서를
뒤집는다.

**작성자가 시험을 안 돌린 것이 아니다** — 112 에 *"브라우저 시험이 하나 잡았다"*
가 적혀 있고 111 은 *"화면 조각만 끄면 셋이 실패한다"* 까지 확인해 뒀다.
**"돌렸다" 와 "이 커밋에서 깨끗한 환경으로 돌았다" 가 다를 뿐이다.**

### 병합은 로컬 `--ff-only` 로 했다

PR 은 열되 **GitHub 의 병합 버튼을 안 눌렀다.** GitHub 의 "Rebase and merge" 는
fast-forward 가 가능한 상황에서도 커밋을 다시 써서 SHA 가 달라지고, 그러면
**작성자의 로컬 브랜치가 `main` 과 갈라지고**(계정마다 작업 트리가 따로인 이
저장소에서 실제로 물리는 자리다) **태그가 브랜치에 없는 커밋을 가리킨다.**

로컬에서 `git merge --ff-only` 로 붙여 push 하면 **GitHub 이 그것을 알아보고 PR 을
자동으로 `MERGED` 로 닫는다.** CI·리뷰 자리는 얻고 SHA 는 지킨다.

### 앞으로의 절차

```
브랜치 작업 → git fetch origin && git rebase origin/main
           → 시험을 **다시** 돌린다
           → git push --force-with-lease
           → gh pr create → CI
           → git merge --ff-only → push → 태그 → 배포
```

**함정 셋을 devlog 에 적었다.** ① 인자 없는 `git pull --rebase` 는 `main` 을 안
들여온다(그것은 `rebase @{upstream}` 이고 work 브랜치의 upstream 은 자기 자신이다)
② **얹은 뒤 시험을 다시 돌린다** — rebase 는 충돌 나는 자리만 보여 주는데 이
저장소에서 위험한 것은 **안 나는 쪽**이다(106 의 stash 가 그렇게 버려졌다)
③ `--force-with-lease` 의 임대는 `git fetch` 가 갱신하므로 `--force-if-includes`
를 함께 준다.

### 열려 있던 것 하나가 닫혔다

`HANDOFF` 9.9 가 *"CI 가 이미지를 Docker Hub 로 올리는지 아직 확인 안 했다"* 를
08-10 부터 들고 있었다. `v0.8.0`~`v0.11.2` 는 **전부 이 머신에서 손으로 올렸다** —
*"시험을 통과한 것만 이미지가 된다"* 는 관문이 실제로는 사람 손에 걸려 있었다.

`v0.12.0` 태그에서 `Docker Hub 로그인` 레이어가 실제로 돌았고
`honestjung/diaruga:v0.12.0` 이 레지스트리에 섰다 — **CI 가 올린 첫 이미지다.**
PR 에서는 굽기만 하고 로그인을 건너뛴다: **굽기는 늘 검증하되 올리는 것은 태그일
때만이다.**

고칠 것"* 이 사흘째 붙어 있었고 `CLAUDE.md` 는 더 낡아 있었다.
